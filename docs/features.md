# Features

RnRomManager keeps a personal backup collection of Game Boy, Game Boy Color, Game Boy Advance, Nintendo 64, Nintendo Entertainment System, Super Nintendo Entertainment System, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Commodore 64, Game Gear, Master System, Mega Drive / Genesis, 32X, TurboGrafx-16 / PC Engine, Nintendo Switch, PlayStation, PlayStation Portable, GameCube, Wii, Xbox 360, Saturn, Nintendo DS, Nintendo 3DS, Sega CD and 3DO ROMs. You drop files into an ingest folder; ingestion identifies each one (against the No-Intro DATs by hash, for the disc systems against the Redump DATs by hash, or for Switch against [titledb](https://github.com/blawar/titledb) by title ID), names it, groups it with the game's other releases, fetches box art and stores it as one ZIP per game. Switch dumps, Nintendo DS dumps, Nintendo 3DS dumps and disc images are too large for a ZIP, so they're stored as files next to their game's ZIP (see [External storage](#external-storage-nintendo-switch-nintendo-ds-nintendo-3ds-and-disc-systems); an Admin can keep Nintendo DS inside the ZIP instead). Everyone can browse and download; admins run ingestion, resolve files it couldn't identify, edit the library and keep it healthy.

## Account types

An account is one of two types:

- **Site user:** a read-only library, plus their own things. They browse, search and download the library (Library, Reports, Collections discovery and Game detail, including Play and the Zip Contents tab), read release notes and see ratings, and manage their own [collections](#collections), bundle queues, keyboard shortcuts, password and [saves](#game-detail). They can't edit games, images, release notes, ratings or favourites, or publisher logos.
- **Admin:** everything: Ingestion, Review, Integrity, Admin and job pages, every library edit (edit metadata, retry media, merge, move, delete, images, release notes, rating and favourite, publisher logos, merging or dismissing duplicate groups in Reports), and every user's saves. A Site user who opens an Admin page sees "Not allowed"; an Admin-only request answers `403 Forbidden`.

In the API an Admin has `roles: ["admin"]` and a Site user `roles: []`. The first account, and an account the `--reset-password` command promotes because no enabled Admin is left, is an Admin. Upgrading from a version with the `rom-manager` role folds it into `admin` ([deployment](deployment.md#upgrades)).

The navbar stays at the top of the window while you scroll, and shows the pages your account type can use (in the order Library, Ingestion, Review, Reports, Integrity, Admin), with the current page highlighted. The **Shortcuts** button in the footer opens your [keyboard shortcuts](#keyboard-shortcuts). The user menu has **Change password** and **Logout**; the theme button switches between Light, Dark and Auto (follows your system), remembered per browser. Times are shown in your browser's time zone. Search has no keyboard hint in the navbar; its shortcuts still work. Closing a dialog or navigating away from one restores page scrolling.

## Navigation bar, footer and page titles

- **Navbar:** Library, Collections, Reports and (Admins) **ROM Tools** (an adjustable-wrench icon) on the left. On the right, the **Bundle** cart (an icon with the file count as a badge), **Search** (a magnifier; its tooltip names **Ctrl+K**) and your user menu. Bundle and Search are icons only; screen readers still hear "Bundle 2 files in the cart" and "Search". On a phone, where the navbar is collapsed into a menu, the menu closes once you pick a link in it (a user-menu item included) or a shortcut or button takes you to another page. Below `lg` (992px) **Search** sits next to the menu button, outside the menu, and the user menu is shown open inside the menu under your username (no extra tap); the theme and Logout buttons don't close the menu (Logout leaves the page anyway).
- **User menu:** **Admin** first (Admins only; marked as current on any `/admin` page), then **Theme** (Light, Dark or Auto, the current one marked), **Change password** and **Logout**.
- **Footer:** on every signed-in page a slim bar is fixed to the bottom: **About** (the version, a link to the project on GitHub, the attribution for libretro-database and libretro-thumbnails, and the licence of every component), the version (a link to the GitHub releases page, "RnRomManager <version>"; on a phone, below the `sm` breakpoint, just the version; "RnRomManager" until it loads) and the **Shortcuts** button (a help icon with the text "Shortcuts"; its tooltip says "Keyboard Shortcuts"). For Admins, while any job runs (started here, by the scheduler, at startup or in another tab), the footer also shows its label and progress (for example "Moving ROMs 3/120" with a small bar, an animated one while the total is unknown), linking to [Jobs](#jobs); it's hidden while a password change is forced. About's licence list has a search box (name or licence) and scrolls on its own, with its header row kept in view, so the dialog itself doesn't scroll. The page keeps room below its content and toasts appear above the footer. Every toast closes itself after 5 seconds, those with a link included; while the pointer is over one or focus is inside it, it stays, and it gets another 5 seconds once both have left. The sign-in page has no footer; while a password change is forced, the shortcuts button is hidden but About and the version still work. For Admins two icon buttons sit right before Shortcuts: **Next missing image** and **Open the first review item**, which do exactly what their [shortcuts](#keyboard-shortcuts) do. The footer stays on one line: below `sm` (576px) the About and Shortcuts labels and the job's "label n/total" are hidden visually (still read by screen readers), leaving the icons and the progress bar, and it keeps clear of a phone's home indicator (the page uses `viewport-fit=cover`).
- **Tab icons:** the ROM Tools tabs (Ingestion, Review, Deleted ROMs, Integrity) and the Admin tabs (Users, DATs, Settings, ROM Zip Config, Backups, Logs, Auditing) each show an icon before the label.
- **Install as an app:** the site has a web app manifest (`/manifest.webmanifest`, name "RnRomManager", short name "RnRom", standalone, `#212529`) and icons, so a phone or desktop browser can install it to the home screen; there's no offline mode (no service worker).
- **Tabs:** every row of tabs (a game's tabs, a review item's tabs, Reports, Newly Added's systems, Activity's sections, Admin, ROM Tools and Collections) stays on one line and scrolls sideways when it doesn't fit, instead of wrapping; the active tab is scrolled into view when the page opens and when you switch tabs.
- **Page titles:** the section pages (Library, Collections, Reports, the ROM Tools pages and Admin) show their heading only on narrow screens, where the navbar is collapsed. On wider screens the navbar already says where you are, so the heading is hidden visually but stays for screen readers. Pages about one thing (a game, a collection, a review item, a job) keep their own title.

## Global search

**Search** (the magnifier) in the navbar, **Ctrl+K** / **Cmd+K** or **Ctrl+Space** (some systems use Ctrl+Space to switch input methods; use Ctrl/Cmd+K there) opens a search box from any page, even while typing in a field. It's off while another dialog is open and until you've changed a forced password. The dialog is extra wide. From 2 characters it shows three groups: first the [reports](#reports) whose name contains every word you typed (as chips with the report's icon; Missing Metadata and Activity for Admins only; Enter or a click opens the report, Shift+Enter does nothing), then up to 5 of your [collections](#collections) whose name contains every word you typed (sorted by name), as compact chips with a small cover, the name and `· <n>` games, then the 20 best games. Every word you type must appear in the title, developers, publishers, genres or the file name of one of the game's DLC or updates; an exact title ranks first, then titles that start with what you typed, then by how many words hit the title (weighted most), developers, publishers, DLC/update names and genres, then A–Z. Each game is a row with its box art, title, system badge (short name) and, on wider screens, `year · regions · size` and its rating and favourite; when no word matched the title, the title says why it was found (e.g. "Publisher: Nintendo", or "DLC: Orbit Expedition - Star Pack" / "Update: …" with the name without its `[…]` tags). Opening a game found by a DLC or update name opens its DLC or Updates tab. On a phone the year, regions, size and rating are left out. Up/Down move through both groups, Enter (or a click) opens the collection or game. A game that plays in the browser shows a **Play** icon at the end of its row: clicking it, or **Shift+Enter** on the highlighted game, closes the search, opens the game's page and starts its primary release in the Play dialog (a PSP game opens its play tab at once and then the game's page); Shift+Enter on a collection or a game that can't play does nothing. If one of the two searches fails, its error shows and the other group's results stay. Escape closes the search and puts the focus back where it was.

## Keyboard shortcuts

These work from any page, even while typing in a field, but not while a dialog is open or before a forced password change:

| Action | Default | Who |
|---|---|---|
| Open global search | **Ctrl+K**, **Ctrl+Space**, **Cmd+K** (fixed) | everyone |
| Go to Library | **Alt+Shift+L** | everyone |
| Go to Collections | **Alt+Shift+C** | everyone |
| Go to Ingestion | **Alt+Shift+I** | `admin` |
| Go to Review | **Alt+Shift+F** | `admin` |
| Open the first review item (the Review page when the queue is empty) | **Alt+Shift+G** | `admin` |
| Go to Reports | **Alt+Shift+R** | everyone |
| Go to Integrity | **Alt+Shift+T** | `admin` |
| Go to Admin (Users) | **Alt+Shift+A** | `admin` |
| Go to Deleted ROMs | **Alt+Shift+D** | `admin` |
| Next missing image: open the next game in the [Missing Images](#reports) report | **Alt+Shift+M** | everyone |
| Next missing metadata: open the next game in the [Missing Metadata](#reports) report | not assigned (set your own) | `admin` |

(On a Mac, Alt is Option and Meta is Cmd.) The navigation shortcuts use Alt+Shift because Ctrl+I/F/G/L are the browser's own (italic, find, find next, address bar). On some Windows setups Alt+Shift switches the input language; rebind them if so. If a shortcut you set earlier uses one of the newer defaults (R, T, A, D), yours keeps working: when two actions share a key, the one higher in this table runs, and the shortcuts dialog shows the conflict.

**Next missing image** works differently: if another of your shortcuts already uses **Alt+Shift+M**, that one keeps it and Next missing image starts out "Not assigned", with a note saying its default is in use. Saving other changes leaves it that way. Edit it to give it another key, or **Reset to defaults** to give both actions their defaults back.

**Next missing image** steps through the Missing Images report in its unfiltered order (system, then title), whatever the report page's own filters are. On a game page it opens the next game after the current one, wrapping round to the first; anywhere else it opens the first game in the report. A game you have just fixed still counts as the place to continue from. When the current game is the only one left it stays put and says "This game is the only one still missing images."; when none are left it says "No more games are missing images."; if the lookup fails an error toast says so. The game opens on its **Images** tab, and for Admins the **Upload Image** dialog opens there, ready for an image URL; the address then shows just `?tab=images`, so a reload or Back doesn't open the dialog again. Pressing it again while a lookup is running does nothing extra, and the answer is ignored if you have moved to another page meanwhile. Anyone can open and view the game; changing its images still needs the `rom-manager` role.

**Next missing metadata** (Admins) has no key until you give it one. It steps through the Missing Metadata report in its unfiltered order (title, then id), the same way: on a game page it opens the game after the current one, wrapping round; anywhere else the first game. It opens the game page (its **Releases** tab) with a **Next missing metadata** button in the action row, so you can fix the year, developer or publisher and move on. When the current game is the only one left it says "This game is the only one still missing metadata."; when none are left "No more games are missing metadata."; a failed lookup shows "Couldn't find the next game missing metadata.".

The **Shortcuts** button in the footer opens **Keyboard Shortcuts**, which lists the shortcuts your account type allows. **Run** on any row (global search included) closes the dialog and does what the shortcut does; it's disabled, with "Save or cancel your changes to run a shortcut" above the table, while you're editing a key or have unsaved changes. **Edit** a row, then press the new keys: the first key with a modifier becomes the shortcut; **Backspace** or **Delete** clears it ("Not assigned"); **Escape** stops editing without closing the dialog. A shortcut must include Ctrl, Alt or Meta, can't be Ctrl+Alt without Shift or Meta (that's AltGr on many keyboards), can't be a search shortcut, and can't be used by another action you can use; a key that breaks a rule shows why on its row and isn't taken. Keys are A–Z, 0–9 and F1–F12, read from the physical key, so the keyboard layout and Option don't change the letter. **Reset to defaults** puts every row back; nothing is saved until **Save**, which applies the changes at once. Shortcuts are saved per account, so they follow you to other browsers. An `admin`'s shortcuts for admin pages are kept if the role is removed; if two actions you can use end up on the same key (the role was given back), only the first in the table fires and the dialog asks you to change the other.

## Sign in and change password

- **Sign in** (`/login`): username and password. Any failure (unknown user, wrong password, locked or disabled account) shows the same "Invalid username or password." message. Five failed attempts lock an account for 15 minutes, and more than 10 attempts a minute from one address are refused for a while. After signing in you go back to the page you were sent from, or to the Library. Sessions last 7 days from the last use.
- **Change password** (`/change-password`): current password, new password and confirmation. Passwords are 12–128 characters and must not be the username. A new account, the first Admin and an account an Admin reset must change their password before using any other page. The new password must differ from the current one. Changing it signs out your other sessions but keeps this one.

## Library

The home page (`/`) shows every game, 48 per page.

- **Count:** above the results, how many games match, with thousands separators (`1,250 games`).
- **Grid or list:** the buttons on the right switch between box-art cards and a table (title, system, year, regions, rating, number of releases, primary ROM size). Your choice is remembered in this browser. Cards show the box art filling a square frame (non-square art is cropped at the edges; the full image is on the game's Images tab) with a system badge in the system's colour at its top left and the primary ROM size as a badge at its top right, then the title on one line (hover or focus it for the full title) and the year and regions. A game with updates (releases flagged `Update`) shows an **updates** badge with their count at the bottom left of the box art (after the title in the list), and a game with DLC a **DLC** badge (puzzle icon, `3 DLC`) right after it. A game whose system plays in the browser (Game Boy, Game Boy Color, Game Boy Advance, NES, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Game Gear, Master System and PlayStation) has a round **Play** button at the bottom right of the box art (in the list, a play button in the last column) that starts its primary release straight away, as the game page's [Play](#game-detail) does; it's hidden in Select mode and for a release stored outside the ZIP, except a PlayStation disc. The list shows the size in its own column and the system as a coloured badge. The size is omitted when no primary exists. The stars and heart stay on one line under the title. On a phone (below the `sm` breakpoint) the grid shows two cards per row (three from 360px wide) and cards have no stars and heart, since they don't fit; rate a game in the list view or on its page. A card's **Remove from collection** button still shows there. In the dark theme cards are a step lighter than the page; hovering or focusing a card lifts it slightly with a shadow (only the shadow when the browser asks for reduced motion).
- **Filters:** one toolbar holds the search box, the **System**, **Region**, **Letter** and **Sort** menus, the sort direction, **Favourites**, **Clear all**, **Select** and Grid/List (always last); it wraps on narrow screens, and below `md` (768px) the search box takes the whole first row. Search applies from 2 characters as you type (every word must appear, in any order, in the title, developers, publishers, genres or a DLC/update file name); region matches any release in that region; letter is `#` for names that don't start with A–Z, or A–Z; **Favourites** (the heart button) shows only favourite games. Each menu button reads its field and the chosen value (`System: Game Boy`) and is filled while a value is chosen. In the menus, each System, Region and Letter row shows how many games it would give with the other active filters, right-aligned (`1,250`); a row with none shows `0`, greyed, and can still be picked. The **All systems** and **All letters** rows show the total; **All regions** shows none, since a game can count in several regions. The System menu shows each system's badge and full name and has a filter box at the top (it matches the name, id or short name). The menus work with the keyboard (arrow keys, Escape). The counts load separately (no counts while they load or if they fail), don't change when you page or sort, and aren't refreshed by rating or favouriting a card until the next filter change. Games are filed by their stored title, so *The Legend of Zelda* is under **L** (`Legend of Zelda, The`).
- **Sort:** title (default), year, date added or rating (best first by default); the arrow button flips the direction. Games without a year, or not rated, are always last. Changing the sort resets the direction.
- **Active filters:** below the toolbar a row of chips shows each active filter, with its count (`System: Game Boy (1,234)`, `Region: USA (9)`, `Letter: A (3)`, `Search: "zelda"`, `Favourites`); × on a chip clears just that one. The row is hidden when no filter is set. **Clear all**, in the toolbar after Favourites, clears the search box, every filter and the page, and keeps the sort, direction and Grid/List view; it's always shown and disabled when the search box is empty and no filter or later page is set. The empty state's **Clear filters** does the same.
- **Remembered:** the Library keeps your last filters, sort and page in this browser. Opening `/` (the navbar link, the game page's **Back to Library**, **Alt+Shift+L**) brings them back; a link with its own filters wins and is remembered instead. Going to `/` while already on the Library forgets them; **Clear all** leaves only the sort and direction remembered. Collection pages don't use or change it.
- **Rating and favourite:** click a star (1–5) to rate a game, the same star again to clear it, and the heart to mark it a favourite. An Admin can do this on the cards, the list and the game page; the values are shared, so everyone sees the same rating, and a Site user sees the stars and heart read-only. A changed card stays where it is until the list reloads. If a job is running, the rating is tried once more after a second, then undone with "Another job is running".
- Filters live in the address bar, so a filtered view can be bookmarked or shared, and Back/Forward step through your changes.

- **Add to collection:** **Select** (in the toolbar, before Grid/List) shows a checkbox on each card or row, with **Select all on this page**; **Add to collection…** adds the ticked games to one of your [collections](#collections) and says how many were new. The selection clears when you change page, a filter or the sort, or turn Select off.

An empty library offers Admins a link to Ingestion.

## Collections

Every signed-in user can group library games from any system into **collections** ("Pokemon", "My favourites"). Collections are private: nobody else, Admins included, can see or change yours.

- **Collections** in the navbar (or **Alt+Shift+C**) lists yours as cards (cover, name, game count) sorted by name, with a name filter and paging (both kept in the address bar; rows per page are remembered in this browser). **New collection** asks for a name, optional Markdown notes (View/Edit/Preview, at most 64 KiB, like release notes) and an optional cover (a PNG or JPEG file or URL, at most 8 MiB), then opens the new collection. If the cover can't be saved, the collection is still created and an error says so.
- Names are 1–100 characters and unique per user, ignoring case but not accents: "pokemon" clashes with "Pokemon", "Pokémon" doesn't.
- A collection's page shows its cover, name, game count and notes, with **Edit** (name and notes are saved with Save; a cover change or removal applies at once) and **Delete** (removes the collection, never its games). Below are its games with the Library's grid/list, search, system filter, Favourites and paging, sorted by when they were added to the collection (newest first) or by title, year or rating; the view is kept in the address bar. **Add games** searches every system and leaves out games already in the collection. Every game picker (Add games, Move/Merge/Attach and Review) shows each result's cover (or the system icon) and, when it searches every system, a short system name such as `SNES` (the full name on hover); each game has a **Remove from collection** button.
- On a game's page, **Collections** lists yours with a checkbox each (the first 200 by name; filter to find more): ticking or unticking applies at once. Badges under the title link to the collections that hold the game.
- A game stays in its collections when it's edited, and moves with it when it's merged into another game or its last release is moved away (keeping the earlier added date where both were in a collection). A game that disappears from the library (e.g. a library folder not mounted) stops showing in its collections and comes back with it.
- Collections live in the database; covers are files in `Paths:Collections` ([configuration](configuration.md)), not in the library ZIPs and not in database backups ([deployment](deployment.md#backup-and-restore)). Changes to collections aren't audited and never wait for a running job.

### Publishers and genres

The Collections page has four tabs: **User collections** (the default, everything above), **Publishers**, **Genres** and [**Systems**](#systems). They're links, so each tab, selection and page has its own address you can bookmark or share (`/collections?tab=publishers&key=…`), and Back/Forward step through them. Changing tab clears the selection and paging.

- **Publishers** and **Genres** list every value in the library's game metadata, across every system, with how many games have it, sorted by name, paged. Each publisher or genre in a game's list counts on its own (a game with two publishers is in both).
- Values are matched exactly after trimming spaces and ignoring case. Accents and punctuation count: "Café" and "Cafe", or "Bandai Namco" and "Namco", are different groups. A group shows its spelling that sorts first (e.g. "NINTENDO" over "Nintendo").
- Choosing a group shows its games from every system with the Library's grid (system badges, quick play, links to each game; at most four cards wide here and on the Systems tab, since the list takes a third of the page), paged. A link to a group no game has any more says so and offers the way back.
- **List look and search:** long names are cut short with `…` on one line (hover for the full name); each count is a pill badge; the selected row is highlighted in the primary colour. A search box tops each list (Publishers, Genres and Systems): it keeps the groups whose name contains what you typed (ignoring case; Systems also match by id), applies after 300 ms, goes back to the first page and is kept in the address as `find=` (it survives selecting a group or paging, and is dropped when you change tab). The selected group stays selected even when the search hides it. With no match the list says `No publishers match “…”.` (genres, systems likewise).
- The lists are recomputed at most once a minute, so a metadata edit can take up to a minute to show here; a deleted game drops out at once.
- **Logos:** every publisher and genre shows a logo: its shared logo if an Admin set one, else bundled starter art, else a text banner (its name). Every logo, a system's included, sits in the same fixed frame. Starter art covers well-known publishers (Nintendo, Sega, Capcom, Konami, Bandai Namco, Electronic Arts, Square Enix, Ubisoft, Activision, Atari; plain name tiles made for RnRomManager, not the publishers' own logos) and the most common genres (Action, Adventure, Platform, Shooter, Shoot'em Up, Fighting, Beat'em Up, Sports, Racing, Driving, Puzzle, Role-Playing (RPG), Strategy, Simulation, Board Game; a Bootstrap Icons glyph plus the name). Nothing is fetched from other sites for the starter art. An image that fails to load falls through to the next choice.
- **Change logo** (the pencil beside a publisher or genre, shown to Admins only) opens the logo dialog: the current logo and where it comes from, a **URL / File** choice (URL each time it opens), **Save logo** and, when there is one, **Remove shared logo**. A URL is downloaded by the server (http or https, public addresses only, 15 seconds); a file is uploaded. Either way it must be a PNG or JPEG of at most 512 KiB and 2048 pixels per side. The change applies for everyone and is [audited](#file-action-auditing); the last save wins. A logo stays when its group leaves the library for a while and shows again when it's back. Logos are stored in the database, so database backups include them.

### Systems

The **Systems** tab (`/collections?tab=systems`) lists every supported system with its logo (a shared logo an Admin set, else a text banner of its name; systems have no starter art) and game count, systems with no games included. Admins get a **Change logo** pencil on each row and a **Change logo** button beside the selected system's heading; it opens the same logo dialog as publishers and genres. The small system badges elsewhere in the app keep their icons. Choosing one (`?tab=systems&system=gb`) shows its games with the Library's grid, title A–Z, paged; the rows per page are remembered in this browser. The selection and page are in the address, like the other tabs. An address with an unknown system (ids are case-sensitive: `gb`, not `GB`) says the system isn't supported and links back to all systems.

- **Emulators** (above the games, shown even when the system has no games) opens the "<system> Emulators" dialog, a list of known emulators for that system (the game page's **Emulators** button opens the same dialog), grouped by **Windows**, **macOS**, **Linux**, **Android** and **iOS** (only groups with an emulator show). Each entry links to the project's own site in a new tab and shows where the link goes; RetroArch entries name the core to use (e.g. "RetroArch core: Gambatte"). A system with no known emulators says so.
- **Links only:** RnRomManager doesn't host, mirror or check these downloads, and never links to ROMs, BIOS files, keys or firmware. The list is `src/RnRomManager.Web/src/lib/systemEmulators.json`, checked by hand when it changes; every supported system must have an entry ([adding a system](adding-a-system.md)).

## Bundle Creator

Every signed-in user can collect individual ROM files from any games and systems into a **cart** and download them one after another.

- **Adding files:** on a game's page, the cart button on each release's main file, and on each separately downloadable file of a disc set, adds that file. A file is added once (the button then says it's in the bundle); a different file with the same name is a separate entry. The cart keeps the order you add files in, up to 500 files. A disc set's other files (cue sheet, other tracks) aren't added with it.
- **The cart:** **Bundle** in the navbar (with the number of files, on desktop and mobile; hidden until you've changed a forced password) opens it. Each file shows its game and whether it's still in the library. **Refresh** checks again, as opening the page and loading a queue do. A file whose release was deleted, moved to another game or renamed shows as unavailable; it's never swapped for another release, and you can remove it or keep it. **Remove** drops one file, **Clear** (after confirming) all of them.
- **Where the cart lives:** in this browser, per account, so it survives a reload but not a change of browser. Signing out or switching accounts hides it; signing back in on this browser brings it back.
- **Saved queues:** **Save cart as queue** stores a named copy of the cart on your account (at most 100 queues of 500 files each). Names are 1–100 characters and unique per account, ignoring case but not accents, like collection names; saving over an existing name asks first, and fails if the queue was changed elsewhere meanwhile (the list reloads, so you can try again). **Load** replaces the cart, asking first when the cart has other files. **Delete** asks first and leaves the cart alone. Queues are private: nobody else, Admins included, can see them. They keep files that went missing from the library, so you can save again after a library change.
- **Download queue** sends the cart's files to your browser's downloads one at a time, in cart order. It works on a copy of the cart taken when you press it; changing the cart meanwhile doesn't change the run. Each file starts only after the server has finished sending the one before (or it failed). Progress shows how many files were *sent* and each file's state; a file that's no longer in the library or can't be opened is marked failed and skipped. "Sent" means the server finished sending it: your browser decides where it's saved, how files with the same name are named, and whether it was kept.
  - **Browser permission:** browsers often ask once whether this site may download multiple files (in Chrome: *Automatic downloads*, from the download icon in the address bar or Site settings). If the browser doesn't start a file within 30 seconds, the run pauses and says to allow it, then **Retry**.
  - **Pauses:** the run also pauses when the server can't be reached (**Retry** goes on with the same file), when your session ended (**Sign in**), when another download for your account is running (for example in another tab), or when the server is busy. If the server lost track of a file (it restarted), that file shows *Transfer status unknown*; **Send it again** or **Skip it**.
  - **Stop after current file** lets the current file finish, then stops. **Retry** after a run sends the failed and not-yet-sent files again in their original order, never the ones already sent; **Download queue** starts a new run from the current cart.
  - When the run is paused, stopped or done, **Download the remaining files manually** lists normal download links for the files not yet sent.
  - Leaving the page or signing out stops the run; a file your browser already started may still finish. Reloading the page ends the run and keeps the cart.

## Game detail

Opening a game (`/games/{id}`) shows its cover image (a placeholder cartridge when no box art was found), title, rating and favourite (editable, as in the Library), a table of system, year, developers, publishers and genres (`—` when empty; long values, the system name included, wrap inside the table so it never scrolls sideways, even on a phone), and the description.

- The buttons under it are one row of small buttons, each with an icon and text, in order: **Download ZIP**, **Download ROM**, **Google**, **Collections**, **Emulators** (the game's system's "<system> Emulators" dialog, as on the [Systems](#systems) tab; focus returns to the button when it closes) and **Manage**. Manage is a menu with **View info.json** and, for Admins, after a divider, Edit metadata, Retry media, Merge into… and, after another divider, Delete game (see [Edit actions](#game-detail)). For Admins the information table also has a small pencil button (**Quick edit**, tooltip "Edit metadata") at the end of its System row that opens Edit metadata. **Back to Library** above returns to the Library with its remembered filters. **Download ZIP** downloads the whole game as stored in the library ([format](zip-format.md)). **Download ROM** downloads the single ROM; with several releases it's a menu of every ROM with its size, primary first. For Switch the ZIP holds no ROMs: **Download ZIP** says so in its tooltip ("ROM files are downloaded per release") and each release downloads from its own file.
- **Releases**, **Updates** (only when the game has updates), **DLC** (only when it has DLC), **Images** and **Saves** are tabs with counts, followed by **Zip Contents**; each tab has an icon before its name. Releases opens by default; `?tab=updates` opens Updates (Releases on a game without updates), `?tab=dlc` DLC (likewise), `?tab=images` Images and `?tab=zip` Zip Contents. Switching tabs updates the URL without reloading the game. Edit buttons work from either tab.
- **Google** (with the Google "G" icon) opens a new tab searching for the quoted display title and system name.
- **View info.json** (in the Manage menu) opens the JSON exactly as stored in the ZIP, read-only. One toolbar row holds **Expand all** / **Collapse all** on the left and **Copy** on the right; below it the JSON sits in a bordered pane that scrolls on its own (at most 60% of the window height), so the dialog doesn't. Objects and arrays expand as a tree: the first two levels start open. Invalid JSON is shown as raw text in the same pane, under a warning and a toolbar with only Copy; fetch failures offer Retry.
- **Releases** shows one card per ROM, so nothing scrolls sideways on a phone. Each card has a stripe down its left edge in the system's colour (the one its badge uses) and a tinted header, so you can see where each release starts. The card header has the chevron and file name (wrapping, never cut off) on the left and, on the right, a **Primary** badge for the main release, the version and disc badges, an **External** badge (its tooltip is the file's name next to the ZIP) for a Switch release, one badge per region, then the release's buttons (note, play, download, bundle). The body starts with the release's note, when it has one (below), then a table with one row per value: the original file name (the name it had when it was ingested, only when that differs, with a copy button), size, SHA1, CRC32 and MD5 (with copy buttons), revision, languages and flags (when set), how it was identified (`DAT`, `Manual` or `Title DB`), the DAT name and version, the DAT entry, and the date added. Long values wrap. Below the table, **Header details** (left) opens the cartridge header (there's none for a system without one, such as Atari 2600) and, for Admins, **Edit release**, **Make primary** (on every release but the primary), **Move release** and **Delete release** (right). **Make primary** makes that release the game's primary; it stays primary when releases are added, moved in or out, or deleted, until it leaves the game, when the app picks the primary again. For a disc set the size is the whole set's (the main file plus its other files), and an **N files** button (N counts every file, so 3 for a cue and two tracks) opens a table of the main file then each other file, with its size, SHA1 (copy button) and a download button; the header's download button and **Download ROM** still download the main file only. Cards start collapsed to their header: the chevron at its start (or a click on empty header space; not on its buttons, and not when you're selecting the file name to copy it) shows or hides the body. With two or more releases, **Expand all** / **Collapse all** above the cards opens or closes every card. Open cards stay open when the page reloads the same game (after a note, a rating, a move…) and start collapsed again on another game. The header dialog shows two fields per row; the download button downloads that ROM.
- **Updates** lists the releases flagged `Update` (Switch updates; any system whose identification flags a release `Update` gets the tab), which Releases then leaves out: `Releases (n)` counts the releases that are neither updates nor DLC. Updates are listed newest first: by version (`1.10.0` before `1.9.0`; one with a version before one without), then the `v<N>` revision, then the newer date added, then the file name. Each card is a release card (download, note, External badge and the `rom-manager` actions) with a **Version x.y.z** badge when the update has one; **Expand all** works on the tab you're on. The header's **Download ROM** lists only the releases, not the updates or DLC (download those from their cards); a game with no releases offers its updates there, or with no updates either its DLC, and its Releases tab says "No releases other than updates and DLC."
- **DLC** lists the releases flagged `DLC` (Switch DLC; any system whose identification flags a release `DLC` gets the tab), by name (numbers in order, so `Pack 2` before `Pack 10`). A release flagged both `Update` and `DLC` counts as an update. Each card is a release card as on Updates, without a version badge; **Expand all** works there too.
- **Release notes:** every release has a note button (yellow and filled, "View note", when it has a note; outlined, "Add note", when not) that opens its Markdown note. Every signed-in user can read notes; only an Admin edits them. A Site user sees the button only on a release with a note, and the note opens read-only (no View/Edit/Preview switch, **Save** or **Delete note**, only Close). A note opens in **View** (rendered Markdown; links open in a new tab); a release without one opens in **Edit**. **Edit** is a plain text box with a byte counter (at most 65,536 bytes); **Preview** renders what you typed. **Save** stores it (saving an empty note deletes it); **Delete note** asks "Delete this note?" in place. Closing the dialog discards unsaved changes. An expanded release card also shows its note, rendered, at the top of its body under **Release note** (loaded the first time the card opens; links work as in the dialog), with an **Edit note** (Admin) or **View note** (Site user) button that opens the dialog. Notes live in the game's ZIP ([format](zip-format.md#release-notes)), so they travel with the library and move with their release; they aren't searchable. While a job runs, saving shows "Another job is running".
- **Play** (Game Boy, Game Boy Color, Game Boy Advance, NES, SNES, Nintendo DS, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Game Gear, Master System, Mega Drive / Genesis, 32X, PlayStation, PSP, Saturn, Sega CD, 3DO, Commodore 64, Commodore Amiga and TurboGrafx-16 / PC Engine): each release card on the Releases, Updates and DLC tabs has a green play button, before the download button, for every signed-in user. It opens the release in a large dialog running [EmulatorJS](https://emulatorjs.org) (Gambatte for GB/GBC, mGBA for GBA, Handy for Lynx, Virtual Jaguar for Jaguar, Beetle VB for Virtual Boy, Stella 2014 for Atari 2600, a5200 for Atari 5200, ProSystem for Atari 7800, Gearcoleco for ColecoVision, SMS Plus GX for Game Gear and Master System, Genesis Plus GX for Mega Drive / Genesis and Sega CD, PicoDrive for 32X, FCEUmm for NES, Snes9x for SNES, DeSmuME for Nintendo DS, PCSX ReARMed for PlayStation, PPSSPP for PSP, Yabause for Saturn, Opera for 3DO, VICE (x64sc) for Commodore 64, PUAE for Commodore Amiga, Beetle PCE for TurboGrafx-16 / PC Engine), served by the app itself (PSP opens in its own tab instead, below); click **Start Game** inside it to begin (browsers need a click before they play sound). The player shows a progress bar while it loads the release and prepares the emulator: a percentage when the size is known, an animated bar (with the bytes received) otherwise. The ROM is read from the library ZIP through the release's download URL, so nothing is extracted to disk. Keys pressed inside the emulator go to the game, not to the app's shortcuts, and Escape there doesn't close the dialog; **Close**, × or Escape outside it do, and stop the game. Save states are off. EmulatorJS's quick save and load keys (1, 2 and 3 for the slot) still work, but those states live in memory only and are lost when the dialog closes. In-game (battery) saves are kept in your browser only, per release file name, and survive closing the dialog and reloading on that browser; they're written every 30 seconds (EmulatorJS's System Save interval, which you can change in its settings), so **wait 30 seconds after saving in a game before closing the dialog**. Two releases with the same file name would share saves; DAT file names are unique per system. Each time the Play dialog opens (from the game page, the Library or a collection's quick play, Global Search or a save's **Play**), and each time a PSP play link is clicked, the play is recorded in the audit log as `GamePlayed`, which the [Activity](#reports) report lists.
  - **ColecoVision BIOS:** Gearcoleco needs the console's BIOS, which the app can't ship. An Admin copies it as `colecovision.rom` (any case) into the BIOS folder (`Paths:Bios`, `/app/bios` in Docker; see [configuration](configuration.md) and [deployment](deployment.md#volumes-and-permissions)). The play page checks for it before loading the ROM; without it, it says *This system needs its BIOS: ask an Admin to put colecovision.rom in the BIOS folder (Paths:Bios).*
  - **Game Gear and Master System** always use SMS Plus GX: the emulator's core selector is hidden for them and a core chosen there earlier is ignored (other emulator settings and SMS Plus GX's own options stay). SMS Plus GX picks the hardware itself (`auto`): it starts as a Master System II, switches to Game Gear when the `TMR SEGA` header at `0x7ff0` has a Game Gear region code, then applies its built-in CRC list. A Game Gear ROM those checks miss runs as a Master System (wrong screen size and palette) whether it's stored as `.gg` or `.sms`.
  - **NES** always uses FCEUmm (the core selector is hidden and a core chosen there earlier is ignored) and plays the stored headered `.nes`; it needs no BIOS.
  - **PlayStation** always uses PCSX ReARMed (core selector hidden, as for NES) and plays **one disc per launch**: each disc of a multi-disc game is its own release with its own Play button, and discs can't be swapped inside a session. A release plays whether it's a standalone `.bin`, `.iso` or `.chd` or a cue with its `.bin` tracks (all of them, audio included, are sent together through [`play-disc`](#browse-the-library-through-the-api)); the files stay next to the ZIP and are never rewritten. A cooked (`MODE1/2048`) image plays only as a standalone `.iso`. The whole disc, at most **2 GiB**, is downloaded and unpacked in the browser's memory before it starts, so a large disc needs a lot of free memory and may not load on a phone. **BIOS:** the core has a built-in HLE BIOS, so no file is needed; for better compatibility an Admin can copy their own 512 KiB `scph5501.bin` (any case) into the BIOS folder (`Paths:Bios`), and the core then boots the real firmware. A BIOS file of another size stops the launch with a message naming `scph5501.bin`; the core's own BIOS setting (Auto or HLE) in the emulator menu is kept. A disc over 2 GiB or with a cue sheet that doesn't match its stored tracks says so instead of starting. In-game saves are kept per disc (the cue's or image's name), so two releases don't share them.
  - **PSP** always uses PPSSPP and opens in **a new browser tab** (its Play button is a link, announced as opening a new tab), because PPSSPP needs threads, which browsers only allow on a cross-origin isolated page; the rest of the app stays as it is. Closing the tab stops the game. The tab needs **HTTPS or a loopback address** (`localhost`, `127.0.0.1`): opened over plain HTTP on a LAN address it says *PSP games need a secure page…*; without the isolation headers (a proxy that drops `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy`, see [deployment](deployment.md#reverse-proxy)) it says *This page isn't cross-origin isolated…*; without WebGL 2 it says *PSP games need WebGL 2…*. These checks run before anything is downloaded. The release's `.iso` (at most **2 GiB**) streams through [`play-disc`](#browse-the-library-through-the-api) and is held in the tab's memory, briefly about three times over while it loads, so a 1.8 GB dual-layer image can need 5–6 GB of free memory. PPSSPP needs no BIOS; it brings the PSP system fonts in its asset archive. An image over 2 GiB, or a release that isn't one non-empty `.iso` named as stored, says so instead of starting. Whether PPSSPP's in-game saves survive closing and reopening the tab hasn't been verified yet: don't rely on them.
  - **Mega Drive / Genesis** always uses Genesis Plus GX (core selector hidden) with the Mega Drive gamepad (A, B, C, X, Y, Z, Mode and Start; the Controls menu lists the generic RetroPad names and the default keys don't change). `.md`, `.gen` and `.bin` releases all play. The app doesn't ship this core (its licence forbids commercial use): an Admin supplies three EmulatorJS 4.2.3 files through `Emulator:GenesisCorePath` ([configuration](configuration.md#genesis-plus-gx-core), [deployment](deployment.md#genesis-plus-gx-core)). Play shows anyway; before loading the ROM the page checks the files and says *Genesis and Sega CD games need the Genesis Plus GX core files: ask an Admin to set them up (Emulator:GenesisCorePath).* when they're missing, or *…don't match EmulatorJS 4.2.3: ask an Admin to replace them…* when one has the wrong size or SHA-256.
  - **32X** always uses PicoDrive (core selector hidden) with the 32X gamepad. Like Genesis Plus GX, the app doesn't ship it (its licence forbids commercial use): an Admin supplies three EmulatorJS 4.2.3 files through `Emulator:PicodriveCorePath` ([configuration](configuration.md#picodrive-core), [deployment](deployment.md#picodrive-core)). Play shows anyway; before loading the ROM the page checks the files and says *32X games need the PicoDrive core files: ask an Admin to set them up (Emulator:PicodriveCorePath).* when they're missing, or *The PicoDrive core files don't match EmulatorJS 4.2.3…* when one is wrong. Mega Drive / Genesis never uses PicoDrive.
  - **SNES** always uses Snes9x (core selector hidden) with EmulatorJS's SNES gamepad, and needs no BIOS. Stored `.sfc` releases play, and so do older ones stored as `.smc`; both play from the bytes in the ZIP (an `.smc` dump with a copier header is stored headerless as `.sfc` when it's ingested). Like Genesis Plus GX, the app doesn't ship it (its licence forbids commercial use): an Admin supplies three EmulatorJS 4.2.3 files through `Emulator:Snes9xCorePath` ([configuration](configuration.md#snes9x-core), [deployment](deployment.md#snes9x-core)). Play shows anyway, on the library card for an embedded primary release and on each embedded release; before loading the ROM the page checks the files and says *SNES games need the Snes9x core files: ask an Admin to set them up (Emulator:Snes9xCorePath).* when they're missing, or *The Snes9x core files don't match EmulatorJS 4.2.3: ask an Admin to replace them (Emulator:Snes9xCorePath).* when one is wrong. On a fresh browser EmulatorJS uses the legacy (WebGL 1) build; turning WebGL 2 on in its settings switches to the modern one. If the core file can't be downloaded after **Start Game**, the player shows *Error downloading core (&lt;file&gt;)*.
  - **Saturn** always uses Yabause (core selector hidden) with the Saturn gamepad, and plays **one disc per launch** like PlayStation: a standalone `.bin` or `.chd` or a cue with its `.bin` tracks, at most **2 GiB**, through [`play-disc`](#browse-the-library-through-the-api). A release stored as `.nrg` has no Play button (Yabause can't read Nero images). **BIOS:** without one the core uses its built-in HLE BIOS; an Admin can copy their own 512 KiB `saturn_bios.bin` (any case) into the BIOS folder (`Paths:Bios`), and the core then boots the real firmware. A BIOS file of another size stops the launch with a message naming `saturn_bios.bin`. **Expect less than PlayStation:** Yabause in WebAssembly is slow on weak devices (phones, older laptops), and its HLE BIOS boots fewer games than a real `saturn_bios.bin`, so some games won't start or run smoothly; neither is something the app can fix.
  - **Sega CD** always uses Genesis Plus GX, the core Mega Drive / Genesis uses (same `Emulator:GenesisCorePath` files, core selector hidden, Mega Drive gamepad), and plays **one disc per launch** like PlayStation: a standalone `.bin`, `.iso` or `.chd` or a cue with its `.bin` tracks, at most **2 GiB**, through [`play-disc`](#browse-the-library-through-the-api). Its play URL carries `disc=1`, which is how the shared core tells a Sega CD disc from a Mega Drive cartridge. **BIOS (required):** an Admin copies at least one of the regional 128 KiB BIOS files `bios_CD_U.bin` (USA), `bios_CD_E.bin` (Europe) or `bios_CD_J.bin` (Japan) into the BIOS folder (`Paths:Bios`); every one found is handed to the core. The page checks the core files first, then asks for the three BIOS files one after another (U, E, J): without any it says *Sega CD games need a BIOS: ask an Admin to put bios_CD_U.bin, bios_CD_E.bin or bios_CD_J.bin in the BIOS folder (Paths:Bios).*, and a file of another size stops the launch with a message naming it, before the disc is downloaded. **Region:** the app doesn't read the disc's region, so a disc whose region's BIOS is missing (a Japanese disc with only `bios_CD_U.bin`, say) fails inside the emulator with its generic error; add that region's BIOS.
  - **3DO** always uses Opera (core selector hidden, EmulatorJS's 3DO gamepad) and plays **one disc per launch** like PlayStation: a standalone `.bin` or `.iso` or a cue with its `.bin` tracks, at most **2 GiB**, through [`play-disc`](#browse-the-library-through-the-api); every 3DO release is a disc, so its play URL always loads from play-disc. Like Genesis Plus GX, the app doesn't ship Opera (its licence forbids commercial use): an Admin supplies three EmulatorJS 4.2.3 files through `Emulator:OperaCorePath` ([configuration](configuration.md#opera-core), [deployment](deployment.md#opera-core)). Play shows anyway; before anything else the page checks the files and says *3DO games need the Opera core files: ask an Admin to set them up (Emulator:OperaCorePath).* when they're missing, or *The Opera core files don't match EmulatorJS 4.2.3: ask an Admin to replace them (Emulator:OperaCorePath).* when one is wrong. **BIOS (required):** an Admin copies at least one of the 1 MiB 3DO BIOS files `panafz10.bin`, `panafz1.bin`, `panafz1j.bin`, `goldstar.bin` or `sanyotry.bin` into the BIOS folder (`Paths:Bios`). The page asks for them one after another in that order; a missing file is skipped and every one found is handed to the core. Without any it says *3DO games need a BIOS: ask an Admin to put panafz10.bin, panafz1.bin, panafz1j.bin, goldstar.bin or sanyotry.bin in the BIOS folder (Paths:Bios).*, and a file of another size stops the launch with *The 3DO BIOS &lt;name&gt; in the BIOS folder (Paths:Bios) must be 1 MiB: ask an Admin to replace it.*, before the disc is downloaded. With several present, Opera boots the first in its own order (`panafz1.bin`, `panafz1j.bin`, `panafz10.bin`, `goldstar.bin`, `sanyotry.bin`). **BIOS mismatch:** the app doesn't read the disc, so a game that needs a particular console's BIOS may fail inside the emulator; add that BIOS, and remove the ones Opera would pick first. The Kanji font ROM some Japanese games need isn't supported. **Saves:** Opera keeps the 3DO's NVRAM (its in-game saves) in its own file, per release file name, and writes it only when the game resets or stops. So closing the dialog with **Close**, × or Escape first asks the player to save, and the dialog closes once it has (at most 3 seconds, the buttons disabled meanwhile); the game restarts for a moment as it saves. The player's own **Exit** button (shown for 3DO only) saves too. **Closing the browser tab, reloading or leaving the page loses** anything saved in a game since the dialog was last closed. Two releases with the same file name share one NVRAM file. The NVRAM can't be exported or imported.
  - **Commodore 64** uses VICE (x64sc), whose files an Admin supplies ([configuration](configuration.md#vice-core)); it needs no BIOS and plays **one tape, disk side or cartridge per launch**: each side of a multi-side game is its own release with its own Play button, and sides can't be swapped inside a session. VICE starts the file by its extension; keys reach the emulator while it has focus.
  - **Commodore PET** uses VICE (xpet), from the same Admin-supplied folder; it needs no BIOS and starts a `.prg` or `.d64` by its extension.
  - **Commodore VIC-20** uses VICE (xvic), from the same folder; it needs no BIOS and maps a cartridge by its extension (`.20`, `.40`, `.60`, `.a0`), which ingest keeps.
  - **Commodore Amiga** uses PUAE, which ships in the image and boots its built-in AROS Kickstart (no BIOS, fair compatibility). It loads one `.adf` per launch, so a multi-disk game can't swap to its next disk.
  - **TurboGrafx-16 / PC Engine** uses Beetle PCE (`mednafen_pce`), which ships in the image. It plays HuCard `.pce` releases from the ZIP and needs no BIOS; PC Engine CD and SuperGrafx aren't supported.
  - **Nintendo DS** always uses DeSmuME (the core and threads settings are hidden, and a core chosen earlier, such as melonDS, is ignored) with EmulatorJS's DS gamepad, and plays the `.nds` release from its file next to the ZIP (or, for a game the storage migration hasn't moved yet, from the ZIP) at any size the library stores (up to 512 MiB). Both screens show, the lower one below the upper one. The mouse or trackpad is the **stylus**: press on the lower screen to touch it (a press must last a moment; the DS reads the touch screen once a frame), and the pointer is never captured. These are the defaults; a viewer's own saved settings for the game win. No BIOS or firmware is needed or used: DeSmuME runs on its built-in ones, even if its settings say to use external files. Battery saves work like other systems' (in your browser, per release file name, written every 30 seconds), so **wait 30 seconds after saving before closing the dialog**. EmulatorJS's save-file export and import buttons are hidden for DS, because DeSmuME keeps its own `.dsv` save file that they don't read. Touch screens aren't supported: finger input on a phone or tablet hasn't been tested. On 2026-11-14 a 512 MiB cartridge started in about 5 seconds in Playwright's Chromium 156 (headless, three cold starts), with Chromium's renderer peaking at about 2.2 GiB, so give the browser memory to spare for the largest games.
  - **Game Gear controls** (with a Start button on the touch gamepad and in the controls menu) are chosen from the release's file name: a `.gg` release gets them; a Game Gear release stored as `.sms` gets the Master System controls.
  - **Touch controls:** on a phone or tablet (a device whose main pointer is a finger, not a touchscreen laptop with a mouse or trackpad) EmulatorJS's on-screen gamepad is shown when the game starts, in the layout EmulatorJS uses for the core; turn it off in EmulatorJS's own settings menu (**Virtual Gamepad**) and it stays off in that browser. The PSP tab gets it too.
  - **Screenshot** (Admins): the Play dialog's toolbar has a **Screenshot** button after the save buttons. It takes a PNG of the running game at its native size (EmulatorJS's own screenshot format and upscale settings are ignored) and shows it over the game with **Save as Snap** and **Discard**; **Save as Snap** adds it to the game's images as a Snap ("Screenshot saved to the game's images"), and the game page shows it at once. A new screenshot replaces the one shown; closing the dialog discards it. Before the game has started it says "Start the game first.". PSP has no Screenshot button (its player is a separate tab).
- **Images** has, for Admins, **Google Images** (opens Google Images in a new tab for the same query as the header's **Google** link) and the **Upload Image** button, right-aligned above the grid, and shows every image of the game as a thumbnail with its type (Box art, Screenshot, …), a **Cover** badge on the one shown at the top and a **Placeholder** badge on the default cartridge art, its size as a badge at the top right and its dimensions below. A tile lifts slightly with a shadow on hover or focus (only the shadow when the browser asks for reduced motion). Click one to see it full size. Under each image, **Download** (everyone) saves it as `<game title>-<image id>.<ext>`, followed for Admins by **Use as cover** and **Delete**.
- **Zip Contents** browses the game's ZIP: a folder tree on the left (the root is the ZIP's file name; every folder starts expanded, only the chevron expands or collapses one, and selecting a folder never changes that; the selected folder is highlighted) and the selected folder's sub-folders and files on the right, in a table with cell borders, with size and compressed size as badges, the modified time and a download button per file (a folder row leaves those cells empty; long names are cut off, with the full name on hover, so the table never scrolls sideways; below the `md` breakpoint the compressed size and modified columns are hidden). Reloading the same game keeps the folders you collapsed; another game starts expanded again. A breadcrumb above selects any parent folder, and a footer line counts the files and their total size and compressed size for the whole ZIP. The listing loads the first time you open the tab and again after the game changes; the selected folder is kept while it still exists.
- If the game changed since you opened it (someone edited it, or an ingest added a release), an action on a release reloads the page and says "This game changed, please retry".

**Image management** (Admin):

- **Upload Image** opens a dialog for a PNG or JPEG (at most 8 MiB) and its type (the **Box art** / **Screenshot** buttons, Box art by default). **URL** (the default) takes an http or https address: the server downloads the image (public internet addresses only, at most 15 seconds and 8 MiB, PNG or JPEG) and stores it like an upload, then says "Image added from <host>.". When the server can't use the URL (it couldn't connect, timed out, got an error status or too many redirects, the address is private or local, or the response isn't a PNG or JPEG of at most 8 MiB) the reason appears under the field with **Upload a file instead**, which switches to File and keeps the type: download the image yourself and upload the file. **File** uploads a file from your computer; you can also drag an image file onto the dialog, which switches to File and uses it (with several files, the first, and the dialog says so). Each time the dialog opens it starts on URL, empty, with the cursor in **Image URL**; pressing Enter there uploads as the **Upload** button does. A failed upload keeps the dialog open with the error; a successful one closes it. A game holds at most 20 images, and the same image can't be added twice. Uploading box art replaces the placeholder, and takes over as cover if the placeholder was the cover. When that placeholder was the cover, the upload (from a file or a URL) also starts an integrity check of that game alone, in the background, so its *DefaultBoxArt* issue clears without a full deep check; it's skipped when another job is running (the next Quick or Deep run clears it). A snap, a second box art or any other edit starts none.
- **Use as cover** makes any image the one shown at the top and in the Library.
- **Delete** removes an image (not the placeholder, which comes and goes on its own). Deleting the cover hands it to the first remaining box art, else the first remaining image, else the placeholder comes back.

Ingestion and **Retry media** only ever replace the placeholder; they never remove or replace an image you uploaded.

**Edit actions** (Admin; the game-level ones are in the **Manage** menu, the release ones in an expanded release card), each confirmed in a dialog:

- **Edit metadata:** title, year, developers, publishers and genres (one per line), description. Renaming a game also renames its ZIP. The displayed title is always derived from the title (a trailing ", The" moves to the front).
- **Retry media:** look up box art and a snap again for this game (replacing only the placeholder).
- **Merge into…:** move every release into another game of the same system (pick it by typing at least 2 characters of its name) and delete this one. The target keeps its own title, metadata and cover; only its empty fields are filled from this game. This game's images (not its placeholder) are copied over, and its box art replaces a placeholder on the target. A merge that would leave more than 20 images is refused. Up to five same-system suggestions appear above the picker. They search the cleaned title (up to eight words), falling back to the first word of at least three characters when nothing matches. Clicking a suggestion fills and selects the target; typing again clears it. Failed suggestion requests leave the picker usable.
- **Edit release** (Admins, in a release's details, on the Releases, Updates and DLC tabs) changes its tags: **Kind** (Release, Update or DLC), **Regions** (a checkbox list: World, USA, Europe, Japan, Asia, Australia, Korea and Brazil first, then the rest A–Z, then any region the release already has that isn't in the list), **Languages** (comma-separated codes, `En,Fr`), **Revision** (`Rev 1`), **Disc** (disc systems only), **Hack**, **Translated** and, for an update, **Version** (`1.0.1`). A line shows the new file name ("File name unchanged" when it stays); **Save** sends only what you changed, and nothing at all when you changed nothing. The release is renamed to match, editing only the changed tags' groups of its name ([format](zip-format.md#naming)); a disc system's releases keep their file names ("Disc releases keep their file name; only the tags change."), and an external release's file on disk keeps its name. Its note and the saves that name it follow. Success toasts "Release updated: <file name>" and switches to the tab the release now belongs to. Flags keep their order: a tag turned on is added at the end, and changing a release to Release or DLC drops its version. A release the Admin had made primary stops being the chosen primary when it becomes an update or DLC.
- **Move release** (in a release's details): move one release to another game, or to a new game with a title you choose. A game left with no releases is deleted.
- **Delete release** (in a release's details) and **Delete game:** the confirmation says when the release's note (or the game's notes) go too. The ROM files are moved to `ingest/<system>/_removed/`; an Admin can restore them to Ingestion, or delete them for good, on [Deleted ROMs](#deleted-roms). Deleting a game's last release deletes the game.

Edits and jobs take turns: while a job runs, an edit shows "Another job is running".

**Saves** (`?tab=saves`, between Images and Zip Contents) holds the game's save states and battery saves, stored in the game's ZIP ([format](zip-format.md#saves)). Saves are private: a save belongs to the user who uploaded it (its `uploadedBy`, matched ignoring case; a save with none belongs to nobody). A Site user sees and manages only their own saves; another user's save acts as if it doesn't exist. An Admin sees and manages every save, and an Admin's edit keeps the owner. The game's ZIP still holds every user's saves, so **Download ZIP** and the **Zip Contents** tab show them all to anyone who can open the game:

- A card headed **Saves**, with **Add save** on the right, holds the table, which lists each save, newest change first: name (with its description below), **State** or **Battery**, the release it belongs to ("Release removed" when that release is gone; the save stays, and plays again if a release of that name comes back), size and when and by whom it was last changed. An Admin also sees an **Owner** column (after Release) with the uploader, or *Unknown*.
- **Add save** takes a release, the kind, a name (1–100 characters), an optional description (up to 1,000 characters) and one file of any type (up to 256 MiB). Each user can have at most 25 saves per release (other users' saves don't count, for Admins too); a game's whole `saves.json` is still limited to 1 MiB, counting everyone's saves. **Edit** changes the name and description, **Replace** uploads new bytes, **Download** saves it as `<game title> - <save name><extension>`, and **Delete** asks first. Each change is audited (`SaveAdded`, `SaveUpdated`, `SaveDeleted`) and, like every edit, waits for a running job ("Another job is running").
- **Play** (shown when the save's release can be played in the Play dialog) opens the dialog with the save loaded as soon as the game starts. A battery save asks first, since it replaces the browser's own save for that release. Battery saves can't be played on DeSmuME (DS) or Opera (3DO), whose battery saves don't go through EmulatorJS's save file; PSP saves can be uploaded and downloaded but not played from here.
- The **Play dialog** has **Save state to library** (every core it hosts) and **Save battery to library** (all but DeSmuME and Opera). They copy the running game's state or battery save into this list: they replace your own newest save of that kind for the release, or add one as `State|Battery <date time>`, to be renamed later (another user's save is never replaced); nothing is written to the library unless you click them. Saving fails with a message before the game has started, while 3DO is saving on close, when the emulator can't save states, or when there's no battery save yet.
- **Battery saves load and store themselves** (all cores with **Save battery to library**): opening Play without a chosen save starts the game with your newest battery save of that release (a spinner shows while it's looked up; a failed lookup plays without one), replacing the emulator's own in-browser copy. Closing the dialog copies the battery save into the library: it replaces the save you played (when it's your own battery save), else your newest battery save of the release, else adds one, and toasts "Battery save stored in the library". A game with no battery save, one that never started, or a player that doesn't answer within 5 seconds stores nothing and says nothing; any other failure toasts "Couldn't store the battery save" and the dialog still closes. An Admin playing another user's save never overwrites it. Closing while **Save battery to library** runs waits for it. Every close of a started game rewrites the ZIP. Battery saves from other emulators (`.sav`, `.srm`) can be uploaded as **Battery** (the upload form says so).
- **Save counts** (the Library's save badge and `Saves (n)`) count only your own saves for a Site user, and every save for an Admin. A Site user's counts come from a per-user table the library fills each time a game's ZIP is written; after an upgrade they read 0 on a game until its ZIP is next written (any edit or save change, or a sync that finds the ZIP changed).
- When a game's `saves/` folder can't be read, every save action answers "This game's saves folder can't be read. An Admin must repair it." The app never repairs it; an Admin fixes the ZIP by hand ([format](zip-format.md#saves)).

## Ingestion

`/ingestion` (Admin) lists the files waiting in each system's ingest folder (`ingest/gb/`, `ingest/gbc/`, `ingest/gba/`, `ingest/n64/`, `ingest/nes/`, `ingest/snes/`, `ingest/vb/`, `ingest/a2600/`, `ingest/a5200/`, `ingest/a7800/`, `ingest/lynx/`, `ingest/jaguar/`, `ingest/coleco/`, `ingest/gg/`, `ingest/sms/`, `ingest/md/`, `ingest/s32x/`, `ingest/tg16/`, `ingest/switch/`, `ingest/psx/`, `ingest/psp/`, `ingest/gc/`, `ingest/wii/`, `ingest/x360/`, `ingest/saturn/`, `ingest/nds/`, `ingest/3ds/`, `ingest/segacd/`, `ingest/3do/`, `ingest/c64/`, `ingest/pet/`, `ingest/vic20/`, `ingest/amiga/`) with size and time. The **Run** section shows only while a job runs (progress and Cancel) or while DATs are missing (a link to **Admin → DATs**). **Pending files (n)**, **Failed files (n)** and **Last runs** are accordion panels below it (`n` counts files across all systems), one open at a time; Pending files starts open and holds **Import all** and **Import selected (n)** at its top. `?tab=failed` and `?tab=runs` open that panel instead (old links keep working) and are then removed from the address. Closing a panel keeps your checkbox selections and doesn't reload the lists.

- Drop `.gb`/`.gbc` files, or `.zip`/`.7z` archives of them, into either of those two folders: the cartridge header decides whether a game is stored as Game Boy or Game Boy Color. Drop `.gba` files (or archives of them) into `ingest/gba/`. Drop Nintendo 64 dumps (`.z64`, `.v64` or `.n64`, or archives of them) into `ingest/n64/`: all three byte orders are accepted, converted to big-endian before hashing (the order comes from the file's first bytes, not its extension) and stored as `.z64`, so the same game dumped in two orders is a `Duplicate`. Drop NES dumps into `ingest/nes/`: only headered `.nes` files (iNES or NES 2.0 header), hashed with the header as the No-Intro DAT does; headerless (`.unh`), UNIF, Famicom Disk System and NSF files aren't supported, and a dump whose header differs from No-Intro's goes to Review. Drop SNES dumps (`.sfc` or `.smc`, or archives of them) into `ingest/snes/`: a 512-byte copier header is stripped before hashing whenever the file size is 512 bytes past a multiple of 1 KiB (whatever the extension), so headered `.smc` dumps match the No-Intro DAT; the game is stored as `.sfc` without the copier header, and the same game with and without one is a `Duplicate`. Satellaview, Sufami Turbo, `.swc`/`.fig` and interleaved or split dumps aren't supported. Drop Atari 2600 dumps (`.a26` or `.bin`, or archives of them) into `ingest/a2600/`: a matched dump is stored under the DAT's ROM name (`.a26` or `.bin`, as the DAT says). 2600 cartridges have no header, so an unmatched file is never `InvalidHeader`: it always goes to Review (`NoDatMatch`, suggestions from the file name), and once resolved it's stored as `.a26`. Supercharger `.wav` tapes aren't supported. Drop Atari Lynx dumps (`.lnx` or `.lyx`, or archives of them) into `ingest/lynx/` and Atari Jaguar dumps (`.j64`, `.jag`, `.rom`, `.abs` or `.cof`, or archives of them) into `ingest/jaguar/`. Lynx headers are optional and Jaguar cartridges have no standard header. Unmatched files go to Review (`NoDatMatch`), and a release resolved without a DAT entry uses `.lnx` or `.j64`, respectively. Lynx `.bll` homebrew and Jaguar CD are unsupported. Drop Virtual Boy dumps (`.vb`, or archives of them) into `ingest/vb/`, Atari 5200 dumps (`.a52` or `.bin`) into `ingest/a5200/` and Atari 7800 dumps (`.a78` with its header, or a headerless `.bin`) into `ingest/a7800/`. None of them fails as `InvalidHeader` (Virtual Boy and 5200 cartridges have no header and the 7800 header is optional), so an unmatched file goes to Review; resolved without a DAT entry it's stored as `.vb`, `.a52` or `.a78`. libretro's 7800 metadat lists only the `.bin` dumps, so a game matched by its `.a78` dump has no year, developer, publisher or genre. Drop ColecoVision dumps (`.col`, `.rom` or `.bin`, or archives of them) into `ingest/coleco/`: a matched dump is stored under the DAT's ROM name (`.col`). An unmatched file must start with the cartridge magic `AA 55` or `55 AA`, or it fails as `InvalidHeader`; with it, it goes to Review (`NoDatMatch`, suggestions from the file name) and once resolved it's stored as `.col`. MegaCart and other homebrew ROMs over 32 KiB, Coleco ADAM and Super Game Module titles aren't supported. Drop Commodore 64 tapes (`.tap`, `.t64`), disk images (`.nib`, `.d64`, `.g64`), cartridges (`.crt`, `.bin`) and programs (`.prg`), or archives of them, into `ingest/c64/`. None fails as `InvalidHeader` (the CRT/TAP/G64/NIB headers are optional), so an unmatched file goes to Review, which keeps its extension. libretro has no C64 metadat, so C64 games have no year, developer, publisher or genre; each side of a multi-side game is its own release. Drop Commodore PET programs (`.prg`) and disk images (`.d64`) into `ingest/pet/`: they are matched against libretro's TOSEC PET DAT, have no header (an unmatched file goes to Review, which keeps its extension) and no metadata. Drop Commodore VIC-20 cartridge dumps (`.a0`, `.20`, `.40`, `.60` or `.bin`, or archives of them) into `ingest/vic20/`: they are matched against libretro's No-Intro VIC-20 DAT, have no header (an unmatched file goes to Review, which keeps its extension, since it names the load address) and no metadata. Drop Commodore Amiga floppy images (`.adf`, or archives of them) into `ingest/amiga/`: they are matched against libretro's TOSEC Amiga DAT, have no header (an unmatched file goes to Review) and no metadata; each disk of a multi-disk game is its own release. `.ipf`, `.adz`, `.dms`, `.hdf` and WHDLoad `.lha` aren't supported. Drop Game Gear dumps (`.gg` or `.sms`, or archives of them) into `ingest/gg/`: `.sms` covers the Game Gear DAT's SMS-mode games, and a matched dump is stored under the DAT's ROM name (`.gg` or `.sms`). The `TMR SEGA` header (at 0x7FF0, 0x3FF0 or 0x1FF0) is optional, since many Japanese carts have none, so an unmatched file is never `InvalidHeader`: it goes to Review (`NoDatMatch`, suggestions from the file name). SG-1000 games aren't supported. Drop Master System dumps (`.sms` or `.sg`, or archives of them) into `ingest/sms/`: the same optional `TMR SEGA` header as Game Gear, so an unmatched file goes to Review (`NoDatMatch`, suggestions from the file name) and once resolved it's stored as `.sms`. A `.sms` file in `ingest/gg/` is still a Game Gear file and one in `ingest/sms/` a Master System file: the folder decides. Drop Mega Drive / Genesis dumps (`.md`, `.bin` or `.gen`, or archives of them) into `ingest/md/`: a matched dump is stored under the DAT's ROM name (`.md`, so a matched `.bin` or `.gen` becomes `.md`). The `SEGA` header at 0x100 is optional, so an unmatched file goes to Review (`NoDatMatch`, suggestions from the header's title and the file name) and once resolved it's stored as `.md`. Interleaved `.smd` dumps, Mega-CD and Pico aren't supported. Drop 32X dumps (`.32x`, or archives of them) into `ingest/s32x/`: 32X games carry the same optional `SEGA` header at 0x100 (system type such as `SEGA 32X`), read the same way, so an unmatched file goes to Review (`NoDatMatch`, suggestions from the header's title and the file name) and once resolved it's stored as `.32x`; a `.md`, `.bin` or `.gen` file there, or a `.32x` file in `ingest/md/`, fails as `UnsupportedType`. 32X CD games and `.bin` 32X dumps aren't supported. Drop TurboGrafx-16 / PC Engine HuCard dumps (`.pce`, or archives of them) into `ingest/tg16/`: the DAT mixes Japanese PC Engine and US TurboGrafx-16 releases, and a matched dump is stored under the DAT's ROM name (`.pce`). A 512-byte copier header is stripped before hashing whenever the file size is 512 bytes past a multiple of 8 KiB, so headered dumps match the DAT and are stored without it; the same game with and without one is a `Duplicate`. The strip goes by size alone, so three aftermarket protos in the DAT whose real size fits that rule (`Gnop`, `Masteroids`, `Light Cycles`) don't match and go to Review. HuCards have no header, so an unmatched file is never `InvalidHeader`: it always goes to Review (`NoDatMatch`, suggestions from the file name), and once resolved it's stored as `.pce`. SuperGrafx, TurboGrafx-CD / PC Engine CD and bit-reversed (undecrypted) US dumps aren't supported. Drop Nintendo DS cartridge dumps (`.nds`, or archives of them) into `ingest/nds/`: a matched dump is stored as a file next to the game's ZIP under the DAT's ROM name (see [External storage](#external-storage-nintendo-switch-nintendo-ds-nintendo-3ds-and-disc-systems)), and the No-Intro DAT's `.bcn`, `.bin` and `.ids` entries are ignored. An unmatched file with a bad cartridge header CRC fails as `InvalidHeader`; with a valid one it goes to Review (`NoDatMatch`, suggestions from the header's title and the file name) and once resolved it's stored as `.nds`. Archives hold at most 256 MiB of ROM data, so a dump over that must be dropped loose. DSiWare and DSi-mode execution aren't supported. Drop Nintendo 3DS dumps (`.3ds`, `.cci` or `.cia`) into `ingest/3ds/`: a matched dump is stored as a file next to the game's ZIP under the DAT's ROM name with its own extension kept (lower-cased, so a `.cci` stays `.cci`), and there is no **Play** button. Archives hold at most 256 MiB of ROM data, so most dumps must be dropped loose. Decrypted or trimmed dumps never match the DAT: they go to Review (an unmatched `.cia` always does; an unmatched `.3ds`/`.cci` needs an `NCSD` header, or it fails as `InvalidHeader`), and Review keeps their extension. Drop Nintendo Switch dumps (`.nsp`, `.xci`, `.nsz` or `.xcz`) into `ingest/switch/`; see [External storage](#external-storage-nintendo-switch-nintendo-ds-nintendo-3ds-and-disc-systems) for how they're identified and stored. Drop PlayStation discs (a `.cue` with its `.bin` tracks, or a `.bin`/`.iso`/`.chd`) into `ingest/psx/`, Saturn discs (a `.cue` with its `.bin` tracks, or a `.nrg`/`.chd`) into `ingest/saturn/`, PSP, GameCube and Xbox 360 `.iso` files into `ingest/psp/`, `ingest/gc/` and `ingest/x360/`, and Wii `.iso` or `.wbfs` files into `ingest/wii/` (split `.wbf1`, `.wbf2`… files aren't picked up: join them first); see [Disc sets](#disc-sets) for how they're matched and stored. A Wii disc dropped in `ingest/gc/` (or a GameCube disc in `ingest/wii/`) is stored under the system its header names. Switch files inside an archive are ingested only within the usual archive limits (100 entries, 256 MiB extracted), so in practice only small files such as DLC. Because `.md` is also Markdown, a `README.md` inside an archive in `ingest/md/` is treated as a ROM entry: a small one fails `TooSmall` (the game is still ingested, but the archive goes to `_failed/`), a larger one goes to Review. `.bin` is accepted in `ingest/a2600/`, `ingest/a5200/`, `ingest/a7800/`, `ingest/coleco/`, `ingest/c64/`, `ingest/vic20/` and `ingest/md/`: the folder decides the system. Game Boy, Game Boy Advance, Nintendo 64, NES, SNES, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Commodore 64, Commodore VIC-20, Commodore Amiga, Game Gear, Master System, Mega Drive, 32X, TurboGrafx-16 and Switch are separate families, so a file with another family's extension in a system's folder (a `.gba` file in a GB folder, a `.n64` file in `ingest/gb/`, …) fails as `UnsupportedType`. Size limits (per file, so per track for a disc set): 336 bytes–16 MiB for GB/GBC, 192 bytes–32 MiB for GBA, 4 KiB–64 MiB for N64, 4,112 bytes–64 MiB + 528 bytes for NES, 8 KiB–8 MiB + 512 bytes for SNES, 64 KiB–4 MiB for Virtual Boy, 2–64 KiB for Atari 2600, 4–64 KiB for Atari 5200, 4 KiB–1 MiB for Atari 7800, 1 KiB–1 MiB for Lynx, 16 KiB–16 MiB for Jaguar, 8–32 KiB for ColecoVision, 1 KiB–8 MiB for Commodore 64, 2–64 KiB for Commodore VIC-20, 256 KiB–4 MiB for Commodore Amiga, 8 KiB–1 MiB for Game Gear, 2 KiB–4 MiB for Master System, 8 KiB–16 MiB for Mega Drive, 16 KiB–4 MiB for 32X, 72 KiB–2.5 MiB + 512 bytes for TurboGrafx-16 (checked on the file as dropped, before the strip), 1 KiB–64 GiB for Switch, 16 bytes–1 GiB for PlayStation and Saturn, 16 bytes–8 GiB for PSP, 32 KiB–9 GiB for GameCube and Wii, 2 KiB–9 GiB for Xbox 360, 512 bytes–512 MiB for Nintendo DS, 16 KiB–4 GiB for Nintendo 3DS. GameCube and Wii share their limits on purpose: ingest checks a file's size against the first system of the family that lists its extension. An unmatched file whose header isn't valid for its system fails as `InvalidHeader`; for N64 that only checks the first byte, so a junk file with an N64 extension may land in Review instead; for NES it checks the `NES` + EOF magic; for GameCube and Wii the disc header's magic word (PlayStation, PSP, Xbox 360 and Saturn have no header check, so an unmatched file always goes to Review); for SNES the internal header (LoROM, HiROM or ExHiROM) must have a valid checksum/complement pair, or a printable title with a map mode that fits its location (a file under 32 KiB has no header to check and goes to Review). Subfolders, hidden files and files changed in the last 10 seconds are left for the next run.
- **Import all** runs through every waiting file, showing progress and the current file. While a large Switch file is hashed, or copied into the library (when `ingest/` and `roms/` are on different volumes or the file system can't rename or hard-link), a second, thinner bar shows that file's progress: `Hashing`, `Copying to library` or `Copying` (to `_failed/`, `_duplicates/` or back after a failed import), with bytes done of the total, the speed and the time left once a second has passed. Small in-ZIP ROMs show no second bar. **Cancel** stops after the current item (a whole archive is finished first). Each pending file has a checkbox (all checked after every reload; a header checkbox per system, and **Select all** / **Clear selection**); **Import selected (n)** ingests only the checked files and leaves the rest in place. It is disabled when nothing or everything is checked. Ingestion needs the DATs of every system, Switch's titledb file included: until they've been downloaded the page shows a link to **Admin → DATs** instead of the import buttons, and both imports return `409 DatsMissing` (also for a selection without Switch files).
- **Delete** (the trash button on a row, or **Delete selected (n)** for the checked files) permanently deletes pending files from the ingest folder, with their pending Review items. It can't be undone. A confirmation lists up to 10 files as `system/name`. **Shift+click** on a row's delete button skips the confirmation, except for a `.zip`/`.7z` archive, which always asks; **Delete selected** always asks. Delete buttons are disabled while a job runs.
- **Failed files** lists, per system, the files in its `_failed/` folder with the reason from their `.error.txt` (`—` when there is none), size and time, 20 per page. Its checkboxes start empty after every reload. Deleting a failed file (same buttons and rules as above) also deletes its `.error.txt`. Files in `_duplicates/` aren't listed; those in `_removed/` are on [Deleted ROMs](#deleted-roms).
- **Last runs** lists the 10 most recent runs with their outcome counts; open one for the details.

What happens to each file:

| Outcome | Meaning | The file |
|---|---|---|
| Ingested | identified and added to the library (new game or new release) | deleted from ingest |
| Repaired | a byte-identical copy of a library ROM that integrity had flagged as damaged or missing | deleted, library entry rewritten |
| Duplicate | already in the library | moved to `_duplicates/` |
| Review | not in the DATs, or matches a game that several library games share | stays in ingest; shown in the Review queue |
| Failed | not a usable ROM (wrong type, too small/large, invalid header, unsafe or corrupt archive, dismissed) | moved to `_failed/` with a `.error.txt` explaining why |
| Error | a problem on the server's side (disk, database) | left in place; the next run retries it |
| Skipped | changed in the last 10 seconds | left for the next run |

Box art and snaps come from libretro-thumbnails, or for Switch from the image URLs titledb lists (Nintendo's `img-eshop.cdn.nintendo.net`, PNG or JPEG); a game gets the placeholder when none is found, which **Retry media** or **Integrity → Retry missing media** can fix later.

## External storage (Nintendo Switch, Nintendo DS, Nintendo 3DS and disc systems)

Each system either keeps its ROMs inside the game's ZIP (every cartridge system but Nintendo DS and Nintendo 3DS) or stores them **externally**: as plain files next to the ZIP. Switch, Nintendo DS and Nintendo 3DS name each file `<ZipBase>.<rom fileName>` (for example `roms/switch/O/Orbit Expedition.zip` and `roms/switch/O/Orbit Expedition.Orbit Expedition [0100000000010000][v0].nsp`); the disc systems keep each file's exact name (see [Disc sets](#disc-sets)). The ZIP still holds `info.json`, images and notes; `info.json` names each file ([format](zip-format.md#external-rom-files)). Every system in a family stores the same way. Only Nintendo DS can change: an Admin switches it under **Admin → ROM Zip Config** (see [ROM Zip Config](#rom-zip-config)); every other system's storage is fixed.

- **Ingest:** a Switch file is hashed in one streamed read, never loaded into memory, and its header is read from its first MiB. The title ID comes from the PFS0's ticket name (`<id>….tik`) when the header has one, else from the first `[0100…]` in the file name (XCI dumps don't carry it in the plain header). A header ID that isn't a Switch ID (such as a Switch 2 `0400…` ticket) means no match, whatever the file name says. The file is moved next to the ZIP right before the ZIP write and moved back if that write fails; it keeps its own extension (`.xci` stays `.xci`).
- **titledb matching:** the low bits of the title ID say what it is. A base game matches its own titledb entry; an update (`…800`) and DLC (including DLC data patches and application deltas) match through their base game's entry, and are stored in the base game's ZIP flagged `Update` or `DLC` (shown on the Game page's Updates or DLC tab). The release is named from its own entry when titledb has one (else the base name, with ` (DLC)` for DLC), with `[<TitleId>][v<N>]` and `N` from `[v<N>]` in the file name; the identification method is `TitleDb`. An update also gets its version from the first `[x.y.z]` tag in the file name (`DREDGE[UPD][1.0.1].nsp` → `1.0.1`), added to its name as `[<TitleId>][v<N>][1.0.1]` so two updates of a game never clash, and shown on the Game page's Updates tab. A file whose title ID comes from its name (no ticket in the dump) and is a base game's ID, but whose name contains `[UPD]` (any case), is taken as that game's update; a title ID read from the file itself is never changed by `[UPD]`. The base game's release is the primary one even when it's flagged Hack; updates and DLC are primary only when no base release is left. A new game takes its year, publisher and genres from the base entry. Anything titledb doesn't cover goes to Review (`NoDatMatch`, with titledb suggestions), or fails `InvalidHeader` when the header isn't a PFS0 or XCI.
- **Downloads:** each release downloads its own file, with HTTP range support (downloads can resume); **Download ZIP** returns the metadata ZIP only.
- **Edits** work as for every system and need an Admin and the same global job lock. A title edit renames the ZIP and every file together (a disc system's files keep their names, and move only when the letter folder changes); moving or merging a release moves its file next to the target ZIP; deleting a release or game moves its files to `ingest/switch/_removed/`. Any failure moves the files back.
- **Integrity** checks every external file's length on each run and its SHA1 on a deep run (`EntryMissing`, `EntrySizeMismatch`, `HashMismatch`), and reports files in a system folder that no game lists as `OrphanFile`. Ingesting a byte-identical copy repairs a missing or damaged file, as for embedded ROMs.
- **Library Size** counts each game's ZIP plus the recorded sizes of its external files (a disc set's other files included), including files that are missing.
- **Nintendo DS** is stored next to the ZIP by default (it became external in the release that added save management), and an Admin can store it inside the ZIP instead ([ROM Zip Config](#rom-zip-config)). A DS game whose ROMs are in the other place than the configured one (a game stored before that release, or one the **storage job** hasn't reached since the setting changed) waits for the storage job to move it, in either direction: the job starts by itself once the app has started (retried every 5 minutes while another job runs) and after each change, takes one item per game (`Migrated`, or `Error` with a reason such as `InsufficientSpace`, `IoError` or `VerifyFailed`, leaving that game's ZIP and files untouched) and records `RomsExternalized` or `RomsEmbedded` in the audit log. Moving into the ZIP streams each file in, checks every entry's size and SHA-1 against `info.json` before the new ZIP replaces the old one, and only then deletes the files (a file changed meanwhile is kept, as is every file when the database update fails; Integrity then reports them as `OrphanFile`). Until it is moved, such a game plays, lists and downloads from wherever its ROMs are, but every edit to it, including rating, notes, images and saves, answers `409 StorageMigrationPending`, an import of a new release into it ends as `Error` (`StorageMigrationPending`) and stays in ingest, and integrity reports it as `LegacyEmbeddedStorage` (Warn). New DS releases, Review resolutions and ingest-folder handling follow the configured storage; a byte-identical copy of a DS ROM in either place is a `Duplicate`. Admins resume the job from **Integrity → Resume ROM storage moves (N)** or **Admin → ROM Zip Config → Resume moves**, shown while such games remain (`GET /api/jobs/storage-migration` → `{pendingGames}`, `POST` → `202 {jobId}`, `204` when none wait, `409 JobRunning`).

### Disc sets

PlayStation, PSP, GameCube, Wii, Xbox 360, Saturn, Sega CD and 3DO are identified against the libretro [Redump](http://redump.org/) DATs (`metadat/redump/`), which have no year, developer, publisher or genre files, so their games have none of those until you edit them. Their files are stored externally under their **exact names**: no `<ZipBase>.` prefix and no ` (2)` suffix.

- **Wii WBFS:** if a `.wbfs` file has no SHA1 match, ingestion uses the first four characters of its Wii game ID to look up Redump serials, then filters by disc number and revision. One match stores the file under the DAT ROM stem with its `.wbfs` extension and own hashes, identified by `Game ID`. With zero or multiple matches, a valid WBFS header sends it to Review.
- **Sets (PlayStation, Saturn, Sega CD, 3DO):** each run first groups every loose file in `ingest/psx/`, `ingest/saturn/`, `ingest/segacd/` or `ingest/3do/` by its `.cue`: a cue (at most 64 KiB, `FILE "<name>" BINARY` lines) and the `.bin` tracks it names are one set, processed together even in an **Import selected** run when any one of them is checked. The set's data track is the one track whose hash is in the DAT; the game is stored as one release whose main file is that track, with the cue and the other tracks as its **files**, each under its own name next to the ZIP.
- **Waiting sets** stay in ingest, `Skipped`, and are retried on the next run: `IncompleteSet` when a file the cue names is missing (or the cue can't be read; then the `.bin` files starting with its name wait too), or when a lone `.bin` matches a `(Track N)` data track whose cue hasn't arrived; `UnsupportedSetMember` when the cue names something other than a `.bin`; `SetConflict` when two cues name the same file; `AmbiguousGroup` when two or more games share the data track's title; `AlreadyInReview` for an unmatched track whose bytes are already queued (silent audio tracks repeat). A track that's too small or too large fails on its own and the rest wait as `IncompleteSet`.
- **No match:** every member goes to Review as `NoDatMatch`; when two or more tracks match the DAT, as `AmbiguousSet`. A complete unmatched set is resolved in Review as one release from any of its members (see [Review queue](#review-queue)); an `AmbiguousSet` member, or a `.cue`/`.bin` whose set isn't complete in ingest, can only be deleted. A lone `.iso`, `.wbfs`, `.nrg` or `.chd` can be resolved.
- **CHD (PlayStation, Saturn, Sega CD):** a MAME `.chd` is always a release of its own. Redump lists the `.bin` tracks, and a CHD's own hash covers its compressed container, so a `.chd` never matches the DAT and always goes to Review as `NoDatMatch`. Resolve it with **Manual**, a **DAT pick** (stored as `<DAT game> (Unverified).chd`) or **Attach** (Release, Hack, Translated or `Disc <n>`), or dismiss it. A `.cue` that names a `.chd` waits with it as `UnsupportedSetMember`. A `.chd` and a bin/cue of the same disc are separate releases: they can't be attached to one game as the same disc.
- **Single files:** an `.iso` or `.chd` (or a `.bin` no cue names, matching a single-track DAT entry) is one release with no other files, named after the DAT entry. A `.cue`/`.bin` in `ingest/psp/`, `ingest/gc/`, `ingest/wii/` or `ingest/x360/` fails `UnsupportedType`.
- **Archives:** a `.zip` or `.7z` in a disc system's folder is `Skipped` `ArchiveNotSupported` and left in place; drop disc images loose.
- **Names:** a name already used in the target folder stops the import (`Error` `NameTaken`, nothing moved), and a name over 250 UTF-8 bytes is `Error` `NameTooLong`; rename the file and ingest again. Title edits, moves and merges refuse a taken name with `409 NameTaken` before any file moves; within one letter folder the files don't move at all.
- **Edits and integrity:** every file of a set moves with its release (move, merge, a title edit to another letter folder) and goes to `_removed/` with it; integrity checks each file's length (and hash on a deep run) and reports a missing track by its name. Dropping the whole set again repairs a missing or damaged cue or track.
- **GameCube / Wii header:** the release's header shows the disc's game id, disc number, version and title.

## Jobs

`/jobs` (Admin, from the footer's job indicator or a job page's **All jobs** link) shows the running job in a table like the recent jobs (label, progress with current item, start time, a link to its page and **Cancel** when it can be cancelled) or a "No job running." row, then every recent job, newest first and paged: label, trigger, status, start and end time and a link to its page. The list reloads when the running job ends. Job labels are Title Case everywhere a job type shows (footer, Jobs, job pages, Activity, Integrity, Ingestion and DATs): Ingest, Integrity Check, DAT Refresh, Media Retry, Review, Moving ROMs, Repacking ZIPs, Moving Saves to User Folders (an unknown type shows as is). The running table keeps fixed column widths, so a long current item ends in "…" (its full text in the tooltip) instead of resizing the table; on a phone the table scrolls sideways.

## Job detail

`/jobs/{id}` (Admin) is headed "<label> Job" (for example "Ingest Job", "Ingest (Quick) Job", "DAT Refresh Job") and shows any job (ingestion, integrity check, DAT refresh, media retry, review resolution, storage job, save folder job), with an **All jobs** link back to `/jobs`: status, start and finish time, how it was started, its summary (counts, or a review resolution's `reviewId`, `fileName`, `gameId`, `code` and `errors`; a value that isn't text or a number shows as JSON) and any error, with live progress while it runs (in fixed-width columns, the current item truncated with its full text in the tooltip), plus a **Current file** row with the same per-file bar while a large file is hashed or copied. For an ingestion it also lists every item with its outcome, reason and details (filter by outcome), and links each ingested file to its game.

**Moving saves to user folders** (`SaveFolders`) runs once, by itself, after the app starts on a version that keeps saves in per-user folders ([format](zip-format.md#saves)), retrying every 5 minutes while another job runs. It reads every game's saves: a game with none or already moved is `Skipped`, an old-layout game is rewritten with each save in its owner's folder (a save without an owner becomes `admin`'s) and is `Moved`, and an unreadable saves folder, a game still waiting for the storage job, low disk space or a failed write is `Error` (that game moves on its next save write). Its summary is `{moved, skipped, error}`; each moved game is audited as `SaveUpdated` "Moved saves to user folders". When it ends without being cancelled the `app_settings` row `saves.folders.migrated` is set to `true` and it never runs again (a restored backup from before it runs it again, harmlessly).

`POST /api/jobs/{id}/cancel` (Admin) cancels the running job: `202`, `404` when that job isn't running, and `409 NotCancellable` ("This job can't be cancelled.") for a review resolution.

## Review queue

`/review`, the **Review Queue** (Admin; the navbar badge shows how many are waiting), lists files ingestion couldn't place: file, system, size, the title from the cartridge header, the reason and when it was added. Open one to see its hashes and header and choose a resolution:

An item's page shows how many items are still pending under its title ("1,234 items to go", "1 item to go", "No items left"; the item on screen counts while it's pending), numbers in its header table with thousands separators, and an icon on each tab (Suggestions, Matched DAT entry, Attach, Manual).

Filter the list by file name or header title (case-insensitive substring), system and reason. Text applies after 300 ms; filters and page are kept in the URL and saved in this browser. An explicit URL wins; opening `/review` without filter parameters restores the saved view. **Clear** removes both URL and saved state. A filtered empty list says "No review items match this filter."

- **Not in the DATs** (`NoDatMatch`):
  - **Suggestions:** up to five DAT entries with similar names, with a match score. **Use** adds the file as an *unverified* release of that entry (its hashes differ from the DAT's, so it gets an `(Unverified)` file name and flag). For Switch the entries come from titledb (`<title> [<TitleId>]`, no size shown), the page says "Choose a titledb result to identify this release by title ID." and **Use** stores the release exactly as automatic matching would for that ID (method `TitleDb`, no `Unverified` flag), named from the file's own `[v<N>]` and extension. One **This file is an update** checkbox above the suggestions and the search results (ticked to start with when the file name contains `[UPD]`, any case) applies to every **Use**: ticked, a base game's entry stores the file as that game's update (its ID + `800`), and an update's entry as that update, flagged `Update` with its version and the toast "Added update of <entry>."; ticking it for a DLC entry is refused.
  - **Use and Next**, next to each suggestion's **Use**, resolves the file exactly as **Use** does and then opens the next Pending item of the queue (the first one in the queue's order, within your saved filter) instead of the game; when none is left it opens the game. It is disabled while the page looks the next item up, when that lookup fails, and when no other item is left (then its tooltip says "No more items in the review queue.").
  - **Search the DAT** finds other entries by name; **Use** works the same way.
  - **Attach to a game as a new release, a hack or a translation:** pick the game and choose under **Attach as**: **Release** (the default), Hack or Translated. **Release** adds the file as another release of the game: its regions, languages, revision and flags are read from its own file name (a disc set's from its cue's name, without `Disc <n>` or `Track <n>`), it gets the flag `Unverified` and ` (Unverified)` in its file name (each not added twice), so DAT-verified releases stay primary; a clashing file name gets ` (2)`… Hack and Translated keep the game's title and get only that flag. On a disc system you can also choose **Disc** with a disc number (1–99, required) to add the file as another disc of any game of the system: it takes the game's title and its primary release's regions, languages and revision, gets the flag `Disc <n>`, and keeps its own file name plus ` (Disc <n>)` (not added twice when the name already has it).
  - **Manual entry:** title, regions, languages, flags (comma-separated) and revision, plus an optional **Disc** number (1–99) on a disc system, which becomes the flag `Disc <n>` after the other flags (a typed `Disc <n>` flag is replaced); the resulting file name is previewed. If several games already have that title, attach it to one of them instead.
- **Unmatched disc sets** (a `.cue` and its `.bin` tracks, all `NoDatMatch`): every member's page shows a **Set** card listing the files ("Resolving this item adds all N files as one release."), and any member's page resolves the whole set with the same tabs: a DAT pick (every file must fit the chosen system), Attach (Release, Hack, Translated or Disc) or Manual. The set becomes one release whose main file is the cue's first track (track 1, the data track by convention), with the cue and the other tracks as its files, each under its own name. A set whose track 1 is already in the library is refused as `Duplicate`, and nothing moves. A set member has no **Dismiss**. Limits: a set with an `AmbiguousSet` member, with a member that ingest skipped as `AlreadyInReview` (its bytes were already queued from another file, so it has no row of its own), or inside an archive can only be deleted.
- **More than one track matched** (`AmbiguousSet`, disc systems): two or more tracks of a set matched the DAT, so the set can't be stored; it can only be deleted.
- **Disc track files without a set** (a `.cue` or `.bin` of a disc system whose set isn't complete in ingest): the item page shows "Disc track files must match the Redump DAT to be imported." instead of the tabs, with no Dismiss button; only **Delete** remains. Fix the files (or refresh the DATs) and drop the whole set again.
- **Several games share its title** (`AmbiguousGroup`): the file matched a DAT entry by hash or a Wii WBFS game ID, and more than one library game has that title (e.g. after a move). Pick the game to **Attach** it to. The release keeps the original identification method.
- A file resolved with a DAT entry (picking a DAT game, or Attach for `AmbiguousGroup`) is stored with the DAT ROM name's extension (a Game Gear SMS-mode game stays `.sms`); when the DAT lists the chosen game more than once (Atari 7800 has `.a78` and `.bin` entries), the entry with the file's own extension is used, else the first; Manual entry and Hack/Translated attach use the system's first extension (`.gb`, `.col`, `.gg`, `.sms`, `.md`, `.32x`, `.pce`, …), except for Switch and the disc systems, where every resolution keeps the file's own extension. A system whose handler sets `KeepsSourceExtension` (Commodore 64 does) also keeps the file's own extension, for a DAT pick too. A disc image resolved with a DAT entry is named `<DAT game name> (Unverified)<ext>`.
- **Dismiss:** a loose file moves to `_failed/`; an archive is left as it is.
- **Delete** (on the item page, and the Delete button on each row of the queue): permanently deletes the file from the ingest folder after showing everything known about it in a dialog titled "Delete File: <file name>" (only its body scrolls; the title and buttons stay in view, and header numbers show thousands separators). For a file inside an archive, the whole archive is deleted, including every other file in it (the dialog warns). Every pending item from the same file or archive goes with it. Hold **Shift** while clicking Delete on either page to skip confirmation for a loose file; an archive always requires confirmation. Success names the deleted file, the queue reloads (moving back a page if necessary), and item-page deletion returns to the queue with its saved filter.

**Several at once:** tick rows (or the header box for the whole page; it shows a dash when only some are ticked). The selection is kept while you page through the same filter and cleared when the filter changes. **Delete selected (n)** asks first, listing up to 10 file names (`… and n more`) and warning when an archive entry is selected (it deletes its whole archive, other pending items included); **Shift+click** skips the question unless an archive entry is selected. The toast says how many were deleted and how many couldn't be; items already removed with their archive are skipped quietly.

The queue is paged (10–100 rows, your choice remembered per browser). An item's page shows the file details and header on the left and the ways to resolve it as tabs on the right: Suggestions (when there are any), Attach and Manual for `NoDatMatch` (an unmatched set's members included), Matched DAT entry for `AmbiguousGroup`, and none for a disc track file without a set.

**Review queue** (a button above the item) returns to the queue. Moving to another item without leaving the page (Use and Next, the Review next shortcut, a set member's link) starts that item afresh: the default tab, the update checkbox from its own file name, and empty search, Attach and Manual forms.

**Google it** in every item header opens a new tab with a quoted name, system name and `rom`. A header title with at least three letters or digits is preferred, otherwise the filename without its extension; parenthesized/bracketed tags are removed, underscores and dots become spaces. An empty cleaned name falls back to CRC32. These links only contact Google when clicked.

Every resolution runs as a background job (`ReviewResolve`), so a multi-GB Switch or disc image is hashed and moved without holding the request open. While it runs, every review item page shows "Resolving <file>…" with a spinner and the current file's step bar (`Hashing`, `Copying to library`), and disables its actions. On the item's own page, a resolution that ends opens the game (or, after **Use and Next**, the next item), or shows its error as an immediate failure would. If the file was removed from the ingest folder in the meantime, the item disappears with a message and you're back in the queue. If you've left the page, you're never taken anywhere: a toast says "<file> added to the library." with an **Open game** link, or "Resolving <file> failed: <code>." with an **Open review item** link (none when the source is gone). A resolution can't be cancelled: the Ingestion and Integrity pages show no Cancel button for it. After a full reload, or in another tab, the page doesn't know about the running resolution, and its actions get the usual "Another job is running" toast; a resolution whose job row stays `Running` (its final update failed) keeps the pages busy until a reload.

A `DbWriteFailed` result means the file and ZIP are already in the library and only the database update failed: the next ingest or integrity run brings the database in line. For a disc set, the set's rows then stay Pending but can't be resolved (their files are gone from ingest); **Delete** clears them one member at a time, and the next ingest run removes them too. A failure after the file was moved, whose move back put the file under a new ` (2)` name in `ingest/switch/` but couldn't update the Review item, also returns `DbWriteFailed`, naming both paths: once the original path is free, move the recovered copy back to it, or simply run ingestion again.

## Deleted ROMs

`/deleted` (Admin; navbar **Deleted ROMs**, with a badge counting the files) lists the ROMs that library edits (deleting a release or a game) moved to `ingest/<system>/_removed/`. Each system has a card (its badge, name and file count) with its files, 20 per page: name, size and modified time (an external system's file keeps its original time). **Select all** ticks every file of every system.

- **Restore** (per file, or **Restore selected (n)**) moves the files back to `ingest/<system>/` (a pending file of the same name is never replaced; the restored one gets ` (2)`…) and starts an import of just those files; the toast links to the job. If the import can't start (DATs missing, another job just began), the files wait on Ingestion. A file deleted less than 10 seconds ago is skipped by that import as too recent and also waits on Ingestion. Restore a disc set's `.cue` and tracks together, or each goes to Review on its own.
- **Delete** (per file, or **Delete selected (n)**) deletes the files permanently after a confirmation listing up to 10 of them; **Shift+click** skips it. It can't be undone.

Both are disabled while a job runs. Every restore and delete is audited.

## Reports

`/reports` opens **Newly Added**. The tabs, in order: Newly Added, Library Size, Missing Images, Duplicates, Multiple Releases, Games With Hacks, Image Resolutions, then Missing Metadata and Activity. Every signed-in user can use the first seven; **Missing Metadata** and **Activity** are for Admins only (their tabs are hidden for Site users, and their addresses show "Not allowed"). Each tab has an icon: Every report's **System** filter (Missing Images, Duplicates, Multiple Releases, Games With Hacks, Image Resolutions, Missing Metadata) is the Games page's System dropdown, without counts: a filterable menu of the systems that have ROMs (plus the chosen one), starting at **All systems**; its button reads "System" or "System: <name>" and is filled while a system is chosen.

- **Newly Added** (`/reports/newly-added`): the 10 newest games of each system, newest first, one tab per system (its badge with the short name, the full name as its tooltip; systems A–Z, the first selected), showing that system's Game (link), Added and Releases. Switching tabs doesn't reload the report. Empty: "No games yet."
- **Library Size:** total bytes (each game's ZIP plus the recorded sizes of its external files, a disc set's other files included, missing ones included) and game count, a treemap, and an equivalent table with games (or releases), **Updates** (releases flagged `Update`), sizes and percentages. Click a system tile, or anywhere in its table row, to drill into `?system=<id>`; Back returns to the library view. The link in each row's first cell stays for the keyboard and screen readers, and Ctrl/Cmd/middle click on it opens a new tab. A small Library button at the right of each system's cell ("Open <system> in Library") opens the Library filtered to that system. Game tiles and links open the game. Systems use the same colours as their badges. The system treemap draws the 300 largest games and one unclickable "n others" tile; the table lists every game. Empty libraries or systems show an empty state.
- **Missing Images:** filter by system and page through games with **No cover** or **Placeholder art**. A game matching both appears once as No cover. A placeholder that is not the cover does not count. Game links open the Images tab. An empty report says "Every game has a cover image."
- **Duplicates:** groups of games in the same system that share a release base title, compared without case or accents. This does not compare hashes, DAT names or games across systems. Filter by system and page through the groups. A game may appear in several groups. Each row shows title, releases, ZIP size and added date. Admins can choose a merge target (most releases, then oldest, suggested first), confirm **Merge into selected**, or **Dismiss**. Other users see the list. Dismissal hides that membership until a game joins or leaves the group. Merge can stop part way through; the error reports how many sources already merged. Empty: "No duplicate games found."
- **Multiple Releases:** games with at least **Minimum releases** releases (2 by default; the list offers 2 up to the highest count in the library). Releases are a game's ROMs flagged neither `Update` nor `DLC`; **Updates** counts the `Update` ones and **Size** is the game's size as in Library Size. A **System** filter (before Minimum releases) limits the list, and the threshold's choices, to one system. Click a column header to sort by it (again to reverse); game and system sort A–Z first, the numbers largest first. 50 games per page. Empty: "No games have <n> or more releases."
- **Games With Hacks** (`/reports/hacks`): games with at least one release flagged `Hack`: Game (link to its Releases tab), System, **Hacks** (releases flagged `Hack`), **Releases** (as in Multiple Releases) and Size, sorted by Hacks (largest first) by default; every column sorts, with a **System** filter and 50 games per page. Empty: "No games have hacked releases."
- **Image Resolutions** (`/reports/image-resolutions`): every stored image that isn't placeholder art (box art, screenshots, title screens and others), smallest first (by width × height), to find low-resolution art: a preview, Game (link to its Images tab), System, Type, **Resolution** (`<width> × <height>`) and Size, with an image count above and 50 per page. Filters: **System**, **Type** (All types, Box art, Screenshot, Title screen, Other), **Max width** and **Max height** (in px, 1–100000, empty for no limit; with either set an image is listed when its width **or** its height is at most the limit; any other value counts as empty) and **Clear**. Empty: "No images yet.", or "No images match these filters." while a filter is set.
- **Missing Metadata** (`/reports/missing-metadata`, Admin): games with no release year, no developer or no publisher. Filter by **System**, **Missing** (Any, Year, Developer or Publisher) and **Title** (a search of the display title, applied 300 ms after you stop typing); **Clear** resets the three. Columns: Game, System, Year, Developer and Publisher, with a **Missing** badge for each missing value; Game, System and Year sort (click again to reverse; games with no year sort last either way). A line above the table gives the count ("1,234 games"). Game links carry `?from=missing-metadata`, which shows the **Next missing metadata** button on the game page ([shortcut](#keyboard-shortcuts)). Empty: "Every game has its year, developer and publisher.", or "No games match these filters." with a filter set.
- **Activity** (`/reports/activity`, Admin): what happened recently, in one tab per section (Added ROMs, Sign-ins, Plays, Saves, Edits, Deletions, Recent jobs, Last backup; Added ROMs is selected first), each with an empty state. A note above the section tabs says the audit-based sections (sign-ins, plays, saves, edits, deletions) cover the last 30 days, the audit log's retention.
  - **Added ROMs:** the last 20 releases added, newest first: time, game (link), release, system and size (the release with its set files).
  - **Sign-ins:** who signed in last, then the last 20 `SignedIn`, `SignInFailed` and `LockedOut` events: time, user, outcome.
  - **Plays:** the last 20 browser plays (`GamePlayed`): time, user, game, release.
  - **Saves:** the last 20 save uploads, changes and deletions.
  - **Edits:** the last 20 metadata edits, release edits, release moves, merges, cover changes and image adds and deletes.
  - **Deletions:** the last 20 deleted games and releases; a game that's gone shows its ZIP's file name, without a link.
  - **Recent jobs:** the last 10 jobs: job name, status, start time (linking to the job) and duration (`12s`, `3m 4s`, `1h 2m`; "running" while unfinished).
  - **Last backup:** the last backup run's time and result (with its error when it failed); after a restart, the newest backup file, marked "since restart: no backup run".
  In the audit sections the action is shown by its name and an action with no user as *System*, as on the Auditing page. The three sources (the activity report, jobs and backups) load at once, and one that fails shows its error with a retry in its own sections while the others still show.

Image Resolutions keeps its filters and page in the URL too (`?system=&type=&maxWidth=&maxHeight=&page=`) and remembers them in the browser: opening it without any of those brings back the last view.

## Integrity

`/integrity` (Admin) keeps the library and database consistent.

- **Status:** a small table with the last quick and deep check and the next scheduled quick check (daily at `Integrity:QuickCheckTime`, see [configuration](configuration.md); "Not scheduled" when disabled).
- **Game checks:** adding the first real box art to a game whose cover is the placeholder runs a deep-strength check of that game's ZIP and files only (an `Integrity (Game)` job in Jobs and in the recent runs; cancellable). It resolves only that game's issues, never orphan or duplicate ones, and doesn't count as the last deep check.
- **Run quick** opens only ZIPs that changed since the database last saw them; **Run deep** opens every ZIP and re-checks every file's hash; while it re-hashes a Switch ROM, a second bar shows that file's `Hashing` progress. **Retry missing media** looks up box art and snaps for every game that has a placeholder or no snap. While a job runs, its progress and **Cancel** take the buttons' place.
**Issues** and **History** are accordion panels, one open at a time; Issues starts open.

- **Issues:** what the checks found, filtered by status (open by default) and type, linked to the game where there is one. Database differences are repaired automatically and listed as *AutoRepaired*; problems with the files themselves are reported, never fixed by moving or deleting files. A damaged ROM can be repaired by ingesting a byte-identical copy.
- **History:** the last 10 integrity checks and media retries.
- **Resume ROM storage moves (N)** (shown while Nintendo DS games still wait to be moved into or out of their ZIPs) starts the storage job again; such games are reported as `LegacyEmbeddedStorage` (Warn) until it moves them (see [External storage](#external-storage-nintendo-switch-nintendo-ds-nintendo-3ds-and-disc-systems)).

## Admin

`/admin` (Admin, from the user menu) has seven tabs:

- **Users:** every account with its type, status and last sign-in. Change an account's **Type** (Admin or Site user; saved at once, and the account is signed out), **Disable**/**Enable** it (accounts are never deleted; a disabled account's sessions end on its next request and its sign-in fails like a wrong password), or **Reset password** (sets a new one the user must change, and clears a lockout). **Create user** opens a dialog for a username (3–64 letters, digits, `.`, `_` or `-`), an initial password the user must change at first sign-in, and its **Account type** (Site user by default). You can't change your own type or disable yourself (those controls are greyed out on your own row; the API answers `409 SelfChange`), and the last enabled Admin can't be disabled or demoted (`409 LastAdmin`). Resetting your own password is allowed: you're signed out and sign in with the new one.
- **DATs:** the version and download time of each DAT, Switch's titledb file included (its version is the UTC date it was downloaded). **Refresh DATs** downloads the current No-Intro and metadata DATs and the disc systems' Redump DATs from libretro-database, and the titledb file (`Sources:TitleDbUrl`); if any download or check fails, the previous set stays in use. Below the button, **Automatic refresh** and **DAT files** (the list) are accordion panels, one open at a time; Automatic refresh starts open. Each DAT in the list has a **Download** button that downloads the file as cached on the server. **Automatic refresh:** the DATs are also refreshed daily, by default at 04:00 server time; turn it off or change the time here and **Save** (the next run is shown). A scheduled refresh runs as a job like a manual one, with no user; if another job is running at that time it tries again every minute until it starts, and skips the day if the next day's time comes first. Missed runs while the app was down aren't caught up. It needs outbound access to GitHub; an offline install logs a failed job each day until you turn it off.
- **Settings:** the effective configuration, read-only, with secrets masked.
- **ROM Zip Config:** see [ROM Zip Config](#rom-zip-config).
- **Backups:** the daily database backup, in three accordion panels: **Schedule**, **Status** and **Backups (n)** (only the list starts open). **Schedule:** on/off, the time (server time; the server's time zone is named next to it) and how many backups to keep (1–365), saved with **Save**. **Status:** the next run (in your time zone) and the last result, since the app started. **Back up now** runs one and waits for it. Below, every backup with its time and size, newest first, each with **Restore**. Restore asks to confirm, then: takes a safety backup of the current database, replaces every table with the backup's, applies newer migrations, marks jobs left Running as Aborted and signs everyone out, you included (you go to the sign-in page). While it runs every other page and API call answers "A backup is being restored" (`503`). Afterwards run Integrity → **Run quick**, since the library ZIPs may be newer than the backup. It's refused while a job or another backup runs. A backup can also be restored at startup; see [deployment](deployment.md#restoring-a-backup).

Newest at the bottom, following along while you're scrolled to the end; **Pause** holds new lines until **Resume**; the level box hides less important lines. ## Reference: behaviour and API

The sections below describe what happens behind each page in detail, with the API endpoints the UI uses. Every `/api` call except sign-in needs a session; POST, PATCH and DELETE also need the antiforgery header (the UI handles both).

### Ingestion review queue

An unmatched ROM with a plausible header stays in ingest and creates a `Pending` review item with outcome `Review NoDatMatch`. A headerless ROM uses its ingest folder's system. If DAT identification succeeds but several games own the same system and base title, the item becomes `Review AmbiguousGroup`; it stores the DAT identity and candidate game IDs.

Unmatched items include up to five suggestions for distinct base titles from the classified system's loaded DATs. The scorer compares the header title and original filename stem, using the higher of token overlap and edit similarity, plus a size-match boost. Each base title contributes its highest-scoring release; ties use ascending ROM name. Suggestions below 0.4 are excluded, and suggestions refresh whenever the file is processed again.

Files behind pending items are processed on every ingest run. If a file becomes DAT-matched and is ingested, its review item becomes `Resolved` with the resulting game ID. Other non-review outcomes remove its pending row; files skipped because they are too recent retain their row. A copy at another source path becomes a duplicate while the original review remains pending. Missing pending sources are removed at the start of the run.

Re-dropping a dismissed loose file resets it to pending and processes it again. For an archive, the review item records the archive path and entry name. Review or error outcomes keep the archive in ingest. A dismissed entry in the same archive fails with reason `Dismissed`, causing the archive to move to `_failed/` unless another entry still needs review or encounters an error. A duplicate previously resolved from the same archive counts as ingested when choosing the archive's fate, allowing a fully resolved archive to be deleted on its next run.

### Resolve reviews through the API

All review endpoints require an `admin` session, and POST and DELETE requests require the antiforgery header.

- `GET /api/review?status=Pending&page=1&pageSize=48` lists pending items (maximum page size 200), including `isArchive`. Optional `system`, `reason` (`NoDatMatch` / `AmbiguousGroup` / `AmbiguousSet`) and `q` filter both rows and total. `q` matches the original file name or header title, is trimmed, at most 100 characters, and matches `%`, `_` and backslash literally. Blank `q` is absent; unknown system/reason or an overlong search gives `400 ValidationFailed`. `Resolved` and `Dismissed` history can also be listed.
- `GET /api/review/{id}` returns `systemName`, the header, hashes, suggestions, queued DAT identity and candidate games, and:
  - `resolvable`: `false` for a disc system's `.cue`/`.bin` item whose complete unmatched set isn't found (it can only be deleted), `true` otherwise, so also for a complete unmatched set's member;
  - `dismissible`: `false` for every `.cue`/`.bin` item of a disc system;
  - `fileSets`: whether the item's system is a disc system (disc numbers apply);
  - `setMembers`: the unmatched set the item belongs to, `[{ reviewId, fileName, sizeBytes }]` cue first, or `null`.
- `GET /api/dat/search?system=gb&q=Tetris&limit=20` searches loaded DAT game names using a case-insensitive substring (up to 20 results), each game name once (the Redump DATs repeat a game per serial).
- `POST /api/review/{id}/resolve` accepts `Dat`, `Attach` or `Manual` actions, checks the request and the item, and starts a `ReviewResolve` job: `202 { jobId }`. Only these answers are synchronous: `400 ValidationFailed` for the request, `404` for an item that doesn't exist or isn't Pending, `409 SetFileNotResolvable`, and `409 JobRunning` while another job runs. Everything else arrives in the job's summary (`GET /api/jobs/{jobId}`): `{ reviewId, fileName, gameId, code, errors }`, with `gameId` set and `code` null on success. The job has one item per review row it acted on (`Ingested` with the game, or `Error` with the code as its reason). An optional `update: true` (only with `Dat`, a titledb system, and a base or update entry) stores the pick as an update; otherwise it's `400 ValidationFailed` on `update` and nothing changes.
- `POST /api/review/{id}/dismiss` returns 204 (`409 SetFileNotResolvable` for any `.cue`/`.bin` item of a disc system). Loose files move to `_failed/` with a `Dismissed` sidecar; archives stay in place until the next ingest run.
- `POST /api/review/delete` with `{ "ids": [1, 2] }` deletes several items at once: 1–500 distinct positive ids (else `400 ValidationFailed`, field `ids`). Under one job lock (`409 JobRunning`, nothing deleted) each id is deleted as `DELETE /api/review/{id}` does, in order; an id that's unknown or no longer `Pending` (for example removed with its archive earlier in the batch) is skipped. It returns `200 { deleted, skipped, failed: [{ id, code }] }`. The SPA sends larger selections in batches of 500.
- `DELETE /api/review/{id}` returns 204. It deletes the source from the ingest folder (the loose file, or the whole archive), then every `Pending` item with the same source path (loose file) or archive path; resolved and dismissed rows stay as history. Only a `Pending` item can be deleted (`404 NotFound` otherwise). A source that is already gone still removes the rows and returns 204. A file that can't be deleted (locked, no permission) returns `500 DeleteFailed` and changes nothing.

`Dat` takes `datSystem` and `datGameName` for a NoDatMatch item. The selected DAT game supplies naming, tags and metadata from its ROM: the one with the source file's extension when the DAT lists the game more than once, else the first (the DAT search still lists each game name once, with its first ROM's name and size); the release keeps its actual hashes, uses Manual identification with the selected DAT identity, and gains an `Unverified` flag and filename suffix. On a disc system the file is named `<datGameName> (Unverified)<source extension>` and its tags come from the DAT game name.

`Attach` takes `targetGameId` and `flag` (`Hack`, `Translated`, `None`, `Disc` or `Release`; anything else is `400` "Must be Hack, Translated, None, Disc or Release."). `Release` attachments use the target game's title, take regions, languages, revision and flags from the original file name (a set's cue name, dropping `Disc <n>`/`Track <n>` flags), add the flag `Unverified` and name the file `<original stem> (Unverified)<ext>` (each once), identified as Manual; a `disc` with `Release` is `400`. Hack/Translated attachments use the target game's title as their base title, empty regions/languages, null revision and only the selected flag. `None` is available only for AmbiguousGroup items and requires one of their candidate games; it keeps the queued DAT identification and normal DAT filename. `Disc` (disc systems only) takes `disc` and adds the file as a release of any game of the system, with the game's title, its primary release's regions, languages and revision, and the flag `Disc <n>`.

`Manual` takes `title`, `regions[]`, `languages[]`, optional `revision`, `flags[]`, and an optional `disc` (disc systems only), which becomes the flag `Disc <n>` after the other flags. Naming uses the title, regions, revision and flags; the release receives no DAT metadata. DAT and Manual actions group into existing games using the same rules as ingestion. Multiple candidates fail as `AmbiguousGroup`; choose Attach to select the game.

`disc` is 1–99 (`400 ValidationFailed` on `disc` otherwise), allowed only with `Manual` or `Attach` with flag `Disc` (where it's required); on a system that isn't a disc system the job fails with `ValidationFailed` on `disc`.

Resolving any member of a complete unmatched bin/cue set resolves the whole set as one release (track 1 as the main file, every file under its own name, all or nothing) and marks every member Resolved in one transaction.

The job runs under the global job lock and can't be cancelled; dismissal and deletion take the lock themselves (`409 JobRunning` when busy). A missing source fails as `SourceMissing` and removes its stale review row. Successful resolution records the game, Admin and UTC time, then deletes a loose source; resolving an archive entry leaves its archive in place. Changed source bytes fail verification.

Failures retain a Pending review for retry. The summary's `code` is the failure: `ValidationFailed` (with `errors`), `NotFound` (also a missing Attach target), `SourceMissing`, `AmbiguousGroup`, `TargetZipUnreadable`, `InfoJsonNewerSchema`, `Duplicate`, `SetFileNotResolvable` (a set no longer complete), `NameTaken`, `NameTooLong` (a disc system's name already taken in the folder or over 250 UTF-8 bytes), `IoError`, `VerifyFailed` or `DbWriteFailed`. A DB mirror failure can leave a verified ZIP on disk; the next ingest pre-pass repairs the DB from that ZIP before processing sources, as with normal ingestion.

### Browse the library through the API

Every signed-in user, Admin or Site user, can read the library. Lists and details come from the database mirror; images and ROM bytes are streamed from the game's ZIP.

- `GET /api/systems` lists every registered system, sorted by display name (case-insensitive), with its `shortName` (such as `GB`), game count, ROM count and the distinct regions of its ROMs (sorted). Systems without games report zero counts and no regions. Every system list in the UI (Library, collection, Review, Duplicates, Missing images and Audit filters) shows them in this alphabetical order.
- `GET /api/games` returns a page of `{id, system, systemName, systemShortName, displayTitle, releaseYear, regions[], romCount, boxArtUrl, primarySizeBytes, rating, favourite, matchedOn, updateCount, playRomId, playRomFileName, playDisc, browserCore}` (`updateCount` counts the releases flagged `Update`, while `romCount` still counts every release; `playRomId` and `playRomFileName` are the primary release (lowest id if several) when the system has a browser core and that release is in the ZIP (or, for PlayStation, PSP, Saturn and Sega CD, stored next to it) and isn't an `.nrg` image, else `null`; `playDisc` is `true` when `playRomId` is set and that release is stored next to the ZIP (the play page then loads it through `play-disc`), else `false`; `browserCore` is the system's core or `null`; `systemName` is the system's display name and `systemShortName` its short name such as `SNES`, each the id if it isn't registered; `boxArtUrl` is the cover image; `primarySizeBytes` includes a disc set's other files) (48 per page by default, maximum 200; a page past the end is empty).
  - `system` must be a registered system id. `letter` is `#` or `A`–`Z` (any case) and matches the ZIP's letter folder; send `#` as `%23`.
  - `region` matches a game when any of its releases has exactly that region. `q` is split on whitespace into at most 8 distinct words (more is `400`), and a game matches when every word is a case-insensitive substring of the display title, title, developers, publishers or genres; `%`, `_` and `\` match literally. With `q`, `matchedOn` is `{field, value}` (`developer`, `publisher` or `genre`, and the first matching value in that order) when no word matched a title, else `null`. `favourite` is exactly `true` (only favourites) or `false` (only the others).
  - `collection` (a collection id of yours) lists only that collection's games, with every other filter still applied; not a GUID → `400` (field `collection`), someone else's or unknown → `404`. With it, `added` sorts by when each game was added to the collection.
  - `notInCollection` (a collection id of yours) leaves out that collection's games, with every other filter still applied (combined with `collection` for the same id the result is empty); not a GUID → `400` (field `notInCollection`), someone else's or unknown → `404`.
  - `sort` is `title` (default), `year`, `added`, `rating` or `relevance`; `dir` is `asc` or `desc`, defaulting to `asc` for title/year and `desc` for added/rating. Games without a year (or rating) are listed last in both directions; equal ratings are ordered by title, other equal values by game id.
  - `relevance` scores each game: 100 when a title equals `q` (whitespace collapsed), 60 when a title starts with it, and per word 40 if it's in a title, 20 in the developers, 20 in the publishers and 10 in the genres; highest first, then by title. It ignores `dir`, and without `q` it sorts by title.
  - Invalid values return `400 ValidationFailed` with a per-field `errors` object.
- `GET /api/games/facets` returns the Library filter counts: `{systems: [{id, count}], regions: [{region, count}], letters: [{letter, count}]}`. It takes `system`, `letter`, `region`, `q` and `favourite`, validated as for `GET /api/games` (same `400 ValidationFailed` errors); other keys (`sort`, `page`, `collection`, …) are ignored. Each list counts the games matching every filter except its own (so `systems` ignores `system`), lists only values with at least one game, and is ordered ordinally; a game counts once for each distinct region among its releases.
- `GET /api/games/{id}` returns the game's `info.json` fields (without `schemaVersion` and `metadata.appVersion`) plus `id`, `systemName`, `browserCore` (the EmulatorJS core that plays the system in the browser, `gambatte`, `mgba`, `handy`, `virtualjaguar`, `beetle_vb`, `a5200`, `prosystem`, `stella2014`, `gearcoleco`, `smsplus`, `fceumm` or `pcsx_rearmed`, else `null`; every response that returns the game detail carries it) and `hasDefaultBoxArt` (`rating` and `favourite` included). `roms[]` lists the primary release first, then by file name, with identification and hashes flattened (`identificationMethod`, `datName`, `crc32`, `sha1`, `sizeBytes`, …), an update's `version` (else `null`), the parsed `header` and a `downloadUrl`, plus `files` (`null`, or a disc set's other files in order, each `{id, fileName, sizeBytes, crc32, md5, sha1, downloadUrl}`) and `totalSizeBytes` (`sizeBytes` plus every file). `images[]` holds `id`, `type`, `fileName`, `source`, `isDefault`, `isCover`, `sizeBytes`, `width`, `height` and `url`.
- `GET /api/games/{id}/images/{imageId}` returns the PNG or JPEG (by file extension) with `ETag` set to its SHA1 and `Cache-Control: private, max-age=86400`; a matching `If-None-Match` returns 304. With `?download=true` it's sent as an attachment named `<displayTitle>-<imageId>.<ext>` (the title made safe for a file name and cut to 180 characters, then the suffix; `image-<imageId>.<ext>` when nothing of the title is left); any other value than `true`/`false` is `400`.
- `POST /api/games/{id}/roms/{romId}/played` (any signed-in user, antiforgery header) records a browser play as a `GamePlayed` audit row (system, game, user, the game's ZIP path, the release's file name as details) and returns `204`; an unknown game, or a release that isn't in it, is `404 NotFound`. It writes nothing else and takes no job lock. The SPA sends it without waiting and ignores any error.
- `GET /api/games/{id}/download` returns the game's ZIP with range support and an RFC 5987 `filename*` in `Content-Disposition`.
- `GET /api/games/{id}/info-json` returns the stored `info.json` bytes as `application/json`, even if invalid JSON. A missing game, ZIP or entry returns `404 NotFound`; an unreadable ZIP or an entry over 1 MiB returns `500 IoError` before sending the response.
- `GET /api/games/{id}/roms/{romId}/download` streams one ROM from the ZIP under its library file name, with `Content-Length` set to the release's recorded size (a ZIP entry that turns out shorter aborts the response).
- `GET /api/games/{id}/roms/{romId}/files/{fileId}/download` streams one file of a disc set under its file name, with range support; a file of another release, or a name another game also claims in that folder, is `404`.
- `GET /api/games/{id}/zip-entries` returns `{zipName, entries: [{path, sizeBytes, compressedSizeBytes, modifiedUtc}]}`: the ZIP's file name and every file entry (folder entries left out), ordered by `path` ordinally, with the central directory's sizes. `modifiedUtc` is the entry's stored time read as server local time (see [ZIP format](zip-format.md#writes)). An unknown game or a missing ZIP returns `404`; an unreadable ZIP `500 IoError`.
- `GET /api/games/{id}/roms/{romId}/play-disc` (any signed-in user) returns one PlayStation, Saturn, Sega CD or 3DO disc, or one PSP UMD image, for the play page. A standalone `.bin`, `.iso` or `.chd` (PSP: only a single `.iso`; Saturn has no stored `.iso`) streams unchanged as `application/octet-stream` with its `Content-Length` and `Accept-Ranges: none`. A cue set streams as an uncompressed `application/zip` (UTF-8 entry names) holding a playback copy of the cue and every track at the archive root, without `Content-Length` but with `X-Content-Bytes` (the playback cue's and tracks' lengths summed, a little less than the ZIP itself) so the player can show progress: the cue keeps its stored base name with a lowercase `.cue`, and the tracks are renamed `track-01.bin`, `track-02.bin`… in the cue's FILE order. The playback cue keeps only `FILE`, `TRACK`, `INDEX` and `PREGAP` lines in canonical form (uppercase, single spaces, LF, no BOM), since that is all the emulator's cue parser reads; the cue and tracks on disk are never changed, and nothing is written to disk. The cue must name each stored track of the release exactly once (ignoring case), each `FILE` must be `BINARY` with at least one track, tracks run `01`, `02`… with `AUDIO`, `MODE1/2352` or `MODE2/2352`, and each track has an optional `INDEX 00`, an optional `PREGAP` and then one `INDEX 01` at valid `MM:SS:FF` positions (seconds 00–59, frames 00–74). A cooked `MODE1/2048` image plays only as a standalone `.iso`. Every file is opened and checked before the response starts; each is then sent up to the length it had when opened, and a file that shrinks meanwhile cuts the response off. Range headers are ignored (the whole payload is sent), every response from the endpoint is `Cache-Control: no-store`, and nothing is audited. Errors: another game's release, an unknown release, a release that isn't PlayStation, PSP, Saturn, Sega CD or 3DO, or a missing, unsafe or ambiguously claimed file (another release or game in the folder claims the same name, ignoring case) is `404 NotFound`; an unreadable file `500 IoError`; an empty file, a name that differs from its external file name, a single file that isn't a `.bin`, `.iso` or `.chd`, a set that isn't one cue with 1–99 `.bin` tracks (so a `.chd` in a set), a malformed or incomplete cue, or any `.nrg` file (alone or in a set) `409 InvalidPlayDisc` (PSP: anything but one non-empty `.iso` named as stored); more than 2 GiB in total (the cap is inclusive) `409 PlayDiscTooLarge`. Signed out it's `401 Unauthorized`, and a session that must change its password gets `403 PasswordChangeRequired`.
- `GET /api/games/{id}/zip-entries/download?path=<entry>` streams the file entry with exactly that name as `application/octet-stream`, named after its last path segment (RFC 5987 `filename*`), capped at its stored length. A missing or empty `path` returns `400 ValidationFailed` (`errors.path`); a name that isn't a file entry (a folder name, `../x`, …), an unknown game or a missing ZIP `404`; an unreadable ZIP `500 IoError`. The name is only looked up in the ZIP, never on disk. Downloads aren't audited.
- `GET /api/emulator/bios/{name}` (any signed-in user) streams a BIOS file from `Paths:Bios` ([configuration](configuration.md)) for the play page, as `application/octet-stream` without range support, and every response it gives is `Cache-Control: no-store`. `name` must be a whole file name of 1–64 letters, digits, `_`, `.` and `-`, starting with a letter or digit and not ending in a dot; it is matched against the folder ignoring case. An invalid name, a missing or empty file, a directory, a link or reparse point, or names that differ only in case return `404 NotFound`; a file that can't be read (a permission or sharing error) `500 IoError`. Signed out it's `401 Unauthorized`, and a session that must change its password gets `403 PasswordChangeRequired`. `HEAD` isn't mapped (`404`). Downloads aren't audited.
- `GET /api/emulator/cores/{core}/{name}` (any signed-in user) serves one of the three files of an operator-supplied core: `genesis_plus_gx` from `Emulator:GenesisCorePath` ([configuration](configuration.md#genesis-plus-gx-core)), `picodrive` from `Emulator:PicodriveCorePath` ([configuration](configuration.md#picodrive-core)) `snes9x` from `Emulator:Snes9xCorePath` ([configuration](configuration.md#snes9x-core)), `opera` from `Emulator:OperaCorePath` ([configuration](configuration.md#opera-core)) or `vice_x64sc` from `Emulator:ViceCorePath` ([configuration](configuration.md#vice-core)). The two `.data` payloads are sent as `application/octet-stream` and the `.json` report as `application/json`. Core and file names match exactly (case-sensitive); an unknown core, any other name (`..%2F…` included), an unset or missing folder, and a missing, empty or unsafe file are `404 NotFound`. The file's length and SHA-256 are checked against the pinned EmulatorJS 4.2.3 values before anything is sent, and the checked bytes are what's sent; a mismatch is `409 GenesisCoreMismatch`, `409 PicodriveCoreMismatch`, `409 Snes9xCoreMismatch` or `409 OperaCoreMismatch`, titled *The Genesis Plus GX core file…* / *The PicoDrive core file…* / *The Snes9x core file…* / *The Opera core file doesn't match EmulatorJS 4.2.3*, and an unreadable file `500 IoError`. Range headers are ignored, every response is `Cache-Control: no-store`, and nothing is audited.
- `HEAD /api/emulator/cores/{core}` (any signed-in user) checks a core's whole set without a body: `204` when all three files are there and match, `404` when the core is unknown or isn't set up or a file is missing, `409` when a file doesn't match (the log names it), `500` when one can't be read (across the files, `500` wins over `409`, and `409` over `404`); `Cache-Control: no-store`. The play page runs it before fetching a Genesis, 32X or SNES ROM.
- `GET /api/emulator/genesis/{name}` and `HEAD /api/emulator/genesis` are kept as aliases of the `genesis_plus_gx` routes and answer exactly as they do.

ROM and image ids change whenever a game is rewritten. A stale id, an image or ROM belonging to another game, or a ZIP missing from disk returns `404 NotFound`; an unreadable ZIP returns `500 IoError`. ZIPs are opened so that an ingest or edit can still replace them during a download.

### Collections through the API

Every route needs only a signed-in user and acts on your own collections: another user's collection id answers `404` exactly like a missing one. Mutations need the antiforgery header.

- `GET /api/collections?q=&page=&pageSize=` returns a page of `{id, name, gameCount, coverUrl, updatedAt}` sorted by name. `q` (at most 255 characters, 8 words) matches names containing every word, ignoring case and accents; `%` and `_` match literally. `gameCount` counts only games still in the library.
- `POST /api/collections` with `{name, notes?}` → `201` with `{id, name, notes, coverUrl, gameCount, createdAt, updatedAt}`; `PATCH /api/collections/{id}` with `{name?, notes?}` → `200` with the same (an absent field is unchanged; `notes: null` or `""` clears it); `GET /api/collections/{id}` returns it; `DELETE /api/collections/{id}` → `204` (memberships and cover files go with it). Names are trimmed, 1–100 characters; notes have `
` line endings, at most 65,536 UTF-8 bytes, whitespace-only meaning none. Errors: `400 ValidationFailed` (`name`, `notes`), `409 CollectionNameTaken`.
- `POST /api/collections/{id}/cover` (multipart `file`, PNG or JPEG, at most 8 MiB; `413 PayloadTooLarge` above) and `POST /api/collections/{id}/cover/from-url` with `{url}` (downloaded like a [game image from a URL](#edit-the-library-through-the-api), same errors) replace the cover and return the detail; `DELETE /api/collections/{id}/cover` removes it. `GET /api/collections/{id}/cover` (the `coverUrl`, `?v=` changing with each cover) streams it with `Cache-Control: private, max-age=86400`; `404` when there's none or its file is missing.
- `POST /api/collections/{id}/games` with `{gameIds: [...]}` (1–500 ids, else `400 gameIds`) → `200 {added}`: ids already in it, or not library games, are skipped. `DELETE /api/collections/{id}/games/{gameId}` → `204`, also when it wasn't there.
- `GET /api/games/{id}/collections` returns `[{id, name}]`: your collections holding the game, by name (`404` for an unknown game).

`updatedAt` changes only when a request changes something (an add with `added: 0` doesn't).

### Bundle Creator through the API

Every route needs only a signed-in user and acts on your own queues and downloads: another user's queue id or ticket answers `404` like a missing one. Mutations need the antiforgery header. A request body above 2 MiB answers `413 PayloadTooLarge`.

- **Entries** are `{gameId, releaseSha1, member, gameTitle, fileName}`: the game's GUID, the release's lowercase 40-character SHA-1, and for a set file `member: {sha1, fileName}` (the stored file name, compared exactly), else `null`. Labels are 1–255 code points. At most 500 entries, without duplicates.
- `GET /api/bundle-queues` returns `[{id, name, revision, itemCount}]`. `POST /api/bundle-queues` with `{name, entries}` → `201` with `{id, name, revision, entries}` (revision 1); `GET /api/bundle-queues/{id}` returns it. `PUT /api/bundle-queues/{id}` with `{name, entries, revision}` replaces it and returns it with the next revision. `DELETE /api/bundle-queues/{id}?revision=<n>` → `204`. Errors: `400 ValidationFailed`, `404`, `409 BundleQueueChanged` (stale revision), `409 BundleQueueNameTaken`, `409 BundleQueueLimit` (100 queues). Entries that no longer resolve are accepted and kept.
- `POST /api/bundle-files/resolve` with `{items: [{gameId, releaseSha1, member}]}` (up to 500) returns `{items: [{available, gameTitle, fileName, downloadUrl}]}` in input order, with the current names and the normal download link, or `available: false` and nulls.
- `POST /api/bundle-downloads` with `{gameId, releaseSha1, member}` → `201 {ticket, fileUrl}`; `404` when unavailable; `409 BundleDownloadBusy` while your previous ticket is pending or sending; `503 BundleDownloadsFull` while 100 tickets are pending or sending. `GET /api/bundle-downloads/{ticket}/file` sends the whole file once (no ranges; a second claim is `409 BundleDownloadConsumed`) with the same file name as the normal download. `GET /api/bundle-downloads/{ticket}` returns `{state, errorCode}`: `pending`, `sending`, `sent`, `failed` (with `Unavailable`, `OpenFailed`, `Aborted`, `Stalled` or `IoError`) or `expired`. Ticket responses are `Cache-Control: private, no-store`. A ticket not fetched within 30 seconds expires; a transfer with no progress for two minutes fails as `Stalled`. Finished tickets are kept for five minutes (at most 2,000); a restart forgets all tickets.

### Publishers and genres through the API

Every route needs only a signed-in user; writes need the antiforgery header. `{kind}` is exactly `publishers` or `genres` (anything else is `404`). A group's `key` is the lowercase hexadecimal SHA-256 of its normalized name (trimmed of leading and trailing Unicode whitespace, lowercased, accents kept); any other `key` shape is `400 ValidationFailed`. Paging is the usual `page`/`pageSize` (default 48, at most 200).

- `GET /api/discovery/{kind}` returns a page of `{key, name, gameCount, logoUrl}` sorted by normalized name; `logoUrl` is `/api/discovery/{kind}/logo?key=…&v=<ticks>` when a shared logo is set, else `null` (the SPA then uses its starter art or the name). `name` is at most 255 characters (cut with `…`). An optional `q` keeps only the groups whose `name` contains it (trimmed, ignoring case; blank is absent), applied before paging; it never changes grouping or keys. A trimmed `q` over 100 characters is `400 ValidationFailed` (`errors.q`).
- `GET /api/discovery/{kind}/games?key=` returns the group's games in the [`/api/games` item shape](#browse-the-library-through-the-api), sorted by display title, system and id; `404` when no game has that value.
- **Logos** (`{kind}` here is `publishers`, `genres` or `systems`; for `systems` the `key` is the system id, 1–32 lowercase letters or digits, and `GET /api/systems` items carry the same `logoUrl`):
  - `GET /api/discovery/{kind}/logo?key=` serves the shared logo with its type, `Cache-Control: private, no-cache` and `X-Content-Type-Options: nosniff`; `404` when there's none. It's served even while the group isn't in the library.
  - `PUT /api/discovery/{kind}/logo?key=` (Admin; multipart, exactly one PNG or JPEG in `file`, at most 512 KiB and 2048 pixels per side) → `204`; `400 ValidationFailed` (`file`) for anything else, `413 PayloadTooLarge` above 576 KiB of request, `404` for a group not in the library or an unregistered system.
  - `PUT /api/discovery/{kind}/logo/from-url?key=` (Admin; JSON `{url}`) downloads the image (http/https, at most 1024 characters, no user info, public addresses only, 15 s) and stores it after the same checks → `204`. `400 ValidationFailed` (`url`) for a bad URL or an unusable image; `400 ImageUrlBlocked` for a private or local address; `502 ImageDownloadFailed` when the download fails; `404` (checked before anything is downloaded) for a group not in the library or an unregistered system.
  - `DELETE` on the logo route → `204`, or `404` when there's no logo.
  - An unknown `{kind}` is `404`; a malformed `key` is `400 ValidationFailed` (`key`).
- The indexes are recomputed at most once a minute.

### Rate games through the API

`PATCH /api/games/{id}/rating` is Admin-only and needs the antiforgery header. It takes `{rating?, favourite?}`: `rating` is a whole number 1–5 or `null` (clears it), `favourite` a boolean, and an absent property stays unchanged. Ratings are shared per game and stored in the ZIP's `info.json` ([format](zip-format.md)), so a rating rewrites the ZIP like any edit: it takes the global job lock (`409 JobRunning` while a job or another edit runs) and returns the full game detail, with new ROM and image ids. Errors: not an object, neither property, or a wrong value → `400 ValidationFailed` (field `""`, `rating` or `favourite`); an unknown game → `404`; a newer `info.json` schema → `409 InfoJsonNewerSchema`; a write failure → `500`. The `rom-manager` `PATCH /api/games/{id}` ignores `rating` and `favourite`.

Other edits keep a game's rating and favourite. A merge keeps the target's rating (or takes the source's when the target has none) and makes the target a favourite if either game was; a release moved to a new game starts unrated and not a favourite.

### Select ingestion files through the API

`GET /api/jobs/current` (Admin) returns the running job (`204` when idle): `id`, `type`, `mode`, `status`, `current`, `total`, `currentItem`, `startedAt` and `step`. `step` is `null` unless a streamed phase of the current file runs, else `{ "phase", "bytesDone", "bytesTotal", "bytesPerSecond" }`. `phase` is `Hashing` (an external ROM's ingest hash or a deep integrity re-hash), `CopyingToLibrary` (an external ROM copied into the library) or `Copying` (copied to `_failed/`, `_duplicates/` or back on a rollback); a same-volume rename reports none. `bytesPerSecond` is the average since the phase began, `null` for its first second or while nothing is done. Sizes in the app show in B, KiB, MiB, or GiB from 1 GiB up.

`POST /api/jobs/ingest` (Admin) accepts no body, or `{ "files": null }`, to import every pending file. `{ "files": [{ "system": "gb", "name": "x.zip" }] }` imports only those exact system/top-level filename pairs from the job's snapshot. Unknown systems/files, disappeared files and repeated entries are ignored. Unselected files stay untouched and produce no job items; progress counts the selected snapshot. Select an archive by its own filename. An empty list or missing/empty system/name gives `400 ValidationFailed`; malformed JSON is also `400`. Selection is rebuilt with everything checked whenever the UI reloads, and is not saved across page loads.

### Delete ingestion files through the API

`GET /api/ingest/failed` (Admin) returns, per registered system in registry order, `{ system, files: [{ name, sizeBytes, modifiedAt, reason }] }`: the top-level files of `ingest/<system>/_failed/` (missing folder → `[]`), ordered by name, without `.error.txt` sidecars. `reason` is the `reason:` line of the file's `.error.txt`, or null.

`POST /api/ingest/delete` (Admin) takes `{ "files": [{ "system": "gb", "folder": "pending", "name": "x.gb" }] }`, `folder` being `pending` (`ingest/<system>/`), `failed` (`ingest/<system>/_failed/`) or `removed` (`ingest/<system>/_removed/`, [Deleted ROMs](#deleted-roms); no Review rows are touched). A missing or non-JSON body, an empty list, more than 500 entries, an unregistered system, another folder, or a name that is empty, `.`/`..`, contains `/` or `\`, is hidden or OS junk, or (for `failed`) ends `.error.txt` gives `400 ValidationFailed` (`errors.files`) and deletes nothing. A running job gives `409 JobRunning`. Otherwise each entry is deleted in order (a file that's already gone counts as deleted; repeated entries are skipped): a failed file takes its `.error.txt` with it, and a pending file's `Pending` Review rows go once the file is gone (resolved and dismissed rows stay). A file that can't be deleted keeps its Review rows and sidecar and is reported; the rest continue. The response is `200 { deleted, failed: [{ system, folder, name }] }`. The SPA sends larger selections in batches of 500.

### Deleted ROMs through the API

`GET /api/ingest/removed` (Admin) returns, for each registered system with at least one file, in registry order, `{ system, files: [{ name, sizeBytes, modifiedAt }] }`: the top-level files of `ingest/<system>/_removed/`, ordered by name, without dot-files or OS junk.

`POST /api/ingest/restore` (Admin) takes `{ "files": [{ "system": "gb", "name": "x.gb" }] }`, validated as `POST /api/ingest/delete` entries with folder `removed` (`400 ValidationFailed`, field `files`; repeated entries are ignored). Under the job lock (`409 JobRunning`, nothing moved) each file moves from `_removed/` to `ingest/<system>/` under a free name (never replacing a file); a missing file or a failed move is listed in `failed`. Each move is audited as `RemovedRestored`. Then an ingest job starts for exactly the restored files under their new names. The response is `200 { restored, failed: [{ system, name }], jobId }`, `jobId` being null when nothing was restored or the job couldn't start (the files then wait on Ingestion). The job's 10-second `TooRecent` rule applies: a file written to `_removed/` just before (an embedded system's ROM is written when its release is deleted) is skipped and stays pending.

### Report APIs

Report GETs need any signed-in user, except `/activity`, `/missing-metadata` and `/missing-metadata/next` (Admin). Paged responses are `{items, page, pageSize, total}`; page starts at 1, pageSize is 1-200, and an unknown system filter gives `400 ValidationFailed`.

- `GET /api/reports/library-size` returns `{totalBytes, gameCount, updateCount, systems: [{system, systemName, bytes, gameCount, updateCount}]}` (`updateCount` counts releases whose flags contain `Update`), where a game's bytes are `games.zip_size_bytes` plus the recorded `size_bytes` of its external ROMs and their set files (missing files included). Systems with games are sorted by bytes descending.
- `GET /api/reports/library-size/{system}` returns `{system, systemName, bytes, updateCount, games: [{id, displayTitle, bytes, romCount, updateCount}]}`, sorted by bytes descending, then title. A registered empty system returns an empty list; an unknown system gives `404 NotFound`.
- `GET /api/reports/missing-images?system=&page=&pageSize=` defaults to 50 rows, sorted by system/title, each `{id, displayTitle, system, systemName, reason}` (`NoCover` or `Placeholder`). NoCover wins if both apply.
- `GET /api/reports/missing-images/next?afterGameId=` returns `{id, currentIsOnly}`: the report row after that game in the unfiltered order (system, title, id), wrapping to the first row other than it. Without `afterGameId`, or when that game is gone, it is the first row. `id` is null when no other game is missing images; `currentIsOnly` is then true if `afterGameId` itself still is. A bad id is `400`.
- `GET /api/reports/missing-metadata?system=&missing=&q=&sort=&dir=&page=&pageSize=` (Admin) returns games with `release_year` null or an empty `developers` or `publishers` list, each `{id, displayTitle, system, systemName, releaseYear, developers, publishers}`, 50 per page by default. `missing` is `any` (default), `year`, `developer` or `publisher`; `q` (at most 100 characters, trimmed) matches the display title, `%` and `_` literally; `sort` is `name` (default), `system` or `year` and `dir` `asc` (default) or `desc`, matched ignoring case; ties sort by title then id, and no year sorts last. Bad values give `400 ValidationFailed` keyed by the parameter.
- `GET /api/reports/missing-metadata/next?afterGameId=` (Admin) returns `{id, currentIsOnly}` like `missing-images/next`, in the unfiltered order (display title, id).
- `GET /api/reports/newly-added?system=` returns `{systems: [{system, systemName, games: [{id, displayTitle, addedAt, releaseCount}]}]}`: per system with games (or only `system`), its 10 newest games by creation time then id, both descending; systems by name. An unknown `system` is `400 ValidationFailed` ("Choose a registered system.").
- `GET /api/reports/hacks?system=&sort=&dir=&page=&pageSize=` returns `{items: [{id, displayTitle, system, systemName, hackCount, releaseCount, bytes}], page, pageSize, total}`: games with a release flagged `Hack`. `sort` is `name`, `system`, `hacks` (default), `releases` or `size`; `dir` `asc` or `desc` (default `asc` for name and system); ties by title, then id. Validation as for multiple-releases.
- `GET /api/reports/image-resolutions?system=&type=&maxWidth=&maxHeight=&page=&pageSize=` (every signed-in user) returns `{items: [{imageId, gameId, displayTitle, system, systemName, type, width, height, sizeBytes}], page, pageSize, total}`: every stored image that isn't placeholder art, smallest area (`width × height`) first, then system, title and image id. `type` is `BoxArt`, `Snap`, `TitleScreen` or `Other` (any case; a number is rejected); `maxWidth` and `maxHeight` are 1–100000, and with either set an image is listed when its width is at most `maxWidth` **or** its height at most `maxHeight`. Invalid `system`, `type`, `maxWidth` or `maxHeight` is a `400` keyed by that field; paging as for the other reports (50 by default).
- `GET /api/reports/multiple-releases?system=&min=&sort=&dir=&page=&pageSize=` returns `{maxReleases, items, page, pageSize, total}`: games with at least `min` (2–10000, default 2) releases (rows not flagged `Update`), each `{id, displayTitle, system, systemName, releaseCount, updateCount, bytes}` (`bytes` as in library-size). `sort` is `name`, `system`, `releases` (default), `updates` or `size` and `dir` `asc` or `desc` (both case-insensitive; default `asc` for name and system, `desc` otherwise); ties sort by title, then id (name by system, then id), always ascending. Defaults to 50 rows. `maxReleases` is the highest release count in the library, or in `system` when given (0 when empty), whatever `min` is. An unknown `system` is `400 ValidationFailed`. An out-of-range number or unknown `sort`/`dir` gives `400 ValidationFailed`.
- `GET /api/reports/duplicates?system=&page=&pageSize=` defaults to 25 groups, sorted by system/base title. Each is `{system, systemName, baseTitle, gamesKey, games}`. Games contain `{id, displayTitle, romCount, zipSizeBytes, createdAt, boxArtUrl}`, ordered by releases descending, then oldest, then id.
- `POST /api/reports/duplicates/dismiss` (Admin) takes `{system, baseTitle, gamesKey}` and returns 204. `gamesKey` is the SHA-256 of sorted, comma-joined game ids. Repeated and stale dismissals are harmless. Unknown system, missing fields, baseTitle over 255 characters or a key other than 64 lowercase hex digits gives `400 ValidationFailed`.
- `POST /api/reports/duplicates/merge` (Admin) takes `{targetGameId, sourceGameIds}` (1-20 distinct sources, none the target) and returns `{targetGameId}`. It uses ordinary library merges, with the job lock taken per source. The first failure stops the loop and returns the ordinary problem plus `merged`, the source ids already moved. A `DbWriteFailed` source is included because its files changed. A job starting between sources can cause `409 JobRunning` after partial success.
- `GET /api/reports/activity` (Admin; a Site user gets `403`) returns `{lastSignIn, addedRoms, signIns, plays, saves, edits, deletions}`, every list at most 20 items, newest first (ties by id, highest first), every time UTC with `Z`. `lastSignIn` is `{username, at}` for the newest `last_login_at`, or `null`. `addedRoms` items are `{romId, gameId, gameTitle, fileName, system, sizeBytes, addedAt}`, by date added, `sizeBytes` being the release with its set files. The other lists are audit rows in the `/api/admin/audit` item shape (with `gameTitle`, below): `signIns` (`SignedIn`, `SignInFailed`, `LockedOut`), `plays` (`GamePlayed`), `saves` (`SaveAdded`, `SaveUpdated`, `SaveDeleted`), `edits` (`GameUpdated`, `ReleaseMoved`, `GamesMerged`, `CoverSet`, `PrimarySet`, `ReleaseEdited`, `ImageAdded`, `ImageDeleted`) and `deletions` (`GameDeleted`, `ReleaseDeleted`). They cover the audit log's 30 days. The Activity page also reads `GET /api/jobs?pageSize=10` and `GET /api/admin/backups`.

### File action auditing

`GET /api/admin/audit` and `/api/admin/audit/actions` require Admin. The first returns `{items, page, pageSize, total}`, default pageSize 100 (maximum 200), newest time then highest id first. Each item has `{id, occurredAt, action, system, gameId, user, jobId, path, targetPath, details, gameTitle}`; `gameTitle` is the game's current display title, `null` when there's no game or it's gone. Actions returns the available action names.

Filters: `action`, registered `system`, exact `user` (case/accent-insensitive username), `scheduled=true` (no user id and no username, so a failed sign-in with an unknown name isn't listed), `q` (trimmed substring of path, target or details, at most 200 characters, LIKE characters literal), `from` inclusive and `to` exclusive (ISO 8601 instants with an offset). Blank user/q are absent. Scheduled plus user, unknown action/system, invalid dates, from >= to, or invalid paging gives `400 ValidationFailed`. The UI converts local From to midnight and local To to the next day's midnight, preserving local-day boundaries across daylight saving changes.

Rows record successful ingestion, ZIP repair, extension rename, failed/duplicate moves, archive/review deletion, ingest file deletion (`IngestFileDeleted`, details `pending`, `failed` or `removed`), restoring a deleted ROM (`RemovedRestored`, from `_removed/` to its new pending path), metadata edits, release/game deletion, image add/delete/cover, media fetch, release move, merge, DAT refresh, a shared logo being replaced or removed (`PublisherLogoReplaced`/`PublisherLogoRemoved`, `GenreLogoReplaced`/`GenreLogoRemoved`, `SystemLogoReplaced`/`SystemLogoRemoved`, by the Admin who did it; details `<name> (key <key>)`, or `key <key>` when the group is no longer in the library; for systems `<name> (system <id>)` or `system <id>`, with the system set so the System filter finds them; a URL upload adds ` from <url>`), a live backup restore (`BackupRestored`, details `<file>; safety backup <file>`, written after the restore so it survives it), and a browser play (`GamePlayed`, by the user who played, with the game's ZIP path and the release's file name as details; one row per Play dialog opening or PSP link click). Review resolve/dismiss writes one file-action row with the requesting user (a resolve also carries its `ReviewResolve` job's id); job actions include their job id and the requester's username, while scheduled jobs have no user. Deleting the last release writes GameDeleted. No-op metadata/cover changes, media retries that write nothing, and already-missing review files write no row. Rating/favourite, reads, settings changes, integrity and temporary cleanup/rollback are excluded.

Account events are recorded too, with no system, game, job or path; `details` holds `key=value` pairs separated by spaces:

| Action | User | Details |
|---|---|---|
| `UserCreated` | the Admin | `user=<name> type=admin\|site-user` |
| `UserTypeChanged` | the Admin | `user=<name> from=<type> to=<type>` |
| `UserDisabled`, `UserEnabled` | the Admin | `user=<name>` |
| `PasswordReset` | the Admin, or *System* for `--reset-password` | `user=<name>`; from the command line `user=<name> via=cli`, plus ` promoted=admin` when it made the user an Admin and ` reenabled=true` when the user was disabled |
| `PasswordChanged`, `SignedIn` | the user | none |
| `SignInFailed` | the user, or the name typed when no such user exists (cut to 64 characters) | `reason=unknown-user\|disabled\|locked-out\|wrong-password` (the first that applies, in that order) |
| `LockedOut` | the user | `until=<UTC time>` |

A change of both type and status writes `UserTypeChanged` then `UserDisabled`/`UserEnabled`; a change that changes nothing, or fails, writes nothing. The attempt that locks an account writes `SignInFailed` then `LockedOut`. A sign-in refused before the password check (missing fields, a bad antiforgery token, the rate limit) writes nothing. The **User** filter matches who acted; search `user=<name>` to find actions on an account. The name typed into a failed sign-in can be a mistyped password; it stays visible to Admins until the 30-day purge. The command-line reset writes its row directly, after printing the password; if that write fails it warns and still succeeds.

Paths use `roms/` or `ingest/` prefixes; archive entries appear as `ingest/<archive> › <entry>`. Paths outside both roots use only the filename. Events keep their username snapshot after account changes, and have no game/user foreign keys. Rows older than 30 days are purged at startup and daily at 00:05 UTC. Recording is best effort: a bounded queue and background writer keep file actions independent of log failures; failed/full writes are warned and dropped, and a crash can lose queued events. A ZIP changed before a DB mirror failure still gets a row. The log has no undo action.

### Edit the library through the API

Admins can edit metadata, delete, move and merge, and manage images (a Site user gets `403 Forbidden`). These requests need the antiforgery header. Each edit takes the global job lock, so it returns `409 JobRunning` while a job or another edit runs. Every edit starts from the game ZIP's own `info.json`, writes the ZIP atomically, then updates the database.

- `PATCH /api/games/{id}` takes any of `title`, `releaseYear`, `developers`, `publishers`, `genres` and `description`, and returns the updated game (same shape as `GET /api/games/{id}`). Omitted fields stay unchanged; `releaseYear` and `description` accept `null` to clear them.
  - `title`: 1–255 characters after trimming, and it must not sanitize to an empty file name. `displayTitle` is always derived from it.
  - `releaseYear`: `null` or 1970–2100. Each list: at most 20 items of 1–255 characters, trimmed with duplicates removed. `description`: at most 4000 characters.
  - A title change renames the ZIP (`roms/<system>/<letter>/<title>.zip`, with ` (2)`, ` (3)`, … if another game already has the name). On a disc system the external files keep their names; if the letter folder changes they move with it, and a name already taken there is `409 NameTaken` with nothing moved. The new ZIP is written and committed before the old one is deleted. A change that only differs in letter case keeps the existing file, because file names compare case-insensitively.
- `PATCH /api/games/{id}/roms/{romId}` (Admin) edits a release's tags and answers `{fileName}` (the name after the edit). Every property is optional: `kind` (`release`, `update` or `dlc`), `regions` (≤ 10 distinct values, each a known No-Intro region or one the release already has; `[]` = none), `languages` (≤ 20 distinct codes of 1–16 letters or `-`), `revision` (≤ 32 characters, no parentheses; `null` clears), `disc` (1–99, disc systems only; `null` clears), `hack`, `translated` (booleans) and `version` (a dotted version, updates only; `null` clears). An unknown property, a body that isn't an object or a bad value is `400 ValidationFailed` keyed by field. No change writes nothing. The release is renamed as described in [ZIP format](zip-format.md#naming); a rename that carries saves is refused with `409 SavesUnreadable` when the game's `saves.json` can't be read. Also `404`, `409 JobRunning`, `409 StorageMigrationPending`, `409 TargetZipUnreadable`/`InfoJsonNewerSchema`, `409 SavesIndexFull`, `500`. Audited as `ReleaseEdited` (details `<old> → <new>` when renamed). `GET /api/systems/regions` (any signed-in user) lists the regions in the form's order; `GET /api/games/{id}` carries `fileSets` (a disc system).
- `DELETE /api/games/{id}/roms/{romId}` returns 204. It moves the ROM's bytes to `ingest/<system>/_removed/` (adding ` (2)`, … on a name clash), rebuilds the ZIP without it and recomputes the primary release. Removing the last release deletes the game.
- `DELETE /api/games/{id}` returns 204. It moves every ROM to `_removed/`, then deletes the ZIP and the game's rows.
- `POST /api/games/{id}/roms/{romId}/move` takes `{targetGameId}` (an existing game) or `{newGameTitle}` (a new game), and returns `{targetGameId}`. Both games' ZIPs are rebuilt with the primary release recomputed, and a game left without releases is deleted. A new game gets the metadata of the moved release's DAT entry and its own box art and snap lookup; an existing target's metadata and images stay as they are. If the source ZIP can't be rebuilt after the target was written, the target is put back.
- `POST /api/games/{id}/merge` takes `{targetGameId}` and returns it. Every release of the source moves into the target in one write; then the database is updated and the source ZIP deleted. The target keeps its title, metadata and cover, except that empty fields (year, developers, publishers, genres, description) are filled from the source. The source's non-default images are copied with new names (`boxart-NN` / `snap-NN`); its placeholder is dropped. A target placeholder is removed when the source brings real box art (and if it was the cover, the first such box art becomes the cover); a target without images takes the first copied one as cover. More than 20 images in the result is `409 TooManyImages`, with nothing changed.
- Move and merge targets must be a different game in the same system (`400 ValidationFailed` otherwise); an unknown target is `404 NotFound`. A moved release keeps its file name (with ` (2)`, … on a clash; on a disc system a clash, in the target game or the target folder, is `409 NameTaken` with nothing moved) and its base title. Later releases with that base title therefore follow it when it is the only game holding the title; if the source still holds it too, later releases go to review as `AmbiguousGroup`.

- `POST /api/games/{id}/images` (multipart: `file`, `type` = `BoxArt` or `Snap`) adds an image and returns the game. The format is detected from the bytes (PNG or JPEG, never from the file name) and the image is stored as `boxart-NN.png`/`.jpg` or `snap-NN.…` with the lowest free number. Box art replaces the placeholder (taking over as cover if the placeholder was); the first image of a game without images becomes its cover. Errors: `400 ValidationFailed` (field `file`: missing, over 8 MiB, not a PNG/JPEG, unreadable dimensions; field `type`), `409 TooManyImages` (20 already), `409 DuplicateImage` (same SHA1 already in the game), `413` for a request over 8 MiB + 64 KiB.
- `POST /api/games/{id}/images/from-url` (JSON `{url, type}`) downloads the image and adds it exactly like an upload, with `sourceUrl` set to the URL as sent; the audit row's details are `<fileName> from <url>`. In order: `400 ValidationFailed` before any download (`url`: required, at most 1024 characters, absolute `http`/`https` without user info; `type` as above), `404` for an unknown game (nothing downloaded), then the download: one GET, no proxy, no retries, at most 3 redirects, 15 seconds for the headers and the whole body, at most 8 MiB read. Every connection, each redirect included, must go to a public address (private, loopback, link-local, CGNAT, multicast, documentation, reserved and IPv6 tunnelling ranges are refused, checked on the resolved addresses at connect time); otherwise `400 ImageUrlBlocked`. Download failures are `502 ImageDownloadFailed` with the cause in `title`: `couldn't connect.`, `timed out.`, `too many redirects.` or `HTTP <code>.`. An empty, over-8 MiB or non-PNG/JPEG body is `400 ValidationFailed` on `url`. After that the upload's rules apply (`409 DuplicateImage`, `409 TooManyImages`, `409 JobRunning`, placeholder replacement); the download happens before the job lock is taken.
- `DELETE /api/games/{id}/images/{imageId}` removes an image and returns the game; `409 DefaultImage` for the placeholder. Deleting the cover moves it to the first remaining box art by file name, else the first remaining image, else the placeholder is added back as cover.
- `POST /api/games/{id}/images/{imageId}/cover` makes that image the cover and returns the game.

Image ids change on every write, so take them from the returned game. Removed ROMs stay in `_removed/` (ingestion ignores it) until an Admin restores or permanently deletes them on [Deleted ROMs](#deleted-roms) (`POST /api/ingest/restore`, `POST /api/ingest/delete` with folder `removed`). A ROM whose ZIP entry no longer matches its recorded SHA1 is still moved as it is; a listed entry that is absent from the ZIP has nothing to move and is skipped.

Errors: an unknown game, a ROM of another game, or a release the ZIP no longer lists return `404 NotFound`. A ZIP that can't be read or has a newer `info.json` schema returns `409 TargetZipUnreadable` or `409 InfoJsonNewerSchema` without changing anything. A corrupt entry returns `500 VerifyFailed`, and an IO failure returns `500 IoError`; in both cases the ZIP is unchanged and any copies already made in `_removed/` are taken back. `500 DbWriteFailed` means the ZIP changed but the database didn't; the next ingest or integrity run repairs the database from the ZIP.

### Retry missing media

Thumbnails come from libretro-thumbnails, looked up by the primary release's DAT game name first, then the other releases in rank order; releases without a DAT game name (Manual) are skipped. For Switch they're the box-art and screenshot URLs of each release's titledb entry (found by the `[<TitleId>]` at the end of its DAT game name), fetched as PNG or JPEG through a client that only talks to Nintendo's image host and never follows redirects; an image body that takes longer than 20 seconds counts as a failure. Both actions need the antiforgery header (the per-game retry the `rom-manager` role, the job the `admin` role), and take the global job lock (`409 JobRunning` when busy).

- `POST /api/games/{id}/media/retry` re-runs the lookup for one game whose box art is the default or missing, or which has no snap, and returns the game. A found box art replaces only a default one, and a missing box art gets at least the default. A found snap is added only when the game has none. The game is rewritten only when something changed; finding nothing still returns 200 with the game unchanged. Errors are the same as for the other library edits.
- `POST /api/jobs/media-retry` starts a `MediaRetry` job and returns `202 {jobId}`. It runs the same lookup for every game with the default box art, no box art or no snap, ordered by title. Games where every release is Manual are skipped. Per-game errors are logged and the job continues. The summary is `{updated, notFound, skipped, error}`; there are no job items.
- After 3 consecutive network failures (timeouts, connection errors, or 5xx/408 after retries; a 404 doesn't count), the job stops and ends `Failed` with the error `thumbnail host unreachable`. Games already updated keep their new media.

### Integrity checker

The `Integrity` job checks the library against its `info.json` files and the database. It runs as a quick check every day at `Integrity:QuickCheckTime` (see [configuration](configuration.md)), or on demand. It takes the global job lock (a scheduled run is skipped when another job is running) and never moves or deletes library files.

1. **Database repair.** Each ZIP's database rows are replaced from its `info.json`; rows whose ZIP is gone are deleted unless the same game id turned up at another path. Every repair is recorded as an `AutoRepaired` issue (`DbRowInserted`, `DbRowUpdated`, `DbRowDeleted`). ZIPs with a duplicate game id, or with a ROM another game already holds, keep their existing rows and are reported as `DuplicateGameId` / `DuplicateSha1`.
2. **Scan.** Every file directly in `roms/`, everything under a folder that isn't a registered system, and every non-ZIP file (including stale `*.zip.tmp`) under a system folder is an `OrphanFile`; these are never opened. Every `.zip` under a system folder is checked. A non-ZIP file a game in that folder lists as an external ROM isn't an orphan.
3. **Per ZIP.** Quick mode opens a ZIP only when its size or whole-second modification time differs from its database row; otherwise it checks only the location. Deep mode opens every ZIP and also recomputes the SHA1 of every ROM and image entry (`HashMismatch`). An opened ZIP is checked for `ZipUnreadable`, `InfoJsonMissing` / `InfoJsonInvalid` / `InfoJsonNewerSchema`, `EntryMissing`, `EntrySizeMismatch`, `EntryUnlisted`, `MissingBoxArt` and `DefaultBoxArt` (Info). Every ZIP is checked for `WrongLocation`: system folder, letter folder and file name must match its title (case-insensitively; a ` (2)`-style clash suffix is accepted). For an external system, each file the database lists is checked by length on every run (`EntryMissing`, `EntrySizeMismatch`) and by SHA1 on a deep run (`HashMismatch`), even when its ZIP isn't opened; linked or special files are never followed.

An issue found again updates the open issue with the same type, path and entry rather than adding a new one. A completed run resolves an open issue it didn't find again, but only if it actually performed that check: a quick run can't clear entry or `info.json` problems on a ZIP it didn't open, and only a deep run clears `HashMismatch`. Orphans and duplicates are re-checked by every run, and an issue on a ZIP that no longer exists is resolved. A cancelled run records what it found but resolves nothing.

At the end of each completed run, jobs started more than 180 days ago (with their items) and resolved or auto-repaired issues older than 180 days are deleted. The job summary holds `zips`, `opened`, `issues`, `newIssues`, `resolved`, `repaired`, `purgedJobs` and `purgedIssues`.

All integrity endpoints need an Admin session; the POST also needs the antiforgery header.

- `POST /api/jobs/integrity` with `{"mode": "Quick"}` or `{"mode": "Deep"}` starts a run and returns `202 {jobId}` (`409 JobRunning` when busy, `400 ValidationFailed` for another mode). Follow it with `GET /api/jobs/{jobId}`.
- `GET /api/integrity/status` returns `{lastQuick, lastDeep, nextScheduledAt}`: the latest job of each mode (or `null`) and the next scheduled quick check in UTC (`null` when the schedule is disabled).
- `GET /api/integrity/issues?status=&type=&page=&pageSize=` returns a page of issues, newest first. `status` is `Open`, `AutoRepaired` or `Resolved`; `type` is any issue type above.

### Saves through the API

Every route is open to any signed-in user (antiforgery header on writes) and returns `404 NotFound` for an unknown game or save. For a Site user another user's save, or one with no owner, is answered exactly as an unknown id (`404`, after `JobRunning` and `SavesUnreadable`); an Admin reaches every save. A Nintendo DS game still waiting for the storage job answers writes with `409 StorageMigrationPending`, an unreadable `saves/` folder `409 SavesUnreadable`, a running job `409 JobRunning`; each `409` carries a sentence in its `title`.

- `GET /api/games/{id}/saves` → `{items: [{id, name, description, kind, releaseFileName, romId, sizeBytes, extension, uploadedBy, uploadedAt, updatedBy, updatedAt}]}`, newest `updatedAt` first, only the caller's own for a Site user; `romId` is `null` for an orphan; `uploadedBy` is the owner.
- `POST /api/games/{id}/saves` (multipart: `romId`, `kind` `state`|`battery`, `name`, optional `description`, then exactly one `file`, 1 byte–256 MiB) → `201` with the item. The text parts must come before the file; checks run before the file is read (`400`, `404`, `409`, `409 SaveLimitReached` when the uploader already has 25 saves for the release), and an upload over 256 MiB is `413 PayloadTooLarge`. `409 SavesIndexFull` when `saves.json` would pass 1 MiB.
- `PATCH /api/games/{id}/saves/{saveId}` with `{name?, description?}` → `200` item (no change writes nothing).
- `PUT /api/games/{id}/saves/{saveId}/file` (multipart, one `file`) → `200` item; a new extension renames the entry.
- `DELETE /api/games/{id}/saves/{saveId}` → `204`; the last one removes `saves.json`.
- `GET /api/games/{id}/saves/{saveId}/download` streams the bytes as `application/octet-stream` with their `Content-Length`.

### Release notes through the API

- `GET /api/games/{id}` gives each release `hasNote` (read from the ZIP's entry names; `false` for every release when the ZIP can't be opened) and `originalFileName`.
- `GET /api/games/{id}/roms/{romId}/note` (any signed-in user) returns the note as `text/markdown; charset=utf-8`; `404 NotFound` when the game, release or note doesn't exist; `409 NoteTooLarge` above 64 KiB.
- `PUT /api/games/{id}/roms/{romId}/note` (Admin) with `{text}` saves it (`204`). Line endings become `\n`; empty or whitespace-only text deletes the note; more than 65,536 UTF-8 bytes, or a missing `text`, is `400` with a `text` field error.
- `DELETE /api/games/{id}/roms/{romId}/note` (Admin) deletes it (`204`; `404` when there's none).

PUT and DELETE rewrite the ZIP under the job lock like any edit (`409 JobRunning`, `409 InfoJsonNewerSchema`); the game's fields, including `updatedAt`, don't change, and notes aren't audited (they're logged at Info).

### Keyboard shortcuts through the API

- `GET /api/auth/me/hotkeys` returns `{bindings: {<id>: string | null}, implicitUnassigned: [<id>]}` for every editable action (`nav.library`, `nav.collections`, `nav.ingestion`, `nav.review`, `review.next`, `nav.reports`, `nav.integrity`, `nav.admin`, `nav.deleted`, `reports.missingImage.next`, `reports.missingMetadata.next`), defaults filled in (`reports.missingMetadata.next` has none, so it is `null` until set). `implicitUnassigned` lists actions shown as null only because another allowed action's stored shortcut holds their default (today only `reports.missingImage.next`).
- `PUT /api/auth/me/hotkeys` with `{bindings}` replaces your shortcuts (an action left out goes back to its default; `{}` resets all) and returns the result. Shortcuts are written `Ctrl+Alt+Shift+Meta+<Key>` (modifiers in that order); other orders and letter case are accepted and normalised. Unknown actions, `search`, bad formats and the rules above are `400` with field errors keyed `bindings.<id>`. Only shortcuts that differ from the default are stored (`users.hotkeys`). Bindings sent for actions your roles don't allow are ignored, and stored ones are kept. Leaving out an action listed in `implicitUnassigned` keeps it unassigned; sending it with a key in use is the normal duplicate error. The `PUT` response has the same shape as the `GET`.

Both are blocked until a forced password change is done.

### Database backups through the API

All three need `admin`.

- `GET /api/admin/backups` returns `{enabled, time, retention, timeZone, nextRunAt, running, lastResult: {at, ok, fileName, error} | null, backups: [{fileName, sizeBytes, createdAt}]}`, backups newest first. `nextRunAt` is UTC, `null` when disabled.
- `PUT /api/admin/backups/settings` with `{enabled, time: "HH:mm", retention: 1–365}` (all required) saves the schedule and reschedules at once; returns the GET body. Errors are `400` with field errors `enabled`, `time` or `retention`.
- `POST /api/admin/backups` runs a backup and waits for it: `201` with `{fileName, sizeBytes, createdAt}`; `409 BackupRunning` when one is already running; `500 BackupFailed` when it fails (the cause is in the log and in `lastResult`).
- `POST /api/admin/backups/{fileName}/restore` restores a listed backup while the app runs and returns `200 {restored, safetyBackup}`, signing the caller out (the auth cookie is cleared and a fresh anonymous antiforgery token issued, as logout does). Refusals change nothing: `400 ValidationFailed` (`fileName`) for anything but a name the list shows; `409 JobRunning` or `409 BackupRunning`; `404` for a missing file; `409 BackupTooNew` (from a newer app; `detail` says why) or `400 InvalidBackup` (unreadable ZIP or manifest, missing schema or table data); `409 Busy` when other requests didn't finish within 10 s; `500 BackupFailed` when the safety backup fails. After the tables were dropped a failure is `500 RestoreFailed`, naming the safety backup to restore. See [deployment](deployment.md#restoring-a-backup).

A scheduled run that finds a manual one running is skipped (logged at Info). The settings live in the `app_settings` table (`backup.enabled`, `backup.time`, `backup.retention`); missing rows mean the defaults.

### DAT refresh schedule through the API

- `GET /api/admin/dats/settings` (Admin) returns `{enabled, time: "HH:mm", timeZone, nextRunAt}` (`nextRunAt` UTC, `null` when disabled).
- `PUT /api/admin/dats/settings` (Admin) with `{enabled, time}` (both required) saves it, reschedules at once and returns the GET body. A body that isn't an object is `400` (field `""`); a non-boolean `enabled` is `400` (`enabled`); a bad time is `400` (`time`). Not audited, like the backup settings. Stored in `app_settings` (`dats.autoRefresh.enabled`, `dats.autoRefresh.time`); missing or invalid rows mean the defaults (on, `04:00`).
- `GET /api/admin/dats/{datName}/download` (Admin) streams one listed DAT (a main DAT or the titledb file) from the DAT cache as an `application/octet-stream` attachment under its file name. `datName` is looked up exactly in the live manifest (the first match when a name repeats); no path from the client reaches the file system. An unknown name, a missing or unreadable manifest or file, or a file a refresh is replacing is `404`. The file is opened so that a DAT refresh can still replace the cache folder during the download.

### ROM Zip Config

**Admin → ROM Zip Config** opens with a line on what it controls, then lists every system: its badge (a link to the Library filtered to that system), its **Folder** (the short code, e.g. `nds`; its tooltip says to put ROMs in `ingest/nds` and that they're stored in `roms/nds`), then under **ROM storage** its **Default** and **Configured** storage as icons (a ZIP file for "Stored in ZIP", stacked files for "Beside ZIP", each with a tooltip and an accessible name; Configured adds "N games still to move" while the storage job hasn't reached them) and, in **Change**, for a system that can change (Nintendo DS and Nintendo 3DS), a **Store in ZIP** / **Store beside ZIP** button for the other choice, disabled while any job runs. The button asks to confirm: every game of the system is rewritten one at a time, which takes hours for a large library and is heavy on disk and CPU; until it ends no other job can run and no game can be edited; games it doesn't reach (cancelled or failed) stay read-only until they're moved; it can be cancelled from the Jobs page and resumed later; free space of about one game's ROMs plus its ZIP is needed. Storing DS in the ZIP also makes saves slower (a save rewrites the whole ZIP, ROM included, up to 512 MiB). Storing 3DS in the ZIP makes every edit rewrite ROMs of up to 4 GiB, and imports read each ROM into memory, so 3DS dumps over about 2 GiB are refused as too large while it's on. Confirming saves the choice and starts the storage job (a toast links to the Jobs page); it's refused while another job runs, and nothing is saved then. **Resume moves** shows above the table while games still wait. A failed or cancelled run leaves the system mixed: games already moved stay moved, the rest stay readable but read-only, and the choice isn't reverted; changing it back starts a job toward the new value.

Under **ZIP compression**, the **Level** column shows each in-ZIP system's level as a coloured badge (Store grey, Medium blue, High green) with a pencil **Edit** button, and the **Repack** column its **Repack again** button (a system whose ROMs are beside its ZIP shows "—"): **Store** (no compression: the fastest, for large ROMs that don't compress, like DS), **Medium** (the default; Deflate, Fastest for ROMs and saves over 128 MiB, as before) or **High** (Deflate's smallest size; much slower writes). A legend table under the table compares them, with the same badges (Medium marked **Default**) and a speed icon per level. **Edit** asks for the level and warns that every game ZIP of the system is rewritten one at a time (long, heavy on disk and CPU, no other job and no edits until it ends; a cancel leaves some ZIPs at the old level, still playable, and **Repack again** finishes; each game needs free space about the size of its uncompressed ROMs). Confirming starts the **Repacking ZIPs** job, which saves the level first and then rewrites every game (a toast links to the job). **Repack again** rewrites every game at the current level. While it runs, edits, ingest and save uploads, replacements and deletes get "Another job is running". Each game is checked (free space, verified write, atomic replace) and gets a job item, `Repacked` or `Error` with the reason; a failed game keeps its ZIP. Every later write of a game (an edit, save, image or storage move) uses its system's level too.

- `GET /api/admin/rom-storage` (Admin) → `[{id, displayName, defaultEmbedRoms, embedRoms, configurable, pendingGames, zipCompression, compressionConfigurable}]`, one per system, ordered as `/api/systems`; `zipCompression` is `Store`, `Med` or `High` (`Med` when none is stored) and `compressionConfigurable` is true while the system's ROMs are in its ZIP.
- `PUT /api/admin/zip-compression/{systemId}` (Admin), body `{level: "Store" | "Med" | "High"}` (exact case): `404` for an unknown system, `400` (`errors.level`, "Must be Store, Med or High.") for a missing body or another value, `400 NotConfigurable` for a system whose ROMs are beside its ZIP, `204` when it's already the level, else `202 {jobId}`: the `ZipRepack` job saves `storage.zipCompression.<systemId>` in `app_settings`, records `ZipCompressionChanged` in the audit log (details `<old> → <new>`, for example `Med → Store`, by the requesting Admin) and repacks every game. `409 JobRunning` when another job runs; nothing is saved then.
- `POST /api/admin/zip-compression/{systemId}/repack` (Admin): the same `404` and `NotConfigurable`, then `202 {jobId}` (a repack at the current level, nothing saved or audited) or `409 JobRunning`.
- `PUT /api/admin/rom-storage/{systemId}` (Admin), body `{embedRoms: bool}`: `404` for an unknown system, `400` (`errors.embedRoms`) for a missing body or a non-boolean, `400 NotConfigurable` for a system that can't change, `204` when it's already the configured value (nothing saved), else `202 {jobId}`: the storage job saves `storage.embedRoms.<systemId>` in `app_settings`, records `RomStorageChanged` (`in ZIP` / `beside ZIP`) and moves the games; `409 JobRunning` while another job runs (nothing saved).

### Admin settings, logs and About

- `GET /api/admin/settings` (Admin) returns the effective configuration: the same redacted model that is logged at startup (including every storage root, such as `paths.bios`, and `backup.restoreFrom`). The connection string has its password removed, and `adminInitialPassword` shows `***` when one is set.
- `GET /api/admin/logs/recent` (Admin) returns the last 20 log events the server holds in memory as a JSON array, oldest first (`[]` when there are none).
- `GET /api/admin/logs` (Admin) downloads `rnrommanager-logs-<UTC time>.zip`. It contains every `*.log` file in `Paths:Logs` (including today's file while the app is writing to it), `settings.json` (the redacted configuration) and `version.txt`.
- `GET /api/admin/logs/stream` (Admin) is a server-sent event stream (`text/event-stream`). It first sends the buffered events newer than the `Last-Event-ID` header (all of them when the header is missing, unreadable or newer than anything buffered), then each new event as `id: <number>` and `data: {time, level, logger, message, exception}`. Ids keep increasing across restarts. A `: keep-alive` comment follows every 15 seconds; at each one the stream ends if the user was disabled, lost `admin` or was signed out.
- `GET /api/about` (any signed-in user, even before a forced password change) returns `{version, licenses[]}`; the footer and About use it. Each licence entry is `{name, license, url}`, covering the app, libretro-database (CC BY-SA 4.0) and every direct NuGet and npm dependency. The list lives in `src/RnRomManager.Api/licenses.json`; a test fails when a dependency is added to `Directory.Packages.props` or `package.json` without an entry there.

Every `/api` endpoint's required access (anonymous, any user or Admin) is checked by a single table-driven test that fails when a new endpoint has no entry.
