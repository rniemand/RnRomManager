# Features

RnRomManager keeps a personal backup collection of Game Boy, Game Boy Color, Game Boy Advance, Nintendo 64, Nintendo Entertainment System, Super Nintendo Entertainment System, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Game Gear, Master System, Mega Drive / Genesis, 32X, TurboGrafx-16, Nintendo Switch, PlayStation, PlayStation Portable, GameCube, Wii, Xbox 360 and Saturn ROMs. You drop files into an ingest folder; ingestion identifies each one (against the No-Intro DATs by hash, for the disc systems against the Redump DATs by hash, or for Switch against [titledb](https://github.com/blawar/titledb) by title ID), names it, groups it with the game's other releases, fetches box art and stores it as one ZIP per game. Switch dumps and disc images are too large for a ZIP, so they're stored as files next to their game's ZIP (see [External storage](#external-storage-nintendo-switch-and-disc-systems)). Everyone can browse and download; admins run ingestion, resolve files it couldn't identify and keep the library healthy, and ROM managers edit it.

## Roles

An account has any of two roles, or none:

- **No role:** Library, Reports and Game detail (browse, search, download, rate and favourite, release notes), and their own keyboard shortcuts.
- **`admin`:** Ingestion, Review, Integrity, Admin and job pages. Anyone else who opens one of them sees "Not allowed".
- **`rom-manager`:** the edit actions on Game detail (edit metadata, retry media, merge, move, delete), image management, and merging or dismissing duplicate groups in Reports.

The roles don't include each other: an `admin` without `rom-manager` can't edit games. The first account, and an account the `--reset-password` command promotes because no enabled admin is left, gets both. Upgrading from a version with the single Admin/User role gives every Admin both roles and every User none, and signs everyone out once.

The navbar stays at the top of the window while you scroll, and shows the pages your roles can use (in the order Library, Ingestion, Review, Reports, Integrity, Admin), with the current page highlighted. Its **(?)** button opens your [keyboard shortcuts](#keyboard-shortcuts). The user menu has **Change password** and **Logout**; the theme button switches between Light, Dark and Auto (follows your system), remembered per browser. Times are shown in your browser's time zone. Search has no keyboard hint in the navbar; its shortcuts still work. Closing a dialog or navigating away from one restores page scrolling.

## Global search

**Search** in the navbar, **Ctrl+K** / **Cmd+K** or **Ctrl+Space** (some systems use Ctrl+Space to switch input methods; use Ctrl/Cmd+K there) opens a search box from any page, even while typing in a field. It's off while another dialog is open and until you've changed a forced password. The dialog is extra wide. From 2 characters it shows two groups: up to 5 of your [collections](#collections) whose name contains every word you typed (sorted by name), as compact chips with a small cover, the name and `· <n>` games, then the 20 best games. Every word you type must appear in the title, developers, publishers or genres; an exact title ranks first, then titles that start with what you typed, then by how many words hit the title (weighted most), developers, publishers and genres, then A–Z. Each game is a row with its box art, title, system badge (short name) and, on wider screens, `year · regions · size` and its rating and favourite; when no word matched the title, the title says why it was found (e.g. "Publisher: Nintendo"). On a phone the year, regions, size and rating are left out. Up/Down move through both groups, Enter (or a click) opens the collection or game; if one of the two searches fails, its error shows and the other group's results stay. Escape closes the search and puts the focus back where it was.

## Keyboard shortcuts

These work from any page, even while typing in a field, but not while a dialog is open or before a forced password change:

| Action | Default | Who |
|---|---|---|
| Open global search | **Ctrl+K**, **Ctrl+Space**, **Cmd+K** (fixed) | everyone |
| Go to Library | **Alt+Shift+L** | everyone |
| Go to Collections | **Alt+Shift+C** | everyone |
| Go to Ingestion | **Alt+Shift+I** | `admin` |
| Go to Review | **Alt+Shift+F** | `admin` |
| Open the first review item (the Review page when the queue is empty) | **Alt+Shift+G** | `admin` |
| Go to Reports | **Alt+Shift+R** | everyone |
| Go to Integrity | **Alt+Shift+T** | `admin` |
| Go to Admin (Users) | **Alt+Shift+A** | `admin` |
| Go to Deleted ROMs | **Alt+Shift+D** | `admin` |

(On a Mac, Alt is Option and Meta is Cmd.) The navigation shortcuts use Alt+Shift because Ctrl+I/F/G/L are the browser's own (italic, find, find next, address bar). On some Windows setups Alt+Shift switches the input language; rebind them if so. If a shortcut you set earlier uses one of the newer defaults (R, T, A, D), yours keeps working: when two actions share a key, the one higher in this table runs, and the shortcuts dialog shows the conflict.

The **(?)** button in the navbar lists the shortcuts your roles allow. **Edit** a row, then press the new keys: the first key with a modifier becomes the shortcut; **Backspace** or **Delete** clears it ("Not assigned"); **Escape** stops editing without closing the dialog. A shortcut must include Ctrl, Alt or Meta, can't be Ctrl+Alt without Shift or Meta (that's AltGr on many keyboards), can't be a search shortcut, and can't be used by another action you can use; a key that breaks a rule shows why on its row and isn't taken. Keys are A–Z, 0–9 and F1–F12, read from the physical key, so the keyboard layout and Option don't change the letter. **Reset to defaults** puts every row back; nothing is saved until **Save**, which applies the changes at once. Shortcuts are saved per account, so they follow you to other browsers. An `admin`'s shortcuts for admin pages are kept if the role is removed; if two actions you can use end up on the same key (the role was given back), only the first in the table fires and the dialog asks you to change the other.

## Sign in and change password

- **Sign in** (`/login`): username and password. Any failure (unknown user, wrong password, locked or disabled account) shows the same "Invalid username or password." message. Five failed attempts lock an account for 15 minutes, and more than 10 attempts a minute from one address are refused for a while. After signing in you go back to the page you were sent from, or to the Library. Sessions last 7 days from the last use.
- **Change password** (`/change-password`): current password, new password and confirmation. Passwords are 12–128 characters and must not be the username. A new account, the first Admin and an account an Admin reset must change their password before using any other page. Changing it signs out your other sessions but keeps this one.

## Library

The home page (`/`) shows every game, 48 per page.

- **Grid or list:** the buttons on the right switch between box-art cards and a table (title, system, year, regions, rating, number of releases, primary ROM size). Your choice is remembered in this browser. Cards show the box art filling a square frame (non-square art is cropped at the edges; the full image is on the game's Images tab) with a system badge in the system's colour at its top left and the primary ROM size as a badge at its top right, then the title on one line (hover or focus it for the full title) and the year and regions. A game with updates (releases flagged `Update`) shows an **updates** badge with their count at the bottom left of the box art (after the title in the list). A game whose system plays in the browser (Game Boy, Game Boy Color, Game Boy Advance, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Game Gear and Master System) has a round **Play** button at the bottom right of the box art (in the list, a play button in the last column) that starts its primary release straight away, as the game page's [Play](#game-detail) does; it's hidden in Select mode and for a release stored outside the ZIP. The list shows the size in its own column and the system as a coloured badge. The size is omitted when no primary exists. In the dark theme cards are a step lighter than the page; hovering or focusing a card lifts it slightly with a shadow (only the shadow when the browser asks for reduced motion).
- **Filters:** one toolbar holds the search box, the **System**, **Region**, **Letter** and **Sort** menus, the sort direction, **Favourites** and Grid/List; it wraps on narrow screens. Search applies from 2 characters as you type (every word must appear, in any order, in the title, developers, publishers or genres); region matches any release in that region; letter is `#` for names that don't start with A–Z, or A–Z; **Favourites** (the heart button) shows only favourite games. Each menu button reads its field and the chosen value (`System: Game Boy`) and is filled while a value is chosen. In the menus, each System, Region and Letter row shows how many games it would give with the other active filters, right-aligned (`1,250`); a row with none shows `0`, greyed, and can still be picked. The **All systems** and **All letters** rows show the total; **All regions** shows none, since a game can count in several regions. The System menu shows each system's badge and full name and has a filter box at the top (it matches the name, id or short name). The menus work with the keyboard (arrow keys, Escape). The counts load separately (no counts while they load or if they fail), don't change when you page or sort, and aren't refreshed by rating or favouriting a card until the next filter change. Games are filed by their stored title, so *The Legend of Zelda* is under **L** (`Legend of Zelda, The`).
- **Sort:** title (default), year, date added or rating (best first by default); the arrow button flips the direction. Games without a year, or not rated, are always last. Changing the sort resets the direction.
- **Active filters:** below the toolbar a row of chips shows each active filter, with its count (`System: Game Boy (1,234)`, `Region: USA (9)`, `Letter: A (3)`, `Search: "zelda"`, `Favourites`); × on a chip clears just that one. **Reset filters** at its end clears every filter, the sort, the direction and the page. The row is hidden when nothing is set.
- **Remembered:** the Library keeps your last filters, sort and page in this browser. Opening `/` (the navbar link, `← Library`, **Alt+Shift+L**) brings them back; a link with its own filters wins and is remembered instead. Going to `/` while already on the Library, or **Reset filters**, forgets them. Collection pages don't use or change it.
- **Rating and favourite:** click a star (1–5) to rate a game, the same star again to clear it, and the heart to mark it a favourite. Any signed-in user can do this on the cards, the list and the game page; the values are shared, so everyone sees the same rating. A changed card stays where it is until the list reloads. If a job is running, the rating is tried once more after a second, then undone with "Another job is running".
- Filters live in the address bar, so a filtered view can be bookmarked or shared, and Back/Forward step through your changes.

- **Add to collection:** **Select** shows a checkbox on each card or row, with **Select all on this page**; **Add to collection…** adds the ticked games to one of your [collections](#collections) and says how many were new. The selection clears when you change page, a filter or the sort, or turn Select off.

An empty library offers Admins a link to Ingestion.

## Collections

Every signed-in user can group library games from any system into **collections** ("Pokemon", "My favourites"). Collections are private: nobody else, Admins included, can see or change yours.

- **Collections** in the navbar (or **Alt+Shift+C**) lists yours as cards (cover, name, game count) sorted by name, with a name filter and paging (both kept in the address bar; rows per page are remembered in this browser). **New collection** asks for a name, optional Markdown notes (View/Edit/Preview, at most 64 KiB, like release notes) and an optional cover (a PNG or JPEG file or URL, at most 8 MiB), then opens the new collection. If the cover can't be saved, the collection is still created and an error says so.
- Names are 1–100 characters and unique per user, ignoring case but not accents: "pokemon" clashes with "Pokemon", "Pokémon" doesn't.
- A collection's page shows its cover, name, game count and notes, with **Edit** (name and notes are saved with Save; a cover change or removal applies at once) and **Delete** (removes the collection, never its games). Below are its games with the Library's grid/list, search, system filter, Favourites and paging, sorted by when they were added to the collection (newest first) or by title, year or rating; the view is kept in the address bar. **Add games** searches every system and leaves out games already in the collection. Every game picker (Add games, Move/Merge/Attach and Review) shows each result's cover (or the system icon) and, when it searches every system, a short system name such as `SNES` (the full name on hover); each game has a **Remove from collection** button.
- On a game's page, **Collections** lists yours with a checkbox each (the first 200 by name; filter to find more): ticking or unticking applies at once. Badges under the title link to the collections that hold the game.
- A game stays in its collections when it's edited, and moves with it when it's merged into another game or its last release is moved away (keeping the earlier added date where both were in a collection). A game that disappears from the library (e.g. a library folder not mounted) stops showing in its collections and comes back with it.
- Collections live in the database; covers are files in `Paths:Collections` ([configuration](configuration.md)), not in the library ZIPs and not in database backups ([deployment](deployment.md#backup-and-restore)). Changes to collections aren't audited and never wait for a running job.

## Game detail

Opening a game (`/games/{id}`) shows its cover image (a placeholder cartridge when no box art was found), title, rating and favourite (editable, as in the Library), a table of system, year, developers, publishers and genres (`—` when empty; long values, the system name included, wrap inside the table so it never scrolls sideways, even on a phone), and the description.

- The buttons under it are, in order, **Download ZIP**, **Download ROM**, **Google** and **View info.json**. **Download ZIP** downloads the whole game as stored in the library ([format](zip-format.md)). **Download ROM** downloads the single ROM; with several releases it's a menu of every ROM with its size, primary first. For Switch the ZIP holds no ROMs: **Download ZIP** says so in its tooltip ("ROM files are downloaded per release") and each release downloads from its own file.
- **Releases**, **Updates** (only when the game has updates) and **Images** are tabs with counts, followed by **Zip Contents**. Releases opens by default; `?tab=updates` opens Updates (Releases on a game without updates), `?tab=images` Images and `?tab=zip` Zip Contents. Switching tabs updates the URL without reloading the game. Edit buttons work from either tab.
- **Google** (with the Google "G" icon) opens a new tab searching for the quoted display title and system name.
- **View info.json** opens the JSON exactly as stored in the ZIP, read-only. One toolbar row holds **Expand all** / **Collapse all** on the left and **Copy** on the right; below it the JSON sits in a bordered pane that scrolls on its own (at most 60% of the window height), so the dialog doesn't. Objects and arrays expand as a tree: the first two levels start open. Invalid JSON is shown as raw text in the same pane, under a warning and a toolbar with only Copy; fetch failures offer Retry.
- **Releases** shows one card per ROM, so nothing scrolls sideways on a phone. Each card has a stripe down its left edge in the system's colour (the one its badge uses) and a tinted header, so you can see where each release starts. The card header has the file name (wrapping, never cut off), a **Primary** badge for the main release, an **External** badge (its tooltip is the file's name next to the ZIP) for a Switch release, one badge per region, and the release's buttons (note, play, download, delete). The body lists, two per row on wide screens: the original file name (the name it had when it was ingested, only when that differs, with a copy button), size, SHA1, CRC32 and MD5 (with copy buttons), revision, languages and flags (when set), how it was identified (`DAT`, `Manual` or `Title DB`), the DAT name and version, the DAT entry, and the date added. Below them, **Header details** opens the cartridge header (there's none for a system without one, such as Atari 2600) and, for `rom-manager`, **Move release** moves it. For a disc set the size is the whole set's (the main file plus its other files), and an **N files** button (N counts every file, so 3 for a cue and two tracks) opens a table of the main file then each other file, with its size, SHA1 (copy button) and a download button; the header's download button and **Download ROM** still download the main file only. Cards start collapsed to their header: the chevron at its start (or a click on empty header space; not on its buttons, and not when you're selecting the file name to copy it) shows or hides the body. With two or more releases, **Expand all** / **Collapse all** above the cards opens or closes every card. Open cards stay open when the page reloads the same game (after a note, a rating, a move…) and start collapsed again on another game. The header dialog shows two fields per row; the download button downloads that ROM.
- **Updates** lists the releases flagged `Update` (Switch updates; any system whose identification flags a release `Update` gets the tab), which Releases then leaves out: `Releases (n)` counts the others. Updates are listed newest first: by version (`1.10.0` before `1.9.0`; one with a version before one without), then the `v<N>` revision, then the newer date added, then the file name. Each card is a release card (download, note, External badge and the `rom-manager` actions) with a **Version x.y.z** badge when the update has one; **Expand all** works on the tab you're on. The header's **Download ROM** lists only the releases, not the updates (download those from their cards); a game with only updates offers its updates there, and its Releases tab says "No releases other than updates."
- **Release notes:** every release has a note button (yellow and filled, "View note", when it has a note; outlined, "Add note", when not) that opens its Markdown note. Any signed-in user can read and edit notes. A note opens in **View** (rendered Markdown; links open in a new tab); a release without one opens in **Edit**. **Edit** is a plain text box with a byte counter (at most 65,536 bytes); **Preview** renders what you typed. **Save** stores it (saving an empty note deletes it); **Delete note** asks "Delete this note?" in place. Closing the dialog discards unsaved changes. Notes live in the game's ZIP ([format](zip-format.md#release-notes)), so they travel with the library and move with their release; they aren't searchable. While a job runs, saving shows "Another job is running".
- **Play** (Game Boy, Game Boy Color, Game Boy Advance, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Game Gear and Master System): each release card on the Releases and Updates tabs has a green play button, before the download button, for every signed-in user. It opens the release in a large dialog running [EmulatorJS](https://emulatorjs.org) (Gambatte for GB/GBC, mGBA for GBA, Handy for Lynx, Virtual Jaguar for Jaguar, Beetle VB for Virtual Boy, Stella 2014 for Atari 2600, a5200 for Atari 5200, ProSystem for Atari 7800, Gearcoleco for ColecoVision, SMS Plus GX for Game Gear and Master System), served by the app itself; click **Start Game** inside it to begin (browsers need a click before they play sound). The ROM is read from the library ZIP through the release's download URL, so nothing is extracted to disk. Keys pressed inside the emulator go to the game, not to the app's shortcuts, and Escape there doesn't close the dialog; **Close**, × or Escape outside it do, and stop the game. Save states are off. EmulatorJS's quick save and load keys (1, 2 and 3 for the slot) still work, but those states live in memory only and are lost when the dialog closes. In-game (battery) saves are kept in your browser only, per release file name, and survive closing the dialog and reloading on that browser; they're written every 30 seconds (EmulatorJS's System Save interval, which you can change in its settings), so **wait 30 seconds after saving in a game before closing the dialog**. Two releases with the same file name would share saves; DAT file names are unique per system.
  - **ColecoVision BIOS:** Gearcoleco needs the console's BIOS, which the app can't ship. An Admin copies it as `colecovision.rom` (any case) into the BIOS folder (`Paths:Bios`, `/app/bios` in Docker; see [configuration](configuration.md) and [deployment](deployment.md#volumes-and-permissions)). The play page checks for it before loading the ROM; without it, it says *This system needs its BIOS: ask an Admin to put colecovision.rom in the BIOS folder (Paths:Bios).*
  - **Game Gear and Master System** always use SMS Plus GX: the emulator's core selector is hidden for them and a core chosen there earlier is ignored (other emulator settings and SMS Plus GX's own options stay). SMS Plus GX picks the hardware itself (`auto`): it starts as a Master System II, switches to Game Gear when the `TMR SEGA` header at `0x7ff0` has a Game Gear region code, then applies its built-in CRC list. A Game Gear ROM those checks miss runs as a Master System (wrong screen size and palette) whether it's stored as `.gg` or `.sms`.
  - **Game Gear controls** (with a Start button on the touch gamepad and in the controls menu) are chosen from the release's file name: a `.gg` release gets them; a Game Gear release stored as `.sms` gets the Master System controls.
- **Images** has the **Upload image** button (for `rom-manager`) right-aligned above the grid, and shows every image of the game as a thumbnail with its type (Box art, Screenshot, …), a **Cover** badge on the one shown at the top and a **Placeholder** badge on the default cartridge art, with its size and dimensions. Click one to see it full size.
- **Zip Contents** browses the game's ZIP: a folder tree on the left (the root is the ZIP's file name; every folder starts expanded, only the chevron expands or collapses one, and selecting a folder never changes that; the selected folder is highlighted) and the selected folder's sub-folders and files on the right, with size and compressed size as badges, the modified time and a download button per file (a folder row shows `—`; long names are cut off, with the full name on hover). Reloading the same game keeps the folders you collapsed; another game starts expanded again. A breadcrumb above selects any parent folder, and a footer line counts the files and their total size and compressed size for the whole ZIP. The listing loads the first time you open the tab and again after the game changes; the selected folder is kept while it still exists.
- If the game changed since you opened it (someone edited it, or an ingest added a release), an action on a release reloads the page and says "This game changed, please retry".

**Image management** (`rom-manager`):

- **Upload image** opens a dialog for a PNG or JPEG (at most 8 MiB) and its type (the **Box art** / **Screenshot** buttons, Box art by default). **URL** (the default) takes an http or https address: the server downloads the image (public internet addresses only, at most 15 seconds and 8 MiB, PNG or JPEG) and stores it like an upload, then says "Image added from <host>.". When the server can't use the URL (it couldn't connect, timed out, got an error status or too many redirects, the address is private or local, or the response isn't a PNG or JPEG of at most 8 MiB) the reason appears under the field with **Upload a file instead**, which switches to File and keeps the type: download the image yourself and upload the file. **File** uploads a file from your computer; you can also drag an image file onto the dialog, which switches to File and uses it (with several files, the first, and the dialog says so). Each time the dialog opens it starts on URL, empty. A failed upload keeps the dialog open with the error; a successful one closes it. A game holds at most 20 images, and the same image can't be added twice. Uploading box art replaces the placeholder, and takes over as cover if the placeholder was the cover. When that placeholder was the cover, the upload (from a file or a URL) also starts an integrity check of that game alone, in the background, so its *DefaultBoxArt* issue clears without a full deep check; it's skipped when another job is running (the next Quick or Deep run clears it). A snap, a second box art or any other edit starts none.
- **Use as cover** makes any image the one shown at the top and in the Library.
- **Delete** removes an image (not the placeholder, which comes and goes on its own). Deleting the cover hands it to the first remaining box art, else the first remaining image, else the placeholder comes back.

Ingestion and **Retry media** only ever replace the placeholder; they never remove or replace an image you uploaded.

**Edit actions** (`rom-manager`), each confirmed in a dialog:

- **Edit metadata:** title, year, developers, publishers and genres (one per line), description. Renaming a game also renames its ZIP. The displayed title is always derived from the title (a trailing ", The" moves to the front).
- **Retry media:** look up box art and a snap again for this game (replacing only the placeholder).
- **Merge into…:** move every release into another game of the same system (pick it by typing at least 2 characters of its name) and delete this one. The target keeps its own title, metadata and cover; only its empty fields are filled from this game. This game's images (not its placeholder) are copied over, and its box art replaces a placeholder on the target. A merge that would leave more than 20 images is refused. Up to five same-system suggestions appear above the picker. They search the cleaned title (up to eight words), falling back to the first word of at least three characters when nothing matches. Clicking a suggestion fills and selects the target; typing again clears it. Failed suggestion requests leave the picker usable.
- **Move release** (in a release's details): move one release to another game, or to a new game with a title you choose. A game left with no releases is deleted.
- **Delete** (per release) and **Delete game:** the confirmation says when the release's note (or the game's notes) go too. The ROM files are moved to `ingest/<system>/_removed/`; an Admin can restore them to Ingestion, or delete them for good, on [Deleted ROMs](#deleted-roms). Deleting a game's last release deletes the game.

Edits and jobs take turns: while a job runs, an edit shows "Another job is running".

## Ingestion

`/ingestion` (Admin) lists the files waiting in each system's ingest folder (`ingest/gb/`, `ingest/gbc/`, `ingest/gba/`, `ingest/n64/`, `ingest/nes/`, `ingest/snes/`, `ingest/vb/`, `ingest/a2600/`, `ingest/a5200/`, `ingest/a7800/`, `ingest/lynx/`, `ingest/jaguar/`, `ingest/coleco/`, `ingest/gg/`, `ingest/sms/`, `ingest/md/`, `ingest/s32x/`, `ingest/tg16/`, `ingest/switch/`, `ingest/psx/`, `ingest/psp/`, `ingest/gc/`, `ingest/wii/`, `ingest/x360/`, `ingest/saturn/`) with size and time. The **Run** section (Import all, progress, Cancel) is always shown; **Pending files (n)**, **Failed files (n)** and **Last runs** are tabs below it (`n` counts files across all systems). Pending files opens by default; `?tab=failed` and `?tab=runs` open the others. Switching tabs keeps your checkbox selections and doesn't reload the lists.

- Drop `.gb`/`.gbc` files, or `.zip`/`.7z` archives of them, into either of those two folders: the cartridge header decides whether a game is stored as Game Boy or Game Boy Color. Drop `.gba` files (or archives of them) into `ingest/gba/`. Drop Nintendo 64 dumps (`.z64`, `.v64` or `.n64`, or archives of them) into `ingest/n64/`: all three byte orders are accepted, converted to big-endian before hashing (the order comes from the file's first bytes, not its extension) and stored as `.z64`, so the same game dumped in two orders is a `Duplicate`. Drop NES dumps into `ingest/nes/`: only headered `.nes` files (iNES or NES 2.0 header), hashed with the header as the No-Intro DAT does; headerless (`.unh`), UNIF, Famicom Disk System and NSF files aren't supported, and a dump whose header differs from No-Intro's goes to Review. Drop SNES dumps (`.sfc` or `.smc`, or archives of them) into `ingest/snes/`: a 512-byte copier header is stripped before hashing whenever the file size is 512 bytes past a multiple of 1 KiB (whatever the extension), so headered `.smc` dumps match the No-Intro DAT; the game is stored as `.sfc` without the copier header, and the same game with and without one is a `Duplicate`. Satellaview, Sufami Turbo, `.swc`/`.fig` and interleaved or split dumps aren't supported. Drop Atari 2600 dumps (`.a26` or `.bin`, or archives of them) into `ingest/a2600/`: a matched dump is stored under the DAT's ROM name (`.a26` or `.bin`, as the DAT says). 2600 cartridges have no header, so an unmatched file is never `InvalidHeader`: it always goes to Review (`NoDatMatch`, suggestions from the file name), and once resolved it's stored as `.a26`. Supercharger `.wav` tapes aren't supported. Drop Atari Lynx dumps (`.lnx` or `.lyx`, or archives of them) into `ingest/lynx/` and Atari Jaguar dumps (`.j64`, `.jag`, `.rom`, `.abs` or `.cof`, or archives of them) into `ingest/jaguar/`. Lynx headers are optional and Jaguar cartridges have no standard header. Unmatched files go to Review (`NoDatMatch`), and a release resolved without a DAT entry uses `.lnx` or `.j64`, respectively. Lynx `.bll` homebrew and Jaguar CD are unsupported. Drop Virtual Boy dumps (`.vb`, or archives of them) into `ingest/vb/`, Atari 5200 dumps (`.a52` or `.bin`) into `ingest/a5200/` and Atari 7800 dumps (`.a78` with its header, or a headerless `.bin`) into `ingest/a7800/`. None of them fails as `InvalidHeader` (Virtual Boy and 5200 cartridges have no header and the 7800 header is optional), so an unmatched file goes to Review; resolved without a DAT entry it's stored as `.vb`, `.a52` or `.a78`. libretro's 7800 metadat lists only the `.bin` dumps, so a game matched by its `.a78` dump has no year, developer, publisher or genre. Drop ColecoVision dumps (`.col`, `.rom` or `.bin`, or archives of them) into `ingest/coleco/`: a matched dump is stored under the DAT's ROM name (`.col`). An unmatched file must start with the cartridge magic `AA 55` or `55 AA`, or it fails as `InvalidHeader`; with it, it goes to Review (`NoDatMatch`, suggestions from the file name) and once resolved it's stored as `.col`. MegaCart and other homebrew ROMs over 32 KiB, Coleco ADAM and Super Game Module titles aren't supported. Drop Game Gear dumps (`.gg` or `.sms`, or archives of them) into `ingest/gg/`: `.sms` covers the Game Gear DAT's SMS-mode games, and a matched dump is stored under the DAT's ROM name (`.gg` or `.sms`). The `TMR SEGA` header (at 0x7FF0, 0x3FF0 or 0x1FF0) is optional, since many Japanese carts have none, so an unmatched file is never `InvalidHeader`: it goes to Review (`NoDatMatch`, suggestions from the file name). SG-1000 games aren't supported. Drop Master System dumps (`.sms`, or archives of them) into `ingest/sms/`: the same optional `TMR SEGA` header as Game Gear, so an unmatched file goes to Review (`NoDatMatch`, suggestions from the file name) and once resolved it's stored as `.sms`. A `.sms` file in `ingest/gg/` is still a Game Gear file and one in `ingest/sms/` a Master System file: the folder decides. Drop Mega Drive / Genesis dumps (`.md`, `.bin` or `.gen`, or archives of them) into `ingest/md/`: a matched dump is stored under the DAT's ROM name (`.md`, so a matched `.bin` or `.gen` becomes `.md`). The `SEGA` header at 0x100 is optional, so an unmatched file goes to Review (`NoDatMatch`, suggestions from the header's title and the file name) and once resolved it's stored as `.md`. Interleaved `.smd` dumps, Mega-CD and Pico aren't supported. Drop 32X dumps (`.32x`, or archives of them) into `ingest/s32x/`: 32X games carry the same optional `SEGA` header at 0x100 (system type such as `SEGA 32X`), read the same way, so an unmatched file goes to Review (`NoDatMatch`, suggestions from the header's title and the file name) and once resolved it's stored as `.32x`; a `.md`, `.bin` or `.gen` file there, or a `.32x` file in `ingest/md/`, fails as `UnsupportedType`. 32X CD games and `.bin` 32X dumps aren't supported. Drop TurboGrafx-16 / PC Engine HuCard dumps (`.pce`, or archives of them) into `ingest/tg16/`: the DAT mixes Japanese PC Engine and US TurboGrafx-16 releases, and a matched dump is stored under the DAT's ROM name (`.pce`). A 512-byte copier header is stripped before hashing whenever the file size is 512 bytes past a multiple of 8 KiB, so headered dumps match the DAT and are stored without it; the same game with and without one is a `Duplicate`. The strip goes by size alone, so three aftermarket protos in the DAT whose real size fits that rule (`Gnop`, `Masteroids`, `Light Cycles`) don't match and go to Review. HuCards have no header, so an unmatched file is never `InvalidHeader`: it always goes to Review (`NoDatMatch`, suggestions from the file name), and once resolved it's stored as `.pce`. SuperGrafx, TurboGrafx-CD / PC Engine CD and bit-reversed (undecrypted) US dumps aren't supported. Drop Nintendo Switch dumps (`.nsp`, `.xci`, `.nsz` or `.xcz`) into `ingest/switch/`; see [External storage](#external-storage-nintendo-switch-and-disc-systems) for how they're identified and stored. Drop PlayStation discs (a `.cue` with its `.bin` tracks, or a `.bin`/`.iso`) into `ingest/psx/`, Saturn discs (a `.cue` with its `.bin` tracks, or a `.nrg`) into `ingest/saturn/`, PSP, GameCube and Xbox 360 `.iso` files into `ingest/psp/`, `ingest/gc/` and `ingest/x360/`, and Wii `.iso` or `.wbfs` files into `ingest/wii/` (split `.wbf1`, `.wbf2`… files aren't picked up: join them first); see [Disc sets](#disc-sets) for how they're matched and stored. A Wii disc dropped in `ingest/gc/` (or a GameCube disc in `ingest/wii/`) is stored under the system its header names. Switch files inside an archive are ingested only within the usual archive limits (100 entries, 256 MiB extracted), so in practice only small files such as DLC. Because `.md` is also Markdown, a `README.md` inside an archive in `ingest/md/` is treated as a ROM entry: a small one fails `TooSmall` (the game is still ingested, but the archive goes to `_failed/`), a larger one goes to Review. `.bin` is accepted in `ingest/a2600/`, `ingest/a5200/`, `ingest/a7800/`, `ingest/coleco/` and `ingest/md/`: the folder decides the system. Game Boy, Game Boy Advance, Nintendo 64, NES, SNES, Virtual Boy, Atari 2600, Atari 5200, Atari 7800, Atari Lynx, Atari Jaguar, ColecoVision, Game Gear, Master System, Mega Drive, 32X, TurboGrafx-16 and Switch are separate families, so a file with another family's extension in a system's folder (a `.gba` file in a GB folder, a `.n64` file in `ingest/gb/`, …) fails as `UnsupportedType`. Size limits (per file, so per track for a disc set): 336 bytes–16 MiB for GB/GBC, 192 bytes–32 MiB for GBA, 4 KiB–64 MiB for N64, 4,112 bytes–64 MiB + 528 bytes for NES, 8 KiB–8 MiB + 512 bytes for SNES, 64 KiB–4 MiB for Virtual Boy, 2–64 KiB for Atari 2600, 4–64 KiB for Atari 5200, 4 KiB–1 MiB for Atari 7800, 1 KiB–1 MiB for Lynx, 16 KiB–16 MiB for Jaguar, 8–32 KiB for ColecoVision, 8 KiB–1 MiB for Game Gear, 2 KiB–4 MiB for Master System, 8 KiB–16 MiB for Mega Drive, 16 KiB–4 MiB for 32X, 72 KiB–2.5 MiB + 512 bytes for TurboGrafx-16 (checked on the file as dropped, before the strip), 1 KiB–64 GiB for Switch, 16 bytes–1 GiB for PlayStation and Saturn, 16 bytes–8 GiB for PSP, 32 KiB–9 GiB for GameCube and Wii, 2 KiB–9 GiB for Xbox 360. GameCube and Wii share their limits on purpose: ingest checks a file's size against the first system of the family that lists its extension. An unmatched file whose header isn't valid for its system fails as `InvalidHeader`; for N64 that only checks the first byte, so a junk file with an N64 extension may land in Review instead; for NES it checks the `NES` + EOF magic; for GameCube and Wii the disc header's magic word (PlayStation, PSP, Xbox 360 and Saturn have no header check, so an unmatched file always goes to Review); for SNES the internal header (LoROM, HiROM or ExHiROM) must have a valid checksum/complement pair, or a printable title with a map mode that fits its location (a file under 32 KiB has no header to check and goes to Review). Subfolders, hidden files and files changed in the last 10 seconds are left for the next run.
- **Import all** runs through every waiting file, showing progress and the current file. While a large Switch file is hashed, or copied into the library (when `ingest/` and `roms/` are on different volumes or the file system can't rename or hard-link), a second, thinner bar shows that file's progress: `Hashing`, `Copying to library` or `Copying` (to `_failed/`, `_duplicates/` or back after a failed import), with bytes done of the total, the speed and the time left once a second has passed. Small in-ZIP ROMs show no second bar. **Cancel** stops after the current item (a whole archive is finished first). Each pending file has a checkbox (all checked after every reload; a header checkbox per system, and **Select all** / **Clear selection**); **Import selected (n)** ingests only the checked files and leaves the rest in place. It is disabled when nothing or everything is checked. Ingestion needs the DATs of every system, Switch's titledb file included: until they've been downloaded the page shows a link to **Admin → DATs** instead of the import buttons, and both imports return `409 DatsMissing` (also for a selection without Switch files).
- **Delete** (the trash button on a row, or **Delete selected (n)** for the checked files) permanently deletes pending files from the ingest folder, with their pending Review items. It can't be undone. A confirmation lists up to 10 files as `system/name`. **Shift+click** on a row's delete button skips the confirmation, except for a `.zip`/`.7z` archive, which always asks; **Delete selected** always asks. Delete buttons are disabled while a job runs.
- **Failed files** lists, per system, the files in its `_failed/` folder with the reason from their `.error.txt` (`—` when there is none), size and time, 20 per page. Its checkboxes start empty after every reload. Deleting a failed file (same buttons and rules as above) also deletes its `.error.txt`. Files in `_duplicates/` aren't listed; those in `_removed/` are on [Deleted ROMs](#deleted-roms).
- **Last runs** lists the 10 most recent runs with their outcome counts; open one for the details.

What happens to each file:

| Outcome | Meaning | The file |
|---|---|---|
| Ingested | identified and added to the library (new game or new release) | deleted from ingest |
| Repaired | a byte-identical copy of a library ROM that integrity had flagged as damaged or missing | deleted, library entry rewritten |
| Duplicate | already in the library | moved to `_duplicates/` |
| Review | not in the DATs, or matches a game that several library games share | stays in ingest; shown in the Review queue |
| Failed | not a usable ROM (wrong type, too small/large, invalid header, unsafe or corrupt archive, dismissed) | moved to `_failed/` with a `.error.txt` explaining why |
| Error | a problem on the server's side (disk, database) | left in place; the next run retries it |
| Skipped | changed in the last 10 seconds | left for the next run |

Box art and snaps come from libretro-thumbnails, or for Switch from the image URLs titledb lists (Nintendo's `img-eshop.cdn.nintendo.net`, PNG or JPEG); a game gets the placeholder when none is found, which **Retry media** or **Integrity → Retry missing media** can fix later.

## External storage (Nintendo Switch and disc systems)

Each system either keeps its ROMs inside the game's ZIP (every cartridge system) or stores them **externally**: as plain files next to the ZIP. Switch names each file `<ZipBase>.<rom fileName>` (for example `roms/switch/O/Orbit Expedition.zip` and `roms/switch/O/Orbit Expedition.Orbit Expedition [0100000000010000][v0].nsp`); the disc systems keep each file's exact name (see [Disc sets](#disc-sets)). The ZIP still holds `info.json`, images and notes; `info.json` names each file ([format](zip-format.md#external-rom-files)). Every system in a family stores the same way, and the choice never changes for a system.

- **Ingest:** a Switch file is hashed in one streamed read, never loaded into memory, and its header is read from its first MiB. The title ID comes from the PFS0's ticket name (`<id>….tik`) when the header has one, else from the first `[0100…]` in the file name (XCI dumps don't carry it in the plain header). A header ID that isn't a Switch ID (such as a Switch 2 `0400…` ticket) means no match, whatever the file name says. The file is moved next to the ZIP right before the ZIP write and moved back if that write fails; it keeps its own extension (`.xci` stays `.xci`).
- **titledb matching:** the low bits of the title ID say what it is. A base game matches its own titledb entry; an update (`…800`) and DLC (including DLC data patches and application deltas) match through their base game's entry, and are stored in the base game's ZIP flagged `Update` or `DLC`. The release is named from its own entry when titledb has one (else the base name, with ` (DLC)` for DLC), with `[<TitleId>][v<N>]` and `N` from `[v<N>]` in the file name; the identification method is `TitleDb`. An update also gets its version from the first `[x.y.z]` tag in the file name (`DREDGE[UPD][1.0.1].nsp` → `1.0.1`), added to its name as `[<TitleId>][v<N>][1.0.1]` so two updates of a game never clash, and shown on the Game page's Updates tab. A file whose title ID comes from its name (no ticket in the dump) and is a base game's ID, but whose name contains `[UPD]` (any case), is taken as that game's update; a title ID read from the file itself is never changed by `[UPD]`. The base game's release is the primary one even when it's flagged Hack; updates and DLC are primary only when no base release is left. A new game takes its year, publisher and genres from the base entry. Anything titledb doesn't cover goes to Review (`NoDatMatch`, with titledb suggestions), or fails `InvalidHeader` when the header isn't a PFS0 or XCI.
- **Downloads:** each release downloads its own file, with HTTP range support (downloads can resume); **Download ZIP** returns the metadata ZIP only.
- **Edits** work as for every system and need the same `rom-manager` role and the same global job lock (rating, favourite and notes stay open to every signed-in user). A title edit renames the ZIP and every file together (a disc system's files keep their names, and move only when the letter folder changes); moving or merging a release moves its file next to the target ZIP; deleting a release or game moves its files to `ingest/switch/_removed/`. Any failure moves the files back.
- **Integrity** checks every external file's length on each run and its SHA1 on a deep run (`EntryMissing`, `EntrySizeMismatch`, `HashMismatch`), and reports files in a system folder that no game lists as `OrphanFile`. Ingesting a byte-identical copy repairs a missing or damaged file, as for embedded ROMs.
- **Library Size** counts each game's ZIP plus the recorded sizes of its external files (a disc set's other files included), including files that are missing.

### Disc sets

PlayStation, PSP, GameCube, Wii, Xbox 360 and Saturn are identified against the libretro [Redump](http://redump.org/) DATs (`metadat/redump/`), which have no year, developer, publisher or genre files, so their games have none of those until you edit them. Their files are stored externally under their **exact names**: no `<ZipBase>.` prefix and no ` (2)` suffix.

- **Wii WBFS:** if a `.wbfs` file has no SHA1 match, ingestion uses the first four characters of its Wii game ID to look up Redump serials, then filters by disc number and revision. One match stores the file under the DAT ROM stem with its `.wbfs` extension and own hashes, identified by `Game ID`. With zero or multiple matches, a valid WBFS header sends it to Review.
- **Sets (PlayStation, Saturn):** each run first groups every loose file in `ingest/psx/` or `ingest/saturn/` by its `.cue`: a cue (at most 64 KiB, `FILE "<name>" BINARY` lines) and the `.bin` tracks it names are one set, processed together even in an **Import selected** run when any one of them is checked. The set's data track is the one track whose hash is in the DAT; the game is stored as one release whose main file is that track, with the cue and the other tracks as its **files**, each under its own name next to the ZIP.
- **Waiting sets** stay in ingest, `Skipped`, and are retried on the next run: `IncompleteSet` when a file the cue names is missing (or the cue can't be read; then the `.bin` files starting with its name wait too), or when a lone `.bin` matches a `(Track N)` data track whose cue hasn't arrived; `UnsupportedSetMember` when the cue names something other than a `.bin`; `SetConflict` when two cues name the same file; `AmbiguousGroup` when two or more games share the data track's title; `AlreadyInReview` for an unmatched track whose bytes are already queued (silent audio tracks repeat). A track that's too small or too large fails on its own and the rest wait as `IncompleteSet`.
- **No match:** every member goes to Review as `NoDatMatch`; when two or more tracks match the DAT, as `AmbiguousSet`. A complete unmatched set is resolved in Review as one release from any of its members (see [Review queue](#review-queue)); an `AmbiguousSet` member, or a `.cue`/`.bin` whose set isn't complete in ingest, can only be deleted. A lone `.iso`, `.wbfs` or `.nrg` can be resolved.
- **Single files:** an `.iso` (or a `.bin` no cue names, matching a single-track DAT entry) is one release with no other files, named after the DAT entry. A `.cue`/`.bin` in `ingest/psp/`, `ingest/gc/`, `ingest/wii/` or `ingest/x360/` fails `UnsupportedType`.
- **Archives:** a `.zip` or `.7z` in a disc system's folder is `Skipped` `ArchiveNotSupported` and left in place; drop disc images loose.
- **Names:** a name already used in the target folder stops the import (`Error` `NameTaken`, nothing moved), and a name over 250 UTF-8 bytes is `Error` `NameTooLong`; rename the file and ingest again. Title edits, moves and merges refuse a taken name with `409 NameTaken` before any file moves; within one letter folder the files don't move at all.
- **Edits and integrity:** every file of a set moves with its release (move, merge, a title edit to another letter folder) and goes to `_removed/` with it; integrity checks each file's length (and hash on a deep run) and reports a missing track by its name. Dropping the whole set again repairs a missing or damaged cue or track.
- **GameCube / Wii header:** the release's header shows the disc's game id, disc number, version and title.

## Job detail

`/jobs/{id}` (Admin) shows any job (ingestion, integrity check, DAT refresh, media retry, review resolution): status, start and finish time, how it was started, its summary (counts, or a review resolution's `reviewId`, `fileName`, `gameId`, `code` and `errors`; a value that isn't text or a number shows as JSON) and any error, with live progress while it runs, plus a **Current file** row with the same per-file bar while a large file is hashed or copied. For an ingestion it also lists every item with its outcome, reason and details (filter by outcome), and links each ingested file to its game.

`POST /api/jobs/{id}/cancel` (Admin) cancels the running job: `202`, `404` when that job isn't running, and `409 NotCancellable` ("This job can't be cancelled.") for a review resolution.

## Review queue

`/review`, the **Review Queue** (Admin; the navbar badge shows how many are waiting), lists files ingestion couldn't place: file, system, size, the title from the cartridge header, the reason and when it was added. Open one to see its hashes and header and choose a resolution:

Filter the list by file name or header title (case-insensitive substring), system and reason. Text applies after 300 ms; filters and page are kept in the URL and saved in this browser. An explicit URL wins; opening `/review` without filter parameters restores the saved view. **Clear** removes both URL and saved state. A filtered empty list says "No review items match this filter."

- **Not in the DATs** (`NoDatMatch`):
  - **Suggestions:** up to five DAT entries with similar names, with a match score. **Use** adds the file as an *unverified* release of that entry (its hashes differ from the DAT's, so it gets an `(Unverified)` file name and flag). For Switch the entries come from titledb (`<title> [<TitleId>]`, no size shown), the page says "Choose a titledb result to identify this release by title ID." and **Use** stores the release exactly as automatic matching would for that ID (method `TitleDb`, no `Unverified` flag), named from the file's own `[v<N>]` and extension. One **This file is an update** checkbox above the suggestions and the search results (ticked to start with when the file name contains `[UPD]`, any case) applies to every **Use**: ticked, a base game's entry stores the file as that game's update (its ID + `800`), and an update's entry as that update, flagged `Update` with its version and the toast "Added update of <entry>."; ticking it for a DLC entry is refused.
  - **Search the DAT** finds other entries by name; **Use** works the same way.
  - **Attach to a game as a hack or translation:** pick the game, choose Hack or Translated. On a disc system you can also choose **Disc** with a disc number (1–99, required) to add the file as another disc of any game of the system: it takes the game's title and its primary release's regions, languages and revision, gets the flag `Disc <n>`, and keeps its own file name plus ` (Disc <n>)` (not added twice when the name already has it).
  - **Manual entry:** title, regions, languages, flags (comma-separated) and revision, plus an optional **Disc** number (1–99) on a disc system, which becomes the flag `Disc <n>` after the other flags (a typed `Disc <n>` flag is replaced); the resulting file name is previewed. If several games already have that title, attach it to one of them instead.
- **Unmatched disc sets** (a `.cue` and its `.bin` tracks, all `NoDatMatch`): every member's page shows a **Set** card listing the files ("Resolving this item adds all N files as one release."), and any member's page resolves the whole set with the same tabs: a DAT pick (every file must fit the chosen system), Attach (Hack, Translated or Disc) or Manual. The set becomes one release whose main file is the cue's first track (track 1, the data track by convention), with the cue and the other tracks as its files, each under its own name. A set whose track 1 is already in the library is refused as `Duplicate`, and nothing moves. A set member has no **Dismiss**. Limits: a set with an `AmbiguousSet` member, with a member that ingest skipped as `AlreadyInReview` (its bytes were already queued from another file, so it has no row of its own), or inside an archive can only be deleted.
- **More than one track matched** (`AmbiguousSet`, disc systems): two or more tracks of a set matched the DAT, so the set can't be stored; it can only be deleted.
- **Disc track files without a set** (a `.cue` or `.bin` of a disc system whose set isn't complete in ingest): the item page shows "Disc track files must match the Redump DAT to be imported." instead of the tabs, with no Dismiss button; only **Delete** remains. Fix the files (or refresh the DATs) and drop the whole set again.
- **Several games share its title** (`AmbiguousGroup`): the file matched a DAT entry by hash or a Wii WBFS game ID, and more than one library game has that title (e.g. after a move). Pick the game to **Attach** it to. The release keeps the original identification method.
- A file resolved with a DAT entry (picking a DAT game, or Attach for `AmbiguousGroup`) is stored with the DAT ROM name's extension (a Game Gear SMS-mode game stays `.sms`); when the DAT lists the chosen game more than once (Atari 7800 has `.a78` and `.bin` entries), the entry with the file's own extension is used, else the first; Manual entry and Hack/Translated attach use the system's first extension (`.gb`, `.col`, `.gg`, `.sms`, `.md`, `.32x`, `.pce`, …), except for Switch and the disc systems, where every resolution keeps the file's own extension. A disc image resolved with a DAT entry is named `<DAT game name> (Unverified)<ext>`.
- **Dismiss:** a loose file moves to `_failed/`; an archive is left as it is.
- **Delete** (on the item page, and the Delete button on each row of the queue): permanently deletes the file from the ingest folder after showing everything known about it in a dialog titled "Delete File: <file name>". For a file inside an archive, the whole archive is deleted, including every other file in it (the dialog warns). Every pending item from the same file or archive goes with it. Hold **Shift** while clicking Delete on either page to skip confirmation for a loose file; an archive always requires confirmation. Success names the deleted file, the queue reloads (moving back a page if necessary), and item-page deletion returns to the queue with its saved filter.

**Several at once:** tick rows (or the header box for the whole page; it shows a dash when only some are ticked). The selection is kept while you page through the same filter and cleared when the filter changes. **Delete selected (n)** asks first, listing up to 10 file names (`… and n more`) and warning when an archive entry is selected (it deletes its whole archive, other pending items included); **Shift+click** skips the question unless an archive entry is selected. The toast says how many were deleted and how many couldn't be; items already removed with their archive are skipped quietly.

The queue is paged (10–100 rows, your choice remembered per browser). An item's page shows the file details and header on the left and the ways to resolve it as tabs on the right: Suggestions (when there are any), Attach and Manual for `NoDatMatch` (an unmatched set's members included), Matched DAT entry for `AmbiguousGroup`, and none for a disc track file without a set.

**Google it** in every item header opens a new tab with a quoted name, system name and `rom`. A header title with at least three letters or digits is preferred, otherwise the filename without its extension; parenthesized/bracketed tags are removed, underscores and dots become spaces. An empty cleaned name falls back to CRC32. These links only contact Google when clicked.

Every resolution runs as a background job (`ReviewResolve`), so a multi-GB Switch or disc image is hashed and moved without holding the request open. While it runs, every review item page shows "Resolving <file>…" with a spinner and the current file's step bar (`Hashing`, `Copying to library`), and disables its actions. On the item's own page, a resolution that ends opens the game, or shows its error as an immediate failure would. If the file was removed from the ingest folder in the meantime, the item disappears with a message and you're back in the queue. If you've left the page, you're never taken anywhere: a toast says "<file> added to the library." with an **Open game** link, or "Resolving <file> failed: <code>." with an **Open review item** link (none when the source is gone). Toasts with a link stay until you close them. A resolution can't be cancelled: the Ingestion and Integrity pages show no Cancel button for it. After a full reload, or in another tab, the page doesn't know about the running resolution, and its actions get the usual "Another job is running" toast; a resolution whose job row stays `Running` (its final update failed) keeps the pages busy until a reload.

A `DbWriteFailed` result means the file and ZIP are already in the library and only the database update failed: the next ingest or integrity run brings the database in line. For a disc set, the set's rows then stay Pending but can't be resolved (their files are gone from ingest); **Delete** clears them one member at a time, and the next ingest run removes them too. A failure after the file was moved, whose move back put the file under a new ` (2)` name in `ingest/switch/` but couldn't update the Review item, also returns `DbWriteFailed`, naming both paths: once the original path is free, move the recovered copy back to it, or simply run ingestion again.

## Deleted ROMs

`/deleted` (Admin; navbar **Deleted ROMs**, with a badge counting the files) lists the ROMs that library edits (deleting a release or a game) moved to `ingest/<system>/_removed/`. Each system has a card (its badge, name and file count) with its files, 20 per page: name, size and modified time (an external system's file keeps its original time). **Select all** ticks every file of every system.

- **Restore** (per file, or **Restore selected (n)**) moves the files back to `ingest/<system>/` (a pending file of the same name is never replaced; the restored one gets ` (2)`…) and starts an import of just those files; the toast links to the job. If the import can't start (DATs missing, another job just began), the files wait on Ingestion. A file deleted less than 10 seconds ago is skipped by that import as too recent and also waits on Ingestion. Restore a disc set's `.cue` and tracks together, or each goes to Review on its own.
- **Delete** (per file, or **Delete selected (n)**) deletes the files permanently after a confirmation listing up to 10 of them; **Shift+click** skips it. It can't be undone.

Both are disabled while a job runs. Every restore and delete is audited.

## Reports

`/reports` opens **Library Size**. Every signed-in user can use all three report tabs:

- **Library Size:** total bytes (each game's ZIP plus the recorded sizes of its external files, a disc set's other files included, missing ones included) and game count, a treemap, and an equivalent table with sizes and percentages. Click a system tile or table link to drill into `?system=<id>`; Back returns to the library view. Game tiles and links open the game. Systems use the same colours as their badges. The system treemap draws the 300 largest games and one unclickable "n others" tile; the table lists every game. Empty libraries or systems show an empty state.
- **Missing Images:** filter by system and page through games with **No cover** or **Placeholder art**. A game matching both appears once as No cover. A placeholder that is not the cover does not count. Game links open the Images tab. An empty report says "Every game has a cover image."
- **Duplicates:** groups of games in the same system that share a release base title, compared without case or accents. This does not compare hashes, DAT names or games across systems. Filter by system and page through the groups. A game may appear in several groups. Each row shows title, releases, ZIP size and added date. ROM managers can choose a merge target (most releases, then oldest, suggested first), confirm **Merge into selected**, or **Dismiss**. Other users see the list. Dismissal hides that membership until a game joins or leaves the group. Merge can stop part way through; the error reports how many sources already merged. Empty: "No duplicate games found."

Missing Images and Duplicates keep their system and page controls in page state.

## Integrity

`/integrity` (Admin) keeps the library and database consistent.

- **Status:** the last quick and deep check and the next scheduled quick check (daily at `Integrity:QuickCheckTime`, see [configuration](configuration.md); "Not scheduled" when disabled).
- **Game checks:** adding the first real box art to a game whose cover is the placeholder runs a deep-strength check of that game's ZIP and files only (an `Integrity (Game)` job in Jobs and in the recent runs; cancellable). It resolves only that game's issues, never orphan or duplicate ones, and doesn't count as the last deep check.
- **Run quick** opens only ZIPs that changed since the database last saw them; **Run deep** opens every ZIP and re-checks every file's hash; while it re-hashes a Switch ROM, a second bar shows that file's `Hashing` progress. **Retry missing media** looks up box art and snaps for every game that has a placeholder or no snap. While a job runs, its progress and **Cancel** take the buttons' place.
- **Issues:** what the checks found, filtered by status (open by default) and type, linked to the game where there is one. Database differences are repaired automatically and listed as *AutoRepaired*; problems with the files themselves are reported, never fixed by moving or deleting files. A damaged ROM can be repaired by ingesting a byte-identical copy.
- **History:** the last 10 integrity checks and media retries.

## Reference: behaviour and API

The sections below describe what happens behind each page in detail, with the API endpoints the UI uses. Every `/api` call except sign-in needs a session; POST, PATCH and DELETE also need the antiforgery header (the UI handles both).

### Ingestion review queue

An unmatched ROM with a plausible header stays in ingest and creates a `Pending` review item with outcome `Review NoDatMatch`. A headerless ROM uses its ingest folder's system. If DAT identification succeeds but several games own the same system and base title, the item becomes `Review AmbiguousGroup`; it stores the DAT identity and candidate game IDs.

Unmatched items include up to five suggestions for distinct base titles from the classified system's loaded DATs. The scorer compares the header title and original filename stem, using the higher of token overlap and edit similarity, plus a size-match boost. Each base title contributes its highest-scoring release; ties use ascending ROM name. Suggestions below 0.4 are excluded, and suggestions refresh whenever the file is processed again.

Files behind pending items are processed on every ingest run. If a file becomes DAT-matched and is ingested, its review item becomes `Resolved` with the resulting game ID. Other non-review outcomes remove its pending row; files skipped because they are too recent retain their row. A copy at another source path becomes a duplicate while the original review remains pending. Missing pending sources are removed at the start of the run.

Re-dropping a dismissed loose file resets it to pending and processes it again. For an archive, the review item records the archive path and entry name. Review or error outcomes keep the archive in ingest. A dismissed entry in the same archive fails with reason `Dismissed`, causing the archive to move to `_failed/` unless another entry still needs review or encounters an error. A duplicate previously resolved from the same archive counts as ingested when choosing the archive's fate, allowing a fully resolved archive to be deleted on its next run.

### Resolve reviews through the API

All review endpoints require an `admin` session, and POST and DELETE requests require the antiforgery header.

- `GET /api/review?status=Pending&page=1&pageSize=48` lists pending items (maximum page size 200), including `isArchive`. Optional `system`, `reason` (`NoDatMatch` / `AmbiguousGroup` / `AmbiguousSet`) and `q` filter both rows and total. `q` matches the original file name or header title, is trimmed, at most 100 characters, and matches `%`, `_` and backslash literally. Blank `q` is absent; unknown system/reason or an overlong search gives `400 ValidationFailed`. `Resolved` and `Dismissed` history can also be listed.
- `GET /api/review/{id}` returns `systemName`, the header, hashes, suggestions, queued DAT identity and candidate games, and:
  - `resolvable`: `false` for a disc system's `.cue`/`.bin` item whose complete unmatched set isn't found (it can only be deleted), `true` otherwise, so also for a complete unmatched set's member;
  - `dismissible`: `false` for every `.cue`/`.bin` item of a disc system;
  - `fileSets`: whether the item's system is a disc system (disc numbers apply);
  - `setMembers`: the unmatched set the item belongs to, `[{ reviewId, fileName, sizeBytes }]` cue first, or `null`.
- `GET /api/dat/search?system=gb&q=Tetris&limit=20` searches loaded DAT game names using a case-insensitive substring (up to 20 results), each game name once (the Redump DATs repeat a game per serial).
- `POST /api/review/{id}/resolve` accepts `Dat`, `Attach` or `Manual` actions, checks the request and the item, and starts a `ReviewResolve` job: `202 { jobId }`. Only these answers are synchronous: `400 ValidationFailed` for the request, `404` for an item that doesn't exist or isn't Pending, `409 SetFileNotResolvable`, and `409 JobRunning` while another job runs. Everything else arrives in the job's summary (`GET /api/jobs/{jobId}`): `{ reviewId, fileName, gameId, code, errors }`, with `gameId` set and `code` null on success. The job has one item per review row it acted on (`Ingested` with the game, or `Error` with the code as its reason). An optional `update: true` (only with `Dat`, a titledb system, and a base or update entry) stores the pick as an update; otherwise it's `400 ValidationFailed` on `update` and nothing changes.
- `POST /api/review/{id}/dismiss` returns 204 (`409 SetFileNotResolvable` for any `.cue`/`.bin` item of a disc system). Loose files move to `_failed/` with a `Dismissed` sidecar; archives stay in place until the next ingest run.
- `POST /api/review/delete` with `{ "ids": [1, 2] }` deletes several items at once: 1–500 distinct positive ids (else `400 ValidationFailed`, field `ids`). Under one job lock (`409 JobRunning`, nothing deleted) each id is deleted as `DELETE /api/review/{id}` does, in order; an id that's unknown or no longer `Pending` (for example removed with its archive earlier in the batch) is skipped. It returns `200 { deleted, skipped, failed: [{ id, code }] }`. The SPA sends larger selections in batches of 500.
- `DELETE /api/review/{id}` returns 204. It deletes the source from the ingest folder (the loose file, or the whole archive), then every `Pending` item with the same source path (loose file) or archive path; resolved and dismissed rows stay as history. Only a `Pending` item can be deleted (`404 NotFound` otherwise). A source that is already gone still removes the rows and returns 204. A file that can't be deleted (locked, no permission) returns `500 DeleteFailed` and changes nothing.

`Dat` takes `datSystem` and `datGameName` for a NoDatMatch item. The selected DAT game supplies naming, tags and metadata from its ROM: the one with the source file's extension when the DAT lists the game more than once, else the first (the DAT search still lists each game name once, with its first ROM's name and size); the release keeps its actual hashes, uses Manual identification with the selected DAT identity, and gains an `Unverified` flag and filename suffix. On a disc system the file is named `<datGameName> (Unverified)<source extension>` and its tags come from the DAT game name.

`Attach` takes `targetGameId` and `flag` (`Hack`, `Translated`, `None` or `Disc`). Hack/Translated attachments use the target game's title as their base title, empty regions/languages, null revision and only the selected flag. `None` is available only for AmbiguousGroup items and requires one of their candidate games; it keeps the queued DAT identification and normal DAT filename. `Disc` (disc systems only) takes `disc` and adds the file as a release of any game of the system, with the game's title, its primary release's regions, languages and revision, and the flag `Disc <n>`.

`Manual` takes `title`, `regions[]`, `languages[]`, optional `revision`, `flags[]`, and an optional `disc` (disc systems only), which becomes the flag `Disc <n>` after the other flags. Naming uses the title, regions, revision and flags; the release receives no DAT metadata. DAT and Manual actions group into existing games using the same rules as ingestion. Multiple candidates fail as `AmbiguousGroup`; choose Attach to select the game.

`disc` is 1–99 (`400 ValidationFailed` on `disc` otherwise), allowed only with `Manual` or `Attach` with flag `Disc` (where it's required); on a system that isn't a disc system the job fails with `ValidationFailed` on `disc`.

Resolving any member of a complete unmatched bin/cue set resolves the whole set as one release (track 1 as the main file, every file under its own name, all or nothing) and marks every member Resolved in one transaction.

The job runs under the global job lock and can't be cancelled; dismissal and deletion take the lock themselves (`409 JobRunning` when busy). A missing source fails as `SourceMissing` and removes its stale review row. Successful resolution records the game, Admin and UTC time, then deletes a loose source; resolving an archive entry leaves its archive in place. Changed source bytes fail verification.

Failures retain a Pending review for retry. The summary's `code` is the failure: `ValidationFailed` (with `errors`), `NotFound` (also a missing Attach target), `SourceMissing`, `AmbiguousGroup`, `TargetZipUnreadable`, `InfoJsonNewerSchema`, `Duplicate`, `SetFileNotResolvable` (a set no longer complete), `NameTaken`, `NameTooLong` (a disc system's name already taken in the folder or over 250 UTF-8 bytes), `IoError`, `VerifyFailed` or `DbWriteFailed`. A DB mirror failure can leave a verified ZIP on disk; the next ingest pre-pass repairs the DB from that ZIP before processing sources, as with normal ingestion.

### Browse the library through the API

Every signed-in user, whatever their roles, can read the library. Lists and details come from the database mirror; images and ROM bytes are streamed from the game's ZIP.

- `GET /api/systems` lists every registered system, sorted by display name (case-insensitive), with its `shortName` (such as `GB`), game count, ROM count and the distinct regions of its ROMs (sorted). Systems without games report zero counts and no regions. Every system list in the UI (Library, collection, Review, Duplicates, Missing images and Audit filters) shows them in this alphabetical order.
- `GET /api/games` returns a page of `{id, system, systemName, systemShortName, displayTitle, releaseYear, regions[], romCount, boxArtUrl, primarySizeBytes, rating, favourite, matchedOn, updateCount, playRomId, playRomFileName, browserCore}` (`updateCount` counts the releases flagged `Update`, while `romCount` still counts every release; `playRomId` and `playRomFileName` are the primary release (lowest id if several) when the system has a browser core and that release is in the ZIP, else `null`; `browserCore` is the system's core or `null`; `systemName` is the system's display name and `systemShortName` its short name such as `SNES`, each the id if it isn't registered; `boxArtUrl` is the cover image; `primarySizeBytes` includes a disc set's other files) (48 per page by default, maximum 200; a page past the end is empty).
  - `system` must be a registered system id. `letter` is `#` or `A`–`Z` (any case) and matches the ZIP's letter folder; send `#` as `%23`.
  - `region` matches a game when any of its releases has exactly that region. `q` is split on whitespace into at most 8 distinct words (more is `400`), and a game matches when every word is a case-insensitive substring of the display title, title, developers, publishers or genres; `%`, `_` and `\` match literally. With `q`, `matchedOn` is `{field, value}` (`developer`, `publisher` or `genre`, and the first matching value in that order) when no word matched a title, else `null`. `favourite` is exactly `true` (only favourites) or `false` (only the others).
  - `collection` (a collection id of yours) lists only that collection's games, with every other filter still applied; not a GUID → `400` (field `collection`), someone else's or unknown → `404`. With it, `added` sorts by when each game was added to the collection.
  - `notInCollection` (a collection id of yours) leaves out that collection's games, with every other filter still applied (combined with `collection` for the same id the result is empty); not a GUID → `400` (field `notInCollection`), someone else's or unknown → `404`.
  - `sort` is `title` (default), `year`, `added`, `rating` or `relevance`; `dir` is `asc` or `desc`, defaulting to `asc` for title/year and `desc` for added/rating. Games without a year (or rating) are listed last in both directions; equal ratings are ordered by title, other equal values by game id.
  - `relevance` scores each game: 100 when a title equals `q` (whitespace collapsed), 60 when a title starts with it, and per word 40 if it's in a title, 20 in the developers, 20 in the publishers and 10 in the genres; highest first, then by title. It ignores `dir`, and without `q` it sorts by title.
  - Invalid values return `400 ValidationFailed` with a per-field `errors` object.
- `GET /api/games/facets` returns the Library filter counts: `{systems: [{id, count}], regions: [{region, count}], letters: [{letter, count}]}`. It takes `system`, `letter`, `region`, `q` and `favourite`, validated as for `GET /api/games` (same `400 ValidationFailed` errors); other keys (`sort`, `page`, `collection`, …) are ignored. Each list counts the games matching every filter except its own (so `systems` ignores `system`), lists only values with at least one game, and is ordered ordinally; a game counts once for each distinct region among its releases.
- `GET /api/games/{id}` returns the game's `info.json` fields (without `schemaVersion` and `metadata.appVersion`) plus `id`, `systemName`, `browserCore` (the EmulatorJS core that plays the system in the browser, `gambatte`, `mgba`, `handy`, `virtualjaguar`, `beetle_vb`, `a5200`, `prosystem`, `stella2014`, `gearcoleco` or `smsplus`, else `null`; every response that returns the game detail carries it) and `hasDefaultBoxArt` (`rating` and `favourite` included). `roms[]` lists the primary release first, then by file name, with identification and hashes flattened (`identificationMethod`, `datName`, `crc32`, `sha1`, `sizeBytes`, …), an update's `version` (else `null`), the parsed `header` and a `downloadUrl`, plus `files` (`null`, or a disc set's other files in order, each `{id, fileName, sizeBytes, crc32, md5, sha1, downloadUrl}`) and `totalSizeBytes` (`sizeBytes` plus every file). `images[]` holds `id`, `type`, `fileName`, `source`, `isDefault`, `isCover`, `sizeBytes`, `width`, `height` and `url`.
- `GET /api/games/{id}/images/{imageId}` returns the PNG or JPEG (by file extension) with `ETag` set to its SHA1 and `Cache-Control: private, max-age=86400`; a matching `If-None-Match` returns 304.
- `GET /api/games/{id}/download` returns the game's ZIP with range support and an RFC 5987 `filename*` in `Content-Disposition`.
- `GET /api/games/{id}/info-json` returns the stored `info.json` bytes as `application/json`, even if invalid JSON. A missing game, ZIP or entry returns `404 NotFound`; an unreadable ZIP or an entry over 1 MiB returns `500 IoError` before sending the response.
- `GET /api/games/{id}/roms/{romId}/download` streams one ROM from the ZIP under its library file name.
- `GET /api/games/{id}/roms/{romId}/files/{fileId}/download` streams one file of a disc set under its file name, with range support; a file of another release, or a name another game also claims in that folder, is `404`.
- `GET /api/games/{id}/zip-entries` returns `{zipName, entries: [{path, sizeBytes, compressedSizeBytes, modifiedUtc}]}`: the ZIP's file name and every file entry (folder entries left out), ordered by `path` ordinally, with the central directory's sizes. `modifiedUtc` is the entry's stored time read as server local time (see [ZIP format](zip-format.md#writes)). An unknown game or a missing ZIP returns `404`; an unreadable ZIP `500 IoError`.
- `GET /api/games/{id}/zip-entries/download?path=<entry>` streams the file entry with exactly that name as `application/octet-stream`, named after its last path segment (RFC 5987 `filename*`), capped at its stored length. A missing or empty `path` returns `400 ValidationFailed` (`errors.path`); a name that isn't a file entry (a folder name, `../x`, …), an unknown game or a missing ZIP `404`; an unreadable ZIP `500 IoError`. The name is only looked up in the ZIP, never on disk. Downloads aren't audited.
- `GET /api/emulator/bios/{name}` (any signed-in user) streams a BIOS file from `Paths:Bios` ([configuration](configuration.md)) for the play page, as `application/octet-stream` without range support, and every response it gives is `Cache-Control: no-store`. `name` must be a whole file name of 1–64 letters, digits, `_`, `.` and `-`, starting with a letter or digit and not ending in a dot; it is matched against the folder ignoring case. An invalid name, a missing or empty file, a directory, a link or reparse point, or names that differ only in case return `404 NotFound`; a file that can't be read (a permission or sharing error) `500 IoError`. Signed out it's `401 Unauthorized`, and a session that must change its password gets `403 PasswordChangeRequired`. `HEAD` isn't mapped (`404`). Downloads aren't audited.

ROM and image ids change whenever a game is rewritten. A stale id, an image or ROM belonging to another game, or a ZIP missing from disk returns `404 NotFound`; an unreadable ZIP returns `500 IoError`. ZIPs are opened so that an ingest or edit can still replace them during a download.

### Collections through the API

Every route needs only a signed-in user and acts on your own collections: another user's collection id answers `404` exactly like a missing one. Mutations need the antiforgery header.

- `GET /api/collections?q=&page=&pageSize=` returns a page of `{id, name, gameCount, coverUrl, updatedAt}` sorted by name. `q` (at most 255 characters, 8 words) matches names containing every word, ignoring case and accents; `%` and `_` match literally. `gameCount` counts only games still in the library.
- `POST /api/collections` with `{name, notes?}` → `201` with `{id, name, notes, coverUrl, gameCount, createdAt, updatedAt}`; `PATCH /api/collections/{id}` with `{name?, notes?}` → `200` with the same (an absent field is unchanged; `notes: null` or `""` clears it); `GET /api/collections/{id}` returns it; `DELETE /api/collections/{id}` → `204` (memberships and cover files go with it). Names are trimmed, 1–100 characters; notes have `
` line endings, at most 65,536 UTF-8 bytes, whitespace-only meaning none. Errors: `400 ValidationFailed` (`name`, `notes`), `409 CollectionNameTaken`.
- `POST /api/collections/{id}/cover` (multipart `file`, PNG or JPEG, at most 8 MiB; `413 PayloadTooLarge` above) and `POST /api/collections/{id}/cover/from-url` with `{url}` (downloaded like a [game image from a URL](#edit-the-library-through-the-api), same errors) replace the cover and return the detail; `DELETE /api/collections/{id}/cover` removes it. `GET /api/collections/{id}/cover` (the `coverUrl`, `?v=` changing with each cover) streams it with `Cache-Control: private, max-age=86400`; `404` when there's none or its file is missing.
- `POST /api/collections/{id}/games` with `{gameIds: [...]}` (1–500 ids, else `400 gameIds`) → `200 {added}`: ids already in it, or not library games, are skipped. `DELETE /api/collections/{id}/games/{gameId}` → `204`, also when it wasn't there.
- `GET /api/games/{id}/collections` returns `[{id, name}]`: your collections holding the game, by name (`404` for an unknown game).

`updatedAt` changes only when a request changes something (an add with `added: 0` doesn't).

### Rate games through the API

`PATCH /api/games/{id}/rating` is open to every signed-in user and needs the antiforgery header. It takes `{rating?, favourite?}`: `rating` is a whole number 1–5 or `null` (clears it), `favourite` a boolean, and an absent property stays unchanged. Ratings are shared per game and stored in the ZIP's `info.json` ([format](zip-format.md)), so a rating rewrites the ZIP like any edit: it takes the global job lock (`409 JobRunning` while a job or another edit runs) and returns the full game detail, with new ROM and image ids. Errors: not an object, neither property, or a wrong value → `400 ValidationFailed` (field `""`, `rating` or `favourite`); an unknown game → `404`; a newer `info.json` schema → `409 InfoJsonNewerSchema`; a write failure → `500`. The `rom-manager` `PATCH /api/games/{id}` ignores `rating` and `favourite`.

Other edits keep a game's rating and favourite. A merge keeps the target's rating (or takes the source's when the target has none) and makes the target a favourite if either game was; a release moved to a new game starts unrated and not a favourite.

### Select ingestion files through the API

`GET /api/jobs/current` (Admin) returns the running job (`204` when idle): `id`, `type`, `mode`, `status`, `current`, `total`, `currentItem`, `startedAt` and `step`. `step` is `null` unless a streamed phase of the current file runs, else `{ "phase", "bytesDone", "bytesTotal", "bytesPerSecond" }`. `phase` is `Hashing` (an external ROM's ingest hash or a deep integrity re-hash), `CopyingToLibrary` (an external ROM copied into the library) or `Copying` (copied to `_failed/`, `_duplicates/` or back on a rollback); a same-volume rename reports none. `bytesPerSecond` is the average since the phase began, `null` for its first second or while nothing is done. Sizes in the app show in B, KiB, MiB, or GiB from 1 GiB up.

`POST /api/jobs/ingest` (Admin) accepts no body, or `{ "files": null }`, to import every pending file. `{ "files": [{ "system": "gb", "name": "x.zip" }] }` imports only those exact system/top-level filename pairs from the job's snapshot. Unknown systems/files, disappeared files and repeated entries are ignored. Unselected files stay untouched and produce no job items; progress counts the selected snapshot. Select an archive by its own filename. An empty list or missing/empty system/name gives `400 ValidationFailed`; malformed JSON is also `400`. Selection is rebuilt with everything checked whenever the UI reloads, and is not saved across page loads.

### Delete ingestion files through the API

`GET /api/ingest/failed` (Admin) returns, per registered system in registry order, `{ system, files: [{ name, sizeBytes, modifiedAt, reason }] }`: the top-level files of `ingest/<system>/_failed/` (missing folder → `[]`), ordered by name, without `.error.txt` sidecars. `reason` is the `reason:` line of the file's `.error.txt`, or null.

`POST /api/ingest/delete` (Admin) takes `{ "files": [{ "system": "gb", "folder": "pending", "name": "x.gb" }] }`, `folder` being `pending` (`ingest/<system>/`), `failed` (`ingest/<system>/_failed/`) or `removed` (`ingest/<system>/_removed/`, [Deleted ROMs](#deleted-roms); no Review rows are touched). A missing or non-JSON body, an empty list, more than 500 entries, an unregistered system, another folder, or a name that is empty, `.`/`..`, contains `/` or `\`, is hidden or OS junk, or (for `failed`) ends `.error.txt` gives `400 ValidationFailed` (`errors.files`) and deletes nothing. A running job gives `409 JobRunning`. Otherwise each entry is deleted in order (a file that's already gone counts as deleted; repeated entries are skipped): a failed file takes its `.error.txt` with it, and a pending file's `Pending` Review rows go once the file is gone (resolved and dismissed rows stay). A file that can't be deleted keeps its Review rows and sidecar and is reported; the rest continue. The response is `200 { deleted, failed: [{ system, folder, name }] }`. The SPA sends larger selections in batches of 500.

### Deleted ROMs through the API

`GET /api/ingest/removed` (Admin) returns, for each registered system with at least one file, in registry order, `{ system, files: [{ name, sizeBytes, modifiedAt }] }`: the top-level files of `ingest/<system>/_removed/`, ordered by name, without dot-files or OS junk.

`POST /api/ingest/restore` (Admin) takes `{ "files": [{ "system": "gb", "name": "x.gb" }] }`, validated as `POST /api/ingest/delete` entries with folder `removed` (`400 ValidationFailed`, field `files`; repeated entries are ignored). Under the job lock (`409 JobRunning`, nothing moved) each file moves from `_removed/` to `ingest/<system>/` under a free name (never replacing a file); a missing file or a failed move is listed in `failed`. Each move is audited as `RemovedRestored`. Then an ingest job starts for exactly the restored files under their new names. The response is `200 { restored, failed: [{ system, name }], jobId }`, `jobId` being null when nothing was restored or the job couldn't start (the files then wait on Ingestion). The job's 10-second `TooRecent` rule applies: a file written to `_removed/` just before (an embedded system's ROM is written when its release is deleted) is skipped and stays pending.

### Report APIs

Report GETs need any signed-in user. Paged responses are `{items, page, pageSize, total}`; page starts at 1, pageSize is 1-200, and an unknown system filter gives `400 ValidationFailed`.

- `GET /api/reports/library-size` returns `{totalBytes, gameCount, systems: [{system, systemName, bytes, gameCount}]}`, where a game's bytes are `games.zip_size_bytes` plus the recorded `size_bytes` of its external ROMs and their set files (missing files included). Systems with games are sorted by bytes descending.
- `GET /api/reports/library-size/{system}` returns `{system, systemName, bytes, games: [{id, displayTitle, bytes, romCount}]}`, sorted by bytes descending, then title. A registered empty system returns an empty list; an unknown system gives `404 NotFound`.
- `GET /api/reports/missing-images?system=&page=&pageSize=` defaults to 50 rows, sorted by system/title, each `{id, displayTitle, system, systemName, reason}` (`NoCover` or `Placeholder`). NoCover wins if both apply.
- `GET /api/reports/duplicates?system=&page=&pageSize=` defaults to 25 groups, sorted by system/base title. Each is `{system, systemName, baseTitle, gamesKey, games}`. Games contain `{id, displayTitle, romCount, zipSizeBytes, createdAt, boxArtUrl}`, ordered by releases descending, then oldest, then id.
- `POST /api/reports/duplicates/dismiss` (`rom-manager`) takes `{system, baseTitle, gamesKey}` and returns 204. `gamesKey` is the SHA-256 of sorted, comma-joined game ids. Repeated and stale dismissals are harmless. Unknown system, missing fields, baseTitle over 255 characters or a key other than 64 lowercase hex digits gives `400 ValidationFailed`.
- `POST /api/reports/duplicates/merge` (`rom-manager`) takes `{targetGameId, sourceGameIds}` (1-20 distinct sources, none the target) and returns `{targetGameId}`. It uses ordinary library merges, with the job lock taken per source. The first failure stops the loop and returns the ordinary problem plus `merged`, the source ids already moved. A `DbWriteFailed` source is included because its files changed. A job starting between sources can cause `409 JobRunning` after partial success.

### File action auditing

`GET /api/admin/audit` and `/api/admin/audit/actions` require Admin. The first returns `{items, page, pageSize, total}`, default pageSize 100 (maximum 200), newest time then highest id first. Each item has `{id, occurredAt, action, system, gameId, user, jobId, path, targetPath, details}`. Actions returns the available action names.

Filters: `action`, registered `system`, exact `user` (case/accent-insensitive username), `scheduled=true` (null user id), `q` (trimmed substring of path, target or details, at most 200 characters, LIKE characters literal), `from` inclusive and `to` exclusive (ISO 8601 instants with an offset). Blank user/q are absent. Scheduled plus user, unknown action/system, invalid dates, from >= to, or invalid paging gives `400 ValidationFailed`. The UI converts local From to midnight and local To to the next day's midnight, preserving local-day boundaries across daylight saving changes.

Rows record successful ingestion, ZIP repair, extension rename, failed/duplicate moves, archive/review deletion, ingest file deletion (`IngestFileDeleted`, details `pending`, `failed` or `removed`), restoring a deleted ROM (`RemovedRestored`, from `_removed/` to its new pending path), metadata edits, release/game deletion, image add/delete/cover, media fetch, release move, merge and DAT refresh. Review resolve/dismiss writes one file-action row with the requesting user (a resolve also carries its `ReviewResolve` job's id); job actions include their job id and the requester's username, while scheduled jobs have no user. Deleting the last release writes GameDeleted. No-op metadata/cover changes, media retries that write nothing, and already-missing review files write no row. Rating/favourite, reads, authentication, account/settings changes, integrity and temporary cleanup/rollback are excluded.

Paths use `roms/` or `ingest/` prefixes; archive entries appear as `ingest/<archive> › <entry>`. Paths outside both roots use only the filename. Events keep their username snapshot after account changes, and have no game/user foreign keys. Rows older than 30 days are purged at startup and daily at 00:05 UTC. Recording is best effort: a bounded queue and background writer keep file actions independent of log failures; failed/full writes are warned and dropped, and a crash can lose queued events. A ZIP changed before a DB mirror failure still gets a row. The log has no undo action.

### Edit the library through the API

Users with the `rom-manager` role can edit metadata, delete, move and merge, and manage images. These requests need the antiforgery header. Each edit takes the global job lock, so it returns `409 JobRunning` while a job or another edit runs. Every edit starts from the game ZIP's own `info.json`, writes the ZIP atomically, then updates the database.

- `PATCH /api/games/{id}` takes any of `title`, `releaseYear`, `developers`, `publishers`, `genres` and `description`, and returns the updated game (same shape as `GET /api/games/{id}`). Omitted fields stay unchanged; `releaseYear` and `description` accept `null` to clear them.
  - `title`: 1–255 characters after trimming, and it must not sanitize to an empty file name. `displayTitle` is always derived from it.
  - `releaseYear`: `null` or 1970–2100. Each list: at most 20 items of 1–255 characters, trimmed with duplicates removed. `description`: at most 4000 characters.
  - A title change renames the ZIP (`roms/<system>/<letter>/<title>.zip`, with ` (2)`, ` (3)`, … if another game already has the name). On a disc system the external files keep their names; if the letter folder changes they move with it, and a name already taken there is `409 NameTaken` with nothing moved. The new ZIP is written and committed before the old one is deleted. A change that only differs in letter case keeps the existing file, because file names compare case-insensitively.
- `DELETE /api/games/{id}/roms/{romId}` returns 204. It moves the ROM's bytes to `ingest/<system>/_removed/` (adding ` (2)`, … on a name clash), rebuilds the ZIP without it and recomputes the primary release. Removing the last release deletes the game.
- `DELETE /api/games/{id}` returns 204. It moves every ROM to `_removed/`, then deletes the ZIP and the game's rows.
- `POST /api/games/{id}/roms/{romId}/move` takes `{targetGameId}` (an existing game) or `{newGameTitle}` (a new game), and returns `{targetGameId}`. Both games' ZIPs are rebuilt with the primary release recomputed, and a game left without releases is deleted. A new game gets the metadata of the moved release's DAT entry and its own box art and snap lookup; an existing target's metadata and images stay as they are. If the source ZIP can't be rebuilt after the target was written, the target is put back.
- `POST /api/games/{id}/merge` takes `{targetGameId}` and returns it. Every release of the source moves into the target in one write; then the database is updated and the source ZIP deleted. The target keeps its title, metadata and cover, except that empty fields (year, developers, publishers, genres, description) are filled from the source. The source's non-default images are copied with new names (`boxart-NN` / `snap-NN`); its placeholder is dropped. A target placeholder is removed when the source brings real box art (and if it was the cover, the first such box art becomes the cover); a target without images takes the first copied one as cover. More than 20 images in the result is `409 TooManyImages`, with nothing changed.
- Move and merge targets must be a different game in the same system (`400 ValidationFailed` otherwise); an unknown target is `404 NotFound`. A moved release keeps its file name (with ` (2)`, … on a clash; on a disc system a clash, in the target game or the target folder, is `409 NameTaken` with nothing moved) and its base title. Later releases with that base title therefore follow it when it is the only game holding the title; if the source still holds it too, later releases go to review as `AmbiguousGroup`.

- `POST /api/games/{id}/images` (multipart: `file`, `type` = `BoxArt` or `Snap`) adds an image and returns the game. The format is detected from the bytes (PNG or JPEG, never from the file name) and the image is stored as `boxart-NN.png`/`.jpg` or `snap-NN.…` with the lowest free number. Box art replaces the placeholder (taking over as cover if the placeholder was); the first image of a game without images becomes its cover. Errors: `400 ValidationFailed` (field `file`: missing, over 8 MiB, not a PNG/JPEG, unreadable dimensions; field `type`), `409 TooManyImages` (20 already), `409 DuplicateImage` (same SHA1 already in the game), `413` for a request over 8 MiB + 64 KiB.
- `POST /api/games/{id}/images/from-url` (JSON `{url, type}`) downloads the image and adds it exactly like an upload, with `sourceUrl` set to the URL as sent; the audit row's details are `<fileName> from <url>`. In order: `400 ValidationFailed` before any download (`url`: required, at most 1024 characters, absolute `http`/`https` without user info; `type` as above), `404` for an unknown game (nothing downloaded), then the download: one GET, no proxy, no retries, at most 3 redirects, 15 seconds for the headers and the whole body, at most 8 MiB read. Every connection, each redirect included, must go to a public address (private, loopback, link-local, CGNAT, multicast, documentation, reserved and IPv6 tunnelling ranges are refused, checked on the resolved addresses at connect time); otherwise `400 ImageUrlBlocked`. Download failures are `502 ImageDownloadFailed` with the cause in `title`: `couldn't connect.`, `timed out.`, `too many redirects.` or `HTTP <code>.`. An empty, over-8 MiB or non-PNG/JPEG body is `400 ValidationFailed` on `url`. After that the upload's rules apply (`409 DuplicateImage`, `409 TooManyImages`, `409 JobRunning`, placeholder replacement); the download happens before the job lock is taken.
- `DELETE /api/games/{id}/images/{imageId}` removes an image and returns the game; `409 DefaultImage` for the placeholder. Deleting the cover moves it to the first remaining box art by file name, else the first remaining image, else the placeholder is added back as cover.
- `POST /api/games/{id}/images/{imageId}/cover` makes that image the cover and returns the game.

Image ids change on every write, so take them from the returned game. Removed ROMs stay in `_removed/` (ingestion ignores it) until an Admin restores or permanently deletes them on [Deleted ROMs](#deleted-roms) (`POST /api/ingest/restore`, `POST /api/ingest/delete` with folder `removed`). A ROM whose ZIP entry no longer matches its recorded SHA1 is still moved as it is; a listed entry that is absent from the ZIP has nothing to move and is skipped.

Errors: an unknown game, a ROM of another game, or a release the ZIP no longer lists return `404 NotFound`. A ZIP that can't be read or has a newer `info.json` schema returns `409 TargetZipUnreadable` or `409 InfoJsonNewerSchema` without changing anything. A corrupt entry returns `500 VerifyFailed`, and an IO failure returns `500 IoError`; in both cases the ZIP is unchanged and any copies already made in `_removed/` are taken back. `500 DbWriteFailed` means the ZIP changed but the database didn't; the next ingest or integrity run repairs the database from the ZIP.

### Retry missing media

Thumbnails come from libretro-thumbnails, looked up by the primary release's DAT game name first, then the other releases in rank order; releases without a DAT game name (Manual) are skipped. For Switch they're the box-art and screenshot URLs of each release's titledb entry (found by the `[<TitleId>]` at the end of its DAT game name), fetched as PNG or JPEG through a client that only talks to Nintendo's image host and never follows redirects; an image body that takes longer than 20 seconds counts as a failure. Both actions need the antiforgery header (the per-game retry the `rom-manager` role, the job the `admin` role), and take the global job lock (`409 JobRunning` when busy).

- `POST /api/games/{id}/media/retry` re-runs the lookup for one game whose box art is the default or missing, or which has no snap, and returns the game. A found box art replaces only a default one, and a missing box art gets at least the default. A found snap is added only when the game has none. The game is rewritten only when something changed; finding nothing still returns 200 with the game unchanged. Errors are the same as for the other library edits.
- `POST /api/jobs/media-retry` starts a `MediaRetry` job and returns `202 {jobId}`. It runs the same lookup for every game with the default box art, no box art or no snap, ordered by title. Games where every release is Manual are skipped. Per-game errors are logged and the job continues. The summary is `{updated, notFound, skipped, error}`; there are no job items.
- After 3 consecutive network failures (timeouts, connection errors, or 5xx/408 after retries; a 404 doesn't count), the job stops and ends `Failed` with the error `thumbnail host unreachable`. Games already updated keep their new media.

### Integrity checker

The `Integrity` job checks the library against its `info.json` files and the database. It runs as a quick check every day at `Integrity:QuickCheckTime` (see [configuration](configuration.md)), or on demand. It takes the global job lock (a scheduled run is skipped when another job is running) and never moves or deletes library files.

1. **Database repair.** Each ZIP's database rows are replaced from its `info.json`; rows whose ZIP is gone are deleted unless the same game id turned up at another path. Every repair is recorded as an `AutoRepaired` issue (`DbRowInserted`, `DbRowUpdated`, `DbRowDeleted`). ZIPs with a duplicate game id, or with a ROM another game already holds, keep their existing rows and are reported as `DuplicateGameId` / `DuplicateSha1`.
2. **Scan.** Every file directly in `roms/`, everything under a folder that isn't a registered system, and every non-ZIP file (including stale `*.zip.tmp`) under a system folder is an `OrphanFile`; these are never opened. Every `.zip` under a system folder is checked. A non-ZIP file a game in that folder lists as an external ROM isn't an orphan.
3. **Per ZIP.** Quick mode opens a ZIP only when its size or whole-second modification time differs from its database row; otherwise it checks only the location. Deep mode opens every ZIP and also recomputes the SHA1 of every ROM and image entry (`HashMismatch`). An opened ZIP is checked for `ZipUnreadable`, `InfoJsonMissing` / `InfoJsonInvalid` / `InfoJsonNewerSchema`, `EntryMissing`, `EntrySizeMismatch`, `EntryUnlisted`, `MissingBoxArt` and `DefaultBoxArt` (Info). Every ZIP is checked for `WrongLocation`: system folder, letter folder and file name must match its title (case-insensitively; a ` (2)`-style clash suffix is accepted). For an external system, each file the database lists is checked by length on every run (`EntryMissing`, `EntrySizeMismatch`) and by SHA1 on a deep run (`HashMismatch`), even when its ZIP isn't opened; linked or special files are never followed.

An issue found again updates the open issue with the same type, path and entry rather than adding a new one. A completed run resolves an open issue it didn't find again, but only if it actually performed that check: a quick run can't clear entry or `info.json` problems on a ZIP it didn't open, and only a deep run clears `HashMismatch`. Orphans and duplicates are re-checked by every run, and an issue on a ZIP that no longer exists is resolved. A cancelled run records what it found but resolves nothing.

At the end of each completed run, jobs started more than 180 days ago (with their items) and resolved or auto-repaired issues older than 180 days are deleted. The job summary holds `zips`, `opened`, `issues`, `newIssues`, `resolved`, `repaired`, `purgedJobs` and `purgedIssues`.

All integrity endpoints need an Admin session; the POST also needs the antiforgery header.

- `POST /api/jobs/integrity` with `{"mode": "Quick"}` or `{"mode": "Deep"}` starts a run and returns `202 {jobId}` (`409 JobRunning` when busy, `400 ValidationFailed` for another mode). Follow it with `GET /api/jobs/{jobId}`.
- `GET /api/integrity/status` returns `{lastQuick, lastDeep, nextScheduledAt}`: the latest job of each mode (or `null`) and the next scheduled quick check in UTC (`null` when the schedule is disabled).
- `GET /api/integrity/issues?status=&type=&page=&pageSize=` returns a page of issues, newest first. `status` is `Open`, `AutoRepaired` or `Resolved`; `type` is any issue type above.

### Release notes through the API

- `GET /api/games/{id}` gives each release `hasNote` (read from the ZIP's entry names; `false` for every release when the ZIP can't be opened) and `originalFileName`.
- `GET /api/games/{id}/roms/{romId}/note` (any signed-in user) returns the note as `text/markdown; charset=utf-8`; `404 NotFound` when the game, release or note doesn't exist; `409 NoteTooLarge` above 64 KiB.
- `PUT /api/games/{id}/roms/{romId}/note` with `{text}` saves it (`204`). Line endings become `\n`; empty or whitespace-only text deletes the note; more than 65,536 UTF-8 bytes, or a missing `text`, is `400` with a `text` field error.
- `DELETE /api/games/{id}/roms/{romId}/note` deletes it (`204`; `404` when there's none).

PUT and DELETE rewrite the ZIP under the job lock like any edit (`409 JobRunning`, `409 InfoJsonNewerSchema`); the game's fields, including `updatedAt`, don't change, and notes aren't audited (they're logged at Info).

### Keyboard shortcuts through the API

- `GET /api/auth/me/hotkeys` returns `{bindings: {<id>: string | null}}` for every editable action (`nav.library`, `nav.collections`, `nav.ingestion`, `nav.review`, `review.next`), defaults filled in.
- `PUT /api/auth/me/hotkeys` with `{bindings}` replaces your shortcuts (an action left out goes back to its default; `{}` resets all) and returns the result. Shortcuts are written `Ctrl+Alt+Shift+Meta+<Key>` (modifiers in that order); other orders and letter case are accepted and normalised. Unknown actions, `search`, bad formats and the rules above are `400` with field errors keyed `bindings.<id>`. Only shortcuts that differ from the default are stored (`users.hotkeys`). Bindings sent for actions your roles don't allow are ignored, and stored ones are kept.

Both are blocked until a forced password change is done.

### Database backups through the API

All three need `admin`.

- `GET /api/admin/backups` returns `{enabled, time, retention, timeZone, nextRunAt, running, lastResult: {at, ok, fileName, error} | null, backups: [{fileName, sizeBytes, createdAt}]}`, backups newest first. `nextRunAt` is UTC, `null` when disabled.
- `PUT /api/admin/backups/settings` with `{enabled, time: "HH:mm", retention: 1–365}` (all required) saves the schedule and reschedules at once; returns the GET body. Errors are `400` with field errors `enabled`, `time` or `retention`.
- `POST /api/admin/backups` runs a backup and waits for it: `201` with `{fileName, sizeBytes, createdAt}`; `409 BackupRunning` when one is already running; `500 BackupFailed` when it fails (the cause is in the log and in `lastResult`).

A scheduled run that finds a manual one running is skipped (logged at Info). The settings live in the `app_settings` table (`backup.enabled`, `backup.time`, `backup.retention`); missing rows mean the defaults.

### Admin settings, logs and About

- `GET /api/admin/settings` (Admin) returns the effective configuration: the same redacted model that is logged at startup (including every storage root, such as `paths.bios`, and `backup.restoreFrom`). The connection string has its password removed, and `adminInitialPassword` shows `***` when one is set.
- `GET /api/admin/logs/recent` (Admin) returns the last 20 log events the server holds in memory as a JSON array, oldest first (`[]` when there are none).
- `GET /api/admin/logs` (Admin) downloads `rnrommanager-logs-<UTC time>.zip`. It contains every `*.log` file in `Paths:Logs` (including today's file while the app is writing to it), `settings.json` (the redacted configuration) and `version.txt`.
- `GET /api/admin/logs/stream` (Admin) is a server-sent event stream (`text/event-stream`). It first sends the buffered events newer than the `Last-Event-ID` header (all of them when the header is missing, unreadable or newer than anything buffered), then each new event as `id: <number>` and `data: {time, level, logger, message, exception}`. Ids keep increasing across restarts. A `: keep-alive` comment follows every 15 seconds; at each one the stream ends if the user was disabled, lost `admin` or was signed out.
- `GET /api/about` (any signed-in user) returns `{version, licenses[]}`. Each licence entry is `{name, license, url}`, covering the app, libretro-database (CC BY-SA 4.0) and every direct NuGet and npm dependency. The list lives in `src/RnRomManager.Api/licenses.json`; a test fails when a dependency is added to `Directory.Packages.props` or `package.json` without an entry there.

Every `/api` endpoint's required role (anonymous, any user, `admin` or `rom-manager`) is checked by a single table-driven test that fails when a new endpoint has no entry.
