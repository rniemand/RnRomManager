# Adding a system

Everything system-specific lives behind one interface, `ISystemHandler` (`src/RnRomManager.Core/Systems/ISystemHandler.cs`). Core, the database, the API and the UI enumerate the registered handlers for folders, DATs, file extensions, size limits and filters; nothing outside a `RnRomManager.Systems.X` project knows about Game Boy. Adding SG-1000 means a new handler (or a project), one registration line, tests and docs, with no changes to the core.

## The contract

```csharp
public interface ISystemHandler
{
    string Id { get; }                            // "gb": folder name, info.json `system`, DB value
    string DisplayName { get; }                   // "Game Boy"
    string ShortName => DisplayName;              // "GB": game pickers' system badge
    string Family { get; }                        // "gameboy": handlers sharing classification and DATs
    IReadOnlyList<string> RomExtensions { get; }  // [".gb"], lower-case with the dot; [0] is used for renames
    long MinRomSizeBytes { get; }                 // smaller files fail as TooSmall
    long MaxRomSizeBytes { get; }                 // larger files fail as TooLarge
    string DatName { get; }                       // "Nintendo - Game Boy": DAT file names + thumbnail folder
    bool EmbedRomsInZip { get; }                  // true: ROMs inside the game ZIP; false: files next to it (no default)
    DatSource DatSource => DatSource.Libretro;    // Libretro (DATs, SHA1) or TitleDb (titledb, title id)
    string DatFolder => DatKind.NoIntro;          // libretro folder of the main DAT: "no-intro" or "redump"
    IReadOnlyList<string> MetadatKinds => DatKind.Metadat;  // metadat files fetched: all four, or [] (none)
    bool FileSets => false;                       // true: exact external names, cue/TOC/CloneCD/MDS sets, Review limits
    bool LegacyEmbeddedRoms => false;             // true: an external system whose older games may still hold their ROMs
    bool RomStorageConfigurable => false;         // true: an Admin may switch EmbedRomsInZip (ROM Zip Config)
    bool DefaultEmbedRomsInZip => EmbedRomsInZip; // EmbedRomsInZip with no stored setting; the registry checks this
    bool KeepsSourceExtension => false;  // true: Review keeps the source extension (the extension is the format)
    string? SourceExtension(string fileName) => Path.GetExtension(fileName).ToLowerInvariant();  // the stored bytes' extension; null → UnsupportedType
    string? BrowserCore => null;                  // EmulatorJS core for the Play button, e.g. "gambatte"
    ReadOnlyMemory<byte> DefaultBoxArtPng { get; }  // 512×512 placeholder box art
    RomHeader? ReadHeader(ReadOnlySpan<byte> rom);  // null = no readable header
    ReadOnlyMemory<byte> NormalizeForHashing(ReadOnlyMemory<byte> rom) => rom;
}

public sealed record RomHeader(
    string? ClassifiedSystemId,                   // which handler Id the header says this ROM is for
    string? Title,                                // used for review suggestions
    bool IsPlausible,                             // false → InvalidHeader when the ROM matches no DAT
    IReadOnlyDictionary<string, object?> Fields); // stored as info.json `header`, shown as a key/value table
```

What each member drives:

| Member | Used for |
|---|---|
| `Id` | `roms/<Id>/` (its letter folders created when its first ROM is written, empty ones removed at startup) and `ingest/<Id>/` (created at startup with its `_*` folders), the system logo key, `info.json` `system`, the database `system_id` (a `VARCHAR`, so no migration), `/api/systems` (sorted by `DisplayName`), the UI's system filter and the `system-<Id>` icon (unmapped ids fall back to a controller icon). An id may start with a digit (`3do`), but a C# project, namespace or class name can't, so spell the number out there (`RnRomManager.Systems.ThreeDo`, `ThreeDoHandler`), and quote such an id as an object key in TypeScript (`'3do'`). |
| `ShortName` | The compact system badge in game pickers (`GameTypeahead`) and `systemShortName` in `GET /api/games`. Defaults to `DisplayName`; every shipped handler overrides it (`GB`, `SNES`, `2600`, `GG`, …). |
| `Family` | Which handlers' headers and DATs are tried for a file. GB and GBC share the `gameboy` family, so a file in either ingest folder is checked against both DATs, and the header decides where it's stored. GBA and N64 are their own `gba` and `n64` families: a `.gba` file in a GB folder fails as `UnsupportedType`. |
| `RomExtensions` | Which ingest files are picked up (case-insensitive). An unmatched file whose extension doesn't fit its classified system is renamed to `RomExtensions[0]`. It also filters the system's No-Intro DAT: entries whose file extension isn't in the list (case-insensitive) are left out of hash matching, review DAT search, suggestions and base titles, since no accepted file could match them. NES lists only `.nes`, so the DAT's headerless `.unh` copies are ignored; N64 drops its few `.bin`/`.cmd`/`.sm` entries. |
| `MinRomSizeBytes` / `MaxRomSizeBytes` | Validation before hashing, per file (each track of a disc set). Ingest checks a file's size against the first member of its family that lists the file's extension, so family members sharing an extension should share limits (GameCube and Wii both allow 32 KiB–9 GiB, or a large Wii disc would fail `TooLarge` against GameCube's). For an embedded system the whole ROM is read into memory for `ReadHeader`, bounded by the maximum; for an external one the file is hashed in one streamed read and `ReadHeader` gets only its first MiB, so the maximum can be large (64 GiB for Switch). For an external family, only the members whose `RomExtensions` and size range fit the file take part in identifying it. |
| `EmbedRomsInZip` | Where the ROMs live (see [ZIP format](zip-format.md#external-rom-files)). Required, with no default, so every handler says it. Every handler of one `Family` must agree: the registry refuses a mixed family at startup, naming it. An external system never normalises bytes (`NormalizeForHashing` isn't called), keeps the source file's extension, and its ROMs download, move and get checked as files. |
| `DatSource` | `Libretro` (the default) fetches the libretro files below (one to five) and matches by SHA1. `TitleDb` fetches the shared [titledb](https://github.com/blawar/titledb) file (`Sources:TitleDbUrl`) once per refresh, stores a compact copy per handler (`cache/dats/titledb/<DatName>.json`), matches by the title id from the header's `titleId` field or the file name, and takes media from the URLs titledb lists. Two systems may never share a `DatName`, whatever their source. |
| `DatName` | For a libretro system, the DAT files fetched per system: `<DatFolder>/<DatName>.dat` plus each metadat file `MetadatKinds` lists (`releaseyear`, `developer`, `publisher`, `genre`), all relative to `Sources:DatBaseUrl` and cached in `cache/dats/<kind>/`; so one to five files. Also the libretro-thumbnails folder name. For a titledb system, the name of its compact file and its row on **Admin → DATs**. |
| `DatFolder` | The libretro folder of the main DAT: `no-intro` (the default), `redump` (the disc systems) or `tosec` (Commodore PET, which has no No-Intro DAT, and Commodore Amiga, whose No-Intro DAT lists only `.ipf`). Admin → DATs and the versions check treat them the same way. |
| `MetadatKinds` | Which metadat files exist for the system (default all four). A kind it doesn't list is neither fetched nor required, and gives empty metadata (no year, developers, publishers or genres). The disc systems list none, since libretro has no Redump metadat. Nintendo 3DS lists a subset (developer, publisher, genre), since libretro has no 3DS `releaseyear` file. |
| `FileSets` | False by default. True (the disc systems) means: external files keep their **exact** names (no `<ZipBase>.` prefix or ` (N)` suffix; a taken name is `NameTaken`), a release may have other files (`files` in info.json), and, when `RomExtensions` includes `.cue`, ingest groups each cue or cdrdao `.toc` with its `.bin` tracks into one release, each CloneCD `.ccd` with its `.img` and optional `.sub`, and each Alcohol 120% `.mds` with its `.mdf` (`IngestSetPlanner`; play-disc builds a cue from the `.toc`, `.ccd` or `.mds`). A `.cue`/`.toc`/`.bin`/`.ccd`/`.img`/`.sub`/`.mds`/`.mdf` Review item can only be deleted, except a PlayStation `.img` that belongs to no set. The registry refuses `FileSets` with `EmbedRomsInZip` true, and a family whose members disagree on it. |
| `LegacyEmbeddedRoms` | False by default. Set it only when an existing embedded system becomes external (Nintendo DS did): `EmbedRomsInZip` false, no `FileSets` (the registry refuses anything else). A game whose `info.json` still lists every ROM without `externalFileName` stays valid and readable as a **legacy** game: it lists, downloads and plays from its ZIP, every write refuses it (`409 StorageMigrationPending`), integrity reports it (`LegacyEmbeddedStorage`), and the storage job (`JobType.StorageMigration`, started after every startup while such games remain) moves its ROMs next to the ZIP. With `RomStorageConfigurable` the same holds in both directions: whichever layout differs from the effective setting is pending and moved. A game mixing embedded and external ROMs is invalid. |
| `RomStorageConfigurable` | False by default. True lets an Admin switch `EmbedRomsInZip` under **Admin → ROM Zip Config**; requires `LegacyEmbeddedRoms` and a `Family` of its own. The handler takes an optional `IRomStorageSettings` and returns `settings?.Override(Id) ?? DefaultEmbedRomsInZip` from `EmbedRomsInZip` (see `NintendoDsHandler`). |
| `DefaultEmbedRomsInZip` | `EmbedRomsInZip` by default; a configurable handler sets it to its storage with no stored setting. The registry's storage rules check this value, so a stored setting never stops startup. |
| `KeepsSourceExtension` | False by default. True means a Review resolution (manual, flag or Dat) keeps the source file's extension instead of `RomExtensions[0]` or the DAT ROM's, for a system whose extensions are distinct formats rather than aliases (C64 `.tap` vs `.crt`). Hash-matched ingest is unchanged. |
| `SourceExtension` | The extension the stored bytes of a source named `fileName` have; null when the handler can't tell, and ingest fails the file `UnsupportedType`. By default the file's own extension, lower-cased. C64, PET and VIC-20 map gzipped VICE images to the image they hold. |
| `BrowserCore` | The [EmulatorJS](https://emulatorjs.org) core that plays the system in the browser, or null (the default) for no **Play** button. `gb` and `gbc` return `gambatte`, `gba` returns `mgba`, `lynx` returns `handy`, `jaguar` returns `virtualjaguar`, `vb` returns `beetle_vb`, `a5200` returns `a5200`, `a7800` returns `prosystem`, `a2600` returns `stella2014`, `coleco` returns `gearcoleco`, `gg` and `sms` return `smsplus`, `md` returns `genesis_plus_gx`, `s32x` returns `picodrive` and `snes`, `satellaview` and `sufami` return `snes9x` (all three cores [operator-supplied](#operator-supplied-cores), served by `/api/emulator/cores/<core>`), `nes` and `fds` return `fceumm`, `psx` returns `pcsx_rearmed`, `psp` returns `ppsspp`, `saturn` returns `yabause`, `segacd` returns `genesis_plus_gx` (shared with `md`), `3do` returns `opera` (operator-supplied; it needs at least one of five 1 MiB BIOS files, fetched by `play.js`, and saves its NVRAM through the modal's close handshake, below), `c64` returns `vice_x64sc`, `pet` returns `vice_xpet` and `vic20` returns `vice_xvic`, `n64` returns `mupen64plus_next` (all operator-supplied, one folder), `amiga` returns `puae` (vendored; it boots its built-in AROS Kickstart, so no BIOS), `tg16` returns `mednafen_pce` (vendored, no BIOS), `tgcd` returns `mednafen_pce` too (shared with `tg16`; it needs a System Card, fetched by `play.js`) and `nds` returns `desmume` (vendored, non-threaded only; `play.js` sets its screen-layout, stylus and mouse-lock defaults and hides its save-file buttons, and the vendored `GameManager.js` syncs its `.dsv` battery save). Play is offered only for releases inside the ZIP, except `pcsx_rearmed`, `ppsspp`, `yabause`, `genesis_plus_gx`, `opera` and `mednafen_pce` (`LibraryEndpoints.ExternalBrowserCores`, `externalBrowserCores` in `emulator.ts`), which play an external PlayStation, Saturn, Sega CD, 3DO or TurboGrafx-CD disc or PSP `.iso` through `play-disc` (on `mednafen_pce` never a lone `.bin` without set files, which Beetle PCE would run as a HuCard: `GameListItem.PrimaryHasFiles` in quick play, `canPlay` on the game page); a core shared by a cartridge system and a disc system (Genesis Plus GX for `md` and `segacd`, Beetle PCE for `tg16` and `tgcd`) can't tell them apart by itself, so the SPA adds `disc=1` to the play URL for an external release (`playUrl`'s `disc` argument, the games list's `playDisc`) and `play.js` loads that release from `play-disc`; Genesis Plus GX's Sega CD path also sets `EJS_disableCue = false`, since upstream skips cue generation for it and a lone `.bin` would load as a cartridge; `ppsspp` needs threads, so it plays only on the isolated `play-psp.html` tab (`opensInNewTab`); a pinned core also goes in the vendor script's `getCore()` guard and `params.js`'s `hidesCoreChooser`. A new core also needs vendoring and allowing in the play page ([development](development.md#browser-emulators)); a core that needs a BIOS file also needs an entry in `params.js`'s `biosFor` (the file the operator puts in `Paths:Bios`; `gearcoleco` → `colecovision.rom`, and `fceumm` → `disksys.rom` for a release named `.fds`, `snes9x` → `STBIOS.bin` for `.st` and `BS-X.bin` for `.bs`; PCSX ReARMed's optional `scph5501.bin` is handled separately in `play.js`). |
| `DefaultBoxArtPng` | Stored when no box art is found. Make your own (the GB/GBC/GBA/N64/NES/Famicom Disk System/SNES/Satellaview/Sufami Turbo/Virtual Boy/Atari 2600/Atari 5200/Atari 7800/Atari Lynx/Atari Jaguar/ColecoVision/Commodore 64/Commodore PET/Commodore VIC-20/Commodore Amiga/Game Gear/Master System/Mega Drive/32X/TurboGrafx-16 / PC Engine/Switch/PlayStation/PSP/GameCube/Wii/Xbox 360/Saturn/Nintendo DS/Nintendo 3DS/Sega CD/3DO/TurboGrafx-CD ones are drawn for this project; their SVG sources are in each project's `Resources/boxart/`). |
| `ReadHeader` | Classification (`ClassifiedSystemId`), the invalid-header rule (`IsPlausible`), review suggestions (`Title`) and the stored header (`Fields`). Return null for a file with no recognisable header; an unmatched headerless file then belongs to the ingest folder's handler. A system whose cartridges have no header returns null always, as `Atari2600Handler` and `SatellaviewHandler` do: its unmatched files always go to Review (never `InvalidHeader`), its releases have no Header button, and `info.json` `header` is null. A system with an optional header returns it when found and null otherwise, as `GameGearHandler` and `MasterSystemHandler` do with `TMR SEGA` (one shared `TmrSegaHeader` reader, classified as the calling handler's id) and `MegaDriveHandler` with the `SEGA` header at 0x100: headerless files still go to Review, and only releases with a header show the Header button. `AtariLynxHandler` and `Atari7800Handler` similarly read the optional `LYNX` and `ATARI7800` cartridge headers. A system with only a magic-bytes check returns a header every time, plausible or not, as `ColecoVisionHandler` does with its `magic` field (`AA55`/`55AA`) and `SufamiTurboHandler` with `headerValid` (Snes9x's `BANDAI SFC-ADX` cart test). `C64Handler` reads one of four optional container headers (`.crt`, `.tap`, `.g64`, `.nib`) and returns null for every other type (`.prg`, `.d64`, `.t64`, `.bin`, `.d71`, `.d81`, `.x64`, `.p00`). |
| `NormalizeForHashing` | The bytes that are hashed **and stored**, and the bytes `ReadHeader` sees. Stored bytes, `info.json` hashes and the integrity checker's deep hashes then always agree. Nintendo 64 is the example: `.v64` (byte-swapped) and `.n64` (little-endian) dumps are converted to big-endian here, so they match the DAT's `.z64` entries and are stored as `.z64` (`RomExtensions[0]`). SNES strips a 512-byte copier header here (by file size), so headered `.smc` dumps match the DAT's `.sfc` entries and are stored as `.sfc`. TurboGrafx-16 combines both patterns: no header (`ReadHeader` always null, like Atari 2600) plus a size-only 512-byte copier strip (size 512 bytes past a multiple of 8 KiB), with `MaxRomSizeBytes` set to the DAT's largest entry plus 512 because the size limit is checked before the strip. |

See the README's [supported systems](../README.md#supported-systems) table for storage, formats, DAT source and browser play.

**Switch, the external + titledb example** (`RnRomManager.Systems.Switch`): `EmbedRomsInZip` is false and `DatSource` is `TitleDb`. `ReadHeader` reads only the first MiB it's given: a PFS0 (`.nsp`, `.nsz`, `.hdf`) yields its file count and, from its ticket names, a `titleId`; an XCI (`HEAD` at 0x100 or 0x1100) yields no id, so the file name's `[0100…]` is used. Every offset is checked with widened arithmetic before it's sliced, and anything damaged gives a null id rather than an error. It needs no `NormalizeForHashing`.

**The disc systems** (`RnRomManager.Systems.Sony`, `.NintendoDisc`, `.Microsoft`, Saturn and Sega CD in `.Sega`, 3DO in `.ThreeDo`, and TurboGrafx-CD in `.Nec`) are the `FileSets` examples. PlayStation, PSP, Xbox 360, Saturn, Sega CD, 3DO and TurboGrafx-CD have no header (`ReadHeader` returns null). GameCube and Wii share the `nintendo-disc` family and one `NintendoDiscHeader.Read(rom, callerId)`: the magic word at 0x1C (GameCube) or 0x18 (Wii) classifies the disc, so a Wii disc dropped in the GameCube folder is stored as Wii. Wii also lists `.wbfs`: the reader recognises the WBFS container and reads the disc-header copy inside it (`container` `wbfs`); GameCube doesn't list it, so a `.wbfs` in the GameCube folder is only eligible for Wii.

**Updates tab.** There is no handler property for it: any system whose identification flags a release `Update` (titledb does, for title IDs ending in `800` and for `[UPD]` files) gets the Game page's **Updates** tab for those releases, ordered by the `version` read from a `[x.y.z]` tag in the file name. A libretro system's DAT flags never include `Update`, so its games show only Releases.

**DLC tab.** Likewise, any system whose identification flags a release `DLC` (titledb does, for DLC title IDs) gets the **DLC** tab for those releases, ordered by file name; a release flagged both `Update` and `DLC` is an update. DLC and update file names are also searchable (Global Search and the Library search).

**Limits of the contract:**

- A release is one file unless the system sets `FileSets`, and then only bin/cue and TOC sets (a `.cue` or cdrdao `.toc` naming `.bin` tracks), CloneCD sets (`.ccd`, `.img`, optional `.sub`, by stem) and MDS sets (`.mds`, `.mdf`, by stem) are grouped. Other multi-file formats (`.gdi`, audio tracks as `.wav`/`.ape`) aren't supported, nor multi-session or scrambled CloneCD images, subchannel or multi-session MDS images, or TOC sets with cooked tracks, `SILENCE`/`ZERO` or `SWAP` (they ingest but don't play). PlayStation, Saturn, Sega CD, 3DO and TurboGrafx-CD also list `.chd` as a single-file format: it's never part of a set and never matches the Redump DAT, so it always goes to Review. Multi-disc games are one release per disc, grouped by title.
- `Fields` values must be JSON primitives (string, number, bool or null), because the UI renders them generically.

## Step by step

1. Create `src/RnRomManager.Systems.<Name>` (class library, referencing `RnRomManager.Core`) and add it to `RnRomManager.slnx`. Add a matching `tests/RnRomManager.Systems.<Name>.Tests` project. A closely related system may instead live in an existing project when that is simpler: Game Boy Advance shares `RnRomManager.Systems.GameBoy` (and its box-art and resource code) but is its own `gba` family, and Nintendo 3DS lives in `RnRomManager.Systems.NintendoDs` as its own `3ds` family. Nintendo 64 has its own project, `RnRomManager.Systems.Nintendo64`, with a small private loader for its embedded box art; NES and SNES follow the same pattern in `RnRomManager.Systems.Nes`, `RnRomManager.Systems.Snes`, `RnRomManager.Systems.Coleco`, `RnRomManager.Systems.Sega`, `RnRomManager.Systems.Nec`, `RnRomManager.Systems.VirtualBoy`, `RnRomManager.Systems.NintendoDs` and `RnRomManager.Systems.Commodore` (short names rather than the full system names). Atari 2600, 5200, 7800, Lynx and Jaguar share the `EmbeddedResources` box-art loader in `RnRomManager.Systems.Atari`. Master System and Mega Drive share `RnRomManager.Systems.Sega` with Game Gear: Master System reuses Game Gear's `TMR SEGA` reader (`TmrSegaHeader`) rather than copying it, and all of them load their box art through one `EmbeddedResources` helper. 32X shows the same for a header: its ROMs carry the Mega Drive header, so `Sega32xHandler` and `MegaDriveHandler` both call the shared `MegaDriveHeader.Read(rom, systemId)`, which classifies the result as the calling system. Also add the new project's `.csproj` to the restore layer in the `Dockerfile`.
2. Implement `ISystemHandler` (one class per `Id`). Embed the default box-art PNG as a resource, together with its source file.
3. Register it in `AppHost.AddSystemHandlers` next to the existing ones:
   ```csharp
   services.AddSystemHandler<Sg1000Handler>();
   ```
   and add a project reference from `RnRomManager.Api`.
4. Add the system to the test data builders in `tests/RnRomManager.TestData` if you want seeded ROMs and fixture DATs for it (`FixtureDatWriter` writes the main DAT plus its metadat files per libretro system, in the folder its `layouts` entry gives (`FixtureDatLayout.NoIntro` by default, `FixtureDatLayout.Redump` for a disc system), or a titledb compact file through its `titleDb` map). Every test fixture that loads DATs for all systems must include the new one, or ingestion's `DatsMissing` preflight fails.
5. Optionally map its icon in `src/RnRomManager.Web/src/lib/components/icons.ts` (`'system-sg1000': 'bi bi-…'`); without it the UI uses the controller fallback.
6. Test the header reader with synthetic ROMs (never commit real ROMs), plus the registry lookups and the box-art PNG (valid, 512×512). See `tests/RnRomManager.Systems.GameBoy.Tests` for the pattern.
7. Add the system to `src/RnRomManager.Web/src/lib/systemEmulators.json`, the Systems tab's emulator links (official project pages only; an empty array if none are known). `SystemEmulatorsCatalogTests` fails until it's there.
8. If the system has a `BrowserCore`, every `RomExtensions` entry must be in that core's compiled-in extension list in `BrowserCoreExtensionsTests`, or be listed in its `Exceptions` with the reason it still works ([development](development.md#browser-emulators)).
9. Update the docs: the [README supported-systems table](../README.md#supported-systems), which `SupportedSystemsTableTests` enforces, [features](features.md) if behaviour differs, and [ZIP format](zip-format.md) for the new `header` fields.

After deployment, an Admin runs **Admin → DATs → Refresh DATs** to download the new system's DATs; ingestion refuses to start (`DatsMissing`) until every registered system has them.

## Operator-supplied cores

Some EmulatorJS cores can't ship in the image because their licence forbids commercial use (Genesis Plus GX for `md`, PicoDrive for `s32x`, Snes9x for `snes`, Opera for `3do`), or because the binary embeds copyrighted system ROMs (VICE for `c64`, `pet` and `vic20`), or because it links code under GPL terms that can't be combined (Mupen64Plus-Next for `n64`: GLideN64 is GPL-2.0-only, RetroArch GPL-3.0-or-later). The operator supplies their files instead, and the app serves them only after checking them. To add one:

1. Add an `Emulator:<Name>CorePath` option to `EmulatorOptions` and `EmulatorOptionsValidator` (empty or absolute; a missing folder means "not set up", not a startup failure), with tests in `OptionsValidatorTests`, `OptionsRegistrationTests` and `EffectiveSettingsTests`.
2. Add an entry to `OperatorCoreManifest.Pinned` (`src/RnRomManager.Api/Endpoints/OperatorCoreManifest.cs`): the core id, its display name, the option accessor, a `<Name>CoreMismatch` problem code, and the exact length and SHA-256 of `<core>-wasm.data`, `<core>-legacy-wasm.data` and the package's `reports/<core>.json`. Take them from `npm pack @emulatorjs/core-<core>@<version>` in a folder outside the repository; never commit the files. Record the core's `valid_extensions` and its `<core>-wasm.data` SHA-256 in `BrowserCoreExtensionsTests` too. The generic `/api/emulator/cores/{core}` routes then serve it.
3. Add the core to `params.js`: the allowlist, `operatorCores` (the 404 message's system label, display name, short name and option key), `hidesCoreChooser`, and `controlSchemeFor` when its first EmulatorJS group isn't the system's.
4. In `scripts/vendor-emulatorjs.mjs`, add it to the explicit-core patch, the non-threaded guard and the no-CDN guard (not to the `cores` list or `package.json`), and check `requiresThreads` in the vendored `emulator.js`: a core that needs threads would need the isolated PSP-style page.
5. Document the option in [configuration](configuration.md), the mount in [deployment](deployment.md), and the core in the README's attribution (as not included).
