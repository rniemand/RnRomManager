# Game updates

## Summary
Switch updates (e.g. `DREDGE[UPD][1.0.1].nsp`) are already ingested as releases of their base game, flagged `Update`, stored as external files and pointed at from `info.json` (external-roms-switch T4–T6, E1–E4). They have no version, so two updates of a game can't be ordered (both are named `… [v0].nsp`, the second gets ` (2)`), a `[UPD]` file without a title ID ends up as a *base* release when resolved in Review, and the Game page mixes updates with releases. This spec adds a release `version` (info.json v5, DB column), uses the `[UPD]` marker, and gives the Game page an **Updates** tab listing a game's updates newest first, each with its download link. It is generic: any system whose identification flags a release `Update` gets the tab; no handler property. Two smaller changes ride along: external file names stop repeating the game title (B13), and uploading the first real box art to a game that shows the placeholder starts a deep integrity check of that game only, so its `DefaultBoxArt` issue clears without a full Deep run (B14–B15).

## Out of scope
- A DLC tab (DLC stays in Releases).
- Editing a release's version (Admin metadata edit, Review manual action).
- Identifying a `[UPD]` file with no title ID by matching its name against titledb automatically (it goes to Review; B8).
- Versions for releases not flagged `Update` (the field stays null for them).
- "Download all updates" / bundling updates into the game ZIP download.
- Reading the version from inside an NSP/XCI (needs keys; the version comes from the file name only).
- A game check for any other edit (snap upload, cover change, a box art added once the placeholder is gone, media retry), a "Check this game" button, or a notice on the Game page that a check started.
- Queueing the game check when the job lock is busy (B15: it is skipped).

## Behaviour

### Version
- **B1 Field.** `info.json` **schema version 5**: each Rom gains `version` (string or null). `InfoJsonRom.Version` (`string?`). Validator: null, or matches `\A[0-9]{1,9}(\.[0-9]{1,9}){1,3}\z` (so at most 39 chars; the DB column is `VARCHAR(40)`), else invalid (`rom '<fileName>' version '<v>' is not a dotted version`). The validator doesn't tie it to the `Update` flag (generic, and a hand-edited file stays readable).
- **B2 Parse.** New `Core/Naming/ReleaseVersion.From(string fileName)`: the first match of `\[([0-9]{1,9}(?:\.[0-9]{1,9}){1,3})\]` (ordinal, ASCII digits only) in the name, group 1; no match → null. `DREDGE[UPD][1.0.1].nsp` → `1.0.1`; `X [v65536].nsp` → null (`v` isn't a digit); `X [2024].nsp` → null (needs a dot); `X [1.2.3.4.5].nsp` → null.
- **B3 When it's set.** Every place that builds a new release from an ingest or Review source sets `Version = Flags contains "Update" (ordinal) ? ReleaseVersion.From(OriginalFileName) : null` through one helper (`ReleaseVersion.For(flags, originalFileName)`): `IngestPipeline` (libretro and titledb matches) and every `ReviewResolver` action that creates a release (`Dat`, `Attach`, manual). Edits that copy an existing release (title edit, move, merge, delete-restore) keep its `Version` unchanged.
- **B4 Upgrade.** `InfoJsonUpgraderV4` (v4 → v5): each object element of `roms` gets `version` = B2 on its `originalFileName` (when a string) if its `flags` is an array containing the string `"Update"`, else `null`. Other shapes are left for the typed read/validator (as `InfoJsonUpgraderV3`). Registered in `AppHost` next to V3. As today the file is rewritten as v5 on its next normal write.
- **B5 Database.** Migration `0019_release_versions.sql`: `ALTER TABLE roms ADD version VARCHAR(40) NULL;` then backfill existing updates with the same rule as B2/B3, exactly (MariaDB string literals need doubled backslashes, and `REGEXP_SUBSTR` returns `''` on no match, hence `NULLIF`):
  ```sql
  UPDATE roms
  SET version = NULLIF(SUBSTRING(REGEXP_SUBSTR(original_file_name, '\\[[0-9]{1,9}(\\.[0-9]{1,9}){1,3}\\]'), 2,
                CHAR_LENGTH(REGEXP_SUBSTR(original_file_name, '\\[[0-9]{1,9}(\\.[0-9]{1,9}){1,3}\\]')) - 2), '')
  WHERE JSON_CONTAINS(flags, '"Update"');
  ```
  A non-match leaves NULL. Needed because DB sync skips ZIPs whose size and mtime are unchanged, so the mirror would never pick the upgraded value up. `RomRow`, `MirrorEntry.ToRows` and the repository insert/select carry it (`DbSync` mirrors through `ToRows`, as for `externalFileName`; no change there). `GET /api/games/{id}` release rows gain `version` (string or null); `src/lib/api/types.ts` `RomDetail.version: string | null`.

### Switch identification
- **B6 Update file name.** For a titledb `Update` match with a version, the rom `fileName` (T5) becomes `<name> [<TitleId>][v<N>][<version>]<ext>`, e.g. `DREDGE [0100ABCD12340800][v0][1.0.1].nsp`, so two updates of one game don't clash. Without a version, and for base/DLC, T5 is unchanged. E1/E2 apply to the result as today (E2 cuts the stem from its end, so a very long name can lose the version tag from the *file name*; the `version` field keeps it).
- **B7 `[UPD]` at ingest.** In T4, when the title id comes from the **file name** (not the header), is a base id (low 13 bits clear) and the file name contains `[UPD]` (ordinal-ignore-case), match `base | 0x800` instead (→ `Update`, base entry required as today; the match's `TitleId`, and so the B6 name, is the update id). A header `titleId` is authoritative and is never changed by `[UPD]`.
- **B8 Review "update" toggle.** `ReviewResolutionRequest` gains `bool? Update`. With `Update == true`: the action must be `Dat`, the item's chosen handler must use `DatSource.TitleDb`, and the picked `datGameName`'s title id must be a base id or an update id (low 13 bits `0x800`; every titledb row, updates and DLC included, is its own DAT game, so Suggestions and search list update entries too); otherwise (DLC, data patch, delta) `400 ValidationFailed` with field `update` (item and source untouched). It then resolves as T9 would for `base | 0x800` for a base pick, or for the picked id as it is for an update pick (both: flags `Update`, B3 version from the item's original file name, B6 name). `Update` null/false keeps today's behaviour. Review item page, for the items it already treats as titledb (its existing `item.system === 'switch'` check, G8; not generalised here): a checkbox **This file is an update** above both the Suggestions and the DAT search results (one checkbox, used by every `Use` button), pre-ticked when the item's original file name contains `[UPD]` (case-insensitive); `useDat` sends `update` with its value; the success toast is `Added update of <datGameName>.` when ticked.

### External file names
- **B13 No repeated title.** E1 (`ExternalRomName.Build`, the on-disk name of an external rom next to its ZIP) drops the title from the rom name when it repeats the ZIP base: when the rom name's stem starts with `zipBase` (ordinal-ignore-case) followed by a space, and something other than spaces follows, the name is `<zipBase>.<rest of the stem, leading spaces trimmed><suffix><ext>`. E.g. `Death's Door` + `Death's Door [0100B31015AF8000][v0].nsp` → `Death's Door.[0100B31015AF8000][v0].nsp`; an update → `Death's Door.[0100B31015AF8800][v0][1.0.1].nsp`. Otherwise E1 is unchanged (`Orbit` + `Orbit.nsp` → `Orbit.Orbit.nsp`; a `(N)` ZIP base, a cut base, or a rom name T5 spelled differently from the title, e.g. a dot run turned into `…`, doesn't match, so keeps the full name). The budget cut, ` (N)` suffix and device-name rules apply to the result as today. Only the pointer changes: the logical `fileName` (info.json, downloads) keeps the full name. Every caller of `Allocate` gets it (ingest, Review, title edit, move, merge, and the external repair of a missing/damaged file in `IngestPipeline`, which re-allocates that one pointer), so a title edit, move or repair renames that game's external files to the new form as it already renames them today. Existing files that aren't touched keep their names (the pointer is stored, nothing derives it; integrity doesn't check pointer names).

### Integrity check after replacing the placeholder box art
- **B14 Trigger.** `LibraryEditor.AddImageAsync` already removes the placeholder when a `BoxArt` is added (I3). When the removed placeholder **was the cover** (the game had `DefaultBoxArt`: `cover.IsDefault`) and the edit succeeds (`Code` null), the result says so: `LibraryEditResult` gains `bool ReplacedDefaultCover` (init, default false). Both image endpoints (`POST /api/games/{id}/images` and `/images/from-url`) then, after the editor has released the job lock, start a game check (B15) through `JobRunner.StartAsync(…, JobTrigger.Manual, <user id>, CancellationToken.None)`. The response is today's game detail, whatever happens to the check. A Snap upload, a second box art, or any other edit never starts one.
- **B15 Game check.** A new `JobMode.Game` (`jobs.mode` is `VARCHAR(16)`, no migration): an `Integrity` job scoped to one game's ZIP path, built by `IntegrityJobFactory` with that path (a settable property `ZipPath` the factory lambda sets after `ActivatorUtilities.CreateInstance`, like `LibraryEditor.ExternalHooks`, not a constructor argument: `ActivatorUtilities.CreateInstance` can't match a null `string?` argument and would try to resolve `string` from DI). In `Game` mode `zips`/`onDisk` are just that ZIP, there are no sync skips (so nothing is `IsUnchecked`), and `ApplyAsync` filters the open issues to that ZIP before resolving. It checks like Deep (opens the ZIP, hashes every ROM and image entry and the game's external files, as `CheckZipAsync`/`CheckExternalAsync` with every `mode == Deep` test true for `Game`) but only that ZIP: no `DbSync.SyncAllAsync` (the edit already mirrored it), no library scan, no orphan or duplicate checks, no retention purge; claimants (G4) still come from the full `ListExternalAsync`. Progress total is 1. A completed run resolves only open issues whose `zip_path` is that ZIP (ignoring case), never `OrphanFile`/`DuplicateGameId`/`DuplicateSha1`, by today's `WasChecked` rules (D48/G2a) as for an opened ZIP in Deep; a cancelled run resolves nothing. If the ZIP isn't a plain file when the job starts, the job records no finding, resolves nothing and logs a warning. Summary: `{ issues, newIssues, resolved }` (numbers only: the web `formatSummary` prints every value as a count; the ZIP path goes in the log line). When the lock is busy (`StartAsync` returns null) or `StartAsync` throws, the check is skipped and logged (Information / Warning); the issue clears on the next Quick or Deep run that opens the ZIP. `GET /api/integrity/status` is unchanged: it reads Quick and Deep only, so a game check never shows as the last deep check. `POST /api/jobs/integrity` keeps accepting only `Quick`/`Deep`. Web: `Job.mode` (`types.ts`, both places) gains `'Game'`; the Jobs page and the Integrity page's recent-runs table show it as they show other modes (`Integrity (Game)`; no filter).

### Game page
- **B9 Tabs.** Tabs are `Releases (<n>)`, `Updates (<m>)`, `Images (<k>)`, `Zip Contents`. An *update* is a rom whose `flags` contains `Update`. The Updates tab is shown only when `m > 0`; `?tab=updates` on a game without updates shows Releases (as an unknown tab does today). `n` counts roms that aren't updates.
- **B10 Lists.** One tabpanel, today's `#releases-panel`, renders both tabs with a switched list (no new component); its `aria-labelledby` is `releases-tab` or `updates-tab` for the active tab, and the Updates tab button's `aria-controls` is `releases-panel` (today each tab uses `<value>-panel`), and its visually hidden heading reads `Releases` or `Updates`. Releases lists the non-update roms in today's order; Updates lists the updates newest first. Each update card is today's release card (same download button, note, External badge and Admin actions) plus a `Version <version>` badge in its header when `version` is set. "Expand/Collapse all" is shown when the visible list has ≥ 2 cards and acts on that list. The header **Download ROM** button/dropdown (`downloadRoms`) lists only non-update roms (updates are downloaded from their cards); a game with only updates keeps today's behaviour for that button over its updates. A game with only updates shows `No releases other than updates.` on the Releases tab.
- **B11 Update order** (pure function `compareUpdates` in `src/lib/releases.ts`), first difference wins: (1) `version`, compared segment by segment numerically (missing segments = 0); a release with a version before one without; higher first; (2) the number in `revision` `v<N>` (none = 0), higher first; (3) `dateAdded`, newer first; (4) `fileName`, ordinal ascending.
- **B12 Unchanged.** Primary release ranking (T6), the download endpoints (G4, G5), integrity, the library list and its counts, collections and reports treat updates exactly as today.

## Risks
- **Schema bump.** Older app versions can't write v5 ZIPs (they report `InfoJsonNewerSchema`, read-only) — same as every bump; documented in `docs/zip-format.md`. Tests that assert `schemaVersion` 4 are updated in step 1.
- **Backfill drift.** The SQL backfill and B2 must agree; step 2's Testcontainers test runs both on the same names (including non-matching ones) and compares.
- **Existing Switch updates keep their old file names** (`… [v0].nsp`, ` (2)`, and the `<title>.<title> …` pointer); only new ingests get B6/B13 names, plus games whose external files a title edit, move, merge or repair already renames. No rename job (user: existing files can stay; names are cosmetic, the version field orders them). A folder then mixes both pointer forms.
- **B13 test churn.** Tests that compute E1 names through ingest or edits (`ExternalRomNameTests`, `IngestPipelineTests`, `ExternalLibraryTests*`, `LibraryEditor` tests, e2e external name asserts) change to the new form; fixtures that hard-code a pointer stay valid, as any stored pointer is.
- **Game check on a big game.** Hashing a Switch game's external files can take minutes and holds the job lock, so edits and other jobs get `409 JobRunning` meanwhile (as during any job). It is cancellable from the Jobs page like any job.
- **Library editors start a job.** The image endpoints are `LibraryEditor`, while starting integrity runs by hand is Admin only. Accepted: the check is automatic, one game, read-only, and recorded with the user's id.
- **`[UPD]` false positive** only affects file-name ids that are base ids; a wrong pick in Review can be fixed with the existing Admin move/delete release.
