# UI shell, group logos, backup restore and DAT schedule

## Summary
A round of polish and small features for every user: a slimmer navbar and a new sticky footer (shortcuts, version, About), page titles only on mobile, logos for genres and systems as well as publishers (with URL upload as the default and a text banner when there's no image), an update count and clickable rows on the Library Size report, a tidier Integrity status and Auditing page. For Admins: restore a backup from the Backups table, and a daily DAT refresh they can configure. Library system folders are created only when a ROM is written to them.

## Out of scope
- Logos in the small `SystemBadge` chips (tables, filters, game pages): they keep their Bootstrap icon.
- Download or delete of backup files, and restoring files (backups hold the database only, as today).
- A general cron/scheduler framework: the DAT schedule is one more `BackgroundService` like `BackupScheduler`.
- Changing which ingest folders exist: `ingest/<system>/{_duplicates,_failed,_removed}` are still created at startup.
- SVG, WebP or GIF logos: logos stay PNG or JPEG, ≤ 512 KiB, ≤ 2048 px per side.

### Logos for publishers, genres and systems
- **B13** Publishers, genres and systems each can have one shared logo, stored in the database (`discovery_logos`, migration 0026). Publishers and genres are keyed by their group key (B2 of collections discovery, 64 hex). Systems are keyed by the SHA-256 of the system id in lowercase ASCII, so the same `key_digest` column holds all three. Existing publisher logos keep working unchanged.
- **B14** API, one route per kind with `kind` ∈ `publishers|genres|systems`:
  - `GET /api/discovery/{kind}/logo?key=` (any signed-in user): the bytes, `private, no-cache`, `nosniff`; 404 when none. For `systems`, `key` is the system id.
  - `PUT /api/discovery/{kind}/logo?key=` (Admin, multipart `file`): as today's publisher upload.
  - `PUT /api/discovery/{kind}/logo/from-url?key=` (Admin, JSON `{ "url": "…" }`): the server downloads the image through `ImageUrlDownloader` (http/https only, ≤ 1024 chars, no userinfo, public addresses only, 15 s, its bounded 8 MiB read) and stores it if it passes the same checks as an upload (PNG/JPEG by content, ≤ 512 KiB, ≤ 2048 px). Success is `204`, like the file upload. Errors, as the game-image and collection-cover `from-url` routes do: `400 ValidationFailed` with `url` for a bad URL (`ParseImageUrl` null) and for downloaded bytes that fail the logo validator (not a PNG/JPEG, over 512 KiB, over 2048 px: the upload's messages); the downloader's own problem passed through unchanged for a blocked address (`400 ImageUrlBlocked`) or a failed download (`502 ImageDownloadFailed`); `404` for an unknown group or system.
  - `DELETE /api/discovery/{kind}/logo?key=` (Admin): removes it; 204, or 404 when there is none.
  - An unknown `kind` is 404. A malformed `key` is `400 ValidationFailed` (`key`): for publishers and genres anything but 64 lowercase hex; for systems anything but 1–32 characters of `[a-z0-9]` (a new check in the logo endpoint only; every registered handler id fits it, and no handler-id rule is added). A well-formed key that isn't a current group (publishers, genres) or a registered system is 404 on both PUTs; GET and DELETE work for any stored key (404 when none is stored), so a logo outlives its group leaving the index for a while (as today).
  - `from-url` order: key check, then the group/system 404, then the URL check, then the download, then the same logo validator as the file upload (pulled out of the private `PublisherLogoEndpoints.ReadLogoAsync` into a shared bytes check: PNG/JPEG, ≤ 512 KiB, ≤ 2048 px, the upload's messages). Only `ParseImageUrl` and `ImageUrlDownloader` are shared with the game-image code; `DownloadedImageError` is not (its 8 MiB rules differ).
  - Every change is audited: `PublisherLogoReplaced`/`PublisherLogoRemoved` as today, and new `GenreLogoReplaced`, `GenreLogoRemoved`, `SystemLogoReplaced`, `SystemLogoRemoved`. System logo events set the audit event's system id (so the Auditing page's System filter finds them); publisher and genre events leave it null, as today. Details keep today's format for every kind: `<name> (key <key>)`, or `key <key>` when the group is no longer in the library; for systems `<display name> (system <id>)`, or `system <id>` for an unregistered id. A URL upload appends ` from <url>` (cut to the audit's 1024 chars).
  - The old `/api/discovery/publishers/logo` URLs are the `publishers` case of the same route, so existing `logoUrl` values keep working.
- **B15** `GET /api/discovery/genres` items carry `logoUrl` like publishers do (null when none, versioned `&v=<updated_at ticks>`). `GET /api/systems` (mapped in `LibraryEndpoints.cs`) items gain `logoUrl` (same rule; `key` is the system id), and the SPA's `SystemInfo` type gains `logoUrl: string | null`. Today's `PublisherLogoEndpointsTests.GenreGroups_HaveNoLogoUrl` is replaced by a genre `logoUrl` test.
- **B16** The SPA's logo for a group is the first that loads of: the shared logo, the bundled starter art (publishers: today's `static/publishers/`; genres: new `static/genres/`, B17), then a **text banner**: the name centred in a bordered, rounded box of the logo's size (`GroupLogo` component, `aria-hidden`, since the name also follows as text). So every publisher, genre and system shows a logo. A failed image falls through to the next source (as publishers do today).
- **B17** Starter genre art: about 15 SVG banners in `static/genres/` (a Bootstrap Icons glyph, MIT, plus the genre name), listed in `starterGenres` in `discovery.ts` by alias and key (SHA-256 of the lowercase alias, recomputed in `discovery.test.ts`) and in `static/genres/manifest.json`. Aliases are the most common libretro `genre` values (exact list fixed in step 7 from the seeded and real DAT genre names, at least: Action, Adventure, Platform, Shooter, Shoot'em Up, Fighting, Beat'em Up, Sports, Racing, Driving, Puzzle, Role-Playing (RPG), Strategy, Simulation, Board Game). The Bootstrap Icons licence is already listed in `licenses.json` (`bootstrap-icons`, MIT); each SVG's source and licence go in the manifest.
- **B18** Systems tab: the system list and the selected system's heading show the system's logo (shared logo, else the text banner; systems have no starter art). `SystemBadge` elsewhere is unchanged.
- **B19** Admins see a **Change logo** (pencil) button beside each publisher, genre and system row (genres and systems are new). It opens the logo modal (one component for the three kinds): current logo preview and its source, in today's `PublisherLogoModal` wording ("Shared logo, set by a user." / "Starter art bundled with RnRomManager." / "No logo: the name shows as text."; e2e asserts the first and last), a **URL / File** choice (radio button group, **URL selected each time the modal opens**), the URL field or the file field, **Save logo**, and **Remove shared logo** when there is one. Client checks mirror the server (URL: http/https, ≤ 1024 chars; file: PNG/JPEG, ≤ 512 KiB); server errors show under the field. On success: toast, close, the list refetches.
- **B20** Fix the stale "any signed-in user may change a logo" comments (`PublisherLogoEndpoints.cs`, `discovery.ts`; `PublisherLogoModal.svelte`'s goes with the file in step 7, and `LogoModal` doesn't repeat it): changes are Admin-only.

### Admin
- **B24** Auditing: the Details column is `text-truncate` with `max-width: 32rem` and the full text as `title`, like Path and Target, so a long `DatsRefreshed` list (≈ 40 DAT names) no longer widens the table and squeezes every row.
- **B25** Auditing: the filters become one toolbar row like the Library's: a search box, `FilterDropdown` menus for **Action** and **System**, a **User** dropdown (a text box plus a **Scheduled only** check), a **Date** dropdown (From and To date inputs), and **Clear**. Action and System use `FilterDropdown` without `counts` (already optional), so `FilterDropdown` itself is unchanged.
- **B26** Backups: each row of the backups table gets a **Restore** button (Admin). It opens a `ConfirmModal` (`confirmClass="btn-danger"`, confirm label **Restore**, `busy` while the request runs) naming the backup and its date and saying: every table is replaced; a safety backup of the current database is taken first; everyone, including you, is signed out; run Integrity → Run quick afterwards, since the library ZIPs may be newer. Confirm calls `POST /api/admin/backups/{fileName}/restore`, with the name passed through `encodeURIComponent` (names can hold a space and parentheses: `rnrommanager-20261117-040000 (2).zip`; the route value arrives decoded).
- **B27** Restore on the server (`BackupService.RestoreAsync`):
  1. `fileName` must be a bare name (the startup restorer's rule 1, one shared helper) that `BackupNames.Parse` accepts (so never a `.tmp` or `.restored` file: exactly the names the backups list shows): else `400 ValidationFailed` (`fileName`). This needs no lock and runs first.
  3. It takes the job lock (`409 JobRunning` when a job or library edit holds it) and the backup lock (`409 BackupRunning`), so no job, edit or scheduled backup runs during it (and no retention can delete the file between the checks below and the restore).
  2. With both locks held: a valid name with no file is `404`; then the file is opened and stays open until the restore ends, and the pre-drop check (rule 3, shared) runs: unknown migrations or a format version other than the current one is `409 BackupTooNew` (detail: the restorer's message); an unreadable ZIP, a missing or incomplete manifest (`BackupArchive.ReadManifest` throws), or a missing schema entry or table data entry that `MySqlBackupStore.RestoreAsync` would read is `400 InvalidBackup`. The shared helper returns the failure; `BackupRestorer` keeps throwing `BackupRestoreException` with today's messages (and also gets the entry check). So only failures after the drop become `RestoreFailed` (B27.10). (Items 2 and 3 run in the order listed here: 1, 3, 2.)
  4. It opens a **maintenance gate** through a Core abstraction, `IMaintenanceWindow.TryEnterAsync(CancellationToken)` (in `Core/Backups`), returning an `IAsyncDisposable` that closes it, or null when in-flight requests didn't finish in time (`409 Busy`). Api implements it with `MaintenanceGate` (singleton, using `IHttpContextAccessor`, which `AppHost` doesn't register today, so step 5b adds `AddHttpContextAccessor()`, to record the calling request as the owner) plus the `AuditWriter` hold below; Core tests use a fake. `MaintenanceGate`'s middleware is registered in `AppHost` right after `UseSecurityHeaders`, before static files and `UseAppAuth`, because cookie validation reads `users`): while open, every `/api` and `/health/ready` request except this restore request (identified by its `HttpContext`, not its path) gets `503 Maintenance` (ProblemDetails, `Retry-After: 5`). `AuditWriter` gets `HoldAsync()` (flushes pending events, then stops inserting; events stay in the bounded channel) and `Release()` (resumes); the restore holds it before the drop and releases it when the gate closes. The gate counts in-flight `/api` requests (not the restore request itself: it opens the gate from inside that request and subtracts it) and, once open, waits up to 10 s for them to finish before the drop (long-lived streams are excluded from the count: endpoints carrying a new `MaintenanceExempt` metadata marker, read through `HttpContext.GetEndpoint()` (there's no explicit `UseRouting`, so `WebApplication` adds it at the start of the pipeline and routing runs before the middleware; don't add a later `UseRouting`), namely `GET /api/admin/logs/stream`, the game ZIP, release and set-file downloads, `zip-entries/download`, `play-disc` and `bundle-downloads/{ticket}/file`; the downloads read files, not tables, after they start; the log stream re-reads its viewer's `users` row on each keep-alive tick, which may fail during the drop (the stream ends, logged by ASP.NET Core) and otherwise ends it at the first tick after the stamps rotate; all of them are 503'd like any other request while the gate is open); if they don't finish in time the restore is refused with `409 Busy` and nothing changes. So no write lands between the drop and the inserts. The gate always closes (finally).
  5. It creates a safety backup while already holding the backup lock (through `BackupService`'s private `RunAsync`, given the saved `backup.retention` like **Back up now**, not `CreateAsync`, which would refuse with `BackupRunning`). `RunAsync`/`ApplyRetention` gain an excluded file name: the source file is neither deleted nor counted in that run's retention, so restoring the oldest kept backup never deletes it. If the safety backup fails, the restore stops before the drop with `500 BackupFailed` (as **Back up now**), nothing changes and the gate closes. Its name is in the result and the audit.
  6. `IBackupStore.RestoreAsync`, then `IDatabaseLifecycle.Migrate()` (an older backup gets the newer migrations), then `IJobRepository.AbortRunningAsync` (a job that was Running when the backup was taken; only that call, not the rest of `CrashRecovery`), then every user's security stamp is rotated (new `IUserRepository.RotateAllSecurityStampsAsync`: one `UPDATE` giving each row its own 32-hex stamp, so every session ends at the next request), then `IDiscoveryRepository.Invalidate()` (new: drops cached indexes and any in-flight build's result), then both schedulers are woken so the restored `app_settings` take effect: `BackupService` raises its own `SettingsChanged`, and calls the new public `DatRefreshSettingsService.NotifySettingsChanged()` (which raises that service's event; C# events can't be raised from outside their class). From the drop onward (store restore, `Migrate`, `AbortRunningAsync`, stamps, invalidation, wake-ups, audit) every call uses `CancellationToken.None`: the request token (tab closed, proxy timeout) can only cancel before the drop.
  7. It records `BackupRestored` (details: `<restored file>; safety backup <file>`) after the restore, so the event survives it, and logs the same Warning lines as the startup restore, including the Integrity advice, but without the startup restorer's "Then remove Backup__RestoreFrom" sentences (it has nothing to remove).
  8. Response: `200 { restored, safetyBackup }`, after signing the caller out and issuing an anonymous antiforgery token exactly as `POST /api/auth/logout` does (`Session.SignOutAsync`, `Session.IssueAntiforgery`). The SPA then clears its session state as `+layout.svelte`'s `logout()` does (`auth.set(null)`, `navCounts.reset()`) and also forgets the cached antiforgery call (`resetClient()` from `lib/api/client.ts`, so the next POST fetches a fresh token), shows a toast and goes to `/login` (without the clear, the login page's `$effect` sends a still-set `auth.me` straight back, and the stale `XSRF-TOKEN` makes the login POST `400 AntiforgeryInvalid`). If the request ends without a response (network error, or a proxy's 502/504), the SPA does the same clear (the stale auth cookie is rejected by the stamp check, so `GET /api/auth/antiforgery` then issues an anonymous token), shows a warning toast "The restore may still be running. Sign in again in a minute, then check Backups." and goes to `/login`; a ProblemDetails error (`JobRunning`, `BackupRunning`, `BackupTooNew`, `InvalidBackup`, `Busy`, `BackupFailed`, `RestoreFailed`) is shown in the modal and the page stays.
  9. The live restore neither writes nor reads the startup restorer's `.restored` marker (that marker only guards `Backup:RestoreFrom`).
  10. If the restore fails after the drop, the database may be partial: it returns `500 RestoreFailed` naming the safety backup, and logs Error; the admin can restore the safety backup (live, or startup `Backup:RestoreFrom`).
  11. Only an Admin who has changed their password can call it (`/api/admin` is AdminOnly and the must-change gate answers `403 PasswordChangeRequired` first). Background work outside the job lock (the `Scheduler`'s daily audit purge, `DiscoveryRepository` builds) may fail while the tables are being replaced; each already catches and logs its failure, and `Invalidate()` discards a build's result.
  12. A host shutdown (SIGTERM, 30 s shutdown timeout) during the drop and inserts can still leave a partial database, since `JobShutdownService` waits only for jobs: documented in `deployment.md` (don't stop the container during a restore; restore the safety backup if it happened).
- **B28** DATs tab: an **Automatic refresh** card with **Enabled** (default on) and **Time** (default `04:00`, container local time, `HH:mm`), **Save**, and the next run time. `GET/PUT /api/admin/dats/settings` (Admin) read and save `dats.autoRefresh.enabled` and `dats.autoRefresh.time` in `app_settings` (missing or invalid stored row = default, as `BackupSettings.FromStored`). The PUT body is `{ enabled, time }`, both required, parsed like `AdminEndpoints.ParseBackupSettings`: a non-object body is `400 ValidationFailed` with key `""`; `enabled` not a JSON boolean is `enabled` ("Must be true or false."); `time` failing `BackupSettings.TimeError` (shared, not copied) is `time` with its message. Both return `{ enabled, time, timeZone, nextRunAt }` (`nextRunAt` null when disabled), like the backup status. Not audited, matching backup settings (settings changes are excluded from the audit). `DatRefreshSettingsService` (Core, singleton) owns load, save and the `SettingsChanged` event, as `BackupService` does for backups.
- **B29** `DatRefreshScheduler` (`BackgroundService`) waits on `ScheduleCalculator.NextDaily` with the injected `TimeProvider`, wakes on `DatRefreshSettingsService.SettingsChanged`, and starts the DAT refresh job through `JobRunner.StartAsync(job, JobTrigger.Schedule, requestedBy: null, …)`, as `Scheduler` starts the quick check (no user: the Auditing page's **Scheduled only** finds its rows; there is no "System" user), built through a new `DatRefreshJobFactory` (like `IntegrityJobFactory`) shared with `POST /api/jobs/dat-refresh`, which today builds `DatRefreshJob` inline from its eight dependencies (the factory builds it the same way, the `HttpClients.Dats` client from `IHttpClientFactory`). `StartAsync` returning null means the lock is busy. If the job lock is busy at the due time it retries every minute until it starts or the next day's due time comes (then that day's run is skipped, logged at Information). Missed runs while the app was down aren't caught up. Failures are the job's usual failures (logged, job status Failed). `DatRefreshJobFactory` is a delegate `IJob DatRefreshJobFactory()` registered in `AppHost`, as `IntegrityJobFactory` is. `DatRefreshScheduler` is registered with `AddHostedService<DatRefreshScheduler>()` (not the factory form `Scheduler` and `BackupScheduler` use, which leaves `ImplementationType` null), so `ApiFactory` can remove it by `ImplementationType` as it removes `StorageMigrationStarter`. In the Api tests, `ApiFactory` doesn't host `DatRefreshScheduler` unless a test sets `RunDatRefreshScheduler` (like `RunStorageMigrationStarter`): the stub settings alone can't turn it off in real-database tests, where it would start a real refresh and take the job lock at 04:00, and `DatEndpointsTests` must still read the default `enabled: true`.

### Library folders
- **B30** Startup no longer creates `roms/<system>/{#,A..Z}`. The folders are created when a ROM is first written there. Today's writers already do: `IngestPipeline` (embedded: `Directory.CreateDirectory` before `FirstFreeIn`; external: `ExternalRomPath.ClassifyDirectory` on the bucket, then `Directory.CreateDirectory` when it is `Missing`, which also creates the missing system folder, then a re-classify that must be `Found`), `LibraryEditor.NewZipPath` (move, merge, retitle) and its classify-then-create external paths (rename, move target); `ReviewResolver` writes through `IngestPipeline`; `StorageMigrationJob` only moves out of a game's existing folder; `LibraryZipWriter` refuses a missing folder (callers create first). Step 3 adds tests that prove it, and a create only where a test shows one missing. `ingest/<system>/…` is still created at startup.
- **B31** Once per startup, in `StartupRunner` right after step 7 (`CrashRecovery`, so folders that held only `*.zip.tmp` leftovers are empty by then) and before any job can start, empty library folders are removed: for each registered system, each of the 27 bucket folders (`StorageFolders.Buckets`: `#`, `A`–`Z`; no other names) that is an empty directory, then `roms/<system>` if it is then empty. A folder holding anything (including hidden files or other folders) is left alone. Every folder is classified with `ExternalRomPath.ClassifyDirectory` first, for embedded and external systems alike (today's `EnsureSystemFolders` checks only external ones): only `Found` is a candidate; `Missing` is skipped silently; anything else (a link, unsafe or unreadable) is logged at Warning and skipped, never deleted through. Failures are logged at Warning and never stop startup.
- **B32** Every reader that lists `roms/<system>` tolerates a missing folder (treated as empty). Today's listers already do: `ExternalRomPath.ScanFolder` (returns nothing on Missing; used by `DbSync.ScanZips`, `IntegrityJob.Scan` and `CrashRecovery`), `IntegrityJob.Scan` (`Directory.Exists` on the root), `ExternalRomName` (`ForFolder`, `AllocateZipPathAsync`: `Directory.Exists`), `ExternalZipBackup` and `StorageMigrationJob` (`ClassifyDirectory` = Found first). Readers that open one known file (`LibraryFiles`, `GameMediaRetry`) only meet a missing folder for a ZIP that is gone, which is today's missing-file case. Step 3 proves the listers on a root with no `roms/<system>`.

## Risks
- **Live restore drops every table** while the app runs (`MySqlBackupStore` drops every base table in one statement; DDL isn't transactional). Mitigations: job and backup locks, the maintenance gate (every other request 503 while the safety backup and the restore run, which can take a while on a large library; audit writes held), a safety backup first, migrations, aborted stale jobs and woken schedulers after, every session ended, the advice to run a quick integrity check.
- **Restore ends the Admin's own session** (security stamps and the data-protection keys in the restored DB): the SPA expects it and goes to `/login`. Data-protection keys created after the backup are gone from the database but may still be in the running app's key ring cache, so cookies and antiforgery tokens issued right after the restore may stop working after the next restart or the key ring's periodic reload from the database (about a day), whichever comes first (one more sign-in). Accepted; documented in `deployment.md`.
- **Table rename** (`publisher_logos` → `discovery_logos`): `MySqlBackupStore` dumps whatever tables exist, and restore recreates the backup's own schema before migrations, so old and new backups both restore. `SchemaMigrationTests` covers the migration on a database with existing logos.
- **Lazy library folders**: a code path that assumed `roms/<system>` exists would throw `DirectoryNotFoundException`; step 3 audits every reader and writer and tests a fresh root with no system folders.
- **Empty-folder cleanup deletes directories**: only empty ones, never through a link or unsafe external folder; covered by tests with files, hidden files and links.
- **URL logo download** is a server-side fetch: it reuses `ImageUrlDownloader` (public addresses only, redirects and DNS rebinding checked, bounded read, 15 s), Admin-only.
- **Daily DAT refresh** hits GitHub once a day by default; offline installs log a failed job daily until an Admin turns it off.
- **Fixed footer** can cover content and toasts: `main` padding and the toast offset are part of B10, and the e2e axe scans check both themes.
