# ROM Zip Storage Config

## Summary
Admins get a **ROM Zip Config** tab on the Admin page that lists every system's default ROM storage (inside the game ZIP, or beside it) and its configured (effective) storage. Systems that opt in (only Nintendo DS for now) get a toggle that, after a confirmation, saves the new setting and starts a background job that moves every game's ROMs into or out of its ZIP. Any running job shows a progress indicator in the footer (Admins) that links to a new **Jobs** list page. With no setting stored, every system behaves exactly as today.

## Out of scope
- Toggles for any system other than `nds`. GBA (and every other embedded system) stays fixed in the ZIP; Switch, 3DS and disc systems stay fixed beside it. File-set systems (`FileSets`) can never be configurable.
- Rolling back a partial move: a failed or cancelled run leaves the system mixed (B9) and is resumed, not undone.
- Queueing the toggle behind a running job: a busy job lock refuses it (B6).
- Editing pending games during a move (they stay read-only, B10). While the job itself runs, every library edit on every system already gets `409 JobRunning` (global job lock).
- Cleaning up a ROM file left beside a ZIP by a crash after an embed was published: Integrity reports it as `OrphanFile` (B14).
- A navbar link to the Jobs page; it's reached from the footer and from job pages.
- Footer progress for non-Admins (`/api/jobs/*` is Admin only).

## Behaviour

### Storage setting
- **B1** New `ISystemHandler.RomStorageConfigurable` (default false; `nds` true) and `ISystemHandler.DefaultEmbedRomsInZip` (default `=> EmbedRomsInZip`; `nds` false). `SystemRegistry` checks its storage rules (family mix, `FileSets` needs external, `LegacyEmbeddedRoms` needs external without `FileSets`) on `DefaultEmbedRomsInZip`, and adds: a `RomStorageConfigurable` handler must be `LegacyEmbeddedRoms` and the only handler of its `Family`. NSubstitute returns false for an unconfigured default interface member, so every test substitute that relies on `EmbedRomsInZip` true for a registry rule (e.g. `SystemRegistryTests.Handler`) also sets `DefaultEmbedRomsInZip`.
- **B2** The setting is stored in `app_settings` as `storage.embedRoms.<systemId>` = `true`/`false` (no migration; the key fits `VARCHAR(64)`). No key = the handler default. A new Core singleton `RomStorageSettings` (`IRomStorageSettings`: `bool? Override(string systemId)`, `Task LoadAsync(CancellationToken)`, `Task SetAsync(string systemId, bool embed, CancellationToken)`) loads the keys of the `RomStorageConfigurable` systems only (`ISettingsRepository.GetAsync` takes names; there is no prefix query). `StartupRunner` calls `LoadAsync` right after `database.Migrate()` (steps 5–6, so after a startup restore; before crash recovery (step 7), the starter and any job). `BackupService.RestoreAsync` calls it again after its `database.Migrate()`, next to `datRefresh.NotifySettingsChanged()` (it holds the job lock, so no job sees the change); a restored value that differs from the ZIPs' layout just makes those games pending (B9), resumed from the Resume button. A value other than `true`/`false` is ignored with a warning (default used). Keys of other systems are never read. `SetAsync` writes the database first, then the in-memory value.
- **B3** `NintendoDsHandler` takes `IRomStorageSettings` (optional; null in tests = default) and its `EmbedRomsInZip => settings?.Override(Id) ?? false`. Every existing `handler.EmbedRomsInZip` site except B5a's path-safety checks therefore follows the setting without change: ingest, review resolve, library editor, writer, `/api/systems` `embedRoms`. The value only changes inside the storage job (B7), which holds the job lock, so no job or edit sees it change mid-run. **Ingest-folder handling follows the setting too** (one rule, no exceptions): `IngestFileScanner` :60, `IngestFileDeleter` :100, `IngestJob` :134/:171/:474, `RemovedFileRestorer` :54, `ReviewResolver` :113/:351, `IngestPipeline` :129/:144/:1130/:1158. A DS Review item or Pending row created before a toggle is resolved, deleted or retried under the new setting; Implement checks each of these sites handles a file created under the other mode and tests it (step 3). The path-safety sites are the exception, fixed by B5a, so `StorageFolders` :54 (startup step 4, before the settings load) never depends on the setting.
- **B4** **Per-game storage.** For a `LegacyEmbeddedRoms` handler, `RomStorage.IsEmbedded(handler, game)` is the game's own layout: true when every ROM's `externalFileName` is null (mixed is still invalid, `InfoJsonValidator` unchanged). Other handlers: `handler.EmbedRomsInZip` (unchanged). `RomStorage.IsLegacy` becomes `IsPending(handler, game)` = `LegacyEmbeddedRoms && IsEmbedded(handler, game) != handler.EmbedRomsInZip` (a game waiting to be moved either way); every caller is renamed (`LibraryEditor` guard, `GameMediaRetry`, `IngestPipeline` :883, `ReviewResolver`, `IntegrityJob` :289, `StorageMigrationJob`).
- **B5** **Reads decide per ROM.** Detail, list, ROM download, Zip Contents, info.json, saves list/download, quick play, play and play-disc work for a game in either layout whatever the setting: a ROM with `externalFileName` is opened as an external file, one without as a `roms/` entry. `LibraryEndpoints` :733 and :755 already decide per game (`game.PrimaryIsExternal`) and stay unchanged. Two sites must change: the owner checks in `IngestPipeline` :995 and `ReviewResolver` :215 combine the handler value with the owner row; for a `LegacyEmbeddedRoms` system they decide from the owner row's `ExternalFileName` alone. `IntegrityJob.CheckLocation` (:461–467) accepts either ZIP name rule (S7a) only while `EmbedRomsInZip` is false; it changes to accept either for every `LegacyEmbeddedRoms` system whatever the setting (ZIPs ingested since 2026-11-16 and every ZIP moved by B8 keep external-style names).
- **B5a** **Path safety (G4) ignores the setting.** A `LegacyEmbeddedRoms` system's folders can hold external files in either setting (pending games, B14 leftovers), so every G4 "is this system/folder external" check treats it as external: `(!h.EmbedRomsInZip || h.LegacyEmbeddedRoms)` in `LibraryFiles.OpenFile` :261–262 (checked open), `LibraryTarget.IsExternal` :75 (`NeedsCheck`), `DbSync` :188 (`GuardEquivalentPathsAsync`), `IntegrityJob.WasChecked` :535 (pointer issues) and `StorageFolders.EnsureSystemFolders` :54 (checked folder creation). For `nds` today this is the current behaviour.

### Toggle and job
- **B6** `PUT /api/admin/rom-storage/{systemId}` (Admin only), body `{ "embedRoms": bool }`:
  - unknown system → `404`; missing/invalid body → `400` validation; system not `RomStorageConfigurable` → `400` ProblemDetails `code` `NotConfigurable`;
  - `embedRoms` equal to the effective value → `204`, nothing saved, no job;
  - otherwise starts the storage job with that change through `JobRunner.StartAsync(trigger Manual, requestedBy caller)` → `202 { jobId }`; busy → `409 JobRunning` (`DatEndpoints.JobRunning`) and **nothing is saved**.
- **B7** The storage job (`StorageMigrationJob`, `JobType.StorageMigration`, cancellable) optionally carries a change: `StorageMigrationJobFactory` becomes `IJob StorageMigrationJobFactory(RomStorageChange? change = null)` with `record RomStorageChange(string SystemId, bool Embed)` in `Core/Storage`; the starter and `POST /api/jobs/storage-migration` pass none. Its first action, under the lock: if the change equals the effective value (another request got there first), nothing is saved or audited; otherwise `RomStorageSettings.SetAsync`, then audit `RomStorageChanged` (system id, Details `in ZIP` / `beside ZIP`, the requesting Admin). If saving fails the job fails before moving anything and the setting is unchanged. It then lists candidates: games of every `LegacyEmbeddedRoms` system whose layout differs from the system's effective storage (`IGameRepository.ListStorageMovesAsync(embedSystemIds, externalSystemIds)`, replacing `ListLegacyEmbeddedAsync`: games of embed systems with any ROM `external_file_name IS NOT NULL`, of external systems with any ROM `external_file_name IS NULL`; ordered by ZIP path). One job item per game (`Migrated` / `Error` with a reason, as today), summary `{ migrated, error }`; cancel and shutdown stop between games; a game is never left half-moved.
- **B8** Per game the job re-opens the ZIP and skips it when it's no longer pending (B4); if that skipped game's DB rows still show the old layout (a crash between publish and mirror), it re-mirrors the ZIP (`MirrorEntry`, as after a move) and records the item as `Migrated`, so `pendingGames` and the starter clear. **Out of the ZIP** (external target): exactly today's S5–S6 (`<ZipBase>.<rom fileName>` names via `ExternalRomName`, crash-leftover reuse, free-space check, audit `RomsExternalized`). **Into the ZIP** (embedded target, new):
  1. Free space: the game's ROMs + its ZIP + `SpaceMarginBytes` on the library volume, else `Error` `InsufficientSpace`.
  2. Each external file is opened through `ExternalRomPath` (checked, snapshot taken); a missing, linked or changed file → `Error` `IoError`.
  3. The ZIP is rewritten through `LibraryZipWriter.WriteCheckedAsync` with every ROM as a `roms/<fileName>` entry streamed from its file and `externalFileName` null (notes, images and saves carried; never refused on `SavesUnreadable`); each file is hashed while it is streamed into the new ZIP, and its size and SHA-1 are checked against `info.json` before the ZIP is published; a mismatch → `Error` `VerifyFailed`, ZIP untouched, files untouched. The ZIP keeps its path.
  4. The ZIP is mirrored (`DbWriteFailed` on failure, as today), then each external file is deleted if its snapshot is unchanged since step 2 (otherwise kept and logged). Audit `RomsEmbedded` (new) with `n ROM(s), m bytes`.
- **B9** **Mixed state.** A cancelled or failed run, or a crash, leaves some games in the old layout. They're readable (B5) and pending (B10). The setting is never reverted by the job. Toggling again starts a job toward the new value; games already there are skipped by the query.
- **B10** Pending games are refused by every write exactly as S3 of the save-state spec refuses legacy games (`409 StorageMigrationPending`; ingest/review into one → item `Error` `StorageMigrationPending`, file stays in ingest). The ProblemDetails title changes to "This game's ROMs are being moved by the storage job. Try again when it has finished." (direction-neutral).
- **B11** **Resume.** The existing routes generalize: `GET /api/jobs/storage-migration` → `200 { pendingGames }` (renamed from `legacyGames`); `POST` → `202 { jobId }`, `204` when none pending, `409 JobRunning`. `StorageMigrationStarter` uses `ListStorageMovesAsync`, so after a restart it resumes pending moves in either direction (unchanged retry rules).
- **B12** `GET /api/admin/rom-storage` (Admin only) → `200 [{ id, displayName, defaultEmbedRoms, embedRoms, configurable, pendingGames }]`, one per handler, ordered as `/api/systems`; `pendingGames` from the B7 query grouped by system (0 for non-configurable systems).
- **B13** Ingest and review of new DS input follow the effective setting (B3): with `nds` embedded, a new DS release is stored as a `roms/` entry (the embedded pipeline, as before 2026-11-16); with it external, beside the ZIP. A byte-identical copy of an existing DS ROM in either layout is a `Duplicate` (owner checks per B5).
- **B14** Integrity: `LegacyEmbeddedStorage` (warning, unchanged type name) is reported for every pending game in either direction (no SPA change). A file left beside a ZIP by a crash between B8 step 3 and its delete is unclaimed and reported as `OrphanFile`.

### SPA
- **B15** Admin page gets a **ROM Zip Config** tab (`/admin/rom-storage`, after Settings). A table: **System** (logo/badge and name), **Default Behaviour** ("Stored in ZIP" / "Beside ZIP"), **Configured Behaviour** (effective value; plus a warning badge "N games still to move" when `pendingGames` > 0), and a last column: for configurable systems a button "Store in ZIP" or "Store beside ZIP" (the opposite of the configured value), disabled while any job runs; empty for the rest. When any configurable system has `pendingGames` > 0 a **Resume moves** button above the table calls `POST /api/jobs/storage-migration`.
- **B16** The toggle opens `ConfirmModal` with the direction's text. Both directions say: every game of the system is rewritten one at a time; this takes a long time (hours for a large library) and is heavy on disk and CPU; until it ends no other job (ingest, integrity, scheduled checks) can run and no game of any system can be edited; afterwards, games it didn't reach (cancel or error) stay read-only until moved; the job can be cancelled from the Jobs page and resumed later (games already moved stay moved); free space of about one game's ROMs + ZIP is needed. **Into ZIP** adds: saving a game state or battery save for this system rewrites the whole ZIP including its ROM (up to 512 MiB), so saves get slower. **Beside ZIP** adds: each ROM becomes a separate file next to its ZIP. Confirm → `PUT`; `202` → `jobs.refresh()` and a success toast with a link to the Jobs page; `204` → reload the table; `409 JobRunning` → `toasts.jobRunning`; other errors → `ErrorAlert`. The table reloads when the job ends (`jobs.onEnded`).
- **B17** **Footer indicator.** For Admins, `AppFooter` watches `jobs` and, while a job runs, shows `<label> <current>/<total>` with a small progress bar (`total` 0 → an indeterminate bar), linking to `/jobs`. Labels come from a new `jobLabel(type)` in `src/lib/jobs.ts` (`Ingest` "Ingest", `Integrity` "Integrity check", `DatRefresh` "DAT refresh", `MediaRetry` "Media retry", `ReviewResolve` "Review", `StorageMigration` "Moving ROMs"). The `jobs` store also polls every 15 s while watched and idle (1.5 s while a job runs, as today), so a job started elsewhere (scheduler, starter, another tab) appears.
- **B18** **Jobs page** `/jobs` (Admin only, `AdminOnly`): a "Running" card for the current job (label, progress, current item, Cancel when `isCancellable`, link to `/jobs/<id>`) or "No job running", then a paged table of recent jobs from `GET /api/jobs` (label, trigger, status, started, ended, link to `/jobs/<id>`), refreshed when the running job ends. The existing `/jobs/[id]` page is unchanged apart from a "All jobs" link back to `/jobs`.
- **B19** Integrity page: the migration button's text becomes **Resume ROM storage moves**, shown while `pendingGames` > 0.

## Risks
- **Data loss during moves:** the into-ZIP path verifies size and SHA-1 before publishing and deletes external files only after the verified ZIP is published and mirrored, and only if unchanged; any failure before publish leaves the game as it was (B8).
- **Disk and time:** every DS ZIP is rewritten with its ROM (up to 512 MiB each); the job holds the lock for hours on a large library, blocking ingest and scheduled jobs. Mitigated by the modal's warning, per-game free-space checks, cancel/resume (B9, B11).
- **Saves on embedded DS** rewrite the full ZIP (accepted, warned in B16).
- **Dynamic `EmbedRomsInZip`:** safe only because the value changes under the job lock (B3); code that caches it across jobs would break — Implement greps for any such cache.
- **Backup restore:** a restored `app_settings` may disagree with the ZIPs on disk; the settings reload (B2) turns those games pending (refused, readable) until an Admin resumes the moves.
- **Downgrade:** an older app version can't read DS ROMs inside ZIPs only if it predates legacy reading; versions since 2026-11-16 read both. Noted in deployment docs.
