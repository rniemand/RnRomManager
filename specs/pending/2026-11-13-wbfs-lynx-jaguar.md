# WBFS, Atari Lynx and Jaguar, systems table and screenshots

## Summary
Wii games in the `.wbfs` container are accepted and identified by the disc's game ID against the Redump DAT's serials (their hashes can never match the DAT's `.iso` hashes). Two new cartridge systems, Atari Lynx and Atari Jaguar, store their ROMs in the game ZIP and play in the browser (EmulatorJS `handy` and `virtualjaguar`; `handy` boots without a BIOS). The README gets a supported-systems table that a test keeps in step with the registered handlers, and the README screenshots are regenerated by a new Playwright script.

## Out of scope
- Split WBFS files (`.wbf1`, `.wbf2`…, made for FAT32): not picked up; join them first.
- Converting `.wbfs` to `.iso` (or the reverse), and any other Wii/GameCube container (`.rvz`, `.wia`, `.ciso`, `.nkit.iso`).
- Serial matching for `.iso` files: an `.iso` that misses its SHA1 still goes to Review as today.
- Resolving a `.wbfs` Review item by picking a DAT entry keeps today's behaviour (method `Manual`, `(Unverified)` name).
- Lynx `.bll`/`.o` homebrew files, Jaguar CD.
- BIOS files for browser play: `handy` treats `lynxboot.img` as optional and skips the boot ROM without it, so no BIOS folder, endpoint or `EJS_biosUrl`.
- Screenshots of pages the README doesn't already show.

## Behaviour

### WBFS
- **B1** `WiiHandler.RomExtensions` becomes `[".iso", ".wbfs"]` (`.iso` stays `[0]`). GameCube doesn't list `.wbfs`; ingest step 1 accepts a file whose extension any family member lists and only the members listing it are eligible (`IngestPipeline` I3), so a `.wbfs` in `ingest/gc/` is only eligible for Wii and is stored as Wii. Size limits are unchanged (32 KiB–9 GiB).
- **B2** `NintendoDiscHeader.Read` recognises a WBFS container: ASCII `WBFS` at 0x00 and a byte at 0x08 (`hd_sec_sz_s`) in 9–12. The first disc's info starts at `1 << hd_sec_sz_s` (512 in practice) with a 0x100-byte copy of the disc header (libwbfs `wbfs_disc_info_t.dhead`); exactly those 0x100 bytes are read like a bare disc (game ID, disc number, version, magic, title from the copy's 0x20), so the title never runs into the WBFS block table that follows. The returned `Fields` gain `container`: `"wbfs"` for a WBFS file, `"iso"` otherwise (so existing `.iso` headers gain `container: "iso"`). A `WBFS` file with an out-of-range sector shift, or fewer than 0x100 bytes after the offset, gives a not-plausible header classified as the caller with `container: "wbfs"` and the other fields null (never throws), so it fails `InvalidHeader` like any unreadable disc. Ingest passes an external file's first MiB, which covers every allowed shift.
- **B3** The DAT parser reads `serial` from each `rom` block, falling back to its `game` block; absent → null. `DatRom` gains `string? Serial = null` (titledb rows keep null). A serial may list several values separated by `,` (each trimmed); libretro's Wii DAT has one value per entry, other Redump DATs list several.
- **B4** `DatStore.BySerialCode(string code)` returns, in DAT order, the ROMs whose serial (any listed value) has `code` as its second `-`-separated segment, compared case-insensitively (`RVL-SP3E-USA-B0` → `SP3E`), **distinct by DAT game name** (first ROM wins, so a game repeated once per serial, or matched by two of its listed serials, appears once). It indexes only the ROMs left after the extension filter (`.iso` is still a Wii extension, so Wii entries stay).
- **B5** Serial matching runs in ingest step 4 only when the SHA1 lookup found nothing, the file's extension is `.wbfs`, and the eligible handler's header is plausible with `container` = `"wbfs"` and a 6-character `gameId`. (A bare disc image renamed `.wbfs` has `container: "iso"` and goes to Review; WBFS content named `.iso` also goes to Review, as today.) Code = `gameId[..4]`. Candidates from `BySerialCode(code)` are narrowed by tags parsed with `NoIntroName.Parse(gameName)`:
  1. disc: header `discNumber` 0 keeps entries whose `Flags` have no `Disc <n>` value or have `Disc 1`; `n > 0` keeps entries with the flag `Disc <n+1>`;
  2. revision: header `version` 0 keeps entries with `Revision` null; `n > 0` keeps entries with `Revision` = `Rev <n>`; other tags are ignored.
  Exactly one candidate → identified (B6). Zero or several → Review as today (`NoDatMatch`, suggestions from the header title).
- **B6** A serial-identified release is built by the same path as a SHA1 match of a `FileSets` system: `LibretroRelease(entry, store, file, external: true, tagsFromGameName: true)` with `Method` = `Serial` instead of `Dat`. So the file name is the DAT ROM stem + `.wbfs` (kept exactly; `NameTaken` if taken), tags come from the DAT game name, grouping/metadata/box art are as for a SHA1 match; the only differences are `identification.method` = `Serial` and the hashes being the `.wbfs` file's own. No `Unverified` flag.
- **B7** `IdentificationMethod` gains `Serial`. info.json schema becomes **v7**: v7 only adds `Serial` as an allowed `identification.method` (the enum's string converter is what rejects unknown methods; `InfoJsonValidator` has no method rule and is unchanged); the v6→v7 upgrader (`InfoJsonUpgraderV6`, `FromVersion` 6) changes nothing (the reader sets the version). An app that only knows v6 treats a v7 file as `InfoJsonNewerSchema` (read-only). `roms.id_method` is `VARCHAR(16)`, so no migration. Metadata lookups (`LibraryEditor.MetadataFor`) treat `Serial` like `Manual` (find the entry by `datGameName`); media retry treats it like `Dat`. The SPA's `identificationMethod` union gains `'Serial'` and the game page's `identifiedBy` label map shows it as `Game ID`. A `.wbfs` resolved in Review is unchanged (Manual, keeps `.wbfs`).

### Atari Lynx and Jaguar
- **B8** Two handlers in `RnRomManager.Systems.Atari`, each its own family, `EmbedRomsInZip` true, libretro No-Intro DAT with all four metadat kinds:

  | | Lynx | Jaguar |
  |---|---|---|
  | `Id` / `Family` | `lynx` | `jaguar` |
  | `DisplayName` / `ShortName` | `Atari Lynx` / `Lynx` | `Atari Jaguar` / `Jaguar` |
  | `RomExtensions` | `.lnx`, `.lyx` | `.j64`, `.jag`, `.rom`, `.abs`, `.cof` |
  | Size | 1 KiB – 1 MiB | 16 KiB – 16 MiB |
  | `DatName` | `Atari - Lynx` | `Atari - Jaguar` |
  | `BrowserCore` | `handy` | `virtualjaguar` |
- **B9** Lynx `ReadHeader`: a file starting with ASCII `LYNX` returns a plausible header classified `lynx` with fields `bank0PageSize`, `bank1PageSize`, `version` (u16 LE at 0x04/0x06/0x08), `title` (0x0A, 32 bytes, Latin-1 up to the first NUL, trimmed, null if empty), `manufacturer` (0x2A, 16 bytes, same rules), `rotation` (0x3A: `none`/`left`/`right` for 0/1/2, else the number). Anything else (headerless `.lyx`, a file shorter than 64 bytes) → null, so it goes to Review as headerless. No `NormalizeForHashing`: the DAT lists headered `.lnx` and headerless `.lyx` dumps separately.
- **B10** Jaguar `ReadHeader` always returns null (no standard header), like Atari 2600.
- **B11** The play page accepts `handy` and `virtualjaguar` (`params.js`'s core list). Both cores (`-wasm` and `-legacy-wasm` `.data` files and `reports/<core>.json`; not the `-thread-` variants, as for `gambatte`/`mgba`) are vendored at 4.2.3 (`@emulatorjs/core-handy`, `@emulatorjs/core-virtualjaguar`, exact versions) and listed in `licenses.json`: `@emulatorjs/core-handy`, `Zlib`, `https://github.com/libretro/libretro-handy`; `@emulatorjs/core-virtualjaguar`, `GPL-3.0`, `https://github.com/libretro/virtualjaguar-libretro`.

## Risks
- **Serial false positive**: a hacked `.wbfs` keeps its original game ID and would be stored as the clean entry. Accepted (user decision); the file's own hashes are recorded and the method `Serial` marks it.
- **Schema bump**: v7 files are read-only for older apps; same pattern as v4–v6.
- **Lynx/Jaguar play** can't be tested automatically (no real ROMs are committed): a headerless `.lyx` may not boot in `handy`, and `handy` runs without the boot ROM. Play is still offered; the PR says so.
- **Bundle size**: two more cores (~7.5 MB unpacked) in the image.
- **Fixtures**: every fixture loading all systems' DATs must include Lynx and Jaguar, or `DatsMissing` fails ingestion tests (step 6 lists them).
