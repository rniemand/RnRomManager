# WBFS, Atari Lynx and Jaguar, systems table and screenshots

## Summary
Wii games in the `.wbfs` container are accepted and identified by the disc's game ID against the Redump DAT's serials (their hashes can never match the DAT's `.iso` hashes). Two new cartridge systems, Atari Lynx and Atari Jaguar, store their ROMs in the game ZIP and play in the browser (EmulatorJS `handy` and `virtualjaguar`); Lynx play needs a BIOS file the Admin supplies. The README gets a supported-systems table that a test keeps in step with the registered handlers, and the README screenshots are regenerated by a new Playwright script.

## Out of scope
- Split WBFS files (`.wbf1`, `.wbf2`…, made for FAT32): not picked up; join them first.
- Converting `.wbfs` to `.iso` (or the reverse), and any other Wii/GameCube container (`.rvz`, `.wia`, `.ciso`, `.nkit.iso`).
- Serial matching for `.iso` files: an `.iso` that misses its SHA1 still goes to Review as today.
- Resolving a `.wbfs` Review item by picking a DAT entry keeps today's behaviour (method `Manual`, `(Unverified)` name).
- Lynx `.bll`/`.o` homebrew files, Jaguar CD.
- An upload UI for BIOS files; the Admin copies the file into the volume.
- Screenshots of pages the README doesn't already show.

## Behaviour

### WBFS
- **B1** `WiiHandler.RomExtensions` becomes `[".iso", ".wbfs"]` (`.iso` stays `[0]`). GameCube doesn't list `.wbfs`, so a `.wbfs` in `ingest/gc/` is only eligible for Wii (existing external-family rule) and is stored as Wii. Size limits are unchanged (32 KiB–9 GiB).
- **B2** `NintendoDiscHeader.Read` recognises a WBFS container: ASCII `WBFS` at 0x00 and a byte at 0x08 (`hd_sec_sz_s`) in 9–12. The disc header copy then starts at `1 << hd_sec_sz_s` (512 in practice) and is read exactly like a bare disc (game ID, disc number, version, magic, title from the copy's 0x20). The returned `Fields` gain `container`: `"wbfs"` for a WBFS file, `"iso"` otherwise (so existing `.iso` headers gain `container: "iso"`). A `WBFS` file with an out-of-range sector shift, or one too short for the copy, gives a not-plausible header classified as the caller (never throws), so it fails `InvalidHeader` like any unreadable disc.
- **B3** The DAT parser reads `serial` from each `rom` block, falling back to its `game` block; absent → null. `DatRom` gains `string? Serial = null` (titledb rows keep null). A serial may list several values separated by `,` (each trimmed).
- **B4** `DatStore.BySerialCode(string code)` returns, in DAT order, the ROMs whose serial (any listed value) has `code` as its second `-`-separated segment, compared case-insensitively (`RVL-SP3E-USA-B0` → `SP3E`), **distinct by DAT game name** (first ROM wins, so a game repeated once per serial, or matched by two of its listed serials, appears once). It indexes only the ROMs left after the extension filter (`.iso` is still a Wii extension, so Wii entries stay).
- **B5** Serial matching runs in ingest step 4 only when the SHA1 lookup found nothing, the file's extension is `.wbfs`, and the eligible handler's header is plausible with `container` = `"wbfs"` and a 6-character `gameId`. (A bare disc image renamed `.wbfs` has `container: "iso"` and goes to Review; WBFS content named `.iso` also goes to Review, as today.) Code = `gameId[..4]`. Candidates from `BySerialCode(code)` are narrowed by tags parsed with `NoIntroName.Parse(gameName)`:
  1. disc: header `discNumber` 0 keeps entries with no `(Disc N)` tag or `(Disc 1)`; `n > 0` keeps `(Disc n+1)`;
  2. revision: header `version` 0 keeps entries with no revision; `n > 0` keeps revision `n` (`(Rev n)`); other tags are ignored.
  Exactly one candidate → identified (B6). Zero or several → Review as today (`NoDatMatch`, suggestions from the header title).
- **B6** A serial-identified release is built by the same path as a SHA1 match of a `FileSets` system: `LibretroRelease(entry, store, file, external: true, tagsFromGameName: true)` with `Method` = `Serial` instead of `Dat`. So the file name is the DAT ROM stem + `.wbfs` (kept exactly; `NameTaken` if taken), tags come from the DAT game name, grouping/metadata/box art are as for a SHA1 match; the only differences are `identification.method` = `Serial` and the hashes being the `.wbfs` file's own. No `Unverified` flag.
- **B7** `IdentificationMethod` gains `Serial`. info.json schema becomes **v7**: v7 only adds `Serial` as an allowed `identification.method`; the v6→v7 upgrader changes nothing but the version. An app that only knows v6 treats a v7 file as `InfoJsonNewerSchema` (read-only). `roms.id_method` is `VARCHAR(16)`, so no migration. Metadata lookups (`LibraryEditor.MetadataFor`) treat `Serial` like `Manual` (find the entry by `datGameName`); media retry treats it like `Dat`. The SPA's `identificationMethod` union gains `'Serial'` and the game page's `identifiedBy` label map shows it as `Game ID`. A `.wbfs` resolved in Review is unchanged (Manual, keeps `.wbfs`).

### Atari Lynx and Jaguar
- **B8** Two handlers in `RnRomManager.Systems.Atari`, each its own family, `EmbedRomsInZip` true, libretro No-Intro DAT with all four metadat kinds:

  | | Lynx | Jaguar |
  |---|---|---|
  | `Id` / `Family` | `lynx` | `jaguar` |
  | `DisplayName` / `ShortName` | `Atari Lynx` / `Lynx` | `Atari Jaguar` / `Jaguar` |
  | `RomExtensions` | `.lnx`, `.lyx` | `.j64`, `.jag`, `.rom`, `.abs`, `.cof` |
  | Size | 1 KiB – 1 MiB | 16 KiB – 16 MiB |
  | `DatName` | `Atari - Lynx` | `Atari - Jaguar` |
  | `BrowserCore` | `handy` (needs BIOS, B11) | `virtualjaguar` |
- **B9** Lynx `ReadHeader`: a file starting with ASCII `LYNX` returns a plausible header classified `lynx` with fields `bank0PageSize`, `bank1PageSize`, `version` (u16 LE at 0x04/0x06/0x08), `title` (0x0A, 32 bytes, Latin-1 up to the first NUL, trimmed, null if empty), `manufacturer` (0x2A, 16 bytes, same rules), `rotation` (0x3A: `none`/`left`/`right`, else the number). Anything else (headerless `.lyx`, a file shorter than 64 bytes) → null, so it goes to Review as headerless. No `NormalizeForHashing`: the DAT lists headered `.lnx` and headerless `.lyx` dumps separately.
- **B10** Jaguar `ReadHeader` always returns null (no standard header), like Atari 2600.
- **B11** `ISystemHandler` gains `BrowserBios BrowserBios => null` with `record BrowserBios(string FileName, string Md5)`; Lynx returns `("lynxboot.img", "fcd403db69f54290b51035d82f835e7b")`. The registry refuses a BIOS without a `BrowserCore` at startup. Startup creates `<Paths:Cache>/bios/` the same way (and with the same failure handling) as the cache's other subfolders. The file name is matched exactly (case-sensitive on Linux).
- **B12** A system with a `BrowserBios` reports `browserCore` (game list and game detail) only while `<Paths:Cache>/bios/<FileName>` exists and its MD5 matches (`BiosStore`, re-checked when the file's size or last-write time changes). Otherwise `browserCore` is null, so no Play button; a wrong MD5 logs one warning per change of the file. The SPA is unchanged.
- **B13** `GET /api/emulator/bios/{core}` (any signed-in user) returns the BIOS bytes for the handler whose `BrowserCore` is `core` and that has a `BrowserBios`, as `application/octet-stream` with `Cache-Control: private, no-cache` and `ETag` = its MD5 (a matching `If-None-Match` → 304), so a replaced file is picked up at once. 401 when signed out; 404 `NotFound` for an unknown core, a core without a BIOS, or a missing/mismatched file.
- **B14** The play page accepts `handy` and `virtualjaguar`. For a core in `params.js`'s `biosCores` (`handy`) it sets `EJS_biosUrl` to `/api/emulator/bios/<core>` before loading `loader.js`. Both cores (`-wasm` and `-legacy-wasm` `.data` files and reports) are vendored at 4.2.3 like `gambatte`/`mgba`, with their licences in `licenses.json`.

## Risks
- **Serial false positive**: a hacked `.wbfs` keeps its original game ID and would be stored as the clean entry. Accepted (user decision); the file's own hashes are recorded and the method `Serial` marks it.
- **Schema bump**: v7 files are read-only for older apps; same pattern as v4–v6.
- **Lynx headerless `.lyx`** may not boot in `handy`; Play is still offered. No real ROMs are committed, so this can't be tested automatically; the PR says so.
- **BIOS** is never shipped or committed; tests use a synthetic file whose MD5 is configured through a test handler, not the real one.
- **Bundle size**: two more cores (~7.5 MB unpacked) in the image.
- **Fixtures**: every fixture loading all systems' DATs must include Lynx and Jaguar, or `DatsMissing` fails ingestion tests.
