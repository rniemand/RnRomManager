# Save State Management

## Summary
Every game ZIP gets a `saves/` folder holding save states (EmulatorJS snapshots) and battery saves (in-game saves), described by `saves/saves.json`. The Game detail page gets a **Saves** tab where any signed-in user uploads, renames, re-describes, replaces, downloads, deletes and plays saves. The browser Play dialog gets two buttons that copy the running game's state or battery save into the ZIP on demand, so the server is written only when a user asks.

First, Nintendo DS ROMs (up to 512 MiB) move out of the ZIP to files next to it, like Switch ROMs, so DS ZIPs stay small and save writes don't rewrite a 512 MiB ZIP. Existing embedded DS ROMs are pulled out by a one-off background job that starts automatically at startup.

## Out of scope
- Automatic syncing of EmulatorJS's in-browser (IndexedDB) battery saves to the server: no interval, close or unload hook writes the ZIP.
- Per-user save folders or privacy: saves are shared by every user of the library.
- PSP (`play-psp.html`, its own tab): no save buttons and no Play-with-save. PSP saves can still be uploaded and downloaded on the Saves tab.
- Battery-save export for cores that don't expose SRAM through EmulatorJS (`desmume`, `opera`, `ppsspp`): the battery button is hidden for them; states still work where the core supports them.
- Converting saves between emulators or validating save contents: bytes are stored as given.
- A database mirror of saves: the list is read from the ZIP on request.
- Moving any other embedded system out of its ZIP, or a setting to choose storage per system.
- Moving external DS ROMs back into ZIPs.
- Re-assigning a save to another release (an orphaned save, B4, can't be re-linked; upload it again instead).

## Behaviour

### Nintendo DS storage
- **S1** The `nds` handler becomes external: `EmbedRomsInZip` false, `FileSets` false (one `.nds` file per release, like Switch). New DS releases (ingest, review resolve) are stored as `<ZipBase>.<rom fileName>` files next to the ZIP through the existing external path (`ExternalRomName.Allocate`, `ExternalRomMove`, `info.json` `externalFileName`); title edit, move, merge, release delete (to `ingest/nds/_removed`) and game delete behave as for Switch. Ingest of DS input follows the external pipeline in full (its archive handling, file-age, hashing, `source_path` and duplicate rules); these documented DS outcomes must hold and are tested: a loose `.nds` and one inside a ZIP/7z are stored external; an invalid header CRC is `InvalidHeader` (failed); a valid-CRC unmatched ROM goes to Review; below 512 bytes or above 512 MiB fails as today; a byte-identical copy of an existing external DS ROM is a duplicate; so is a copy of a legacy game's embedded ROM (SHA-1 match), with no repair (the `IngestPipeline` cross-mode rule, :999, sees an embedded owner and an external input).
- **S2** New `ISystemHandler.LegacyEmbeddedRoms` (default false; `nds` true; `SystemRegistry` allows it only on external, non-`FileSets` handlers). For such a handler, `InfoJsonValidator` (which checks `info.json` only, never ZIP entries) also accepts a game whose ROMs **all** have `externalFileName` null (each is then an embedded `roms/` entry, verified by the writer and integrity as for any embedded game); a game mixing null and set `externalFileName` is still invalid. So existing DS ZIPs keep loading, listing, downloading and playing until they are migrated.
- **S3** A **legacy game** is a game of a `LegacyEmbeddedRoms` system whose `info.json` has embedded ROMs. Every write that changes its ZIP or files refuses instead of taking the external path: `LibraryEditor` patch (title/metadata), release delete, move (as source or target), merge (either side), game delete, cover/image add/delete/set cover/media retry for that game (`LibraryEditor.RetryMediaAsync`; the batch `MediaRetryJob` gets `Skipped` from `GameMediaRetry.RetryAsync` for a legacy game, with no lookup and no write), the release-note save and delete routes, and save operations (B8–B11) return `409 StorageMigrationPending`; ingest and review resolve of a new release into that game end the item as `Error` `StorageMigrationPending` and leave the file in ingest (retried on the next import). Ingest repair needs no guard: every DS input is external and a legacy owner's ROMs are embedded, so the `IngestPipeline` cross-mode rule (:999, with S3a) never repairs a legacy game, and a matching input is a `Duplicate` (S1). The check runs before any other conflict check, so it wins over `SavesUnreadable`. Ratings, favourites and collection membership are database-only and unaffected. Reads (detail, list, ROM download, info.json, Zip Contents, saves list/download, play) are unaffected. The ProblemDetails title is "This game's ROMs are being moved out of its ZIP. Try again when the storage migration job has finished."; the SPA shows it through the existing error paths (each page's `ErrorAlert` or error toast), and `toasts.jobRunning` isn't used for it.
- **S3a** **Effective storage.** One helper, `RomStorage.IsEmbedded(handler, InfoJsonGame)` (true when the handler embeds, or when it's `LegacyEmbeddedRoms` and every ROM is embedded), replaces the handler-wide `EmbedRomsInZip` test only where the game's `info.json` or ROM rows are already at hand: `IntegrityJob` (:524; :453 is S7a), the `IngestPipeline` repair rule (:999) and the S3 guard in `LibraryEditor`/`IngestPipeline`/`ReviewResolver`. Every other site keeps the handler value. `LibraryFiles.OpenFile` (:245), `LibraryTarget` (:75) and `DbSync` (:188) have no game info, and for an external handler they only add the stricter checked open or path guard, which an embedded legacy ZIP also passes. `MediaService` (:84) is a thumbnail-fetch deadline, not storage. ROM download and play already decide per ROM (`LibraryDownload` :42, `canPlay`). Sites that act on ingest-folder files, not on a library game, also keep the handler value, so new DS input is handled as external: `IngestJob` (:134, :171, :477), `IngestFileScanner`, `IngestFileDeleter` (:100), `RemovedFileRestorer` (:54, restores into `ingest/nds/`, never next to a ZIP), `StorageFolders` (:60), `IngestPipeline` (:141, and its `IsExternal(IngestFile)` at :1155). The handler value also stays where the S3 guard has already refused a legacy game before the check runs (`LibraryEditor` :58, :572, :1017, :1439; `ReviewResolver` :214, :308), and in `LibraryEndpoints` :37–38 (`/api/systems` `embedRoms`, a per-system flag). `SystemRegistry` and `InfoJsonValidator` change only as S2 says. Implement re-greps `EmbedRomsInZip` and classifies any site not listed here the same way.
- **S4** **Storage migration job** (`JobType.StorageMigration`, new `JobTrigger.Startup`; both fit the existing `VARCHAR(16)` columns, no schema migration). Its `IJob.Mode` is null (the SPA's `mode` union already allows null); the starter passes `requestedBy` null, so its audit rows carry no user (`JobContext`'s scheduled-run actor), and the Admin route passes the caller's id as `/jobs/integrity` does. A hosted service, `StorageMigrationStarter` (a `BackgroundService` registered in `AppHost`), first awaits `IHostApplicationLifetime.ApplicationStarted` (so `StartupRunner` has finished and Kestrel is listening; it never blocks startup or `/health/ready`). It checks the database for games of `LegacyEmbeddedRoms` systems that still have ROMs with `external_file_name IS NULL` (`IGameRepository.ListLegacyEmbeddedAsync`; the same query gives the job its candidates and the `GET` route its count; it only selects candidates, and S5's re-open of the ZIP decides); if any, it starts the job through `JobRunner.StartAsync` without awaiting the job itself (it holds the job lock, so edits get `409 JobRunning` meanwhile; cancellable; shutdown stops it between games). If the start returns busy (another job runs) or the check throws (logged), it tries again every 5 minutes on the injected `TimeProvider` until no legacy games remain or a run has started; a run that ends with `Error` items isn't retried automatically (Admins re-run it). Admins can also start it from the Integrity page (**Move DS ROMs out of ZIPs**, shown only while `legacyGames` > 0). Routes, in `IntegrityEndpoints` next to `/jobs/integrity` and like it `AdminOnly`: `GET /api/jobs/storage-migration` → `200 { legacyGames: <count of legacy games> }`; `POST /api/jobs/storage-migration` → `202 { jobId }` (as `/jobs/integrity`), `204` when no legacy games remain, `409 JobRunning` (`DatEndpoints.JobRunning`) when busy.
- **S5** Per legacy game, the job: re-opens the ZIP (skips it if it's no longer legacy); for each embedded ROM streams the entry to `<Paths:Cache>/work/storage-migration/<guid>.tmp` (cleaned by crash recovery; nothing temporary is ever written next to a ZIP) while hashing, and checks size and SHA-1 against `info.json`. It then picks the name: it walks `ExternalRomName.Build(zipBase, fileName, n)` for n = 1, 2, …; the first candidate that doesn't exist is taken (the same result `Allocate` gives), but a candidate that exists, is a regular file, is claimed by no ROM row in the database, and has the ROM's size and SHA-1 (a leftover from a crash after the move) is reused and the temp file deleted. Otherwise the temp file is moved there without replacing (`ExternalRomMove`, a verified copy across volumes). It then writes the ZIP through `LibraryZipWriter.WriteCheckedAsync` with every ROM's `externalFileName` set, no `roms/` entries, and those files in `ExternalFiles` (notes, images and saves carried as on any write, including B3's byte-for-byte case: the job never refuses on `SavesUnreadable`), and mirrors it to the database. If any step fails before the ZIP is published, the files it created for that game are deleted and the ZIP is untouched; the item is `Error` with the reason and the next game continues.
- **S6** Each game is one job item: `file_id` = the game id, `system_id` = `nds`, `source_path` = the ZIP's library path (`AuditPaths.Library`), `outcome` `Migrated` or `Error`, `reason` the code (`InsufficientSpace`, `VerifyFailed`, `ZipUnreadable`, `Unexpected`, …, all ≤ 64 chars). Each migrated game records one audit row `RomsExternalized` (path = the ZIP, details = `<n> ROM(s), <bytes> bytes`). Before a game, the job reads `DriveInfo(<ZIP folder root>).AvailableFreeSpace` and the cache volume's; it needs the game's total embedded ROM size plus the ZIP's size plus 64 MiB on the library volume (and the largest ROM on the cache volume when it's a different volume); if short, that item fails with `InsufficientSpace`. If free space can't be read (e.g. a network share), it logs a warning and proceeds.
- **S7** Integrity reports a legacy game as `LegacyEmbeddedStorage` (warning, one per game), and its entry checks treat its `roms/` entries as listed. A migrated game is checked like any external game.
- **S7a** The migration keeps each ZIP's path, so for a `LegacyEmbeddedRoms` system `IntegrityJob.CheckLocation` (:453) accepts either name rule, the embedded one (`FileNameSanitizer`, ` (N)` suffix) or the external one (`ExternalRomName.IsZipNameFor`), whether the game is legacy or migrated; it needs no `info.json`. Other systems are unchanged. A later title edit renames a migrated ZIP by the external rule, as for any external game.
- **S8** Browser play of external DS releases: `desmume` joins `LibraryEndpoints.ExternalBrowserCores` and `emulator.ts`'s `externalBrowserCores`. A new explicit set, `PlayDiscCores` (server) / `playDiscCores` (`emulator.ts`) = `pcsx_rearmed`, `ppsspp`, `yabause`, `genesis_plus_gx`, `opera`, decides `disc`: the games list's `playDisc` becomes `playable && PrimaryIsExternal && PlayDiscCores.Contains(core)`, and a new `usesPlayDisc(core, rom)` in `emulator.ts` (`rom.externalFileName` set and core in `playDiscCores`) replaces `rom.externalFileName !== null` wherever the game page computes `disc` (its PSP link and its `EmulatorModal` `disc` prop) and is what `GameSaves` passes; `GameResults` keeps passing the list item's server `playDisc`. `EmulatorModal` keeps its `disc` prop and computes nothing. So DS loads from `/download` (which already serves external files), never `play-disc`; `play.js` is unchanged. Up to 512 MiB per launch, as today.

### Storage (ZIP)
- **B1** A game ZIP may hold `saves/saves.json` and the files it lists, `saves/<id><extension>`. `id` is a lowercase GUID ("N" format, 32 hex). `extension` comes from the upload's file name: the text after its last `.`, lowercased, when that is 1–8 `[a-z0-9]` (so `x.tar.gz` → `.gz`, `.state` → `.state`); otherwise (none, trailing dot, other characters, longer) it is empty and the upload is still accepted. Entries are never named after user text; the original upload name isn't kept.
- **B2** `saves.json` (UTF-8, at most 1 MiB, written by the app only):
  ```json
  { "version": 1, "saves": [ { "id": "…", "name": "Before boss", "description": "", "kind": "state",
      "release": "Tetris (World) (Rev 1).gb", "extension": ".state", "sizeBytes": 123, "sha1": "…",
      "uploadedBy": "alice", "uploadedAt": "2026-11-16T10:00:00Z", "updatedBy": "alice", "updatedAt": "2026-11-16T10:00:00Z" } ] }
  ```
  `kind` is `state` or `battery`. `release` is the release's `fileName` from `info.json` (numeric rom ids change on every mirror rewrite). The entry is `saves/<id><extension>`. `uploadedBy`/`updatedBy` are usernames at the time (may be `null`; never resolved later). Names need not be unique. A file is **valid** when it parses, `version` is 1, every id is 32 lowercase hex and unique, every `kind` is known, every `extension` matches B1, `name`/`description` follow B8, and every listed entry exists in the ZIP with its `sizeBytes` as its length (a listed-but-missing or wrong-length entry makes the index invalid, so B3's byte-for-byte case and `409 SavesUnreadable` apply, and integrity reports every `saves/` entry as `EntryUnlisted`, B6). A save's `release` matches a release `fileName` case-insensitively (`OrdinalIgnoreCase`, as `InfoJsonValidator` keeps file names unique), for B4 linking, B5 remapping and the B8 limit.
- **B3** Writer behaviour (`LibraryZipWriter`, so every write: ingest, edits, moves, merges, notes, images, repair). `LibraryZipChanges` gets an optional `Saves` (`SavesChange(byte[]? Index, IReadOnlyDictionary<string, Func<Stream>> Added, IReadOnlySet<string> Removed)`; `Index` null removes `saves.json`):
  - **`Saves` null, existing `saves.json` valid:** `saves.json` and every entry it lists are copied from the existing ZIP; other `saves/` entries are dropped.
  - **`Saves` null, no `saves/` entries at all:** nothing is written under `saves/` (an existing ZIP without saves is rewritten exactly as today).
  - **`Saves` null, `saves.json` missing (while other `saves/` entries exist), unreadable, over 1 MiB or invalid:** every `saves/` entry (from `LibraryZip.EntryNames`), `saves.json` included, is copied byte for byte (no data loss on a write that wasn't about saves), each read with its own declared length as the bound; a corrupt entry fails the write with `LibraryZipVerifyException` naming it, as for any copied entry (`LibraryZipWriter.CopyEntryAsync`, the "D34" rule in its comment, :378). The save endpoints and merge then report `409 SavesUnreadable` for that ZIP, delete and replace included: the app never repairs it. An Admin fixes the ZIP by hand (repair or remove its `saves/` folder; integrity's `EntryUnlisted` findings point at it), as `docs/zip-format.md` and `docs/features.md` say.
  - **`Saves` set** (only `LibraryEditor`'s save operations and merge): `Index` is written as `saves.json`; each entry it lists is taken from `Added` if present, else copied from the existing ZIP unless in `Removed`; `saves/` entries not listed are dropped. `Added` keys must be listed in `Index`, or the write is rejected like any stray entry.
  - **Verify:** after the temp ZIP is written, each entry the written `saves.json` lists must exist with its `sizeBytes`; entries from `Added` (newly written bytes) must also match their `sha1`. Entries copied from the existing ZIP (any case) are checked for existence and length only (in the byte-for-byte case, the length of the source entry), so unrelated writes never re-hash saves. A `saves.json` that would serialize to more than 1 MiB is never written: the operation that would produce it (B8–B10, merge, the last-release move) returns `409 SavesIndexFull` ("This game has too many saves. Delete some first.") before anything is written. A failure throws `LibraryZipVerifyException` and the original stays (as for ROMs).
  - Save writes touch no external ROM files (`ExternalFiles` empty), like notes.
- **B4** Saves belong to the game, not the release. A save whose `release` no longer names a release of the game (release deleted, moved to another game; a title edit never renames a release's `fileName`) stays listed with `romId: null`; it can be downloaded, edited, replaced and deleted but not played. Orphans count toward no release's limit. If a release with that `fileName` later joins the game (ingest, move, merge), the save re-links to it and counts toward its limit again; that's intended.
- **B5** Merge (both `MergeAsync` and `MergeExternalAsync`) carries the source game's saves into the target through `Saves`: the target's records followed by the source's (on an id clash the source record gets a new id and entry name), source entries streamed from the source ZIP. A source record's `release` is rewritten to its release's final name in the target (the merge's ` (2)` / `AllocateLogicalName` rename, as `CarryNote` does for notes), so carried saves stay linked; a record that was already an orphan stays as it is. The per-release limit (B8) isn't applied on merge. If either ZIP's saves are unreadable (B3 third case) the merge is refused with `409 SavesUnreadable` before anything is written. Deleting a game (or its last release, which removes the game) deletes its saves with the ZIP. Moving a release leaves its saves in the source game (B4), except when the move takes the source's last release and so deletes the source game: then every source save is carried into the target exactly as on merge (same refusal and remapping rules), in the same target write (`MoveReleaseAsync` and `MoveReleaseExternalAsync`).
- **B6** Integrity: `saves/saves.json` and the entries a valid `saves.json` lists are expected entries (never `EntryUnlisted`); other `saves/` entries (and every `saves/` entry when `saves.json` is missing or invalid) are reported as `EntryUnlisted`, as today. Integrity doesn't hash saves.

### API
All six routes sit in the `/api/games` group with no extra policy, like the note routes: any signed-in user (User or Admin, password changed), antiforgery on writes. Writes take the job lock through `LibraryEditor`.
- **B7** `GET /api/games/{id}/saves` → `200 { items: [ { id, name, description, kind, releaseFileName, romId, sizeBytes, extension, uploadedBy, uploadedAt, updatedBy, updatedAt } ] }`, newest `updatedAt` first. `romId` is the current id of the release named by `releaseFileName`, or `null` (B4). No `saves.json` → empty list. `404 NotFound` for an unknown game; `409 SavesUnreadable` (B3).
- **B8** `POST /api/games/{id}/saves`, `multipart/form-data` with `romId` (a release of this game), `kind` (`state`|`battery`), `name` (trimmed, 1–100 chars, no control chars), optional `description` (≤ 1,000 chars, no control chars except `\n`), and exactly one `file` (1 byte – 256 MiB). **Upload handling** (B8, B10): the endpoint reads the body with `MultipartReader` itself (never `ReadFormAsync`, so the global `FormOptions.MultipartBodyLengthLimit` for images stays as it is), and carries `RequestSizeLimitAttribute(SaveEndpoints.UploadRequestLimit)` (256 MiB + 64 KiB) as endpoint metadata, as the image upload does; a `Content-Length` above that limit is `413` before reading. Text fields are bounded to 4 KiB each and must all come before the `file` part (a `file` part before any of `romId`, `kind`, `name`, an optional `description` after `file`, or an unknown part, is `400`). File-part failures are found only while or after streaming, so they come after the cheap checks: more than 256 MiB → `413` (during the stream); then a missing `file`, a second `file` part, or a 0-byte file → `400`. Once the text fields are read and before any file byte is read, the endpoint runs the cheap checks, in this order, and the first failure answers: `400` validation; `404 NotFound` (game, then release); `409 StorageMigrationPending`; `409 JobRunning` (a `JobLock.TryAcquire()` probe, released at once; `LibraryEditor` takes the lock again for the write, so a job starting in between still ends `409 JobRunning`); `409 SavesUnreadable`; `409 SaveLimitReached`. While streaming: `413`. In the editor's write: the same checks again under the lock, then `409 SavesIndexFull`. B9–B11 use this order: `400` validation (B9 body; none for B11; B10 only checks the content type before streaming), `404` game, `409 StorageMigrationPending`, `409 JobRunning` probe, `409 SavesUnreadable`, `404` save id; then B10 streams its file (`413`, then `400` missing/second/empty `file`); in the editor's write the same checks again under the lock, then `409 SavesIndexFull` (B9, B10). The file part is streamed to `<Paths:Cache>/work/saves/<guid>.tmp` (`CrashRecovery.WorkFolder`, so a crash leftover is cleaned at startup), counting bytes and computing SHA-1 as it goes; more than 256 MiB of file bytes aborts with `413`, whatever `Content-Length` said. `sizeBytes` and `sha1` come from that copy. The temp file is deleted in `finally`. → `201` with the B7 item. Errors: `400` validation (field `errors`; also a missing/second `file` or a non-multipart body), `404 NotFound` (game or release), `409 SaveLimitReached` (already 25 saves naming that release), `409 SavesIndexFull` (B3), `409 JobRunning`, `409 StorageMigrationPending` (S3), `409 SavesUnreadable`, `413` over the limit. Audit `SaveAdded`.
- **B9** `PATCH /api/games/{id}/saves/{saveId}` JSON `{ name?, description? }` (same rules as B8; at least one field) → `200` item; sets `updatedBy/At`. A change to neither value is `200` with no ZIP write and no audit. Errors: `400`, `404`, `409 SavesIndexFull`, `409 JobRunning`, `409 StorageMigrationPending`, `409 SavesUnreadable`. Audit `SaveUpdated`.
- **B10** `PUT /api/games/{id}/saves/{saveId}/file`, multipart with one `file` (rules as B8) → `200` item; replaces bytes, `extension`, `sizeBytes`, `sha1`, `updatedBy/At` (the entry is renamed if the extension changed). Errors as B9 plus `413`. Audit `SaveUpdated`.
- **B11** `DELETE /api/games/{id}/saves/{saveId}` → `204`; removes the record and its entry (and `saves.json` when it was the last). Errors: `404`, `409 JobRunning`, `409 StorageMigrationPending`, `409 SavesUnreadable`. Audit `SaveDeleted`.
- **B12** `GET /api/games/{id}/saves/{saveId}/download` → `200 application/octet-stream` through `Results.Stream(stream, "application/octet-stream", fileDownloadName)` (as `LibraryDownload.Send` does for the ROM download: `filename` plus RFC 5987 `filename*`; no range processing), name `<game title> - <save name><extension>` with characters invalid in Windows file names replaced by `_`. Duplicate names give duplicate download names; that's accepted. Streams the entry (bounded by its `sizeBytes`). `404` when the game, record or entry is missing; `409 SavesUnreadable`.
- **B13** Audit rows: action, game, user, `path` = the ZIP's library path (`AuditPaths.Library`), `details` = `<kind> "<name>" (<saveId>)`, truncated to the column as every audit row. New `AuditActions` `SaveAdded`, `SaveUpdated`, `SaveDeleted` (≤ 32 chars; `audit_events.action` is a free `VARCHAR(32)`, no migration). Added to `All`; the Auditing page loads its action filter from `/api/admin/audit/actions`, so no SPA change.

### Saves tab (SPA)
- **B14** Game detail gets a **Saves** tab between Images and Zip Contents (`?tab=saves`, URL state like the other tabs; the `Tab` union and its `?tab=` parsing accept `saves`). It lists the B7 items in a table (T1–T4): Name (with description below in muted text), Kind (State / Battery badge), Release (file name, `text-truncate` with `title`; "Release removed" muted when `romId` is null), Size (`FileSize`), Updated (local time + `updatedBy`), and row actions: Play, Download, Edit, Replace, Delete (icon buttons with `aria-label` `<Action> <save name>`, e.g. "Delete Before boss", as `IngestFileTable` does). Empty → `EmptyState` "No saves yet".
- **B15** **Add save** button opens a `ConfirmModal` form: Release (select of the game's releases, defaulting to the first), Kind (State/Battery), Name (required), Description, File. Client checks mirror B8 (`src/lib/saves.ts`). Edit opens the same modal with Name and Description only; Replace opens one with File only. Delete uses `ConfirmModal` naming the save. `409 JobRunning` → `toasts.jobRunning`; other errors (including `StorageMigrationPending`, with its title) show in the modal via `ErrorAlert`. The list reloads after every change.
- **B16** Play is shown only when `romId` is set, the release can be played in the modal (`canPlay` and not the PSP tab player), and the save isn't a battery save on `desmume` or `opera` (B18: neither core's battery save goes through EmulatorJS's save file); it opens `EmulatorModal` for that release with the save id. A battery save first asks for confirmation: "Loading this battery save replaces the in-browser save for this release."

### Play dialog
- **B17** `play.js` accepts optional `save=<32 lowercase hex>` and `saveKind=state|battery` query parameters (`parsePlayParams`: both or neither; a malformed or lone one refuses to start, as other bad params do). With them, before adding the loader, it GETs B12's download (401 → session-expiry message; any other failure → "Couldn't load the save." and the loader isn't added). It sets `EJS_onGameStart` (not used today; `loader.js` registers it on the `start` event, which 4.2.3 fires once, at the end of `startGame()`; `gameManager.restart()` doesn't fire it) to a handler that applies the save **once** (a `saveApplied` flag guards any second `start`):
  - `state`: `gameManager.loadState(new Uint8Array(bytes))`.
  - `battery`: as EmulatorJS 4.2.3's own save import does: takes `path = gameManager.getSaveFilePath()`, creates each missing parent folder in `gameManager.FS`, unlinks an existing file at `path`, writes the bytes there and calls `gameManager.loadSaveFiles()`; then `gameManager.restart()` and `gameManager.FS.syncfs(false, …)`, so the in-browser (IndexedDB) save for this release is replaced at once, not at the next 30 s interval.
  A `state` save when `!gameManager.supportsStates()` isn't loaded and shows "This emulator can't load save states." Any other failure (an exception) shows "Couldn't load the save." Both are shown with `play.js`'s `show()` in the page's existing `#status` line; the game keeps running.
- **B18** `EmulatorModal` (the modal never hosts `ppsspp`, which opens in its own tab) shows, while open, a **Save state to library** button for every core, and a **Save battery to library** button except for `desmume` and `opera`. A click posts `{ type: 'rnrm-emulator-export', kind }` to the iframe. `play.js`'s one `message` listener (today `listenForClose`, installed only for `opera`) is installed on `play.html` for every core; its close branch still acts only for `opera` (the modal sends close only for `opera`). It accepts exactly `{ type: 'rnrm-emulator-close' }` or `{ type: 'rnrm-emulator-export', kind: 'state' | 'battery' }` from `window.parent` at `location.origin`; the modal accepts results only from the iframe's `contentWindow` at `location.origin`. - **B19** On `ok`, the modal checks `bytes.byteLength` ≤ 256 MiB (else toasts "This save is larger than 256 MiB" and uploads nothing), then uploads through B8 with the modal's release, the kind, name `<State|Battery> <local yyyy-MM-dd HH:mm>` and no description, file name `save<extension>`, and toasts "Saved to library" (or the API error; `409 JobRunning` → `toasts.jobRunning`). ## Risks
- **DS migration:** a one-off rewrite of every DS ZIP and a copy of every DS ROM; it needs temporary free space per game (S6), runs once at startup, and is safe to interrupt (S5). Until it finishes, DS games are read-only (S3). Operators who back up only `*.zip` must now back up the folder (docs).
- **Disk writes:** every save add/edit/replace/delete rewrites and re-verifies the whole ZIP; after S1 the largest embedded ROMs left are N64 (64 MiB). Mitigated by writing only on explicit user action (B18–B19, no auto-sync) and by `LibraryZipWriter`'s fast compression of large ROM entries. External-ROM systems have small ZIPs.
- **Data loss on ZIP writes:** a writer bug could drop saves on unrelated edits. B3 copies an unreadable `saves.json` byte for byte; `LibraryZipSavesTests` cover copy, drop-unlisted and unreadable cases. An older app version drops `saves/` on its next write (as it does `notes/`): documented, no downgrade.
- **Large uploads:** 256 MiB bodies are streamed to disk through `MultipartReader`, never buffered; the temp file is deleted on every path. Only the two upload routes raise the request-body limit (per endpoint, through `RequestSizeLimitAttribute` metadata over Kestrel's default 30,000,000-byte limit); the global form limit stays at the image size.
- **Big `postMessage` copies:** an export of up to 256 MiB is copied once from the iframe to the modal; the modal refuses larger ones before uploading.
- **Shared saves:** any user can delete any save; mitigated by the audit trail (B13).
- **ZIP growth:** a release can hold 25 × 256 MiB of saves, and save writes have no free-space pre-check (unlike S6). A full disk fails the write as `IoError` (500) with the original ZIP intact, as for any edit; accepted.
- **Battery load overwrites the browser save** for that release (B16 confirmation).
- **EmulatorJS API:** `getState`, `loadState`, `getSaveFile`, `saveSaveFiles`, `loadSaveFiles`, `getSaveFilePath`, `supportsStates`, `restart` and `EJS_onGameStart` are EmulatorJS 4.2.3 APIs; the vendored version is pinned, and `emulatorPlay.test.ts` fakes `gameManager` to prove the calls.
- **Job lock:** saves can't be written while a job runs (`409 JobRunning`), same as notes.
- **Migration holds the job lock:** on a large DS library the S4 job can run for hours after the upgrading start. Meanwhile every edit and manual job start is `409 JobRunning`, and the scheduled quick integrity check is skipped with its existing "another job is running" log (`Scheduler`), not queued. `docs/deployment.md` says so.
