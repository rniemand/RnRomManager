# Save State Management

## Summary
Every game ZIP gets a `saves/` folder holding save states (EmulatorJS snapshots) and battery saves (in-game saves), described by `saves/saves.json`. The Game detail page gets a **Saves** tab where any signed-in user uploads, renames, re-describes, replaces, downloads, deletes and plays saves. The browser Play dialog gets two buttons that copy the running game's state or battery save into the ZIP on demand, so the server is written only when a user asks.

## Out of scope
- Automatic syncing of EmulatorJS's in-browser (IndexedDB) battery saves to the server: no interval, close or unload hook writes the ZIP.
- Per-user save folders or privacy: saves are shared by every user of the library.
- PSP (`play-psp.html`, its own tab): no save buttons and no Play-with-save. PSP saves can still be uploaded and downloaded on the Saves tab.
- Battery-save export for cores that don't expose SRAM through EmulatorJS (`desmume`, `opera`, `ppsspp`): the battery button is hidden for them; states still work where the core supports them.
- Converting saves between emulators or validating save contents: bytes are stored as given.
- A database mirror of saves: the list is read from the ZIP on request.
- Re-assigning a save to another release (an orphaned save, B4, can't be re-linked; upload it again instead).

## Behaviour

### Storage (ZIP)
- **B1** A game ZIP may hold `saves/saves.json` and the files it lists, `saves/<id><extension>`. `id` is a lowercase GUID ("N" format, 32 hex). `extension` comes from the upload's file name: the text after its last `.`, lowercased, when that is 1–8 `[a-z0-9]` (so `x.tar.gz` → `.gz`, `.state` → `.state`); otherwise (none, trailing dot, other characters, longer) it is empty and the upload is still accepted. Entries are never named after user text; the original upload name isn't kept.
- **B2** `saves.json` (UTF-8, at most 1 MiB, written by the app only):
  ```json
  { "version": 1, "saves": [ { "id": "…", "name": "Before boss", "description": "", "kind": "state",
      "release": "Tetris (World) (Rev 1).gb", "extension": ".state", "sizeBytes": 123, "sha1": "…",
      "uploadedBy": "alice", "uploadedAt": "2026-11-16T10:00:00Z", "updatedBy": "alice", "updatedAt": "2026-11-16T10:00:00Z" } ] }
  ```
  `kind` is `state` or `battery`. `release` is the release's `fileName` from `info.json` (numeric rom ids change on every mirror rewrite). The entry is `saves/<id><extension>`. `uploadedBy`/`updatedBy` are usernames at the time (may be `null`; never resolved later). Names need not be unique. A file is **valid** when it parses, `version` is 1, every id is 32 lowercase hex and unique, every `kind` is known, every `extension` matches B1, and `name`/`description` follow B8.
- **B3** Writer behaviour (`LibraryZipWriter`, so every write: ingest, edits, moves, merges, notes, images, repair). `LibraryZipChanges` gets an optional `Saves` (`SavesChange(byte[]? Index, IReadOnlyDictionary<string, Func<Stream>> Added, IReadOnlySet<string> Removed)`; `Index` null removes `saves.json`):
  - **`Saves` null, existing `saves.json` valid:** `saves.json` and every entry it lists are copied from the existing ZIP; other `saves/` entries are dropped.
  - **`Saves` null, no `saves/` entries at all:** nothing is written under `saves/` (an existing ZIP without saves is rewritten exactly as today).
  - **`Saves` null, `saves.json` missing (while other `saves/` entries exist), unreadable, over 1 MiB or invalid:** every `saves/` entry, `saves.json` included, is copied byte for byte (no data loss on a write that wasn't about saves). The save endpoints and merge then report `409 SavesUnreadable` for that ZIP.
  - **`Saves` set** (only `LibraryEditor`'s save operations and merge): `Index` is written as `saves.json`; each entry it lists is taken from `Added` if present, else copied from the existing ZIP unless in `Removed`; `saves/` entries not listed are dropped. `Added` keys must be listed in `Index`, or the write is rejected like any stray entry.
  - **Verify:** after the temp ZIP is written, each entry the written `saves.json` lists must exist with its `sizeBytes`; entries from `Added` (newly written bytes) must also match their `sha1`. Entries copied from the existing ZIP (any case) are checked for existence and length only, so unrelated writes never re-hash saves. A failure throws `LibraryZipVerifyException` and the original stays (as for ROMs).
  - Save writes touch no external ROM files (`ExternalFiles` empty), like notes.
- **B4** Saves belong to the game, not the release. A save whose `release` no longer names a release of the game (release deleted, moved to another game, renamed by a title edit) stays listed with `romId: null`; it can be downloaded, edited, replaced and deleted but not played. Orphans count toward no release's limit.
- **B5** Merge carries the source game's saves into the target through `Saves`: the target's records followed by the source's (on an id clash the source record gets a new id and entry name), source entries streamed from the source ZIP. The per-release limit (B8) isn't applied on merge. If either ZIP's saves are unreadable (B3 third case) the merge is refused with `409 SavesUnreadable` before anything is written. Deleting a game deletes its saves with the ZIP. Moving a release leaves its saves in the source game (B4).
- **B6** Integrity: `saves/saves.json` and the entries a valid `saves.json` lists are expected entries (never `EntryUnlisted`); other `saves/` entries (and every `saves/` entry when `saves.json` is missing or invalid) are reported as `EntryUnlisted`, as today. Integrity doesn't hash saves.

### API
All six routes sit in the `/api/games` group with no extra policy, like the note routes: any signed-in user (User or Admin, password changed), antiforgery on writes. Writes take the job lock through `LibraryEditor`.
- **B7** `GET /api/games/{id}/saves` → `200 { items: [ { id, name, description, kind, releaseFileName, romId, sizeBytes, extension, uploadedBy, uploadedAt, updatedBy, updatedAt } ] }`, newest `updatedAt` first. `romId` is the current id of the release named by `releaseFileName`, or `null` (B4). No `saves.json` → empty list. `404 NotFound` for an unknown game; `409 SavesUnreadable` (B3).
- **B8** `POST /api/games/{id}/saves`, `multipart/form-data` with `romId` (a release of this game), `kind` (`state`|`battery`), `name` (trimmed, 1–100 chars, no control chars), optional `description` (≤ 1,000 chars, no control chars except `\n`), and exactly one `file` (1 byte – 256 MiB). **Upload handling** (B8, B10): the endpoint reads the body with `MultipartReader` itself (never `ReadFormAsync`, so the global `FormOptions.MultipartBodyLengthLimit` for images stays as it is), and sets `IHttpMaxRequestBodySizeFeature.MaxRequestBodySize` to `SaveEndpoints.UploadRequestLimit` (256 MiB + 64 KiB). Text fields are bounded to 4 KiB each. The file part is streamed to `<Paths:Cache>/work/saves/<guid>.tmp` (`CrashRecovery.WorkFolder`, so a crash leftover is cleaned at startup), counting bytes and computing SHA-1 as it goes; more than 256 MiB of file bytes aborts with `413`, whatever `Content-Length` said. `sizeBytes` and `sha1` come from that copy. The temp file is deleted in `finally`. → `201` with the B7 item. Errors: `400` validation (field `errors`; also a missing/second `file` or a non-multipart body), `404 NotFound` (game or release), `409 SaveLimitReached` (already 25 saves naming that release), `409 JobRunning`, `409 SavesUnreadable`, `413` over the limit. Audit `SaveAdded`.
- **B9** `PATCH /api/games/{id}/saves/{saveId}` JSON `{ name?, description? }` (same rules as B8; at least one field) → `200` item; sets `updatedBy/At`. A change to neither value is `200` with no ZIP write and no audit. Errors: `400`, `404`, `409 JobRunning`, `409 SavesUnreadable`. Audit `SaveUpdated`.
- **B10** `PUT /api/games/{id}/saves/{saveId}/file`, multipart with one `file` (rules as B8) → `200` item; replaces bytes, `extension`, `sizeBytes`, `sha1`, `updatedBy/At` (the entry is renamed if the extension changed). Errors as B9 plus `413`. Audit `SaveUpdated`.
- **B11** `DELETE /api/games/{id}/saves/{saveId}` → `204`; removes the record and its entry (and `saves.json` when it was the last). Errors: `404`, `409 JobRunning`, `409 SavesUnreadable`. Audit `SaveDeleted`.
- **B12** `GET /api/games/{id}/saves/{saveId}/download` → `200 application/octet-stream` through `Results.File(stream, …, fileDownloadName)` (as the ROM download: `filename` plus RFC 5987 `filename*`), name `<game title> - <save name><extension>` with characters invalid in Windows file names replaced by `_`. Duplicate names give duplicate download names; that's accepted. Streams the entry (bounded by its `sizeBytes`). `404` when the game, record or entry is missing; `409 SavesUnreadable`.
- **B13** Audit rows: action, game, user, `path` = the ZIP's library path (`AuditPaths.Library`), `details` = `<kind> "<name>" (<saveId>)`, truncated to the column as every audit row. New `AuditActions` `SaveAdded`, `SaveUpdated`, `SaveDeleted` (≤ 32 chars; `audit_events.action` is a free `VARCHAR(32)`, no migration). Added to `All`; the Auditing page loads its action filter from `/api/admin/audit/actions`, so no SPA change.

### Saves tab (SPA)
- **B14** Game detail gets a **Saves** tab after Images (`?tab=saves`, URL state like the other tabs). It lists the B7 items in a table (T1–T4): Name (with description below in muted text), Kind (State / Battery badge), Release (file name, `text-truncate` with `title`; "Release removed" muted when `romId` is null), Size (`FileSize`), Updated (local time + `updatedBy`), and row actions: Play, Download, Edit, Replace, Delete. Empty → `EmptyState` "No saves yet".
- **B15** **Add save** button opens a `ConfirmModal` form: Release (select of the game's releases, defaulting to the first), Kind (State/Battery), Name (required), Description, File. Client checks mirror B8 (`src/lib/saves.ts`). Edit opens the same modal with Name and Description only; Replace opens one with File only. Delete uses `ConfirmModal` naming the save. `409 JobRunning` → `toasts.jobRunning`; other errors show in the modal via `ErrorAlert`. The list reloads after every change.
- **B16** Play is shown only when `romId` is set and the release can be played in the modal (`canPlay` and not the PSP tab player); it opens `EmulatorModal` for that release with the save id. A battery save first asks for confirmation: "Loading this battery save replaces the in-browser save for this release."

### Play dialog
- **B17** `play.js` accepts optional `save=<32 lowercase hex>` and `saveKind=state|battery` query parameters (`parsePlayParams`: both or neither; a malformed or lone one refuses to start, as other bad params do). With them, before adding the loader, it GETs B12's download (401 → session-expiry message; any other failure → "Couldn't load the save." and the loader isn't added). It sets `EJS_onGameStart` (not used today) to a handler that applies the save **once** (a `saveApplied` flag, so the game start fired by its own `restart()` or a later one doesn't reapply it):
  - `state`: `gameManager.loadState(bytes)`.
  - `battery`: writes the bytes to `gameManager.getSaveFilePath()` in `gameManager.FS`, calls `gameManager.loadSaveFiles()`, then `gameManager.restart()`, then `gameManager.FS.syncfs(false, …)`, so the in-browser (IndexedDB) save for this release is replaced at once, not at the next 30 s interval.
  A failure shows "Couldn't load the save." over the running game (the game keeps running).
- **B18** `EmulatorModal` (the modal never hosts `ppsspp`, which opens in its own tab) shows, while open, a **Save state to library** button for every core, and a **Save battery to library** button except for `desmume` and `opera`. A click posts `{ type: 'rnrm-emulator-export', kind }` to the iframe. `play.js` extends its one `message` listener (today only `rnrm-emulator-close`): it accepts exactly `{ type: 'rnrm-emulator-close' }` or `{ type: 'rnrm-emulator-export', kind: 'state' | 'battery' }` from `window.parent` at `location.origin`; the modal accepts results only from the iframe's `contentWindow` at `location.origin`. The page answers `{ type: 'rnrm-emulator-export-result', kind, ok: true, bytes: ArrayBuffer, extension }` (state: `gameManager.getState()`, `.state`; battery: `gameManager.saveSaveFiles()` then `gameManager.getSaveFile()`, both synchronous, `.srm`), or `{ type: 'rnrm-emulator-export-result', kind, ok: false, reason }` with `reason` `not-started` (before game start), `busy` (the 3DO close sync is running; a close request during an export waits for the export reply first), `unsupported` (state when `!gameManager.supportsStates()`), `empty` (no bytes) or `error` (an exception).
- **B19** On `ok`, the modal checks `bytes.byteLength` ≤ 256 MiB (else toasts "This save is larger than 256 MiB" and uploads nothing), then uploads through B8 with the modal's release, the kind, name `<State|Battery> <local yyyy-MM-dd HH:mm>` and no description, file name `save<extension>`, and toasts "Saved to library" (or the API error; `409 JobRunning` → `toasts.jobRunning`). On `ok: false`, it toasts the reason in words. Both buttons are disabled while an export or upload runs. Saves made this way are renamed later on the Saves tab; when the modal closes, an open Saves tab reloads its list.
- **B20** `EJS_Buttons` save/load-state buttons stay hidden (the in-iframe EmulatorJS state UI isn't used); the 30 s battery-save interval to IndexedDB is unchanged.

## Risks
- **Disk writes:** every save add/edit/replace/delete rewrites and re-verifies the whole ZIP (an embedded DS game can be 512 MiB). Mitigated by writing only on explicit user action (B18–B19, no auto-sync) and by `LibraryZipWriter`'s fast compression of large ROM entries. External-ROM systems have small ZIPs.
- **Data loss on ZIP writes:** a writer bug could drop saves on unrelated edits. B3 copies an unreadable `saves.json` byte for byte; `LibraryZipWriterTests` cover copy, drop-unlisted and unreadable cases.
- **Large uploads:** 256 MiB bodies are streamed to disk through `MultipartReader`, never buffered; the temp file is deleted on every path. Only the two upload routes raise the request-body limit (per request, through `IHttpMaxRequestBodySizeFeature`); the global form limit stays at the image size.
- **Big `postMessage` copies:** an export of up to 256 MiB is copied once from the iframe to the modal; the modal refuses larger ones before uploading.
- **Shared saves:** any user can delete any save; mitigated by the audit trail (B13).
- **Battery load overwrites the browser save** for that release (B16 confirmation).
- **EmulatorJS API:** `getState`, `loadState`, `getSaveFile`, `saveSaveFiles`, `loadSaveFiles`, `getSaveFilePath`, `supportsStates`, `restart` and `EJS_onGameStart` are EmulatorJS 4.2.3 APIs; the vendored version is pinned, and `emulatorPlay.test.ts` fakes `gameManager` to prove the calls.
- **Job lock:** saves can't be written while a job runs (`409 JobRunning`), same as notes.
