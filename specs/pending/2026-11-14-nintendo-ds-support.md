# Nintendo DS support

## Summary

Admins can import Nintendo DS cartridge dumps into the library. The app stores each release inside its game's ZIP and offers browser play through the existing release player.

## Out of scope

- DSiWare support, DSi-mode execution, DS Download Play, multiplayer, and BIOS or firmware configuration. The DS unit code is informational for archival import. A DSi-enhanced cartridge may run in DS mode. Import eligibility does not establish that a cartridge can boot.
- Changes to the shared input archive limits, emulator version, or storage format.

## Behaviour

- **B1. Import and storage.** Register Nintendo DS as `nds`, with short name `DS` and family `nds`. Accept case-insensitive `.nds` from `ingest/nds/` loose or in ZIP/7z. Validate 512 bytes through 512 MiB per ROM, inclusive. The input archive caps remain 100 non-directory entries, including skipped entries, and 256 MiB of combined extracted supported ROM bytes. Exceeding either archive cap gives `ArchiveUnsafe`. Import supported dumps larger than 256 MiB loose. Skip other archive member extensions. Reject unsupported loose extensions as `UnsupportedType` and out-of-range loose sizes as `TooSmall` or `TooLarge`. Hash and store the original bytes in the game's ZIP with the standard embedded release naming and `info.json` fields. Import and Review require Admin. Signed-in browse-only users can download the ROM through the standard attachment route, which streams the ZIP entry as `application/octet-stream` and sends the full entry for a Range request. Use the existing download errors and password-change gate.
- **B2. Identification.** Use libretro's No-Intro `Nintendo - Nintendo DS` DAT for SHA-1 identification and its `releaseyear`, `developer`, `publisher` and `genre` metadat for optional CRC32-based enrichment. Filter to `.nds` before indexing hashes, DAT search, suggestions and base titles. Keep standard release naming, grouping and media lookup by DAT game name, and deduplicate within the system by SHA-1 before the header or DAT decision. On upgrade the app starts and creates DS folders. Admin → DATs → Refresh DATs supplies the five required files. Until all five pass cache validation, all import requests, including selections of other systems, return HTTP 409 `DatsMissing` without creating a job. An empty valid catalog is sufficient.
- **B3. Header and Review.** Return null for spans shorter than 0x160 bytes. Read the 12-byte internal title at 0x00 (ASCII through the first NUL, trim trailing spaces, blank becomes null), game code at 0x0C (4 fixed ASCII bytes), maker code at 0x10 (2 fixed ASCII bytes), unit code at 0x12 and ROM version at 0x1E (unsigned bytes). Use ASCII replacement for out-of-range bytes. Expose `title`, `gameCode`, `makerCode`, `unitCode` and `romVersion` in the existing header view. Classify as `nds`. Compute CRC-16 (initial 0xFFFF, reflected polynomial 0xA001) over bytes 0x000–0x15D and compare it with the little-endian value at 0x15E. Return a header marked implausible on mismatch so an unmatched ROM is filed as `InvalidHeader`. A DAT hit remains authoritative. An unmatched ROM with a valid CRC enters Review and its internal title can supply suggestions. Resolve through the existing manual or DAT-selection workflow, reverify the pending source hash before saving, and leave a changed source pending on verification failure.
- **B4. Browser play.** Expose `desmume` for eligible DS releases in the existing game-detail Play dialog. Fetch the selected embedded ROM through its authenticated attachment route. Use the two local non-threaded EmulatorJS 4.2.3 payloads and their build report. Keep generic `nds` controls and settings while pinning concrete DeSmuME before saved core selection. Suppress the core and thread choosers and prevent saved thread settings from selecting threaded assets. Use built-in BIOS and firmware behavior, including when stale core options request external files. Keep browser-local battery saves with the existing release naming and autosave behavior. The default layout shows both screens and accepts pointer input as stylus input on the lower screen. See Verification gates for large-ROM playback and distribution.

## Risks

- The server buffers one full ROM per unchanged embedded ingest or Review read. The download streams. The browser buffers the response and copies it into the emulator filesystem. Measure the server and browser separately.
- The published 4.2.3 core report establishes the build date and options. Verify the exact source and redistribution terms for the packaged binaries before adding the dependency or shipping Play.

## Verification gates

- **Distribution.** Inspect both npm payloads and their embedded build/core metadata. Correlate them with the upstream build run and pin exact DeSmuME, RetroArch and build-script revisions for both variants. Record package integrity, corresponding source and build instructions, and applicable license texts and component notices. The CDN report alone is insufficient to establish the revisions. If provenance or redistribution terms remain unresolved, stop before Step 6. Import remains available after Step 5.
- **Browser size.** Before advertising Play, use the authenticated modal directly in the implementation test environment and run the original test cartridge padded to 512 MiB with a valid capacity and header. Use the repository's Playwright Chromium baseline with a fresh profile for each of three cold starts. Record Chromium version, host RAM and OS, tested sizes, peak browser process memory and startup times. Each run must render both guest screens and respond to a stylus tap within the suite's configured timeout without a browser error or crash. If 512 MiB fails, test lower power-of-two sizes until a size passes all three runs. Set the inclusive limit to the largest validated size. If 512 MiB passes, keep full-size Play. If the unpadded fixture also fails, leave Play disabled and report the failure. When a limit applies, gate release capability on stored ROM size and enforce the same limit in the modal using authoritative release metadata before fetching the ROM, including on direct modal navigation. A rejected launch shows the reason and leaves Download available. Record the measured result and resulting limit in Decisions and the browser documentation before publishing.

## Decisions

- 2026-11-14 Embedded storage → keep the DS ROM bytes inside each game's ZIP (user).
- 2026-11-14 DS input → accept `.nds` only, with the existing shared input archive limits and loose import through 512 MiB (code and No-Intro DAT).
- 2026-11-14 Embedded read memory → reuse the original byte array when importing or resolving unchanged large dumps and verify both entry points (reviewer).
- 2026-11-14 Browser engine → pin DeSmuME 4.2.3 and retain generic DS controls. Use only the packaged non-threaded assets and built-in firmware for DS playback.
- 2026-11-14 Upgrade → retain the existing global DAT preflight and require all five DS catalog files. Keep Basic and Full ROM counts unchanged.
- 2026-11-14 Browser size → measure the supported Chromium baseline. If reliable 512 MiB playback fails, enforce the largest validated size for Play and retain the 512 MiB import and download limit (user).
- 2026-11-14 Distribution → hold browser play until both package variants are tied to exact corresponding source and redistribution notices (user).

## Open decisions and verification

- The source revisions and applicable notices for the packaged binaries are still unverified. Step 6 is gated on that evidence. The CDN report gives build timestamps and options, and the build manifest names the fork and `.dsv` save extension.
- The browser size limit remains to be measured in Step 8. The original runnable fixture, touch response, save persistence and maximum-size import and Review checks are implementation verification.

## Review findings

- A missing DS catalog blocks even a selected import for a different system. The original upgrade language did not make the global preflight or cache validation clear. The startup and refresh regression now checks both. See `IngestJob.cs`, `DatCache.cs` and `IngestEndpointsTests.cs`.
- The existing archive tests could pass without routing any DS member through 7z. The revised cases require distinct DS payloads, verify ignored members and archive budgets, and prove the DAT precedence, extension filter and metadat joins independently. See `IngestArchiveTests.cs`, `ArchiveExtractor.cs` and `IngestPipeline.cs`.
- Both embedded read paths copied whole ROMs. Review also buffers through a growing stream and distinguishes verification from I/O failures. The revised cases check allocation, hash revalidation, ZIP bytes and the authenticated streaming response. See `IngestPipeline.cs`, `ReviewResolver.cs`, `LibraryEndpoints.cs` and `LibraryFiles.cs`.
- A stock modal cannot prove the saved-threads guard without `SharedArrayBuffer`. A visible canvas or successful asset fetch also cannot prove DS touch input. The revised tests exercise the branch in the vendored runtime and use guest-visible screen changes. See `vendorEmulatorjs.test.ts`, `static/emulator/play.js` and the pinned runtime below.
- The E2E seed writer replaces the manifest as a unit. A second DS-only write would drop every other catalog. The script now has a specified single-pass seed handoff, and the fixture remains outside ingest until the count-sensitive assertions finish. See `FixtureDatWriter.cs`, `TestDataCommand.cs`, `scripts/test-e2e.ps1` and `mvp.spec.ts`.
