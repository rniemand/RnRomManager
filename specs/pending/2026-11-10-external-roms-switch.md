# External ROM storage and Nintendo Switch

## Summary
Disc-era and modern systems (Switch, GameCube, Wii, Xbox 360…) have multi-GB images that can't sensibly live inside a game's ZIP or be read into memory. Each system now declares whether its ROMs are **embedded** in the game ZIP (every existing system: yes) or stored **external**: next to the ZIP, named so they group with it, and pointed at from `info.json`. The ZIP keeps everything else (info.json, images, notes, ratings). Nintendo Switch (`switch`) is the first external system, identified by title ID through [blawar/titledb](https://github.com/blawar/titledb) because libretro has no Switch DAT or thumbnails.

## Out of scope
- GameCube, Wii, Xbox 360 and other large systems (later specs; this one builds what they need).
- Moving an existing system between embedded and external (the flag is fixed per system; no conversion tool).
- Building a ZIP with the ROMs on the fly for "Download ZIP" (decision: ZIP as stored + per-release downloads).
- Decrypting Switch content: no keys; XCI title IDs come only from the file name.
- titledb regions other than `US.en.json`; titledb descriptions (game `description` stays Admin-edited only).
- Nintendo Switch 2: its title IDs (`0400…`, 75 in `US.en.json` on 2026-11-10) are left out of the compact titledb file, so its dumps go to Review (T2, T4); a later spec can add it as its own system.
- Ingesting external-system ROMs from archives beyond today's archive limits (`ArchiveExtractor`: 100 entries, 256 MiB streamed in total): a larger `.zip`/`.7z` is rejected as `ArchiveUnsafe`, as today. A Switch file in an archive within those limits (e.g. a small DLC) is ingested from its extracted copy (I2, I5).

## Behaviour

### Storage flag
- **S1 Lookup.** `ISystemHandler` gains a required `bool EmbedRomsInZip { get; }` (no default implementation, so every handler states it). All 13 existing handlers return `true`; `switch` returns `false`. `GET /api/systems` adds `embedRoms` (bool) to each entry. `docs/adding-a-system.md` lists every system with its value. NSubstitute returns `false` for an unconfigured `bool`, so the concrete test handlers (`SystemHandlerDefaultsTests.Plain` and both `Headerless` test implementations) return `true`, and every test's `Substitute.For<ISystemHandler>()` (16 files under `tests/`, e.g. `InfoJsonTests`, `LibraryZipTests`, Data's `IntegrityJobTests` and `LibraryMirrorTests`) sets `EmbedRomsInZip.Returns(true)`; without it those handlers would silently become external.
- **S2 Scope of the storage flag.** External ROM placement, verification, integrity and downloads apply only when `EmbedRomsInZip` is `false`. Embedded releases keep their current storage and downloads. Both storage modes receive schema v4, additive API fields and T8’s format-based image naming.

### External file naming and pointer
- **E1 Name.** An external ROM is the file `<ZipBase>.<rom fileName>` in the ZIP's own folder, where `<ZipBase>` is the ZIP name without `.zip`. Example: `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.zip` and `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.The Legend of Zelda - Tears of the Kingdom [0100F2C0115B6000][v0].nsp`. The shared `<ZipBase>.` prefix sorts them together in any file explorer.
- **E2 Length and clashes.** The final name, including any clash suffix, is at most 250 UTF-8 bytes (so `<final>.tmp` stays under the 255-byte name limit of ext4/NTFS). When it's longer, the rom part's stem (before its extension) is cut from its end, at a char boundary (never splitting a surrogate pair), until it fits; the extension is kept. If the rom stem is cut to nothing and the name still doesn't fit (a long multi-byte `<ZipBase>`: `FileNameSanitizer.MaxLength` is 180 chars, up to 540 bytes), `<ZipBase>` is cut from its end the same way. Reserve both the final name and its staging name against files and directories, including destinations already allocated by this write for missing ROMs. For external games use the same UTF-8 component budget when allocating a ZIP name (at most 250 bytes including `.zip` and any clash suffix, before `.tmp`). Use one ZIP-name builder in ingest, title edit, move-to-new-game and the integrity location check. For an external game, title edit decides whether the ZIP path changes by comparing that builder's budgeted base for the old and new titles (case-insensitively, without clash suffix) instead of today's `Sanitize` comparison in `LibraryEditor.PatchAsync`, so a title change that only differs beyond the byte cut keeps the ZIP and its external files where they are (instead of renaming them to ` (2)`). A name is taken (case-insensitive) when a different file or folder already has it, or when a DB row lists it as the `external_file_name` of any game whose ZIP is in that folder, or when the opened destination ZIP already lists it (including a missing file belonging to another release of the same game) (so a game's missing file can't have its name reused by another game, which I6 self-repair would then overwrite; a dotted `<ZipBase>` such as `Mr. Driller` can produce the same name as another game's) → ` (2)`, ` (3)`… before the extension (candidate 1 has no suffix). Rebuild and truncate each candidate with its actual suffix reserved before checking occupancy. Allocate repair backups independently as siblings ending in `.repair.tmp`, fitting the complete name within 255 UTF-8 bytes even for an existing pointer of 255 characters. Check these candidates against disk entries and other allocations. Implemented once in `Core/Storage/ExternalRomName.cs`.
- **E3 Pointer.** `info.json` **schema version 4**: each Rom gains `externalFileName` (string?, the file name only, resolved in the ZIP's folder). Validator (which now receives an id → `ISystemHandler` lookup instead of the bare id set, since it needs both `EmbedRomsInZip` and `RomExtensions`; `InfoJsonReader` builds it from `ISystemRegistry.All`): for a system with `EmbedRomsInZip = false` it is required; for an embedded system it must be null; when set it is a plain file name (no `/`, `\` or control character, no Windows-invalid characters `<>:"|?*` or DOS device basename: a new public `FileNameSanitizer.IsReservedDeviceName(string name)` tests the part before the first `.` case-insensitively against today's private `Reserved` set plus the Windows superscript variants `COM¹`–`COM³` and `LPT¹`–`LPT³`; `Sanitize` keeps its current set, so embedded naming output is unchanged; E2 allocation applies `IsReservedDeviceName` to external ZIP bases, sidecar names and `_removed` destinations and prefixes a match with `_`, as `Sanitize` does), and not `.` or `..`; unlike a rom `fileName`, `..` inside the name is allowed, because `<ZipBase>` is the sanitized title and may hold `...`, e.g. `Oh...Sir!!`), unique case-insensitively within the game, at most 255 chars, and ends (case-insensitively) with one of the system's `RomExtensions` (so a hand-edited `info.json` can't point a download, move or delete at a ZIP, a `.tmp` or another non-ROM file). The v3→v4 upgrader adds `externalFileName: null`. Register it in `AppHost` alongside the existing v1→v2 and v2→v3 upgraders. Apps before this one treat a v4 file as `InfoJsonNewerSchema` (read-only, existing rule). `identification.method` gains the value `TitleDb` (T4) and image `source` gains `titledb` (T8). A stray `roms/<fileName>` entry for an external ROM is not a validator rule: the writer never writes one (W1) and integrity reports it as `EntryUnlisted` (G1).
- **E4 Database.** Migration `0018_external_roms.sql`: `ALTER TABLE roms ADD external_file_name VARCHAR(255) NULL`. `RomRow`, the mirror and `DbSync` carry it (`NULL` for every existing row; no backfill needed). `GET /api/games/{id}` release rows gain `externalFileName`.

### Ingest of an external ROM
- **I1 Validation.** Extension and size checks as today (`MaxRomSizeBytes` is a `long`). In `IngestJob.ArchiveAsync`, check an external system’s archive container under the ingest root before calling `ArchiveExtractor.Extract`; an unsafe or inconclusive path or a container that vanished since the snapshot records one `Error IoError` item and does not call `FailFile` or `ApplyFate`. Check extracted entries under the job work root. For an external archive, any entry skipped as `TooRecent` keeps the archive in place, just as Review or Error does, even if other entries committed.
- **I2 Streaming hash.** The file is never read whole into memory: one streamed read computes CRC32, MD5 and SHA1 together (`NormalizeForHashing` is not called for external systems). `ReadHeader` receives the first `min(size, 1 MiB)` bytes. Cap the actual streamed bytes at `MaxRomSizeBytes`; if the source grows across the cap during hashing, apply the same `TooRecent` rule. After hashing, the file's length and last-write time are compared with a fresh `FileInfo` read immediately before the hash (not the snapshot's `SizeBytes`/`ModifiedAtUtc`, which for an archive entry are the archive's); an archive entry's extracted copy in `cache/work/<jobId>/` is written by the job itself and skips this check. Recheck the same loose-source snapshot immediately before staging, after target open and media. If length or mtime changed at either check (still being copied in), the item is `Skipped` with reason `TooRecent` (file left in place, picked up by a later run; features.md broadens `TooRecent` to "modified < 10 s ago or changed while being hashed"). Cancellation keeps the documented item boundary: after starting an external loose item, pass `CancellationToken.None` to the entire pipeline and its current-item bookkeeping, including hash, lookups, media and Review updates. Check the job token before starting the next item. The archive already finishes with no cancellation between its entries; embedded loose files retain their current token behavior.
- **I3 Identification, dedupe, review, grouping** follow the existing steps 3–6 (SHA1 dedupe, review lifecycle, identification per the system's DAT source, grouping by system + base title). For an external libretro match, use the DAT ROM stem with the source extension lower-cased for both the stored release and the queued AmbiguousGroup ROM name. Parse the DAT stem for tags as today.
- **I4 Placement (move with rollback).** The move happens in `PackageAsync`, immediately before the ZIP write: after the target ZIP was opened (`TargetZipUnreadable` / `InfoJsonNewerSchema` leave the source untouched in ingest), the media fetch, and the entry-name clash rename. From the move on, the ZIP write, the mirror and `afterMirror` run with `CancellationToken.None`, so neither a job cancel nor a closed review request can strand the file; any exception from the ZIP write (not only `VerifyFailed`/`IoError`) rolls the move back before it is reported. If staging fails before source removal (`IOException`/`UnauthorizedAccessException`, e.g. disk full during a cross-volume copy), the item is `Error IoError`, the source stays where it was, and a partial `<final>.tmp` is deleted best-effort (else integrity reports it as `OrphanFile`). Use the shared W6 staged move. For a loose source that disappears before placement return `Error IoError`; for an unsafe or non-regular ingest source return `Error IoError` without opening or moving it. External Review resolution checks the loose path or the archive container with the G4 resolver before opening it or deciding the source is missing. Only a genuinely absent source follows `SourceMissing` cleanup. Apply the same distinction to `IngestJob`'s stale Pending cleanup: for external systems prune only a confirmed missing path. Keep and log unsafe paths and inconclusive IO or permission failures. Use the archive container path for archived rows. Add `SystemId` to `PendingReviewSource` and to its `IngestReviewRepository` projection so the cleanup selects the storage mode without guessing from the path. Embedded rows retain their current cleanup. An unsafe or non-regular source (including a directory or dangling link at the recorded path) returns `500 IoError` and keeps Pending. Apply the same external source check to Dismiss and to DeleteSourceAsync. For Delete, an unsafe or inconclusive path returns `500 DeleteFailed`, preserves the source and Pending rows and records no `ReviewDeleted` audit. Confirmed absence still clears all Pending rows for the source without an audit. The extracted entry is checked separately before hashing. If final promotion fails after source removal, roll back from the complete temp. If rollback fails, preserve that temp and return `Error IoError` with its path. Then the ZIP is written (its verify checks the external file, W1), the audit row recorded (right after the ZIP write, before the mirror: existing AU4 order), and the DB mirrored. If the ZIP write fails (`VerifyFailed`/`IoError`), the file is moved back to its original ingest path (a ` (2)` name if that path is taken) and the item is `Error` as today. If the DB mirror or `afterMirror` fails, the ZIP already names the file, so it stays in the library and the item is `DbWriteFailed`. The next ingest or integrity run repairs the library mirror from the ZIP. DB repair does not reconstruct a failed Review status update. A retry of an archived Review item follows T9; for a loose file, the next ingest removes the stale Pending row, or retry returns `409 SourceMissing` and removes it. Document that the release can already be in the library after this response. If the move back also fails, the item is `Error IoError` with details naming the actual surviving complete-copy path, which can be a temporary file in ingest. Integrity reports an unlisted surviving file only when it is under the library root. A crash during staging can leave `<final>.tmp`, which may be the only complete copy once the source is removed. Integrity reports it as `OrphanFile` (never deleted automatically; `CrashRecovery` deletes only `*.zip.tmp`). A crash after the rename and before the ZIP write leaves `<final>` unlisted, so integrity reports it as `OrphanFile`; for a loose source that file is the only copy (the Admin moves it back to `ingest/<system>/`).
- **I5 Source deletion.** There is no source left to delete after a successful move (`PackageAsync`'s final `File.Delete` is skipped for external ROMs); an archive entry's extracted copy (in `cache/work/<jobId>/`) is moved the same way. A rollback of an archive entry deletes the moved copy instead of moving it back (the archive itself is untouched and its fate follows the existing rules).
- **I6 Self-repair.** SHA1 dedupe stays global across systems. If the incoming and owning handlers use different storage modes, take the existing `Duplicate` path, even when the owner has an open self-repairable issue. Do not use raw external input to rebuild an embedded ROM or move an embedded source whose normalized bytes may differ from its on-disk bytes. A byte-identical external file whose external destination has an open `EntryMissing`, `EntrySizeMismatch` or `HashMismatch` issue is moved into place over `<externalFileName>` (same tmp + rename) and the ZIP rewritten (`Repaired`, existing rule D30). If the owned path already contains a file, first rename it to a reserved `.repair.tmp` sibling. Keep it until the ZIP commits. On placement or ZIP-write failure restore both the old library file and the incoming source; on ZIP commit delete the backup best-effort (any leftover is `OrphanFile`). Use the opened ZIP’s ROM with the same SHA1 as the repair target. If it is absent or its pointer differs from the mirrored one, return `Error TargetZipUnreadable` with stale mirror details and leave both files untouched; the next ingest or Integrity can reconcile the mirror. The open issues are looked up with entry name = the `externalFileName` (G1's key), not `roms/<fileName>`, and a `Duplicate`'s details read `same as <zip> › <externalFileName>`.
- **I7 Audit.** `Ingested` / `ZipRepaired` rows as today; the details name the release (`release <fileName>`, taken from the stored rom, not from the written ZIP entries, since an external ROM has none), the target path is the ZIP's. Today's `entries.Keys.First(k => k.StartsWith("roms/"))` would throw for an external ROM, so `PackageAsync` takes the release's `fileName` as a parameter instead.

### Library writes
- **W1 Writer.** `LibraryZipWriter` writes no `roms/` entry for a ROM with `externalFileName` and doesn't copy one; its verify checks, for each external file this write placed or renamed (ingest I4, self-repair I6, W2–W4; passed to the writer as `LibraryZipChanges.ExternalFiles`, the set of `externalFileName`s to check: a new optional last record parameter `IReadOnlySet<string>? ExternalFiles = null`, matched ordinal-ignore-case, null = check none), that `<zip folder>/<externalFileName>` exists with length `metadata.sizeBytes` (no rehash; the bytes were hashed at ingest). External files the write didn't touch aren't checked, so metadata edits that leave the ZIP path unchanged, ratings, notes, adding another release and repairing another file still work. A write that renames a present wrong-length file fails verification and rolls back; integrity keeps reporting the bad file (G1). The writer has no system registry: it treats a game as external when its roms carry `externalFileName` (the validator makes that all-or-none per system), and a write as a rebuild at the current path when `existing` is not null and `Path.GetFullPath(existing.Path)` equals `Path.GetFullPath(target)` (ordinal-ignore-case); every other external write publishes a new path. For an external system open the ZIP temp with `FileMode.CreateNew`, and clean it up only if this write created it. An occupied temp yields `IoError` with the original ZIP and occupant intact. Publish a new external ZIP path with no overwrite, including a rename to a new ZIP path. Only a write rebuilding the ZIP at its current path uses replace. If another file takes the newly allocated path before publication, return `IoError` and undo placed ROMs. Notes for external ROMs are kept as today (`notes/<fileName>.md` inside the ZIP). No caller passes a `roms/<fileName>` new entry for an external ROM: ingest (`NewGameAsync`, `AddToGameAsync`), self-repair (`DuplicateOrRepairAsync`), move release and merge add one today, and the writer rejects a new entry `info.json` doesn't list with an `ArgumentException` that no caller catches.
- **W2 Title edit.** When the ZIP path changes, each external file is moved using W6 to its E1 name for the new ZIP **before** the new ZIP is written; `externalFileName` is updated. An external file that is already missing is not renamed (nothing to move; logged at `Warning`) but its `externalFileName` is still updated to the new E1 name, and it isn't in the writer's check set (W1), so the edit succeeds and integrity reports `EntryMissing` under the new name (W3 and W4 do the same). If the ZIP write fails, the renames are undone. If the DB commit fails afterwards, the files keep their new names (the new ZIP lists them), the old ZIP stays, and the result is `DbWriteFailed` as today. Delete the old ZIP only after the DB commit. If that deletion fails, log the old and new ZIP paths and keep the committed result.
- **W3 Move release.** The release's external file is renamed to its E1 name next to the target ZIP (new or existing game) before the target ZIP is written (after a new game's media fetch); rollback as W2 when the target write fails, and also when the source rebuild then fails (after `UndoTargetWriteAsync`; if that undo fails too, the file keeps its new name, which the written target lists). When it was the source's last release, attempt source ZIP deletion after the mirror attempt, including on `DbWriteFailed` (existing rule). If deletion fails, log both paths and keep the mirror result.
- **W4 Merge.** Every external file of the source is renamed to its E1 name next to the target ZIP (after any ` (2)` file-name clash rename of the release) before the target ZIP is written; rollback as W2 on target write failure. After the mirror attempt, including on `DbWriteFailed`, attempt source ZIP deletion as in W3.
- **W5 Delete.** As for embedded ROMs, removed ROMs are never hard-deleted: deleting a release or a game moves each external file (using W6 staging across volumes) to `ingest/<system>/_removed/<fileName>` (the rom `fileName`, without the ZIP prefix; ` (2)`… on a clash), before the ZIP write / ZIP delete, and moves it back to its library name if that write fails (`VerifyFailed`/`IoError`); on `DbWriteFailed` it stays in `_removed/` (existing rules of `RemoveRomsAsync`). A listed external file that is already missing has nothing to move and is skipped (existing rule for absent entries). The `_removed/` path is returned in the copies list like an embedded copy, so `ReleaseDeleted`'s target path names it (existing audit rule).
- **W6 Order and crash safety.** The recovery rules cover process interruption. Every write keeps "file moves first, then ZIP, then DB, then old-ZIP deletion" (delete-game removes the ZIP before deleting the DB row, as today). Share `Core/Storage/ExternalRomMove.cs` between ingest and edits. Reserve staging names and use no-overwrite renames. For the first rename use a same-filesystem-only primitive (Windows `MoveFileExW` without `MOVEFILE_COPY_ALLOWED`; Linux `renameat2` with `RENAME_NOREPLACE`). If the no-replace primitive is unavailable or unsupported (e.g. Linux `EINVAL` from a filesystem that rejects `RENAME_NOREPLACE`, such as an NFS mount), return `IoError` whose details say `no-replace rename is not supported for <path>`, log it at `Error`, and leave the source in place; deployment.md says `/app/roms` and `/app/ingest` must support it for external systems. P/Invoke as `Core/Storage/ProcessIdentity.cs` does (`[DllImport("libc", SetLastError = true)]`; `kernel32` `MoveFileExW` on Windows). Only the explicit cross-device result (`ERROR_NOT_SAME_DEVICE` or `EXDEV`) enters the copy branch. `File.Move` can copy implicitly and cannot distinguish this boundary. Across volumes, stream to an exclusively created sibling ending in `.tmp`, close it, verify the length against the source, then delete the source and rename the complete temp to its destination. For incoming ingest or Review bytes, compute SHA1 while copying and compare it to the previously verified SHA1 before deleting the source. A mismatch keeps the source and removes the owned temp best-effort; ingest skips as `TooRecent`, Review returns `VerifyFailed` and keeps Pending. Use the same protocol for rollback. For rollback to a loose ingest source, reuse the original path if it is free and fits with staging; otherwise allocate a budgeted sibling using the original stem and extension and the usual clash suffix. For rollback to a library pointer, restore exactly the original name or report failure with the surviving path. Allocate a separately budgeted temp for an exact library restore when appending `.tmp` to that pointer would exceed the component limit. Return the actual surviving complete-copy path if rollback cannot finish, including a temp under ingest or `_removed`, and put that path in the caller’s diagnostic. A temp left directly in `ingest/<system>/` is listed by `IngestFileScanner` (it skips only subfolders, dot-files and OS junk), so the next ingest fails it as `UnsupportedType` and moves it to `ingest/<system>/_failed/` with its `.error.txt` (bytes kept). For external-system `MoveToFailed`, budget the final name plus `.error.txt` within 255 UTF-8 bytes, reserve both names against disk entries case-insensitively and recompute the budget for each clash suffix. Create the diagnostic exclusively; an unexpected occupant is logged and left intact. Use the same external allocation and W6 move for `_duplicates/`, reserving final and staging names there. For both external side folders, reject a linked or otherwise unsafe destination directory or ancestor before directory creation or placement (`IoError`, source kept). Embedded side-folder naming and moves stay as today. The deployment guide tells Admins to look there too and to drop the `.tmp` suffix to re-ingest it. Apply E2’s component budget to final and staging names, including under `_removed/`. A pre-existing temp is occupied and never cleaned by a failed attempt. Keep the existing `JobLock` over allocation, moves, writes, undo and DB work (`409 JobRunning` when busy). Library mutations retain the `LibraryEditor` policy (ROM manager permission); Review remains Admin-only. The moves run after every lookup, validation and media fetch of the edit, immediately before the first ZIP write. If one move fails (`IOException`/`UnauthorizedAccessException`), the moves already done are undone, no ZIP is written, and the edit returns `IoError` (`500` ProblemDetails, existing mapping). Edits already write without the request's cancellation token (existing rule), and the moves follow it. An undo that itself fails (a rename back, or a move back from `_removed/`) is logged at `Error` and left as it is; the edit returns the code of the failure that triggered the undo, and integrity reports the file (`EntryMissing`, plus `OrphanFile` when it is still in the library folder). A crash can leave `EntryMissing` for a ZIP pointer, plus `OrphanFile` for an unlisted library file. A move to `_removed/` can leave the only complete copy there, including under a temporary name outside the integrity scan.
- **W7 Interrupted edit recovery.** If both old and new title-edit ZIPs survive, DB sync reports `DuplicateGameId` and preserves the existing row. An interrupted move or merge can leave both ZIPs listing the same SHA1; DB sync reports `DuplicateSha1` for the rejected candidate and can keep the old owner. A sidecar named in a rejected ZIP can appear as `OrphanFile`. Recovery is manual: stop writes and back up both ZIPs and sidecars. For a title edit, keep the ZIP whose pointers match the moved files and move the obsolete ZIP outside `roms/`. For a completed target write after merge or a last-release move, verify the target lists all moved releases and their bytes, then move the obsolete source ZIP outside `roms/`. For a move with surviving source releases and an unwritten source rebuild, keep the target, remove only the moved release and its note from the source ZIP, and recompute the source primary using T6 where applicable. If no target ZIP committed, restore moved files to the source ZIP’s pointers instead. Run Integrity after reconciling the ZIPs. Keep reported orphan bytes until both ZIPs and pointers have been checked.

### Integrity, downloads and reports
- **G1 Quick.** For every game of an external system, each external file is checked by `stat`, in Quick and Deep, whether or not its ZIP is opened, using the DB rows after the DB repair (so also when the ZIP is unreadable): missing → `EntryMissing`, other length → `EntrySizeMismatch` (entry name = the external file name). When a ZIP is opened, `CheckZipAsync` skips ROMs with `externalFileName` in its `roms/` checks (so a stray `roms/<fileName>` for one is `EntryUnlisted`); everything else in the ZIP check is unchanged. The stat runs inside the per-ZIP loop, right after that ZIP's own check (location-only or opened), for the external ROMs the DB lists under that ZIP path (read once, after the DB repair; ZIP paths compared case-insensitively, like the scan's DB lookup), so a cancel stops both; a ZIP with no DB row has nothing to stat. The rows come from a new `IRomRepository.ListExternalAsync(CancellationToken)` returning `ExternalRomRow(Guid GameId, string ZipPath, string ExternalFileName, long SizeBytes, string Sha1)` for every rom with `external_file_name` set; `IntegrityJob` gets `IRomRepository` through `IntegrityJobFactory`, and G3 uses the same list.
- **G2 Deep.** Also streams each external file through SHA1 (with the job's token, like ZIP entry hashes): different → `HashMismatch`. As for ZIP entries, a wrong-length file is still hashed (both `EntrySizeMismatch` and `HashMismatch`); a missing file isn't. If it disappears between stat and open, report `EntryMissing`. Other IO or permission failures reading bytes produce `HashMismatch` with unreadable details. A stat IO or permission failure (other than a missing file or directory) is logged and leaves that release unchecked for resolution. Continue with the remaining files.
- **G2a Resolution (D48).** A completed run resolves an external `EntryMissing` or `EntrySizeMismatch` that it successfully checked and did not see again. Only a completed Deep run can resolve an external `HashMismatch`. For a registered external-system game, only `EntryMissing`, `EntrySizeMismatch` or `HashMismatch` with a nonempty entry name containing no `/` can use this shortcut. `WasChecked` keys outcomes by ZIP path, pointer name and check kind (`LocationOnly` included). A failed stat on one pointer cannot resolve issues for it even when another release was checked. A pointer removed from a successfully mirrored, readable ZIP resolves its old issues on a completed run, subject to Deep for `HashMismatch`. If that ZIP could not be read or mirrored, absence from the pointer list alone cannot resolve the issue. A root-level `EntryUnlisted` remains subject to the ZIP-entry rule. ZIP-entry issues keep today's rule.
- **G3 Orphans.** In a system folder, a non-ZIP file listed (DB rows, after the DB repair) as an external file by a game in that folder (name compared case-insensitively) is not an orphan; every other non-ZIP (including `*.tmp`) is `OrphanFile` as today. When DB repair relocates a game whose sidecars stayed behind, report the old sidecars as orphans and check the new pointers at the new ZIP path. When DB repair prunes a missing ZIP, its remaining sidecars are orphans.
- **G4 ROM download.** `GET /api/games/{id}/roms/{romId}/download` for an external ROM streams the file at `SafePath.Resolve(roms, <the ZIP's folder>/<externalFileName>)` (from the DB rows) with HTTP range support (`enableRangeProcessing`), download name = the rom `fileName`, any signed-in user (as today), not audited. All external reads and mutations use a shared resolver (`Core/Storage/ExternalRomPath.cs`) that applies E3 and `SafePath`, rejects symlinks/reparse points on the file and its ancestors below the configured root, and accepts only regular files at the leaf. Reject FIFOs, sockets and devices before opening them on Linux; apply the same regular-file rule to external ingest and Review sources before hashing. Before opening or moving a claimed library file, check for another mirrored game’s claim to the same directory and name (ordinal-ignore-case), including during self-repair. Download returns `404 NotFound`; mutations return `IoError` before any ZIP write. Integrity records `EntryMissing` with conflict details for each conflicting pointer and skips length and hash checks. The file remains listed for G3. An Admin fixes the ZIP pointers and runs Integrity to rebuild the mirror. The Ingestion page uses the same regular-file and ancestor checks for external systems: `IngestFileScanner.ScanFailed` skips an unsafe `_failed/` directory and unsafe leaves, and treats a missing, unsafe or unreadable diagnostic as no reason without opening it. `IngestFileDeleter` checks paths under the existing job lock and before any delete or Pending cleanup; for an unsafe or inconclusive external file return it in the existing `failed` array, with no audit or Pending changes. ### titledb as a DAT source
- **T1 Source per system.** `ISystemHandler` gains `DatSource DatSource => DatSource.Libretro;` (enum in `Core/Dats`: `Libretro = 0`, `TitleDb = 1`; `Libretro` must be the zero value so the tests' `Substitute.For<ISystemHandler>()` handlers stay libretro). Switch returns `TitleDb`.
- **T2 Refresh.** For a `TitleDb` system the DAT refresh downloads one source file per refresh from `Sources:TitleDbUrl` (new config key, default `https://raw.githubusercontent.com/blawar/titledb/master/US.en.json`; validated, like `DatBaseUrl`, as an absolute http(s) URL; required) with a 256 MiB cap on bytes read, including when no Content-Length is sent, and with the job token on download and parse (libretro DATs keep 64 MiB; the file was 90,699,593 bytes on 2026-11-10), streamed to `cache/work/<jobId>/titledb.json` (never held whole in memory, unlike today's `MemoryStream` buffering of a libretro DAT), parses it from that file once, and stores for each TitleDb handler a compact `cache/dats/titledb/<DatName>.json`. titledb facts (checked 2026-11-10 against the file): the top level is a JSON **object** keyed by nsuId (decimal string), not an array; `id` is a 16-hex upper-case string or null (null in ~7,700 of ~37,500 entries; ~200 ids repeat under several nsuIds); `name` can be null; `developer`, `frontBoxArt` and `version` are always null; `releaseDate` is an int `yyyymmdd`, sometimes just a year (`2020`), or null; `category`, `languages` (duplicates possible), `iconUrl` and `screenshots` can be null; `size` is a JSON integer (up to 90,958,725,120 in the checked snapshot, so it is not an Int32; the eShop download size, not a dump's length, so it is not carried; T3 sizes are 0); every image URL is on `https://img-eshop.cdn.nintendo.net`; the file has base games and DLC but **no update entries**. Parsing reads the downloaded file as a stream with `JsonSerializer.DeserializeAsync<OrderedDictionary<string, TitleDbEntry?>>` (a private record of only the fields used here, so the ~90 MB text is never held whole and document order is kept) and ignores unknown fields. 16 names hold a line break (`Baldo\nThe guardian owls`); T5's whitespace collapse covers them. The compact file is a JSON array (written and read only by `TitleDb.cs`) of `{ "titleId", "name", "publisher", "developer", "releaseYear", "genres", "languages", "boxArtUrl", "snapUrl" }` in that order, camelCase, nulls written: title id upper-cased; release year = `releaseDate / 10000` for eight-digit date values from 10000101 through 99991231, the value itself when it is 1970–2100, else null; this bounds values stored in `games.release_year` (`SMALLINT`). genres = `category` (null → []); languages = `languages` distinct ordinally, in order (null → []); drop null or whitespace-only members from both lists; box-art URL = `iconUrl`, else `frontBoxArt`; snap URL = the first `screenshots` entry. Entries without a valid Switch `id` (`\A0100[0-9A-Fa-f]{12}\z`, the same prefix T4 reads from file names; the 75 Switch 2 ids starting `0400` are skipped, see Out of scope) or with a null or blank `name` are skipped. Also skip entries whose T5 title sanitizes to empty or whose T3 `GameName` exceeds 255 Unicode scalar values (the mirrored `dat_game_name` limit). Apply these checks before deduplicating; a repeated id keeps the first entry in document order. Image URLs are kept only when they fit the 1024-character `images.source_url` column and pass the shared pure URI validator in `TitleDb.cs`: absolute HTTPS, exact DNS host `img-eshop.cdn.nintendo.net` (ordinal-ignore-case), port 443 and no user info. The manifest entry is `File` `titledb/Nintendo - Nintendo Switch.json`, `DatName` the handler's `DatName` (`Nintendo - Nintendo Switch`), `Version` the download date `yyyy.MM.dd` (UTC, from the injected `TimeProvider`), and the compact file's SHA1 (re-checked on load, like every DAT). The refresh fetches `13 × 5 + 1 = 66` files after this spec; its progress total counts each download once (66) and its result `files` is the manifest count (66, one entry per TitleDb handler). The titledb request uses the existing `dats` named client with `HttpCompletionOption.ResponseHeadersRead`: the client's retries, 20 s per-attempt timeout and default `HttpClient.Timeout` end when the response headers arrive, so the body is read under the 256 MiB cap and the job token only (no whole-body timeout; the Admin cancels a stalled refresh), and a failure while reading the body is not retried (the refresh fails, old set kept). A failed download, parse, staged validation or cancellation before publication leaves the old set active. Publication uses the existing DAT directory swap and rollback policy. A valid source object with zero usable entries produces an empty store. A JSON null or wrong top-level type is a parse failure. The compact reader rejects null rows, missing properties (including nullable properties), duplicate title IDs, noncanonical IDs (exactly 16 ASCII hex characters with the `0100` prefix and uppercase letters), invalid normalized names, release years outside 1000–9999, null, non-string or whitespace-only array elements, and URLs that fail T8 or the stored length limit. It accepts empty arrays. Apply the same checks at startup and before swap. Before the swap, load the staged compact file through the same validator as startup.
- **T3 Load.** `DatCache.Load` builds a `DatStore` for a `TitleDb` system from the compact file: one `DatRom` per entry with `GameName` = `<base title form of the name> [<TitleId>]` (unique, used by `/api/dat/search`, suggestions and the review picker unchanged), `RomName` = the T5 rom `fileName` with `N` = 0 and `.nsp`, size 0 and no hashes (`Crc32`, `Md5` and `Sha1` are `""`; excluded from the SHA1 index; `/api/dat/search` returns `crc32: ""` for them), plus `ByTitleId(id)` returning the entry. The store's `DatName` is `titledb` and its `Version` the manifest version; `BaseTitles` and `SuggestionEngine` keep running `NoIntroName.Parse` on `GameName`, which keeps the whole `GameName` (with its ` [<TitleId>]`) when the name has no ` (`, so such an entry is its own suggestion group, and cuts at the first ` (` otherwise (695 titledb names, e.g. `Runbow (Retail Only)` → `Runbow`), so entries sharing that prefix form one group showing one best entry (accepted: `/api/dat/search` matches the full `GameName`, so the picker still finds each). `GET /api/admin/dats` today returns only manifest entries under `no-intro/`; it also returns the `titledb/` entry, as a row `{ datName: "Nintendo - Nintendo Switch", version: "<yyyy.MM.dd>", downloadedAt }` in the same `datName` order, and the refresh job's result `versions` includes it the same way. Missing, not listed in `dats.json`, SHA1 mismatch or unparsable → the system has no DATs (`DatsMissing`, existing rule); `DatCache.Load`'s per-system catch gains `JsonException` (today it catches only IO, `DatParseException`, `InvalidDataException` and `UnsafePathException`, so a corrupt compact file would abort the whole load).
- **T4 Matching.** For a `TitleDb` system, step 4 takes the title id from the header field `titleId`, else from the first match of `\[(0100[0-9A-Fa-f]{12})\]` in the file name (upper-cased). A ticket's name carries the content's own id (the update or DLC id, not the base's; [blawar/nut’s PFS0 parser](https://github.com/blawar/nut/blob/master/Fs/Pfs0.py)), which is what the kind rule below needs. A header id that isn't `0100…` (e.g. a Switch 2 `0400…` ticket) has no titledb entry (T2), so it goes to Review like a file-name id that doesn't match. The entry kind comes from the unsigned 64-bit hex ID: base = id with the low 13 bits cleared; `id == base` → base game, `id == base | 0x800` → update, otherwise apply the DLC and delta cases below. A base game matches when `ByTitleId(id)` exists. An update or DLC matches when `ByTitleId(base)` exists (the DLC's own entry, when present, gives its name). No title id, unsupported kind, or no required entry → Review `NoDatMatch` with file-name suggestions, subject to the existing `InvalidHeader` check for an unmatched non-plausible header. Skip the family’s usual fallback extension rename for external handlers so Review retains the original `.xci`, `.nsz` or `.xcz` extension. `identification` = method `TitleDb`, `datName` `titledb`, `datVersion` the manifest version, `datGameName` the base game's `GameName`. The kind rule matches titledb's data (every base id has its low 13 bits clear, every DLC id has bit 12 set and its base present) and nxdumptool's `title.h` (patch = application + 0x800, add-on content = (application & ~0xFFF) + 0x1000 + index); switchbrew doesn't state it. For an ordinary DLC use `base + 0x1001` through `base + 0x17D0`. For a data patch subtract `0x800`, verify the result is in that DLC range, and use the underlying DLC's titledb name when present while keeping the input ID in the file name. The maximum DLC index is 2000, so `01000000000117D0` patches to `0100000000011FD0`, within the same application bucket. An application delta is exactly `base + 0xC00`; flag and rank it as DLC, name it from the base with ` (DLC)` appended, and retain the delta ID in the filename. Other low-bit patterns go to `NoDatMatch`. See [nxdumptool title helpers](https://raw.githubusercontent.com/DarkMatterCore/nxdumptool/rewrite/include/core/title.h). Step 6 grouping uses the T5 base title (not `NoIntroName.Parse(GameName)`). An `AmbiguousGroup` review row of a `TitleDb` system stores, besides today's `datName`/`datVersion`/`datGameName`/`romName` (the T5 file name), the `titleId`; it also stores the computed base title, regions, languages, revision and flags in `DatIdentification`. `Attach` (flag `None`) uses those queued values, ROM name and DAT version (method `TitleDb`), preserving the release identity across a DAT refresh. Use current metadata from the queued base ID when available, else `DatMetadata.Empty`.
- **T5 Naming.** Base title (grouping key, game title) = the base game's titledb name with `™`, `®`, `©` removed, `: ` → ` - `, whitespace collapsed (every run of `\s`, line breaks included, → one space; trimmed), and a leading `The `, `A ` or `An ` moved to the end of the first ` - ` segment (`The Legend of Zelda: Tears of the Kingdom` → `Legend of Zelda, The - Tears of the Kingdom`; `DisplayTitle` turns it back). Rom `fileName` = `Sanitize(<entry name, ™®© removed, ": " → " - ", whitespace collapsed, each run of two or more `.` → one `…` (U+2026)>) + " [<TitleId>][v<N>]" + <the file's extension, lower-case>` (the validator forbids `..` in a rom `fileName`, and 12 titledb names hold one, e.g. `Oh...Sir! The Insult Simulator` → `Oh…Sir! The Insult Simulator [<TitleId>][v0].nsp`; the game title keeps `...`), where `N` is the first case-sensitive `[v<ASCII digits>]` in the ingest file name parsed as UInt32 and formatted in invariant decimal without leading zeros; no match or overflow → `0`; an update with no entry uses the base name; a DLC with no entry of its own uses `<base name> (DLC)`. `revision` = `v<N>` when `N > 0`, else null. `flags` = `Update` or `DLC` for those kinds. `regions` = []; `languages` = titledb codes with the first letter upper-cased (`en` → `En`), distinct, in order.

## Risks
- **Partial moves.** A crash between file rename, ZIP write and DB commit can leave a file under the wrong name. Integrity reports missing pointers and unlisted files within the library. For an interrupted delete, also check `ingest/<system>/_removed/` for the moved file or its staging copy.
- **Long ingest items.** Hashing a 30 GB file takes minutes and holds the job lock; Cancel stops after the current item, as documented, so a cancel can wait for one long hash. A Switch file waiting in Review stays in `ingest/switch/` and, like every pending source (existing lifecycle), is hashed again by every Import all; Import selected (IN1) avoids that. Disk space: the move needs no extra space on the same disk, the file's size on another. Review resolution and edits run inside the HTTP request, so a cross-volume move or a long re-hash can outlast a proxy timeout: they run without the request's token (T9, W6) and deployment.md tells Admins to raise the proxy's read timeout.
- **titledb is a third-party JSON** (~90 MB): parsed with size caps, unknown fields ignored, URLs allowed only from one https host, image bytes still go through the existing caps and magic-byte checks.
- **Title-ID-only matching** can put a mislabelled file (wrong `[TitleId]` in its name) under the wrong game; the release keeps `originalFileName`, and move/delete fix it.
