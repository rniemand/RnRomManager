# External ROM storage and Nintendo Switch

## Summary
Disc-era and modern systems (Switch, GameCube, Wii, Xbox 360…) have multi-GB images that can't sensibly live inside a game's ZIP or be read into memory. Each system now declares whether its ROMs are **embedded** in the game ZIP (every existing system: yes) or stored **external**: next to the ZIP, named so they group with it, and pointed at from `info.json`. The ZIP keeps everything else (info.json, images, notes, ratings). Nintendo Switch (`switch`) is the first external system, identified by title ID through [blawar/titledb](https://github.com/blawar/titledb) because libretro has no Switch DAT or thumbnails.

## Out of scope
- GameCube, Wii, Xbox 360 and other large systems (later specs; this one builds what they need).
- Moving an existing system between embedded and external (the flag is fixed per system; no conversion tool).
- Building a ZIP with the ROMs on the fly for "Download ZIP" (decision: ZIP as stored + per-release downloads).
- Decrypting Switch content: no keys; XCI title IDs come only from the file name.
- titledb regions other than `US.en.json`; titledb descriptions (game `description` stays Admin-edited only).
- Ingesting external-system ROMs from archives beyond today's archive limits (256 MiB total): a Switch file inside a `.zip`/`.7z` is rejected by the existing limits, as today.

## Behaviour

### Storage flag
- **S1 Lookup.** `ISystemHandler` gains a required `bool EmbedRomsInZip { get; }` (no default implementation, so every handler states it). All 13 existing handlers return `true`; `switch` returns `false`. `GET /api/systems` adds `embedRoms` (bool) to each entry. `docs/adding-a-system.md` lists every system with its value. NSubstitute returns `false` for an unconfigured `bool`, so every test's `Substitute.For<ISystemHandler>()` (16 files under `tests/`, e.g. `InfoJsonTests`, `LibraryZipTests`, Data's `IntegrityJobTests` and `LibraryMirrorTests`) sets `EmbedRomsInZip.Returns(true)`; without it those handlers would silently become external.
- **S2 Embedded systems are unchanged.** Every rule below applies only when `EmbedRomsInZip` is `false`; embedded ZIPs, their writes, integrity checks and downloads behave exactly as today (existing tests prove it).

### External file naming and pointer
- **E1 Name.** An external ROM is the file `<ZipBase>.<rom fileName>` in the ZIP's own folder, where `<ZipBase>` is the ZIP name without `.zip`. Example: `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.zip` and `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.The Legend of Zelda - Tears of the Kingdom [0100F2C0115B6000][v0].nsp`. The shared `<ZipBase>.` prefix sorts them together in any file explorer.
- **E2 Length and clashes.** The final name, including any clash suffix, is at most 250 UTF-8 bytes (so `<final>.tmp` stays under the 255-byte name limit of ext4/NTFS). When it's longer, the rom part's stem (before its extension) is cut from its end, at a char boundary (never splitting a surrogate pair), until it fits; the extension is kept. If the rom stem is cut to nothing and the name still doesn't fit (a long multi-byte `<ZipBase>`: `FileNameSanitizer.MaxLength` is 180 chars, up to 540 bytes), `<ZipBase>` is cut from its end the same way. A name is taken (case-insensitive) when a different file or folder already has it, or when a DB row lists it as the `external_file_name` of another game whose ZIP is in that folder (so a game's missing file can't have its name reused by another game, which I6 self-repair would then overwrite; a dotted `<ZipBase>` such as `Mr. Driller` can produce the same name as another game's) → ` (2)`, ` (3)`… before the extension (`FileNameRules.FirstFree` with that check), cutting further first so the suffixed name still fits. Implemented once in `Core/Storage/ExternalRomName.cs`.
- **E3 Pointer.** `info.json` **schema version 4**: each Rom gains `externalFileName` (string?, the file name only, resolved in the ZIP's folder). Validator (which now receives an id → `EmbedRomsInZip` lookup instead of the bare id set): for a system with `EmbedRomsInZip = false` it is required; for an embedded system it must be null; when set it is a plain file name (no `/`, `\` or control character, and not `.` or `..`; unlike a rom `fileName`, `..` inside the name is allowed, because `<ZipBase>` is the sanitized title and may hold `...`, e.g. `Oh...Sir!!`), unique case-insensitively within the game, at most 255 chars, and ends (case-insensitively) with one of the system's `RomExtensions` (so a hand-edited `info.json` can't point a download, move or delete at a ZIP, a `.tmp` or another non-ROM file). The v3→v4 upgrader adds `externalFileName: null`. Apps before this one treat a v4 file as `InfoJsonNewerSchema` (read-only, existing rule). `identification.method` gains the value `TitleDb` (T4) and image `source` gains `titledb` (T8). A stray `roms/<fileName>` entry for an external ROM is not a validator rule: the writer never writes one (W1) and integrity reports it as `EntryUnlisted` (G1).
- **E4 Database.** Migration `0018_external_roms.sql`: `ALTER TABLE roms ADD external_file_name VARCHAR(255) NULL`. `RomRow`, the mirror and `DbSync` carry it (`NULL` for every existing row; no backfill needed). `GET /api/games/{id}` release rows gain `externalFileName`.

### Ingest of an external ROM
- **I1 Validation.** Extension and size checks as today (`MaxRomSizeBytes` is a `long`).
- **I2 Streaming hash.** The file is never read whole into memory: one streamed read computes CRC32, MD5 and SHA1 together (`NormalizeForHashing` is not called for external systems). `ReadHeader` receives the first `min(size, 1 MiB)` bytes. After hashing, the file's length and last-write time are compared with a fresh `FileInfo` read immediately before the hash (not the snapshot's `SizeBytes`/`ModifiedAtUtc`, which for an archive entry are the archive's); an archive entry's extracted copy in `cache/work/<jobId>/` is written by the job itself and skips this check. If either changed (still being copied in), the item is `Skipped` with reason `TooRecent` (file left in place, picked up by a later run; features.md broadens `TooRecent` to "modified < 10 s ago or changed while being hashed"). Cancellation keeps the documented rule: the current item finishes, including its hash, so the streamed hash is not given the job's cancellation token (today `File.ReadAllBytesAsync` gets it).
- **I3 Identification, dedupe, review, grouping** follow the existing steps 3–6 (SHA1 dedupe, review lifecycle, identification per the system's DAT source, grouping by system + base title).
- **I4 Placement (move with rollback).** The move happens in `PackageAsync`, immediately before the ZIP write: after the target ZIP was opened (`TargetZipUnreadable` / `InfoJsonNewerSchema` leave the source untouched in ingest), the media fetch, and the entry-name clash rename. From the move on, the ZIP write, the mirror and `afterMirror` run with `CancellationToken.None`, so neither a job cancel nor a closed review request can strand the file; any exception from the ZIP write (not only `VerifyFailed`/`IoError`) rolls the move back before it is reported. If the move itself fails (`IOException`/`UnauthorizedAccessException`, e.g. disk full during a cross-volume copy), the item is `Error IoError`, the source stays where it was, and a partial `<final>.tmp` is deleted best-effort (else integrity reports it as `OrphanFile`). The source is moved with `File.Move` to `<final>.tmp` in the target ZIP's folder (a rename on the same disk, else .NET's copy + delete), then renamed to `<final>` (E1/E2). Then the ZIP is written (its verify checks the external file, W1), the audit row recorded (right after the ZIP write, before the mirror: existing AU4 order), and the DB mirrored. If the ZIP write fails (`VerifyFailed`/`IoError`), the file is moved back to its original ingest path (a ` (2)` name if that path is taken) and the item is `Error` as today. If the DB mirror or `afterMirror` fails, the ZIP already names the file, so it stays in the library and the item is `DbWriteFailed` (existing meaning: the next ingest or integrity run repairs the DB from the ZIP). If the move back also fails, the item is `Error IoError` with details naming the library path the file was left at (integrity reports it as `OrphanFile`). A crash mid-move leaves `<final>.tmp`, which integrity reports as `OrphanFile` (never deleted automatically; `CrashRecovery` deletes only `*.zip.tmp`). A crash after the rename and before the ZIP write leaves `<final>` unlisted, so integrity reports it as `OrphanFile`; for a loose source that file is the only copy (the Admin moves it back to `ingest/<system>/`).
- **I5 Source deletion.** There is no source left to delete after a successful move (`PackageAsync`'s final `File.Delete` is skipped for external ROMs); an archive entry's extracted copy (in `cache/work/<jobId>/`) is moved the same way. A rollback of an archive entry deletes the moved copy instead of moving it back (the archive itself is untouched and its fate follows the existing rules).
- **I6 Self-repair.** A byte-identical file whose external file has an open `EntryMissing`, `EntrySizeMismatch` or `HashMismatch` issue is moved into place over `<externalFileName>` (same tmp + rename) and the ZIP rewritten (`Repaired`, existing rule D30). The open issues are looked up with entry name = the `externalFileName` (G1's key), not `roms/<fileName>`, and a `Duplicate`'s details read `same as <zip> › <externalFileName>`.
- **I7 Audit.** `Ingested` / `ZipRepaired` rows as today; the details name the release (`release <fileName>`, taken from the stored rom, not from the written ZIP entries, since an external ROM has none), the target path is the ZIP's. Today's `entries.Keys.First(k => k.StartsWith("roms/"))` would throw for an external ROM, so `PackageAsync` takes the release's `fileName` as a parameter instead.

### Library writes
- **W1 Writer.** `LibraryZipWriter` writes no `roms/` entry for a ROM with `externalFileName` and doesn't copy one; its verify checks that `<zip folder>/<externalFileName>` exists with length `metadata.sizeBytes` (no rehash; the bytes were hashed at ingest). Notes for external ROMs are kept as today (`notes/<fileName>.md` inside the ZIP). No caller passes a `roms/<fileName>` new entry for an external ROM: ingest (`NewGameAsync`, `AddToGameAsync`), self-repair (`DuplicateOrRepairAsync`), move release and merge add one today, and the writer rejects a new entry `info.json` doesn't list with an `ArgumentException` that no caller catches.
- **W2 Title edit.** When the ZIP path changes, each external file is renamed (`File.Move`) to its E1 name for the new ZIP **before** the new ZIP is written; `externalFileName` is updated. If the ZIP write fails, the renames are undone. If the DB commit fails afterwards, the files keep their new names (the new ZIP lists them) and the result is `DbWriteFailed` as today. The old ZIP is deleted last, as today.
- **W3 Move release.** The release's external file is renamed to its E1 name next to the target ZIP (new or existing game) before the target ZIP is written (after a new game's media fetch); rollback as W2 when the target write fails, and also when the source rebuild then fails (after `UndoTargetWriteAsync`; if that undo fails too, the file keeps its new name, which the written target lists). When it was the source's last release, the source ZIP is deleted (existing rule).
- **W4 Merge.** Every external file of the source is renamed to its E1 name next to the target ZIP (after any ` (2)` file-name clash rename of the release) before the target ZIP is written; rollback as W2; the source ZIP is deleted (existing rule).
- **W5 Delete.** As for embedded ROMs, removed ROMs are never hard-deleted: deleting a release or a game moves each external file (`File.Move`, a rename when ingest and roms share a disk, else copy + delete) to `ingest/<system>/_removed/<fileName>` (the rom `fileName`, without the ZIP prefix; ` (2)`… on a clash), before the ZIP write / ZIP delete, and moves it back to its library name if that write fails (`VerifyFailed`/`IoError`); on `DbWriteFailed` it stays in `_removed/` (existing rules of `RemoveRomsAsync`). A listed external file that is already missing has nothing to move and is skipped (existing rule for absent entries). The `_removed/` path is returned in the copies list like an embedded copy, so `ReleaseDeleted`'s target path names it (existing audit rule).
- **W6 Order and crash safety.** Every write keeps "file moves first, then ZIP, then DB, then old-ZIP deletion"; only a failed ZIP write rolls the moves back. The moves run after every lookup, validation and media fetch of the edit, immediately before the first ZIP write. If one move fails (`IOException`/`UnauthorizedAccessException`), the moves already done are undone, no ZIP is written, and the edit returns `IoError` (`500` ProblemDetails, existing mapping). Edits already write without the request's cancellation token (existing rule), and the moves follow it. An undo that itself fails (a rename back, or a move back from `_removed/`) is logged at `Error` and left as it is; the edit returns the code of the failure that triggered the undo, and integrity reports the file (`EntryMissing`, plus `OrphanFile` when it is still in the library folder). A crash between steps leaves at worst `EntryMissing` (ZIP names a file that has another name) plus an `OrphanFile` for the same bytes; both are reported, nothing is deleted automatically.

### Integrity, downloads and reports
- **G1 Quick.** For every game of an external system, each external file is checked by `stat`, in Quick and Deep, whether or not its ZIP is opened, using the DB rows after the DB repair (so also when the ZIP is unreadable): missing → `EntryMissing`, other length → `EntrySizeMismatch` (entry name = the external file name). When a ZIP is opened, `CheckZipAsync` skips ROMs with `externalFileName` in its `roms/` checks (so a stray `roms/<fileName>` for one is `EntryUnlisted`); everything else in the ZIP check is unchanged. The stat runs inside the per-ZIP loop, right after that ZIP's own check (location-only or opened), for the external ROMs the DB lists under that ZIP path (read once, after the DB repair), so a cancel stops both; a ZIP with no DB row has nothing to stat. The rows come from a new `IRomRepository.ListExternalAsync(CancellationToken)` returning `ExternalRomRow(Guid GameId, string ZipPath, string ExternalFileName, long SizeBytes, string Sha1)` for every rom with `external_file_name` set; `IntegrityJob` gets `IRomRepository` through `IntegrityJobFactory`, and G3 uses the same list.
- **G2 Deep.** Also streams each external file through SHA1 (with the job's token, like ZIP entry hashes): different → `HashMismatch`.
- **G2a Resolution (D48).** Because every run stats every external file, any completed run resolves an open external `EntryMissing`/`EntrySizeMismatch` it didn't see again; only a Deep run resolves an external `HashMismatch`. An issue is external when its `entry_name` has no `/` (ZIP entries always start `roms/`, `images/` or `notes/`): `WasChecked` treats it as checked for every ZIP the loop reached, `LocationOnly` included, except `HashMismatch`, which needs Deep. ZIP-entry issues keep today's rule.
- **G3 Orphans.** In a system folder, a non-ZIP file listed (DB rows, after the DB repair) as an external file by a game in that folder (name compared case-insensitively) is not an orphan; every other non-ZIP (including `*.tmp`) is `OrphanFile` as today.
- **G4 ROM download.** `GET /api/games/{id}/roms/{romId}/download` for an external ROM streams the file at `SafePath.Resolve(roms, <the ZIP's folder>/<externalFileName>)` (from the DB rows) with HTTP range support (`enableRangeProcessing`), download name = the rom `fileName`, any signed-in user (as today), not audited. The file is opened `FileShare.Read | FileShare.Delete` (as `LibraryFiles` opens ZIPs; a new `LibraryFiles.OpenExternal` next to `OpenZip`), so a running download never blocks a W2–W5 rename on Windows. A missing file → `404` ProblemDetails `code` `NotFound` (the existing code for a missing ZIP entry).
- **G5 Game download.** `GET /api/games/{id}/download` returns the ZIP as stored (no ROMs). The Game page's ZIP download button gets the tooltip "ROM files are downloaded per release" for external systems.
- **G6 Library Size report.** A game's size is `zip_size_bytes` + the sum of its external ROMs' `size_bytes` (system totals and the per-game drill-down, which also sorts by that combined size). The Duplicates report keeps its `zipSizeBytes` column labelled "ZIP size" (the ZIP only).
- **G7 Game page.** Each external release row shows a small `External` badge whose tooltip is its `externalFileName`. The Zip Contents tab is unchanged (it lists real ZIP entries).

### titledb as a DAT source
- **T1 Source per system.** `ISystemHandler` gains `DatSource DatSource => DatSource.Libretro;` (enum in `Core/Dats`: `Libretro = 0`, `TitleDb = 1`; `Libretro` must be the zero value so the tests' `Substitute.For<ISystemHandler>()` handlers stay libretro). Switch returns `TitleDb`.
- **T2 Refresh.** For a `TitleDb` system the DAT refresh downloads one file from `Sources:TitleDbUrl` (new config key, default `https://raw.githubusercontent.com/blawar/titledb/master/US.en.json`; validated, like `DatBaseUrl`, as an absolute http(s) URL; required) with a 256 MiB cap (libretro DATs keep 64 MiB; the file was 90,699,593 bytes on 2026-11-10), streamed to `cache/work/<jobId>/titledb.json` (never held whole in memory, unlike today's `MemoryStream` buffering of a libretro DAT), parses it from that file, and stores a compact `cache/dats/titledb/<DatName>.json`. titledb facts (checked 2026-11-10 against the file): the top level is a JSON **object** keyed by nsuId (decimal string), not an array; `id` is a 16-hex upper-case string or null (null in ~7,700 of ~37,500 entries; ~200 ids repeat under several nsuIds); `name` can be null; `developer`, `frontBoxArt` and `version` are always null; `releaseDate` is an int `yyyymmdd`, sometimes just a year (`2020`), or null; `category`, `languages` (duplicates possible), `iconUrl` and `screenshots` can be null; every image URL is on `https://img-eshop.cdn.nintendo.net`; the file has base games and DLC but **no update entries**. Parsing walks the object's values in document order with `System.Text.Json` and ignores unknown fields. The compact file is a JSON array (written and read only by `TitleDb.cs`) of `{ "titleId", "name", "publisher", "developer", "releaseYear", "genres", "languages", "boxArtUrl", "snapUrl" }` in that order, camelCase, nulls written: title id upper-cased; release year = `releaseDate / 10000` when `releaseDate ≥ 10000101`, the value itself when it is 1970–2100, else null; genres = `category` (null → []); languages = `languages` distinct, in order (null → []); box-art URL = `iconUrl`, else `frontBoxArt`; snap URL = the first `screenshots` entry. Entries without a valid `id` (`^[0-9A-Fa-f]{16}$`) or with a null or blank `name` are skipped; a repeated id keeps the first entry in document order. Image URLs are kept only when `https` and host `img-eshop.cdn.nintendo.net`. The manifest entry is `File` `titledb/Nintendo - Nintendo Switch.json`, `DatName` the handler's `DatName` (`Nintendo - Nintendo Switch`), `Version` the download date `yyyy.MM.dd` (UTC, from the injected `TimeProvider`), and the compact file's SHA1 (re-checked on load, like every DAT). The refresh fetches `13 × 5 + 1 = 66` files after this spec and stays all-or-nothing: a failed titledb download or parse fails the whole refresh and keeps the old set, as for any libretro file. A compact file with zero entries is valid (loads as an empty store).
- **T3 Load.** `DatCache.Load` builds a `DatStore` for a `TitleDb` system from the compact file: one `DatRom` per entry with `GameName` = `<base title form of the name> [<TitleId>]` (unique, used by `/api/dat/search`, suggestions and the review picker unchanged), `RomName` = the T5 rom `fileName` with `N` = 0 and `.nsp`, size 0 and no hashes (excluded from the SHA1 index), plus `ByTitleId(id)` returning the entry. The store's `DatName` is `titledb` and its `Version` the manifest version; `BaseTitles` and `SuggestionEngine` keep running `NoIntroName.Parse` on `GameName`, which keeps the whole `GameName` (with its ` [<TitleId>]`) when the name has no ` (`, so such an entry is its own suggestion group, and cuts at the first ` (` otherwise (695 titledb names, e.g. `Runbow (Retail Only)` → `Runbow`), so entries sharing that prefix form one group showing one best entry (accepted: `/api/dat/search` matches the full `GameName`, so the picker still finds each). `GET /api/admin/dats` today returns only manifest entries under `no-intro/`; it also returns the `titledb/` entry, as a row `{ datName: "Nintendo - Nintendo Switch", version: "<yyyy.MM.dd>", downloadedAt }` in the same `datName` order, and the refresh job's result `versions` includes it the same way. Missing, not listed in `dats.json`, SHA1 mismatch or unparsable → the system has no DATs (`DatsMissing`, existing rule); `DatCache.Load`'s per-system catch gains `JsonException` (today it catches only IO, `DatParseException`, `InvalidDataException` and `UnsafePathException`, so a corrupt compact file would abort the whole load).
- **T4 Matching.** For a `TitleDb` system, step 4 takes the title id from the header field `titleId`, else from the first match of `\[(0100[0-9A-Fa-f]{12})\]` in the file name (upper-cased). A ticket's name carries the content's own id (the update or DLC id, not the base's; switchbrew Ticket, blawar/nut), which is what the kind rule below needs. The entry kind comes from the id: base = id with the low 13 bits cleared; `id == base` → base game, `id == base | 0x800` → update, otherwise → DLC. A base game matches when `ByTitleId(id)` exists. An update or DLC matches when `ByTitleId(base)` exists (the DLC's own entry, when present, gives its name). No title id, or no entry → Review `NoDatMatch` with file-name suggestions from the titledb names. `identification` = method `TitleDb`, `datName` `titledb`, `datVersion` the manifest version, `datGameName` the base game's `GameName`. The kind rule matches titledb's data (every base id has its low 13 bits clear, every DLC id has bit 12 set and its base present) and nxdumptool's `title.h` (patch = application + 0x800, add-on content = (application & ~0xFFF) + 0x1000 + index); switchbrew doesn't state it. A DLC's data patch (`dlcId + 0x800`) or a delta (`+ 0xC00`) has none of the base/update patterns, so it counts as a DLC of the base (accepted: rare in dumps; its own name comes from titledb when listed, else `<base name> (DLC)`). Step 6 grouping uses the T5 base title (not `NoIntroName.Parse(GameName)`). An `AmbiguousGroup` review row of a `TitleDb` system stores, besides today's `datName`/`datVersion`/`datGameName`/`romName` (the T5 file name), the `titleId`; its `Attach` (flag `None`) rebuilds the release by T4–T7 from that title id and the item's original file name (method `TitleDb`), instead of today's `NoIntroName` parsing of `datGameName`, which would keep ` [<TitleId>]` in the title.
- **T5 Naming.** Base title (grouping key, game title) = the base game's titledb name with `™`, `®`, `©` removed, `: ` → ` - `, whitespace collapsed, and a leading `The `, `A ` or `An ` moved to the end of the first ` - ` segment (`The Legend of Zelda: Tears of the Kingdom` → `Legend of Zelda, The - Tears of the Kingdom`; `DisplayTitle` turns it back). Rom `fileName` = `Sanitize(<entry name, ™®© removed, ": " → " - ", whitespace collapsed, each run of two or more `.` → one `…` (U+2026)>) + " [<TitleId>][v<N>]" + <the file's extension, lower-case>` (the validator forbids `..` in a rom `fileName`, and 12 titledb names hold one, e.g. `Oh...Sir! The Insult Simulator` → `Oh…Sir! The Insult Simulator [<TitleId>][v0].nsp`; the game title keeps `...`), where `N` is the first `[v<digits>]` in the ingest file name, else `0`; an update with no entry uses the base name; a DLC with no entry of its own uses `<base name> (DLC)`. `revision` = `v<N>` when `N > 0`, else null. `flags` = `Update` or `DLC` for those kinds. `regions` = []; `languages` = titledb codes with the first letter upper-cased (`en` → `En`), distinct, in order.
- **T6 Primary release.** `Update` and `DLC` rank with `Hack`/`Translated` (never primary while a base release exists).
- **T7 Metadata.** A new game takes release year, developers (when not null; titledb has none today), publishers (one-item list, [] when null) and genres from the base entry (same "only empty fields" rule for an existing game). `LibraryEditor.MetadataFor` (move release to a new game) does the same for a `TitleDb` system, finding the entry by the ` [<TitleId>]` at the end of the release's `datGameName` (today it would look up an empty CRC and get nothing).
- **T8 Media.** For a `TitleDb` system `MediaService.FindAsync` (which gets `DatCache` injected) resolves each name it is given (`datGameName`s, in the given order) to its entry by the ` [<TitleId>]` at its end and `ByTitleId`, and fetches that entry's box-art and snap URLs (same client, circuit breaker, 5 MiB cap) instead of libretro thumbnails, accepting PNG or JPEG (`PngInfo` / `JpegInfo`); a missing or failed image → the placeholder / no snap, as today. An empty `Sources:ThumbnailBaseUrl` disables all media fetching, titledb included (existing offline switch). Fetched images are named by their format, for every system and on every path (new game, `GameImages.ApplyFetched` when adding a release, Retry media): the extension comes from the magic bytes (`png` / `jpg`); replacing the placeholder keeps its number (`boxart-01.png` → `boxart-01.jpg`), a new snap takes the lowest free `snap-NN.<ext>`. titledb images are stored with `source: titledb` and `sourceUrl` = the URL.
- **T9 Review.** For a Switch review item, the `Dat` action takes a `datGameName` from the titledb store (`<name> [<TitleId>]`) and stores the release as T4–T8 would for that title id, with `N` from the item's original file name: method `TitleDb` and no `Unverified` flag or ` (Unverified)` name part, unlike the libretro `Dat` action (titledb matching never checks hashes, so a picked title is as verified as an automatic match). `Attach` and `Manual` work as today, except the extension: today both end the file name with `RomExtensions[0]` (right for embedded systems, whose bytes may be normalised, e.g. `.v64` → `.z64`), which would store an `.xci` as `.nsp`; for an external system they use the original file's extension, lower-cased. Resolution never reads the file into memory: it re-hashes it streamed (SHA1 must still equal the item's) and places it by I4. For an external system the re-hash runs with `CancellationToken.None`, like edits (today `ReviewResolver` copies the file with the request's token): hashing and moving a multi-GB file can outlast a reverse proxy's read timeout (nginx's default is 60 s), and an aborted request must not make every retry fail; the client may then see a gateway error while the resolution still completes (deployment.md says so). For an external system the `afterMirror` callback (which sets the review row `Resolved`) uses `CancellationToken.None`; today it passes the request's token, so an aborted request after the move would leave the file in the library and the row `Pending`.

### Nintendo Switch handler
- **N1 Contract.** New project `RnRomManager.Systems.Switch`, `SwitchHandler`: `Id` `switch`, `DisplayName` `Nintendo Switch`, `ShortName` `Switch`, `Family` `switch`, `RomExtensions` `[".nsp", ".xci", ".nsz", ".xcz"]`, `MinRomSizeBytes` 1,024, `MaxRomSizeBytes` 68,719,476,736 (64 GiB), `DatName` `Nintendo - Nintendo Switch`, `EmbedRomsInZip` false, `DatSource` `TitleDb`. Registered after `TurboGrafx16Handler`.
- **N2 Header.** `ReadHeader` (first 1 MiB): `PFS0` at 0 → `container` `PFS0`, `fileCount` (uint32 LE at 4), and `titleId` = the first 16 hex chars (upper-case) of a string-table name matching `^[0-9a-fA-F]{32}\.tik$`, else null. Otherwise `HEAD` at 0x100 (a usual dump), else at 0x1100 (a full card image with its 0x1000-byte key area; switchbrew XCI) → `container` `XCI`, `titleId` null (the title id isn't in the plain header). PFS0 entries are 0x18 bytes from 0x10 (u64 offset, u64 size, u32 string offset, u32 reserved), the string table follows them (size: u32 at 8); `.nsz`/`.xcz` keep the PFS0/XCI outer container (nsz formats doc). Otherwise not plausible (`IsPlausible` false → `InvalidHeader` when unmatched, existing rule). A truncated or out-of-range PFS0 table → `titleId` null, still plausible. `Title` null; `ClassifiedSystemId` `switch`.
- **N3 Colour and box art.** `--bs-switch: #2d2d2d` with white text (≈ 13:1, AA) in `app.css` next to `tg16`; `systemColours.switch`; `switch.svg` (drawn for this project, MIT) + 512×512 `switch.png` placeholder, as TurboGrafx-16 did.
- **N4 Ingestion folder.** `ingest/switch/` is created at startup like every system. Ingestion refuses with `DatsMissing` until **Admin → DATs → Refresh DATs** (documented upgrade step).

## Risks
- **Partial moves.** A crash between file rename, ZIP write and DB commit can leave a file under the wrong name. W6 keeps the order fixed so integrity always reports it (`EntryMissing` + `OrphanFile`) and nothing is deleted on its own; the Admin fixes it by renaming the file.
- **Long ingest items.** Hashing a 30 GB file takes minutes and holds the job lock; Cancel stops after the current item, as documented, so a cancel can wait for one long hash. Disk space: the move needs no extra space on the same disk, the file's size on another. Review resolution and edits run inside the HTTP request, so a cross-volume move or a long re-hash can outlast a proxy timeout: they run without the request's token (T9, W6) and deployment.md tells Admins to raise the proxy's read timeout.
- **titledb is a third-party JSON** (~90 MB): parsed with size caps, unknown fields ignored, URLs allowed only from one https host, image bytes still go through the existing caps and magic-byte checks.
- **Title-ID-only matching** can put a mislabelled file (wrong `[TitleId]` in its name) under the wrong game; the release keeps `originalFileName`, and move/delete fix it.
- **A 14th system breaks existing tests** (`DatsMissing`, counts, orders): fixed in the registration step.
