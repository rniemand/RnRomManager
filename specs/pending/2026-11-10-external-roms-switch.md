# External ROM storage and Nintendo Switch

## Summary
Disc-era and modern systems (Switch, GameCube, Wii, Xbox 360…) have multi-GB images that can't sensibly live inside a game's ZIP or be read into memory. Each system now declares whether its ROMs are **embedded** in the game ZIP (every existing system: yes) or stored **external**: next to the ZIP, named so they group with it, and pointed at from `info.json`. The ZIP keeps everything else (info.json, images, notes, ratings). Nintendo Switch (`switch`) is the first external system, identified by title ID through [blawar/titledb](https://github.com/blawar/titledb) because libretro has no Switch DAT or thumbnails.

## Out of scope
- GameCube, Wii, Xbox 360 and other large systems (later specs; this one builds what they need).
- Moving an existing system between embedded and external (the flag is fixed per system; no conversion tool).
- Building a ZIP with the ROMs on the fly for "Download ZIP" (decision: ZIP as stored + per-release downloads).
- Decrypting Switch content: no keys; XCI title IDs come only from the file name.
- titledb regions other than `US.en.json`; titledb descriptions (game `description` stays Admin-edited only).
- Ingesting external-system ROMs from archives beyond today's archive limits (256 MiB total): a Switch file inside a `.zip`/`.7z` is rejected by the existing limits, as today.

## Behaviour

### Storage flag
- **S1 Lookup.** `ISystemHandler` gains a required `bool EmbedRomsInZip { get; }` (no default implementation, so every handler states it). All 13 existing handlers return `true`; `switch` returns `false`. `GET /api/systems` adds `embedRoms` (bool) to each entry. `docs/adding-a-system.md` lists every system with its value.
- **S2 Embedded systems are unchanged.** Every rule below applies only when `EmbedRomsInZip` is `false`; embedded ZIPs, their writes, integrity checks and downloads behave exactly as today (existing tests prove it).

### External file naming and pointer
- **E1 Name.** An external ROM is the file `<ZipBase>.<rom fileName>` in the ZIP's own folder, where `<ZipBase>` is the ZIP name without `.zip`. Example: `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.zip` and `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.The Legend of Zelda - Tears of the Kingdom [0100F2C0115B6000][v0].nsp`. The shared `<ZipBase>.` prefix sorts them together in any file explorer.
- **E2 Length and clashes.** When the name is over 250 UTF-8 bytes, the rom part's stem (before its extension) is cut, at a char boundary, until it fits; the extension is kept. A different file already at that name (case-insensitive) → ` (2)`, ` (3)`… before the extension (`FileNameRules.FirstFreeIn`). Implemented once in `Core/Storage/ExternalRomName.cs`.
- **E3 Pointer.** `info.json` **schema version 4**: each Rom gains `externalFileName` (string?, the file name only, resolved in the ZIP's folder). Validator (which now receives an id → `EmbedRomsInZip` lookup instead of the bare id set): for a system with `EmbedRomsInZip = false` it is required; for an embedded system it must be null; when set it is free of `/`, `\` and `..`, unique case-insensitively within the game, and at most 255 chars. The v3→v4 upgrader adds `externalFileName: null`. Apps before this one treat a v4 file as `InfoJsonNewerSchema` (read-only, existing rule). `identification.method` gains the value `TitleDb` (T4) and image `source` gains `titledb` (T8). A stray `roms/<fileName>` entry for an external ROM is not a validator rule: the writer never writes one (W1) and integrity reports it as `EntryUnlisted` (G1).
- **E4 Database.** Migration `0018_external_roms.sql`: `ALTER TABLE roms ADD external_file_name VARCHAR(255) NULL`. `RomRow`, the mirror and `DbSync` carry it (`NULL` for every existing row; no backfill needed). `GET /api/games/{id}` release rows gain `externalFileName`.

### Ingest of an external ROM
- **I1 Validation.** Extension and size checks as today (`MaxRomSizeBytes` is a `long`).
- **I2 Streaming hash.** The file is never read whole into memory: one streamed read computes CRC32, MD5 and SHA1 together (`NormalizeForHashing` is not called for external systems). `ReadHeader` receives the first `min(size, 1 MiB)` bytes. After hashing, the file's length and last-write time are compared with the values seen before hashing; if either changed (still being copied in), the item is `Skipped` with reason `TooRecent` (file left in place, picked up by a later run; features.md broadens `TooRecent` to "modified < 10 s ago or changed while being hashed"). Cancellation keeps the documented rule: the current item finishes, including its hash.
- **I3 Identification, dedupe, review, grouping** follow the existing steps 3–6 (SHA1 dedupe, review lifecycle, identification per the system's DAT source, grouping by system + base title).
- **I4 Placement (move with rollback).** After identification and before the ZIP write: the source is moved with `File.Move` to `<final>.tmp` in the target ZIP's folder (a rename on the same disk, else .NET's copy + delete), then renamed to `<final>` (E1/E2). Then the ZIP is written (its verify checks the external file, W1), the DB mirrored, and the audit row recorded. If the ZIP write fails (`VerifyFailed`/`IoError`), the file is moved back to its original ingest path (a ` (2)` name if that path is taken) and the item is `Error` as today. If the DB mirror or `afterMirror` fails, the ZIP already names the file, so it stays in the library and the item is `DbWriteFailed` (existing meaning: the next ingest or integrity run repairs the DB from the ZIP). If the move back also fails, the item is `Error IoError` with details naming the library path the file was left at (integrity reports it as `OrphanFile`). A crash mid-move leaves `<final>.tmp`, which integrity reports as `OrphanFile` (never deleted automatically).
- **I5 Source deletion.** There is no source left to delete after a successful move; an archive entry's extracted copy is moved the same way.
- **I6 Self-repair.** A byte-identical file whose external file has an open `EntryMissing`, `EntrySizeMismatch` or `HashMismatch` issue is moved into place over `<externalFileName>` (same tmp + rename) and the ZIP rewritten (`Repaired`, existing rule D30). The open issues are looked up with entry name = the `externalFileName` (G1's key), not `roms/<fileName>`.
- **I7 Audit.** `Ingested` / `ZipRepaired` rows as today; the details name the release (`release <fileName>`, taken from the stored rom, not from the written ZIP entries, since an external ROM has none), the target path is the ZIP's.

### Library writes
- **W1 Writer.** `LibraryZipWriter` writes no `roms/` entry for a ROM with `externalFileName` and doesn't copy one; its verify checks that `<zip folder>/<externalFileName>` exists with length `metadata.sizeBytes` (no rehash; the bytes were hashed at ingest). Notes for external ROMs are kept as today (`notes/<fileName>.md` inside the ZIP).
- **W2 Title edit.** When the ZIP path changes, each external file is renamed (`File.Move`) to its E1 name for the new ZIP **before** the new ZIP is written; `externalFileName` is updated. If the ZIP write fails, the renames are undone. If the DB commit fails afterwards, the files keep their new names (the new ZIP lists them) and the result is `DbWriteFailed` as today. The old ZIP is deleted last, as today.
- **W3 Move release.** The release's external file is renamed to its E1 name next to the target ZIP (new or existing game) before the target ZIP is written; rollback on failure as W2. When it was the source's last release, the source ZIP is deleted (existing rule).
- **W4 Merge.** Every external file of the source is renamed to its E1 name next to the target ZIP (after any ` (2)` file-name clash rename of the release) before the target ZIP is written; rollback as W2; the source ZIP is deleted (existing rule).
- **W5 Delete.** As for embedded ROMs, removed ROMs are never hard-deleted: deleting a release or a game moves each external file (`File.Move`, a rename when ingest and roms share a disk, else copy + delete) to `ingest/<system>/_removed/<fileName>` (the rom `fileName`, without the ZIP prefix; ` (2)`… on a clash), before the ZIP write / ZIP delete, and moves it back to its library name if that write fails (`VerifyFailed`/`IoError`); on `DbWriteFailed` it stays in `_removed/` (existing rules of `RemoveRomsAsync`). A listed external file that is already missing has nothing to move and is skipped (existing rule for absent entries).
- **W6 Order and crash safety.** Every write keeps "file moves first, then ZIP, then DB, then old-ZIP deletion"; only a failed ZIP write rolls the moves back. A crash between steps leaves at worst `EntryMissing` (ZIP names a file that has another name) plus an `OrphanFile` for the same bytes; both are reported, nothing is deleted automatically.

### Integrity, downloads and reports
- **G1 Quick.** For every game of an external system, each external file is checked by `stat`, in Quick and Deep, whether or not its ZIP is opened, using the DB rows after the DB repair (so also when the ZIP is unreadable): missing → `EntryMissing`, other length → `EntrySizeMismatch` (entry name = the external file name). When a ZIP is opened, `CheckZipAsync` skips ROMs with `externalFileName` in its `roms/` checks (so a stray `roms/<fileName>` for one is `EntryUnlisted`); everything else in the ZIP check is unchanged.
- **G2 Deep.** Also streams each external file through SHA1: different → `HashMismatch`.
- **G2a Resolution (D48).** Because every run stats every external file, any completed run resolves an open external `EntryMissing`/`EntrySizeMismatch` it didn't see again; only a Deep run resolves an external `HashMismatch`.
- **G3 Orphans.** In a system folder, a non-ZIP file listed (DB rows, after the DB repair) as an external file by a game in that folder is not an orphan; every other non-ZIP (including `*.tmp`) is `OrphanFile` as today.
- **G4 ROM download.** `GET /api/games/{id}/roms/{romId}/download` for an external ROM streams the file from disk with HTTP range support (`enableRangeProcessing`), download name = the rom `fileName`. A missing file → `404` ProblemDetails `code` `EntryMissing`.
- **G5 Game download.** `GET /api/games/{id}/download` returns the ZIP as stored (no ROMs). The Game page's ZIP download button gets the tooltip "ROM files are downloaded per release" for external systems.
- **G6 Library Size report.** A game's size is `zip_size_bytes` + the sum of its external ROMs' `size_bytes` (system totals and the per-game drill-down, which also sorts by that combined size).
- **G7 Game page.** Each external release row shows a small `External` badge whose tooltip is its `externalFileName`. The Zip Contents tab is unchanged (it lists real ZIP entries).

### titledb as a DAT source
- **T1 Source per system.** `ISystemHandler` gains `DatSource DatSource => DatSource.Libretro;` (enum in `Core/Dats`: `Libretro`, `TitleDb`). Switch returns `TitleDb`.
- **T2 Refresh.** For a `TitleDb` system the DAT refresh downloads one file from `Sources:TitleDbUrl` (new config key, default `https://raw.githubusercontent.com/blawar/titledb/master/US.en.json`; validated as an absolute https URL; required) with a 256 MiB cap (libretro DATs keep 64 MiB), parses it, and stores a compact `cache/dats/titledb/<DatName>.json` holding only: title id (upper-case 16 hex), name, publisher, developer, release year (from `releaseDate` `yyyymmdd`), genres (`category`), languages, box-art URL (`frontBoxArt`, else `iconUrl`) and snap URL (first `screenshots` entry). Entries without a valid `id` are skipped; a repeated id keeps the first entry. Image URLs are kept only when `https` and host `img-eshop.cdn.nintendo.net`. The manifest entry's version is the download date `yyyy.MM.dd` (UTC). The refresh fetches `13 × 5 + 1 = 66` files after this spec and stays all-or-nothing: a failed titledb download or parse fails the whole refresh and keeps the old set, as for any libretro file. A compact file with zero entries is valid (loads as an empty store).
- **T3 Load.** `DatCache.Load` builds a `DatStore` for a `TitleDb` system from the compact file: one `DatRom` per entry with `GameName` = `<base title form of the name> [<TitleId>]` (unique, used by `/api/dat/search`, suggestions and the review picker unchanged), `RomName` = `<name> [<TitleId>][v0].nsp`, size 0 and no hashes (excluded from the SHA1 index), plus `ByTitleId(id)` returning the entry. `GET /api/admin/dats` lists it as `titledb/Nintendo - Nintendo Switch.json`. Missing or corrupt → the system has no DATs (`DatsMissing`, existing rule).
- **T4 Matching.** For a `TitleDb` system, step 4 takes the title id from the header field `titleId`, else from the first `[0100XXXXXXXXXXXX]` (16 hex, case-insensitive) in the file name. The entry kind comes from the id: base = id with the low 13 bits cleared; `id == base` → base game, `id == base | 0x800` → update, otherwise → DLC. A base game matches when `ByTitleId(id)` exists. An update or DLC matches when `ByTitleId(base)` exists (the DLC's own entry, when present, gives its name). No title id, or no entry → Review `NoDatMatch` with file-name suggestions from the titledb names. `identification` = method `TitleDb`, `datName` `titledb`, `datVersion` the manifest version, `datGameName` the base game's `GameName`.
- **T5 Naming.** Base title (grouping key, game title) = the base game's titledb name with `™`, `®`, `©` removed, `: ` → ` - `, whitespace collapsed, and a leading `The `, `A ` or `An ` moved to the end of the first ` - ` segment (`The Legend of Zelda: Tears of the Kingdom` → `Legend of Zelda, The - Tears of the Kingdom`; `DisplayTitle` turns it back). Rom `fileName` = `Sanitize(<entry name, ™®© removed, ": " → " - ">) + " [<TitleId>][v<N>]" + <the file's extension, lower-case>`, where `N` is the first `[v<digits>]` in the ingest file name, else `0`; an update with no entry uses the base name; a DLC with no entry of its own uses `<base name> (DLC)`. `revision` = `v<N>` when `N > 0`, else null. `flags` = `Update` or `DLC` for those kinds. `regions` = []; `languages` = titledb codes with the first letter upper-cased (`en` → `En`), distinct, in order.
- **T6 Primary release.** `Update` and `DLC` rank with `Hack`/`Translated` (never primary while a base release exists).
- **T7 Metadata.** A new game takes release year, developers (when not null), publishers and genres from the base entry (same "only empty fields" rule for an existing game).
- **T8 Media.** For a `TitleDb` system `MediaService.FindAsync` fetches the entry's box-art and snap URLs (same client, circuit breaker, 5 MiB cap) instead of libretro thumbnails, accepting PNG or JPEG (`PngInfo` / `JpegInfo`); a missing or failed image → the placeholder / no snap, as today. An empty `Sources:ThumbnailBaseUrl` disables all media fetching, titledb included (existing offline switch). Fetched images are named by their format, for every system and on every path (new game, `GameImages.ApplyFetched` when adding a release, Retry media): the extension comes from the magic bytes (`png` / `jpg`); replacing the placeholder keeps its number (`boxart-01.png` → `boxart-01.jpg`), a new snap takes the lowest free `snap-NN.<ext>`. titledb images are stored with `source: titledb` and `sourceUrl` = the URL.
- **T9 Review.** For a Switch review item, the `Dat` action takes a `datGameName` from the titledb store (`<name> [<TitleId>]`) and stores the release as T4–T8 would for that title id, with `N` from the item's original file name. `Attach` and `Manual` work as today (Manual's file name: existing rule, extension from the file). Resolution never reads the file into memory: it re-hashes it streamed (SHA1 must still equal the item's) and places it by I4.

### Nintendo Switch handler
- **N1 Contract.** New project `RnRomManager.Systems.Switch`, `SwitchHandler`: `Id` `switch`, `DisplayName` `Nintendo Switch`, `ShortName` `Switch`, `Family` `switch`, `RomExtensions` `[".nsp", ".xci", ".nsz", ".xcz"]`, `MinRomSizeBytes` 1,024, `MaxRomSizeBytes` 68,719,476,736 (64 GiB), `DatName` `Nintendo - Nintendo Switch`, `EmbedRomsInZip` false, `DatSource` `TitleDb`. Registered after `TurboGrafx16Handler`.
- **N2 Header.** `ReadHeader` (first 1 MiB): `PFS0` at 0 → `container` `PFS0`, `fileCount` (uint32 LE at 4), and `titleId` = the first 16 hex chars (upper-case) of a string-table name matching `^[0-9a-fA-F]{32}\.tik$`, else null. Otherwise `HEAD` at 0x100 → `container` `XCI`, `titleId` null. Otherwise not plausible (`IsPlausible` false → `InvalidHeader` when unmatched, existing rule). A truncated or out-of-range PFS0 table → `titleId` null, still plausible. `Title` null; `ClassifiedSystemId` `switch`.
- **N3 Colour and box art.** `--bs-switch: #2d2d2d` with white text (≈ 13:1, AA) in `app.css` next to `tg16`; `systemColours.switch`; `switch.svg` (drawn for this project, MIT) + 512×512 `switch.png` placeholder, as TurboGrafx-16 did.
- **N4 Ingestion folder.** `ingest/switch/` is created at startup like every system. Ingestion refuses with `DatsMissing` until **Admin → DATs → Refresh DATs** (documented upgrade step).

## Risks
- **Partial moves.** A crash between file rename, ZIP write and DB commit can leave a file under the wrong name. W6 keeps the order fixed so integrity always reports it (`EntryMissing` + `OrphanFile`) and nothing is deleted on its own; the Admin fixes it by renaming the file.
- **Long ingest items.** Hashing a 30 GB file takes minutes and holds the job lock; Cancel stops after the current item, as documented, so a cancel can wait for one long hash. Disk space: the move needs no extra space on the same disk, the file's size on another.
- **titledb is a third-party JSON** (~90 MB): parsed with size caps, unknown fields ignored, URLs allowed only from one https host, image bytes still go through the existing caps and magic-byte checks.
- **Title-ID-only matching** can put a mislabelled file (wrong `[TitleId]` in its name) under the wrong game; the release keeps `originalFileName`, and move/delete fix it.
- **A 14th system breaks existing tests** (`DatsMissing`, counts, orders): fixed in the registration step.
