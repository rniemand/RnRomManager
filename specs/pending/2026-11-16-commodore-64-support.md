# Commodore 64 support

## Summary
A new system, Commodore 64 (`c64`): its tapes, disk images, cartridges and programs are stored in the game ZIP, identified against the libretro No-Intro `Commodore - 64` DAT (no metadat files exist for it) and played in the browser through EmulatorJS's VICE core (`vice_x64sc`, vendored, no BIOS). Because a C64 file's extension names its format, a new handler flag makes Review keep the source extension instead of renaming it.

## Out of scope
- Formats the DAT doesn't list (`.t64`, `.d71`, `.d81`, `.p00`, `.x64`, …): refused as `UnsupportedType` like any unlisted extension.
- Disk/tape side swapping during play, `.m3u` playlists, or grouping a game's sides into one playable set: each side is its own release and plays alone.
- VIC-20, Plus/4, C128 or Amiga (the new project only leaves room for them).
- Keyboard overlays, joystick-port selection or any VICE core option beyond EmulatorJS defaults.
- e2e Play checks (no real ROMs can be committed).
- Year/developer/publisher/genre metadata: libretro has no metadat for C64, so C64 games have none.
- New README screenshots.

## Behaviour
- **B1** `C64Handler` in a new `RnRomManager.Systems.Commodore` project:

  | Member | Value |
  |---|---|
  | `Id` / `Family` | `c64` |
  | `DisplayName` / `ShortName` | `Commodore 64` / `C64` |
  | `RomExtensions` | `.crt`, `.tap`, `.nib`, `.d64`, `.g64`, `.prg`, `.bin` (in that order; `.crt` is `[0]`) |
  | `MinRomSizeBytes` / `MaxRomSizeBytes` | 1 KiB / 8 MiB |
  | `DatName` | `Commodore - 64` |
  | `EmbedRomsInZip` | true |
  | `DatSource` / `DatFolder` | Libretro (default) / `no-intro` (default) |
  | `MetadatKinds` | `[]` (all four metadat URLs 404 for this DAT) |
  | `FileSets` / `LegacyEmbeddedRoms` | false (defaults) |
  | `KeepsSourceExtension` | true (B3) |
  | `BrowserCore` | null until step 4, then `vice_x64sc` |
  | `ReadHeader` | B2 |
  | `NormalizeForHashing` | default (unchanged bytes) |

  Facts from the libretro DAT (version 2026.11.14): 3,512 `game` blocks, one ROM each: `.tap` 1,681 (85,670 B – 4.19 MB), `.nib` 1,547 (320–328 KiB), `.crt` 237 (8,272 B – 513 KiB), `.bin` 25 (8–16 KiB), `.prg` 11 (2,010 B – 49 KiB), `.d64` 10 (170.75 KiB), `.g64` 1 (326 KiB). The minimum leaves room below the DAT's smallest (`.prg` 2,010 B) for homebrew; the maximum leaves headroom above 4.19 MB. 657 ROM names carry `(Side N)`/`(Disk N)` while their `game` blocks share one game name (`221B Baker Street (USA, Europe)` has a Side 1 and a Side 2 `.nib` block); each side is stored under its own ROM name as today and grouped by the existing title rules (this spec adds no grouping logic and no test for it). libretro-thumbnails has a `Commodore_-_64` repo.
- **B2** `C64Header.Read` (internal, through `C64Handler.ReadHeader`) recognises four magic strings at offset 0 and returns a plausible header classified `c64`; anything else (`.prg`, `.d64`, `.bin`, a short or damaged file) returns null, so an unmatched file goes to Review, never `InvalidHeader`. Fields, added in this order:
  - **crt**: ≥ 64 bytes, ASCII `C64 CARTRIDGE   ` (16 bytes incl. 3 spaces). `format` `"crt"`, `version` `"<byte 0x14>.<byte 0x15>"` (string, e.g. `"1.0"`), `hardwareType` u16 BE at 0x16, `exrom` byte 0x18, `game` byte 0x19, `title` 32 bytes at 0x20, Latin-1 up to the first NUL, trimmed, null if empty. `RomHeader.Title` = `title`.
  - **tap**: ≥ 20 bytes, ASCII `C64-TAPE-RAW`. `format` `"tap"`, `version` byte 0x0C (number).
  - **g64**: ≥ 12 bytes, ASCII `GCR-1541`. `format` `"g64"`, `version` byte 0x08, `tracks` byte 0x09 (numbers).
  - **nib**: ≥ 14 bytes, ASCII `MNIB-1541-RAW`. `format` `"nib"`, `version` byte 0x0D (number).

  `RomHeader.Title` is null for tap/g64/nib. Numbers are stored unsigned as read.
- **B3** New `ISystemHandler` member `bool KeepsSourceExtension => false;` ("true: the extension names the file's format, so Review keeps the source file's extension"). In `ReviewResolver`, an embedded system with the flag uses the source file's lower-cased extension (`originalExtension`) wherever it would otherwise use `RomExtensions[0]` (the flag-only and manual-entry resolutions) or the DAT ROM's extension (the Dat resolution); the stem is unchanged (from the DAT ROM name for Dat, from the source or entered title otherwise). So a C64 `.tap` resolved manually is stored as `<stem>.tap`, and a `.tap` resolved against a game whose only DAT ROM is `.nib` is stored as `<that ROM's stem> (Unverified).tap`. The Attach resolution with flag `None` (an `AmbiguousGroup` item, named from its queued DAT identification) already carries the DAT ROM's own extension and is unchanged. Every existing handler keeps false, so their behaviour is unchanged (Atari 5200 `.bin` still becomes `.a52`). Matched-by-hash ingest is unaffected (it takes the DAT ROM name, whose extension is the file's own). `IngestPipeline`'s rename of a file whose extension doesn't fit its classified system is unaffected (every C64 extension fits `c64`).
- **B4** Registration: `services.AddSystemHandler<C64Handler>()` appended after `ThreeDoHandler` in `AppHost.AddSystemHandlers`, so ingest folder and id lists end in `…, "3do", "c64"`. `/api/systems` is sorted by `DisplayName`: `Commodore 64` lands between `ColecoVision` and `Game Boy`. `roms/c64/` and `ingest/c64/` are created at startup like every system's.
- **B5** Badge colour (`systemColours.ts` + `app.css`, same in both themes): `c64` `#6c5eb5` (the C64 palette's light blue) with white text (5.4:1, AA). `systemColours.ts` adds `'c64'` last in the union and the map; `app.css` gets one block after the 3DO block, commented with the contrast, in the 3DO block's form. `icons.ts` untouched (controller fallback).
- **B6** Systems tab catalogue (`systemEmulators.json`): `c64` gets VICE (`https://vice-emu.sourceforge.io/`, os `windows`, `macos`, `linux`) and RetroArch (`https://www.retroarch.com/?page=platforms`, the five OSes, note `RetroArch core: VICE x64sc`), in the key order the file uses.
- **B7** Browser play: `@emulatorjs/core-vice_x64sc` `4.2.3` (exact) is a dependency; `vendor-emulatorjs.mjs` appends `vice_x64sc` to `cores` (copies `-wasm`/`-legacy-wasm` `.data` and `reports/vice_x64sc.json`, never the `-thread-` variants); `params.js` appends `vice_x64sc` to `cores`. No `biosFor`, `hidesCoreChooser`, `controlSchemeFor`, `getCore()` pin or `contentFileName` change is needed: EmulatorJS 4.2.3's `c64` group lists only `vice_x64sc`, `requiresThreads` doesn't list it, VICE carries its own system ROMs, and the pinned loader already skips cue generation for `vice_x64sc`. Every C64 release plays (all are inside the ZIP; `canPlay` needs no change); the ROM is passed as a `File` named after the release, so VICE autostarts it by its extension. A multi-side game plays one side per launch: the user picks that side's release Play button on the game page's Releases tab, as for any release today.
- **B8** Licences: `licenses.json` gains `{ "name": "@emulatorjs/core-vice_x64sc", "license": "GPL-2.0", "url": "https://github.com/EmulatorJS/vice-libretro" }` in name order (after `core-stella2014`, before `core-virtualjaguar`). The npm package ships no licence text, so `emulator-licenses/` gains `vice_x64sc-LICENSE.txt` (the GPL-2.0 `COPYING` from `EmulatorJS/vice-libretro` at the revision the binary was built from, byte for byte) and `vice_x64sc-NOTICE.txt` (in `stella2014-NOTICE.txt`'s form: files, npm package and version, the core source revision and build entry, and a pointer to `COMMON-BUILD.txt`), both listed in `vendorEmulatorjs.test.ts`'s expected notices.
- **B9** README: the supported-systems table gains `| Commodore 64 | \`c64\` | In ZIP | \`.crt\`, \`.tap\`, \`.nib\`, \`.d64\`, \`.g64\`, \`.prg\`, \`.bin\` | No-Intro | — |` between ColecoVision and Game Boy (step 3a), with `vice_x64sc` in the Play column from step 4. Step 3a also adds `Commodore 64` at the end of the "Upgrading from a version without …" list (`…, Sega CD, 3DO or Commodore 64?`). Step 4 adds `Commodore 64` to the Play feature bullet's system list (after `3DO`: `…, Sega CD, 3DO and Commodore 64 releases in the browser`) and VICE to the Attribution's core list (`[VICE](https://github.com/EmulatorJS/vice-libretro) (GPL-2.0)`), in the bullet's existing form.

## Risks
- **Play untested on real dumps**: no e2e Play. VICE's autostart of `.nib`/`.g64` and raw `.bin` carts in the EmulatorJS build isn't verified by tests; Play is still offered and the PR says so. Many C64 games need the keyboard (e.g. `RUN`, F-keys); EmulatorJS forwards keys inside the iframe, but mapping is upstream's.
- **Multi-side games**: playable one side at a time; a game that asks for side 2 can't continue in the browser (Out of scope).
- **No metadata**: C64 games have no year, developer, publisher or genre, so Publishers/Genres tabs don't list them.
- **Fixtures**: every fixture loading all systems' DATs must list `C64Dat`, or ingestion tests fail `DatsMissing` (step 3a does them all in one commit).
- **Bundle size**: the VICE core adds ~3 MB (two non-thread payloads of the 6.2 MB package) to the image.
- **New contract member**: `KeepsSourceExtension` is defaulted, so no existing handler changes; `ReviewResolverTests` covers both values.
