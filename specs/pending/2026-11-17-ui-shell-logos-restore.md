# UI shell, group logos, backup restore and DAT schedule

## Summary
A round of polish and small features for every user: a slimmer navbar and a new sticky footer (shortcuts, version, About), page titles only on mobile, logos for genres and systems as well as publishers (with URL upload as the default and a text banner when there's no image), an update count and clickable rows on the Library Size report, a tidier Integrity status and Auditing page. For Admins: restore a backup from the Backups table, and a daily DAT refresh they can configure. Library system folders are created only when a ROM is written to them.

## Out of scope
- Logos in the small `SystemBadge` chips (tables, filters, game pages): they keep their Bootstrap icon.
- Download or delete of backup files, and restoring files (backups hold the database only, as today).
- A general cron/scheduler framework: the DAT schedule is one more `BackgroundService` like `BackupScheduler`.
- Changing which ingest folders exist: `ingest/<system>/{_duplicates,_failed,_removed}` are still created at startup.
- SVG, WebP or GIF logos: logos stay PNG or JPEG, ≤ 512 KiB, ≤ 2048 px per side.

### Logos for publishers, genres and systems
- **B13** Publishers, genres and systems each can have one shared logo, stored in the database (`discovery_logos`, migration 0026). Publishers and genres are keyed by their group key (B2 of collections discovery, 64 hex). Systems are keyed by the SHA-256 of the system id in lowercase ASCII, so the same `key_digest` column holds all three. Existing publisher logos keep working unchanged.
- **B14** API, one route per kind with `kind` ∈ `publishers|genres|systems`:
  - `GET /api/discovery/{kind}/logo?key=` (any signed-in user): the bytes, `private, no-cache`, `nosniff`; 404 when none. For `systems`, `key` is the system id.
  - `PUT /api/discovery/{kind}/logo?key=` (Admin, multipart `file`): as today's publisher upload.
  - `PUT /api/discovery/{kind}/logo/from-url?key=` (Admin, JSON `{ "url": "…" }`): the server downloads the image through `ImageUrlDownloader` (http/https only, ≤ 1024 chars, no userinfo, public addresses only, 15 s) and stores it if it passes the same checks as an upload (PNG/JPEG by content, ≤ 512 KiB, ≤ 2048 px). Errors: `400 ValidationFailed` with `url` (bad URL, download failed, not an image, too large, too big in pixels: one message each), `404` for an unknown group or system.
  - `DELETE /api/discovery/{kind}/logo?key=` (Admin): removes it; 204, or 404 when there is none.
  - An unknown `kind` is 404. A malformed `key` is `400 ValidationFailed` (`key`): for publishers and genres anything but 64 lowercase hex; for systems anything but 1–32 characters of `[a-z0-9]` (the handler id set). A well-formed key that isn't a current group (publishers, genres) or a registered system is 404 on both PUTs; GET and DELETE work for any stored key (404 when none is stored), so a logo outlives its group leaving the index for a while (as today).
  - `from-url` order: key check, then the group/system 404, then the URL check, then the download, then the same logo validator as the file upload (pulled out of `ReadLogoAsync`: PNG/JPEG, ≤ 512 KiB, ≤ 2048 px, the upload's messages). Only `ParseImageUrl` and `ImageUrlDownloader` are shared with the game-image code; `DownloadedImageError` is not (its 8 MiB rules differ).
  - Every change is audited: `PublisherLogoReplaced`/`PublisherLogoRemoved` as today, and new `GenreLogoReplaced`, `GenreLogoRemoved`, `SystemLogoReplaced`, `SystemLogoRemoved`. Details keep today's format for every kind: `<name> (key <key>)`, or `key <key>` when the group is no longer in the library; for systems `<display name> (system <id>)`, or `system <id>` for an unregistered id. A URL upload appends ` from <url>` (cut to the audit's 1024 chars).
  - The old `/api/discovery/publishers/logo` URLs are the `publishers` case of the same route, so existing `logoUrl` values keep working.
- **B15** `GET /api/discovery/genres` items carry `logoUrl` like publishers do (null when none, versioned `&v=<updated_at ticks>`). `GET /api/systems` items gain `logoUrl` (same rule).
- **B16** The SPA's logo for a group is the first that loads of: the shared logo, the bundled starter art (publishers: today's `static/publishers/`; genres: new `static/genres/`, B17), then a **text banner**: the name centred in a bordered, rounded box of the logo's size (`GroupLogo` component, `aria-hidden`, since the name also follows as text). So every publisher, genre and system shows a logo. A failed image falls through to the next source (as publishers do today).
- **B17** Starter genre art: about 15 SVG banners in `static/genres/` (a Bootstrap Icons glyph, MIT, plus the genre name), listed in `starterGenres` in `discovery.ts` by alias and key (SHA-256 of the lowercase alias, recomputed in `discovery.test.ts`) and in `static/genres/manifest.json`. Aliases are the most common libretro `genre` values (exact list fixed in step 7 from the seeded and real DAT genre names, at least: Action, Adventure, Platform, Shooter, Shoot'em Up, Fighting, Beat'em Up, Sports, Racing, Driving, Puzzle, Role-Playing (RPG), Strategy, Simulation, Board Game). The Bootstrap Icons licence is listed in `licenses.json`.
- **B18** Systems tab: the system list and the selected system's heading show the system's logo (shared logo, else the text banner; systems have no starter art). `SystemBadge` elsewhere is unchanged.
- **B19** Admins see a **Change logo** (pencil) button beside each publisher, genre and system row (genres and systems are new). It opens the logo modal (one component for the three kinds): current logo preview and its source (shared / starter / text banner), a **URL / File** choice (radio button group, **URL selected each time the modal opens**), the URL field or the file field, **Save logo**, and **Remove shared logo** when there is one. Client checks mirror the server (URL: http/https, ≤ 1024 chars; file: PNG/JPEG, ≤ 512 KiB); server errors show under the field. On success: toast, close, the list refetches.

### Reports: Library Size
- **B21** The table gains an **Updates** column (right-aligned, `formatCount`) after Games/Releases: on the library view the number of update releases per system, on a system view per game. An update release is a `roms` row whose `flags` contain `Update`, using the existing `JSON_CONTAINS(r.flags, '"Update"')` rule from `LibraryRepositories`. The API adds `updateCount` to each system and game row, and a top-level `updateCount` total to both `/library-size` and `/library-size/{system}` (beside their `bytes` totals).
- **B22** Each table row is clickable: clicking anywhere in a row goes where its first-cell link goes; rows get `cursor: pointer` and a stronger hover highlight in both themes. The link in the first cell stays the keyboard and screen-reader route (the row itself isn't focusable; Ctrl/⌘/middle click on the link still opens a new tab).

### Admin
- **B24** Auditing: the Details column is `text-truncate` with `max-width: 32rem` and the full text as `title`, like Path and Target, so a long `DatsRefreshed` list (≈ 40 DAT names) no longer widens the table and squeezes every row.
- **B25** Auditing: the filters become one toolbar row like the Library's: a search box, `FilterDropdown` menus for **Action** and **System**, a **User** dropdown (a text box plus a **Scheduled only** check), a **Date** dropdown (From and To date inputs), and **Clear**. Each toggle shows its field and chosen value. URL parameters, debouncing and behaviour are unchanged; it wraps on narrow screens. `FilterDropdown` gains an optional "no counts" mode if it needs one.
- **B26** Backups: each row of the backups table gets a **Restore** button (Admin). It opens a `ConfirmModal` (danger) naming the backup and its date and saying: every table is replaced; a safety backup of the current database is taken first; everyone, including you, is signed out; run Integrity → Run quick afterwards, since the library ZIPs may be newer. Confirm calls `POST /api/admin/backups/{fileName}/restore`.
- **B27** Restore on the server (`BackupService.RestoreAsync`):
  1. `fileName` must be a bare name of an existing `rnrommanager-*.zip` in `Paths:Backups` (the startup restorer's rule 1, one shared helper): else `400 ValidationFailed` / `404`.
  2. The manifest check (rule 3, shared) runs before anything changes: a backup from a newer app version is `409 BackupTooNew`; an unreadable ZIP or manifest is `400 InvalidBackup`.
  3. It takes the job lock (`409 JobRunning` when a job or library edit holds it) and the backup lock (`409 BackupRunning`), so no job, edit or scheduled backup runs during it.
  4. It opens a **maintenance gate** (`MaintenanceGate` singleton, middleware early in the pipeline): while open, every `/api` and `/health/ready` request except this restore request gets `503 Maintenance` (ProblemDetails, `Retry-After: 5`), and `AuditWriter` is flushed before the drop and holds new events in memory until the gate closes. The gate counts in-flight `/api` requests (not the restore request itself: it opens the gate from inside that request and subtracts it) and, once open, waits up to 10 s for them to finish before the drop (long-lived streams, the log stream and bundle/library downloads, are excluded from the count); if they don't finish in time the restore is refused with `409 Busy` and nothing changes. So no write lands between the drop and the inserts. The gate always closes (finally).
  5. It creates a safety backup while already holding the backup lock (through `BackupService`'s private run path, not `CreateAsync`, which would refuse with `BackupRunning`). The source file is excluded from that run's retention, so restoring the oldest kept backup never deletes it. Its name is in the result and the audit.
  6. `IBackupStore.RestoreAsync`, then `IDatabaseLifecycle.Migrate()` (an older backup gets the newer migrations), then `IJobRepository.AbortRunningAsync` (a job that was Running when the backup was taken), then every user's security stamp is rotated (every session ends), then `IDiscoveryRepository.Invalidate()` (new: drops cached indexes and any in-flight build's result), then both schedulers are woken (`BackupService.SettingsChanged`, `DatRefreshSettingsService.SettingsChanged`) so the restored `app_settings` take effect.
  7. It records `BackupRestored` (details: `<restored file>; safety backup <file>`) after the restore, so the event survives it, and logs the same Warning lines as the startup restore, including the Integrity advice.
  8. Response: `200 { restored, safetyBackup }`. The SPA shows a toast and goes to `/login`.
  9. The live restore neither writes nor reads the startup restorer's `.restored` marker (that marker only guards `Backup:RestoreFrom`).
  10. If the restore fails after the drop, the database may be partial: it returns `500 RestoreFailed` naming the safety backup, and logs Error; the admin can restore the safety backup (live, or startup `Backup:RestoreFrom`).
- **B28** DATs tab: an **Automatic refresh** card with **Enabled** (default on) and **Time** (default `04:00`, container local time, `HH:mm`), **Save**, and the next run time. `GET/PUT /api/admin/dats/settings` (Admin) read and save `dats.autoRefresh.enabled` and `dats.autoRefresh.time` in `app_settings` (missing row = default; invalid time `400 ValidationFailed` `time`). Both return `{ enabled, time, timeZone, nextRunAt }` (`nextRunAt` null when disabled), like the backup status. Not audited, matching backup settings (settings changes are excluded from the audit). `DatRefreshSettingsService` (Core, singleton) owns load, save and the `SettingsChanged` event, as `BackupService` does for backups.
- **B29** `DatRefreshScheduler` (`BackgroundService`) waits on `ScheduleCalculator.NextDaily` with the injected `TimeProvider`, wakes on `DatRefreshSettingsService.SettingsChanged`, and starts the DAT refresh job with `JobTrigger.Schedule` (audit user shown as System), built through a new `DatRefreshJobFactory` (like `IntegrityJobFactory`) shared with `POST /api/jobs/dat-refresh`. If the job lock is busy at the due time it retries every minute until it starts or the next day's due time comes (then that day's run is skipped, logged at Information). Missed runs while the app was down aren't caught up. Failures are the job's usual failures (logged, job status Failed). The Api tests' stub settings turn it off, like scheduled backups.

### Library folders
- **B30** Startup no longer creates `roms/<system>/{#,A..Z}`. The folders are created when a ROM is first written there (ingest, review resolution, move, merge and storage migration already create their target folder before writing; step 3 checks each and adds the call where one is missing). `ingest/<system>/…` is still created at startup.
- **B31** Once per startup, empty library folders are removed: each `roms/<system>/<bucket>` that is an empty directory, then `roms/<system>` if it is then empty. A folder holding anything (including hidden files) is left alone, as is anything unsafe under an external system (same `SafeToCreate`-style classification, warning and skip). Failures are logged at Warning and never stop startup.
- **B32** Every reader that lists or opens `roms/<system>` tolerates a missing folder (treated as empty). Step 3 checks each of: `IngestPipeline`, `LibraryEditor`, `ExternalRomPath` (incl. `ScanFolder`), `ArchiveExtractor`, `DbSync.ScanZips`, `GameMediaRetry`, `Api/Endpoints/LibraryFiles.cs`, `StorageMigrationJob`, `ReviewResolver`, the integrity job and the reports.

## Risks
- **Live restore drops every table** while the app runs. Mitigations: job and backup locks, the maintenance gate (every other request 503 for the few seconds it takes, audit writes held), a safety backup first, migrations, aborted stale jobs and woken schedulers after, every session ended, the advice to run a quick integrity check.
- **Restore ends the Admin's own session** (security stamps and the data-protection keys in the restored DB): the SPA expects it and goes to `/login`. Data-protection keys created after the backup are gone from the database but may still be in the running app's key ring cache, so cookies issued right after the restore may be invalid after the next restart (one more sign-in). Accepted; documented in `deployment.md`.
- **Table rename** (`publisher_logos` → `discovery_logos`): `MySqlBackupStore` dumps whatever tables exist, and restore recreates the backup's own schema before migrations, so old and new backups both restore. `SchemaMigrationTests` covers the migration on a database with existing logos.
- **Lazy library folders**: a code path that assumed `roms/<system>` exists would throw `DirectoryNotFoundException`; step 3 audits every reader and writer and tests a fresh root with no system folders.
- **Empty-folder cleanup deletes directories**: only empty ones, never through a link or unsafe external folder; covered by tests with files, hidden files and links.
- **URL logo download** is a server-side fetch: it reuses `ImageUrlDownloader` (public addresses only, redirects and DNS rebinding checked, bounded read, 15 s), Admin-only.
- **Daily DAT refresh** hits GitHub once a day by default; offline installs log a failed job daily until an Admin turns it off.
- **Fixed footer** can cover content and toasts: `main` padding and the toast offset are part of B10, and the e2e axe scans check both themes.
