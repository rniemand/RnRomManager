# User Management

## Summary
Accounts become one of two types: **Admin** (full access) and **Site user** (read-only library, plus their own collections, bundle queues, hotkeys, password and **private saves**). The `rom-manager` role is folded into `admin`, so ROM/library management is admin-only. Admins already create users with an initial password (forced change on first login), enable/disable them and reset passwords on `/admin/users`; this spec adds a self-change guard, a "new password must differ" rule, per-user save ownership and counts, and writes every user and account operation to the existing audit log so admins can see what users did.

## Out of scope
- Deleting users (users stay disable-only, as today), renaming users, self-service sign-up or password recovery by email.
- Roles other than Admin / Site user, per-system or per-game permissions.
- Sharing saves between users, or transferring a save to another owner.
- Auditing reads (browsing, downloads, play) or per-user writes that aren't account operations (collections, bundle queues, hotkeys).
- A separate audit retention for user events: they follow the existing 30-day purge (AU5).
- Changing the users API contract shape: it keeps the `roles` array (`["admin"]` or `[]`).
- Hiding saves inside the game ZIP: the whole-game download (`GET /api/games/{id}/download`), the Zip Contents tab (`/zip-entries`) and its entry downloads stay unchanged, so any signed-in user can still get every save that way (Risks).

## Behaviour

### Account types
- **U1** `Roles.All` becomes `[admin]`. An **Admin** has `roles: ["admin"]`; a **Site user** has `roles: []`. `Roles.Parse` rejects `rom-manager` (and anything else) with the existing `roles` validation error, now reading "Roles must be any of: admin.".
- **U2** Migration `0024_fold_rom_manager.sql`: first rotates `security_stamp` (`REPLACE(UUID(), '-', '')`, as `0011`) for each user with a `role = 'rom-manager'` row, then deletes those rows (those sessions end; they sign in again with the new rights). Users with `rom-manager` but not `admin` become Site users; users with both keep `admin`. No other data changes.
- **U3** The `LibraryEditor` authorization policy is removed; every endpoint that used it requires `AdminOnly`. Also `AdminOnly` now: release note save/delete (`PUT|DELETE /api/games/{id}/roms/{romId}/note`), rating/favourite (`PATCH /api/games/{id}/rating`) and publisher logo replace/remove (`PUT|DELETE /api/discovery/publishers/logo`; its `GET` stays open). A Site user gets `403 Forbidden` (existing ProblemDetails) on them.
- **U4** Site users keep: every read (library, game detail, discovery, collections they own, ROM/save downloads of what they can see, play), their own collections (`/api/collections*`), bundle queues and bundle downloads, hotkeys (`/api/auth/me/hotkeys`), logout, change password, and their own saves (S1–S5). Nothing else changes for them.

### User administration (existing, with changes)
- **U5** Create (`POST /api/users`) is unchanged: username and initial password are required by the existing policies; `roles` (account type) is optional, and a missing, null or empty `roles` creates a Site user (existing `Roles.Parse`). The new user has `mustChangePassword: true` and can call only the existing `MustChangeAllowed` routes until they change it (existing `403 PasswordChangeRequired`).
- **U6** `PATCH /api/users/{id}` on the **caller's own id** whose result would have `isDisabled: true` or lack `admin` returns `409 SelfChange` "You can't disable or demote your own account" (the caller is signed in, so they are enabled and admin; any such value is a change). A patch on self that changes nothing still returns 200. `POST /api/users/{id}/reset-password` on self stays allowed (204; it rotates the caller's stamp as today, so their session ends on the next request and they sign in with the new password, then must change it). The check runs after validation and `NotFound`, before `LastAdmin`. The SPA's disabled controls on the own row (Step 9) are a convenience; the server rule governs.
- **U7** `POST /api/auth/change-password` rejects a new password equal to the current one with a `newPassword` validation error "New password must be different from the current password." (checked after the current-password check, before `PasswordPolicy`, as an ordinal comparison of `newPassword` with the just-verified `currentPassword`). This covers the first-login change.
- **U8** Disabling a user (existing) rotates their stamp so their sessions end on the next request; a disabled user's sign-in fails as today (`401 InvalidCredentials`, no hint that the account is disabled).

### Audit of user operations
- **U9** New `AuditActions` (added to `All`, so the audit page's Action filter lists them): `UserCreated`, `UserTypeChanged`, `UserDisabled`, `UserEnabled`, `PasswordReset`, `PasswordChanged`, `SignedIn`, `SignInFailed`, `LockedOut`. Each is recorded through `IAuditLog.Record` only after the operation succeeded (for `SignInFailed`/`LockedOut`: after the counters were written). System, game, job and path columns stay null; the target and facts go in `details`, as `key=value` pairs separated by single spaces:

  | Action | Actor (`user_id`, `username`) | `details` |
  |---|---|---|
  | `UserCreated` | the admin | `user=<name> type=admin\|site-user` |
  | `UserTypeChanged` | the admin | `user=<name> from=<type> to=<type>` |
  | `UserDisabled` / `UserEnabled` | the admin | `user=<name>` |
  | `PasswordReset` (admin route) | the admin | `user=<name>` |
  | `PasswordReset` (CLI `--reset-password`) | none (null, null) | `user=<name> via=cli`, plus ` promoted=admin` when the recovery gave `admin` to a user who lacked it (no other enabled admin; an existing admin is never "promoted"), then ` reenabled=true` when the user was disabled. The CLI's re-enable and promotion are recorded only through this row (no `UserEnabled`/`UserTypeChanged`). The CLI host never starts `AuditWriter`, so this row is written synchronously through `IAuditRepository.InsertAsync` (stamped with the current UTC time), not `IAuditLog.Record`, after the new password is printed; an insert failure writes a warning to stderr and keeps exit code 0 (best effort, AU2), so the operator never loses the password. Like a scheduled job's row it shows as *System* and matches **Scheduled only**. |
  | `PasswordChanged` | the user | (none) |
  | `SignedIn` | the user | (none) |
  | `SignInFailed` | the user when the username exists; else `user_id` null and `username` = the attempted name (truncated to 64 by the repository) | `reason=wrong-password\|unknown-user\|disabled\|locked-out` |
  | `LockedOut` | the user | `until=<yyyy-MM-ddTHH:mm:ssZ>` (UTC) |

  `SignInFailed`'s reason is the first that applies, in `LoginAsync`'s order: `unknown-user`, `disabled`, `locked-out` (lockout still running), `wrong-password`. A login rejected before `LoginAsync` (`400` missing username or password, `429` rate limit) records nothing. A PATCH that changes both type and disabled writes one event per change, `UserTypeChanged` first. A no-op PATCH writes nothing. The startup `AdminSeeder` records nothing. The wrong-password attempt that triggers a lockout writes `SignInFailed` then `LockedOut`.
- **U10** The admin audit page needs no new UI: the existing Action, User and text filters cover the new rows (User filters on the actor; `q` matches `details`, so `user=bob` finds actions on bob). **Scheduled only** (`scheduled=true`) changes from `user_id IS NULL` to `user_id IS NULL AND username IS NULL`, so unknown-user `SignInFailed` rows (null id, attempted name) aren't listed as scheduled. The audit endpoint stays admin-only. `SignedIn` rows may dominate the unfiltered list; the Action filter is the answer (no default filter). Volume is bounded by the login rate limit (10/min/IP) and the 30-day purge; the repository already truncates `username` to 64 and `details` to 1024 characters.

### Private saves
- **S1** A save's **owner** is its `uploadedBy` username (saves.json; matched case-insensitively, usernames being unique and immutable). Saves with `uploadedBy` null have no owner. No saves.json format change; existing saves keep their uploader as owner.
- **S2** `GET /api/games/{id}/saves` returns, for a Site user, only saves they own; for an Admin, all saves (unchanged shape).
- **S3** For a Site user, a save they don't own acts as missing: download, PATCH, file replace and DELETE return `404 NotFound` (the existing ProblemDetails). A non-owned id is answered exactly like an unknown id, at the same point in the existing order (after `JobRunning` and `SavesUnreadable`, which never depend on the save id), so a Site user can't tell the two apart. The viewer (`SaveViewer(string? Username, bool IsAdmin)`, new record in Core, built by the endpoints from the session's name and `admin` role) is a new `SaveViewer viewer` parameter just before the `CancellationToken` of `PrecheckSaveAsync`, `UpdateSaveAsync`, `ReplaceSaveFileAsync` and `DeleteSaveAsync`; ownership is checked where the save id is resolved, both in the precheck and again under the lock (`OpenSaveAsync`). Download checks it in the endpoint. Admins can act on every save; an admin edit keeps `uploadedBy` (owner) and sets `updatedBy` as today.
- **S4** Uploads (`POST /api/games/{id}/saves`, including the Play dialog's copy-to-server buttons) are allowed for every signed-in user and owned by the uploader, as today. `MaxPerRelease` (25) now counts only the uploader's own saves on that release (owner match per S1), for admins too, in the precheck (the viewer's name) and in `AddSaveAsync` (the actor's name); so `SaveLimitReached` says nothing about other users' saves. Its title becomes "You already have 25 saves for this release. Delete one first." `SavesIndexFull` (the game's whole `saves.json` over 1 MiB) stays per game and counts every user's saves, so other users' saves can cause it; its title names no save or user (accepted).
- **S5** The Play dialog's "Play with save" list comes from the same `GET` as the Saves tab, so it shows only S2's saves without SPA changes; covered by `SaveEndpointsTests`. Its **Save to library** (`EmulatorModal`), which today replaces the release's newest save of the same kind from that list, picks only a save whose `uploadedBy` equals the signed-in username ignoring case (S1), and adds a new one when there is none, so an admin (who lists every save) never replaces another user's save.
- **S8** For an Admin, the Saves tab (`GameSaves.svelte`) adds an **Owner** column (after Release) showing `uploadedBy`, or *Unknown* when it is null, so an admin can tell whose save it is after editing it (`updatedBy` then names the admin). Site users, who see only their own saves, get no Owner column. The API is unchanged (`uploadedBy` is already in every item).

### Per-user save counts
- **S6** New table `game_user_save_counts (game_id CHAR(36), username VARCHAR(64), save_count INT)`, primary key `(game_id, username)`, `utf8mb4_unicode_ci` (case-insensitive, like `users.username`), FK to `games` with `ON DELETE CASCADE`. The library mirror (`LibraryMirror.SaveCount` in `LibraryRepositories.cs`) keeps computing `games.save_count` by counting `saves/` entries as today, and in the same ZIP open also reads `saves/saves.json` (at most `GameSaves.MaxIndexBytes`) and parses it with `GameSaves.Parse(bytes, entryLength)` (entry lengths from the open archive); it groups the records by owner with `StringComparer.OrdinalIgnoreCase` and writes one row per owner with ≥ 1 save in the same transaction as the game row (the mirror deletes and re-inserts the game, so the cascade clears old rows). An owner counts only when it passes `UsernamePolicy.Validate` (ASCII, 3–64 characters, so ordinal-ignore-case grouping matches the column's collation and no insert can clash or overflow); any other `uploadedBy`, like null, is unowned. When `saves.json` is absent or unreadable it writes no rows for that game. Unowned saves count only in `games.save_count`. Migration `0025_game_user_save_counts.sql` creates it empty and nothing backfills it: a game's rows appear only when its ZIP is next mirrored, that is written by the app (any edit, rating, note or save change) or found changed (size or mtime) by `DbSync`; an unchanged ZIP is never re-read, so an untouched game keeps no rows (Risks).
- **S7** Every API `saveCount` is viewer-dependent: for an Admin, `games.save_count` (unchanged); for a Site user, their own row's `save_count` or 0. This covers both emitters: `LibraryEndpoints.ToListItemDto` (the library list, which also serves collection game lists through `GET /api/games?collection=`, and discovery game lists) and the game detail (`ToDetail`). Implemented in the endpoints: for a Site user they call new `IGameRepository.GetUserSaveCountsAsync(string username, IReadOnlyCollection<Guid> gameIds, CancellationToken cancellationToken)` (→ `IReadOnlyDictionary<Guid, int>`, games without a row absent) for the page's ids and override `saveCount`; repository list queries don't change. The SPA shows it unchanged (library badge, `Saves (n)` tab).

## Risks
- **Rights removed on upgrade (U2):** `rom-manager`-only users lose library edits and are signed out once. Documented in `docs/deployment.md` upgrade notes.
- **Per-user counts start empty (S6):** after upgrade, a Site user sees save count 0 (no library badge, `Saves (0)`) on a game where they already had saves, while its Saves tab lists them, until that game's ZIP is next written by the app; `DbSync` never re-reads an unchanged ZIP, so an untouched game stays 0. Accepted, no backfill. Admin counts are unaffected. Documented in the upgrade note.
- **Save ownership by username (S1):** safe because usernames are unique (case-insensitive collation) and can't be renamed or deleted; if renames are ever added, ownership must move to user ids.
- **Audit noise / attacker-controlled text (U9):** failed sign-ins for unknown usernames write the attempted name; login is rate-limited (10/min/IP), text is truncated to column length and rendered as text (never HTML) by the existing audit page. An attempted name can be a password typed into the username box; it stays readable by admins until the 30-day purge (accepted). The audit queue is best-effort (AU2): a dropped event is logged as a Warning, never fails the request.
- **Rights gained on upgrade (U3):** admins created with only `admin` couldn't edit the library before; now every admin can. Intended (two account types); in the upgrade note.
- **Privacy leak (S3):** others' saves return 404, not 403, so a Site user can't probe save ids.
- **Saves in the game ZIP (Out of scope):** saves are private in the Saves tab, the Play dialog and the saves API only; the whole-game ZIP download and Zip Contents still expose every save to any signed-in user. Accepted; stated in `docs/features.md`.
