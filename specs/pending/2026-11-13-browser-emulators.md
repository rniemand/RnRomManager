# In-browser emulators (GB, GBC, GBA)

## Summary
Signed-in users can play a Game Boy, Game Boy Color or Game Boy Advance release straight from the Game detail page. A **Play** button on each release card opens a modal running [EmulatorJS](https://emulatorjs.org) (Gambatte for GB/GBC, mGBA for GBA), self-hosted in the image. The ROM is streamed from the library ZIP through the existing download endpoint, so nothing is extracted to disk and nothing needs cleaning up.

## Out of scope
- Save states (the save/load-state buttons are hidden). In-game battery saves stay in the player's browser only (B8); nothing is stored server-side.
- Systems other than `gb`, `gbc`, `gba`; external-storage releases (Switch, disc systems).
- Netplay, cheats, BIOS files, ROM patches, shaders, a controls config UI.
- Loading EmulatorJS from its CDN; multi-threaded (`-thread`) cores (they need cross-origin isolation headers).
- A hotkey to start playing.

## Behaviour
- **B1 Supported systems.** A handler opts in through a new `ISystemHandler.BrowserCore` (`string?`, default `null`): the EmulatorJS core name. `gb` and `gbc` return `gambatte`, `gba` returns `mgba`; every other handler stays `null`.
- **B2 API.** `GET /api/games/{id}` adds a top-level `browserCore`: the game's system handler's `BrowserCore`, or `null` when the handler doesn't set one or the game's system has no registered handler (never a 500). It's set in `DetailAsync`, so every endpoint that returns the game detail (`PATCH /api/games/{id}`, the rating, image, media-retry and release move/delete responses) carries it too: the SPA replaces `game` with those responses, and a missing field would hide the Play button until a reload. No other contract change; no migration, no config key.
- **B3 Play button.** On the Game detail Releases and Updates tabs, a release card shows a Play button when `canPlay(game, rom)` (in `src/lib/emulator.ts`) is true: `game.browserCore` is non-null and `rom.externalFileName` is null. The button is `btn btn-sm btn-outline-success` with Icon `play` (`bi bi-play-fill`) and `aria-label="Play {fileName}"`, placed before the Download button. Every signed-in user sees it (same rule as Download).
- **B4 Modal.** The page holds one `EmulatorModal` instance, driven like `ReleaseNoteModal`: the button sets `playRom = rom` and `playOpen = true`, and the page renders `<EmulatorModal bind:open={playOpen} gameId={game.id} core={game.browserCore} rom={playRom} />`. `EmulatorModal`'s props are `open` (`$bindable`), `gameId: string`, `core: string | null` and `rom: RomDetail | null`. It's a `ConfirmModal` info modal (M1 rules, Close only) with a new `size="xl"`, title `Play {fileName}`. The body is a Bootstrap `ratio ratio-4x3` container (EmulatorJS letterboxes GB/GBC's 10:9 and GBA's 3:2 inside it) holding a same-origin `<iframe>` with `title="Emulator: {fileName}"`, `allow="fullscreen; gamepad; autoplay"` and `src={playUrl(gameId, rom, core)}` = `/emulator/play.html?game={gameId}&rom={rom.id}&core={core}&name={encodeURIComponent(rom.fileName)}`. The iframe is rendered only while `open && rom && core`. Closing the modal (×, Close, or Escape while focus is outside the iframe) removes it, which stops the emulator and its audio. Focus after close follows the existing `ConfirmModal` behaviour (no new focus handling). Escape while focus is inside the iframe goes to the emulator and doesn't close the modal. Keyboard input inside the iframe never reaches the app's global hotkeys (separate document).
- **B5 Play page.** `/emulator/play.html` is a static page with no inline script: a `#game` container, a `#status` line, and `<script type="module" src="play.js">`. `play.js`:
  1. Calls `parsePlayParams(location.search)` from `params.js`: `game` a GUID, `rom` a positive integer, `core` one of `gambatte`/`mgba`, `name` 1–255 chars. Anything else shows "Invalid emulator link." and stops.
  2. `fetch`es `/api/games/{game}/roms/{rom}/download` (same origin, cookies). A non-2xx shows "Couldn't load the ROM (HTTP {status})." (401: "Your session has expired. Sign in again.").
  3. Wraps the bytes as `new File([blob], name.replaceAll('#', '_'))`, so the core sees the real extension (the URL ends in `/download`). EmulatorJS cuts the name it gives the core at the first `#` (`getBaseFileName`), which would drop the extension; `?` can't occur (`FileNameSanitizer`).
  4. Sets the globals `EJS_player = '#game'`, `EJS_core`, `EJS_gameUrl = file`, `EJS_gameName = name`, `EJS_pathtodata = '/emulator/vendor/data/'`, `EJS_disableDatabases = true` (no ROM/core cache in IndexedDB), `EJS_disableAutoLang = false` (with `EJS_language` unset, `loader.js` loads no localization file and uses its built-in English), and `EJS_Buttons = { saveState: false, loadState: false, quickSave: false, quickLoad: false, netplay: false, cheat: false, exitEmulation: false }` (a boolean sets the button's `visible`), and `EJS_defaultOptions = { 'save-save-interval': '30' }` (B8).
  5. Only then appends `<script src="/emulator/vendor/data/loader.js">`. Its `error` event shows "Couldn't load the emulator."

  All status text is set with `textContent`. EmulatorJS's own start button stays (browsers need a click inside the frame before audio).
- **B6 No temp files.** The ROM is read through the existing `GET /api/games/{id}/roms/{romId}/download` (streams the ZIP entry, auth required). There's no server-side extraction, so closing the modal has nothing to delete.
- **B7 Security headers.** Responses whose path `StartsWithSegments("/emulator", StringComparison.OrdinalIgnoreCase)` get their own CSP: `default-src 'self'; script-src 'self' 'unsafe-eval' 'wasm-unsafe-eval' blob:; worker-src 'self' blob:; connect-src 'self' blob: data:; img-src 'self' data: blob:; media-src 'self' blob:; style-src 'self' 'unsafe-inline'; frame-ancestors 'self'`. Every other response keeps today's CSP unchanged, including `frame-ancestors 'none'`. `'unsafe-eval'` is needed because the cores' `.data` files are 7z archives, unpacked in a `blob:` worker (`compression/extract7z.js`, which inherits this policy) whose old Emscripten `cwrap("extract", "number", ["string"])` builds its wrapper with `eval`; the cores' own scripts use no `eval`. If step 5 finds the real cores need more, it adds the minimum, records it in § Decisions and updates B7. EmulatorJS's update check and CDN core fallback (`cdn.emulatorjs.org`) are blocked by `connect-src 'self'` on purpose: console noise only, no third-party requests.
- **B8 Browser saves.** EmulatorJS keeps a cartridge's battery saves in the browser's IndexedDB (an IDBFS mount at `/data/saves`), named after the ROM file the core loads, which is the `File`'s name (the release file name with `#` → `_`, B5; `EJS_gameName` is the unchanged name). They survive closing the modal and reloading, on that browser only. EmulatorJS writes them to IndexedDB on page unload (which removing the iframe doesn't trigger) and on its "System Save interval", which `EJS_defaultOptions` sets to 30 seconds instead of the default 5 minutes (a player's own choice in EmulatorJS's settings, kept in `localStorage`, wins); pausing doesn't write them (in 4.2.3 only a netplay host's pause does). So an in-game save made less than 30 s before closing the modal can be lost; `docs/features.md` says to wait 30 s after saving before closing. Two releases with the same file name would share saves; release file names come from the DATs and are unique per system, so that's accepted and documented.
- **B9 Vendored assets.** EmulatorJS `4.2.3` (`@emulatorjs/emulatorjs`, `@emulatorjs/core-gambatte`, `@emulatorjs/core-mgba`, exact versions) are npm `dependencies`. `@emulatorjs/emulatorjs` has an optional dependency on `@emulatorjs/cores@latest`, which installs every EmulatorJS core (~293 MB); Both core packages depend on `@emulatorjs/emulatorjs@latest`, which would install a second, nested EmulatorJS once a newer version is published. `package.json` gets `"overrides": { "@emulatorjs/cores": "npm:@emulatorjs/core-gambatte@4.2.3", "@emulatorjs/emulatorjs": "$@emulatorjs/emulatorjs" }`, so `cores` resolves to a package we already install, every `@emulatorjs/emulatorjs` resolves to the pinned direct dependency, and the lockfile holds no other cores. `node scripts/vendor-emulatorjs.mjs [outDir]` (web project; `outDir` defaults to `static/emulator/vendor`, relative to the web project) empties `outDir` and writes:
  - from `@emulatorjs/emulatorjs/data/`: `loader.js`, `src/*.js`, `emulator.css`, `compression/*` (except its `README.md`) and `version.json`, under `data/`;
  - from each core package's root: `<core>-legacy-wasm.data` (the one EmulatorJS loads by default: both cores' reports have empty `options`, so `defaultWebGL2` is unset) and `<core>-wasm.data` (loaded only when the player turns WebGL 2 on in EmulatorJS's settings) into `data/cores/`, and `reports/<core>.json` into `data/cores/reports/`;
  - `data/emulator.min.js` (the eight `src/` scripts concatenated in `loader.js`'s order, each followed by `\n`, because `socket.io.min.js` ends in a `//# sourceMappingURL` line comment) and `data/emulator.min.css` (a copy of `emulator.css`), because the npm package ships no minified build and `loader.js` otherwise 404s first;
  - `@emulatorjs/emulatorjs/LICENSE` as `licenses/emulatorjs.txt`. The core packages ship no licence file: each core's text is the `license.txt` inside its `.data` archive (shipped unmodified), which EmulatorJS shows in its own menu.

  A missing source file fails the script (non-zero exit). It runs from the `prebuild` and `predev` npm scripts, so `npm run build` and the Docker image always contain it. No localization files are copied (B5).
- **B10 Static files.** The static file middleware serves `.data` as `application/octet-stream` (ASP.NET's default content-type table has no `.data`, so those files would 404). Unknown paths under `/emulator/` return a plain 404 instead of the SPA's `index.html`, so a missing vendor file fails clearly. A missing path with a file extension already 404s (the SPA fallback is `{*path:nonfile}`); `FallbackEndpoints` adds `/emulator/{**rest:nonfile}` → 404 for extensionless ones. The route must keep `:nonfile`: a matched endpoint makes the static file middleware skip the request, so `/emulator/{**rest}` would 404 every vendored file.
- **B11 Licences.** `licenses.json` lists `@emulatorjs/emulatorjs` (`GPL-3.0`, `https://github.com/EmulatorJS/EmulatorJS`), `@emulatorjs/core-gambatte` (`GPL-2.0`, `https://github.com/EmulatorJS/gambatte-libretro`) and `@emulatorjs/core-mgba` (`MPL-2.0`, `https://github.com/EmulatorJS/mgba`), named exactly as in `package.json` so `LicenseInfoTests` passes and the About page shows them. The licences were confirmed from the 4.2.3 packages' `LICENSE` and the cores' archived `license.txt`. EmulatorJS's licence text is served at `/emulator/vendor/licenses/emulatorjs.txt` (B9).

## Risks
- **GPL in an MIT image:** EmulatorJS is GPL-3.0. It's shipped unmodified as separate files (aggregation), with its licence text and source URL (B11). The app's own code stays MIT.
- **CSP widening:** it's limited to `/emulator/*`, which serves only the vendored files and the play page; the SPA and API keep the strict policy. `'unsafe-eval'` (B7) is the main loosening; with no inline scripts allowed and every query value validated, it only matters if a vendored script itself evals untrusted text. The play page accepts only validated ids and a fixed core list (B5), so it can't be pointed at another URL. Unknown `/emulator/*` paths are 404, never the SPA under the relaxed CSP (B10).
- **Minified build by concatenation (B9):** this relies on the eight scripts being plain globals loaded in order, which is exactly what `loader.js`'s own fallback does. It's verified manually in step 5, and pinned versions keep it stable. Upgrading EmulatorJS means re-checking it.
- **EmulatorJS's build tooling:** `@emulatorjs/emulatorjs` 4.2.3 lists its own build tools (socket.io, http-server, `@node-minify/*`, node-7z, …) as `dependencies`, so about 135 extra packages are installed in the dev tree and the Docker `web` stage, and `npm audit` reports their issues (6 at spec time, via `@node-minify/core` → glob/minimatch). They're never run and never reach the image; CI doesn't run `npm audit`. Accepted.
- **Image size:** about +5 MB (two cores × two variants, plus data).
- **axe:** EmulatorJS's own UI may not pass axe, so the e2e scan of the open modal excludes the iframe (documented in the test). The modal chrome is still scanned.

## Decisions
- 2026-11-13 Where do the EmulatorJS files come from? → Self-hosted from pinned npm packages, copied into the SPA build (user)
- 2026-11-13 Which cores? → Gambatte for GB/GBC, mGBA for GBA (user)
- 2026-11-13 Extract the ROM to a temp file and delete it on close? → No: stream it through the existing download endpoint, so there's nothing to clean up (user)
- 2026-11-13 Inline in the SPA or isolated? → A same-origin iframe with its own CSP; the app's CSP and hotkeys are untouched (user)
- 2026-11-13 Battery saves? → Keep EmulatorJS's browser-local saves and hide the save/load-state buttons (user)
- 2026-11-13 Where does "supported" live? → `ISystemHandler.BrowserCore`, like every other per-system fact (code)
- 2026-11-13 How does the core get a file name with an extension? → Pass a `File` named after the release (EmulatorJS uses its name), since the download URL ends in `/download` (code)
- 2026-11-13 Language? → `EJS_disableAutoLang = false` with no `EJS_language`, because `loader.js` fetches a localization file whenever auto-language is on, even for `en-US` (reviewer R4)
- 2026-11-13 `.data` files and missing vendor files? → Map `.data` to `application/octet-stream`; `/emulator/**` 404s instead of falling back to the SPA (reviewer R1, R6)
- 2026-11-13 Battery-save key? → The release file name; collisions need identical DAT file names, so they're accepted and documented (reviewer R8)
- 2026-11-13 How do `/emulator` paths 404 without breaking static files? → `/emulator/{**rest:nonfile}`: a catch-all without `:nonfile` matches the vendored files too, and the static file middleware skips requests that already matched an endpoint (review)
- 2026-11-13 Core licence files? → The core npm packages have none; their texts ship inside the unmodified `.data` archives (`license.txt`) and only EmulatorJS's `LICENSE` is copied to `licenses/`, with no committed copies of the core texts (user)
- 2026-11-13 Does the e2e start the core? → Yes: it clicks Start Game and checks the core download and start, so the image's B7/B10 setup is tested, not only checked by hand (user)
- 2026-11-13 Where does `browserCore` go in the API? → In `DetailAsync`, so every game-detail response carries it and the SPA's in-place `game` updates keep the Play button (review)
- 2026-11-13 How is `EmulatorModal` driven? → Like `ReleaseNoteModal`: `bind:open` plus a `rom` prop, since `ConfirmModal` takes a boolean `open` (review)
- 2026-11-13 Which core file loads? → The `-legacy` one by default (the cores' reports don't set `defaultWebGL2`); both variants are vendored because the settings menu can switch (review)
- 2026-11-13 Battery saves are flushed only every 5 minutes by default, and removing the iframe doesn't flush them. How to limit the loss? → `EJS_defaultOptions = { 'save-save-interval': '30' }` and document waiting 30 s (or pausing) after an in-game save before closing (user)
- 2026-11-13 Does pausing flush battery saves? → No: in 4.2.3 only a netplay host's pause calls `saveSaveFiles`, so B8 and the docs advise only waiting 30 s; the 30 s interval itself is unchanged (review)
- 2026-11-13 Does the `/emulator` CSP need `'unsafe-eval'`? → Yes: the 7z worker that unpacks each core's `.data` builds its `cwrap` wrapper with `eval` and inherits the page's policy (review)
- 2026-11-13 Release file names with `#`? → Replace `#` with `_` in the `File` name, since EmulatorJS truncates the core's file name at `#` and the extension would be lost (review)
- 2026-11-13 `@emulatorjs/emulatorjs` optionally installs every core through `@emulatorjs/cores@latest` (~293 MB). → An npm `overrides` alias to `@emulatorjs/core-gambatte@4.2.3`, so only the two vendored cores are installed (user)
- 2026-11-13 The core packages depend on `@emulatorjs/emulatorjs@latest`. → A second override, `"@emulatorjs/emulatorjs": "$@emulatorjs/emulatorjs"`, so a newer EmulatorJS release can never be installed nested beside the pinned one (review)
- 2026-11-13 EmulatorJS's build tools are runtime `dependencies` (~135 packages, `npm audit` findings). → Accept and note it in § Risks: they're build-stage only, never run or shipped (user)
- 2026-11-13 Where does the e2e play flow go? → Right after the `game detail with releases expanded` axe scan, while Orbit Blocks' Releases tab is open (review)
