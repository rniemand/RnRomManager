# Release editing, new reports, per-user saves and mobile polish

## Summary
A batch of fixes and features for the maintainer, mostly from using the app on a phone: ROM names containing `..` can be imported on every system; Admins can edit a release's tags (region, languages, revision, disc, hack, translated, kind Release/Update/DLC, version) from the Game page, renaming the release to match; two new reports (Newly Added Games, Games With Hacks) and a System filter on Multiple Releases; saves move to per-user folders inside the game ZIP (one-off background migration); battery saves load and store automatically in the browser player; screenshots lose their black border; and the shell gets mobile fixes (always-visible footer with Admin quick actions, flatter navbar menu, tab icons, Backups accordion, Auditing cards, Library toolbar) plus PWA install support.

## Out of scope
- Editing a release's base title, its other flags (`Beta`, `Proto`, `Unl`…) or its identification (DAT entry, hashes).
- Renaming files on disk: an external ROM's file and every `FileSets` (disc system) release keep their names (B8).
- A manual crop tool for screenshots (B27 trims automatically; a toggle keeps the border).
- An offline service worker or any caching for the PWA (B44).
- Battery-save auto-store for the PSP player (opens in its own tab, outside `EmulatorModal`) and for DeSmuME/Opera (no battery export today, Saves B18).
- Detecting an unchanged battery save before auto-storing it (B24 always writes).
- Renaming users (there is no username change today, so a save folder never has to move).

## Behaviour

### Names with `..`
- **B1** Every system accepts a ROM name containing `..` (e.g. `Hello... World (USA).gb`), in automatic ingest, Review (Dat, Manual, Attach) and info.json validation. Only a name that **is** `.` or `..`, or contains `/` or `\`, is refused. Today this already holds for `FileSets` systems (disc-set B12); the rule now applies to all systems:
  - `ReviewResolver` (the check above `if (external && !system.FileSets)`): the non-`FileSets` branch `filename.Contains("..")` is replaced by the `FileSets` rule (`filename is "." or ".." || filename.IndexOfAny(['/', '\\']) >= 0`) for every system. The error text becomes "The generated ROM filename must not be '.' or '..' or contain '/' or '\\'; use Manual with another title." (field `title`, as today).
  - `InfoJsonValidator.FileNameProblem(…, "roms", dotsInside: true)` for every system (today `handler.FileSets`); images keep `dotsInside: false`. The error text is unchanged.
  - `FileNameSanitizer`, `SafePath`, `ArchiveExtractor` and `ExternalRomPath` already refuse only whole `..` path segments and stay as they are.

### Release editing (Admin)
- **B2 Button.** Each release card on the Game page (Releases, Updates and DLC tabs, the shared `#releases-panel`) gets **Edit release** (`btn btn-sm btn-outline-secondary`, `<Icon name="edit" />`, `aria-label="Edit release {fileName}"`) for Admins only, as the first button of the right-hand Admin group (before **Make primary**). It opens the new `EditReleaseModal.svelte`.
- **B3 Form.** Modal title "Edit release"; the current file name is shown read-only (`font-monospace`, small) under the title. Fields, prefilled from the release:
  - **Kind**: radio group `Release` / `Update` / `DLC` (from flags per DLC B1: `Update` wins over `DLC`).
  - **Regions**: one checkbox per `NoIntroRegions.All` value, in a scrollable box (max-height 12rem), the 8 common ones first (`World`, `USA`, `Europe`, `Japan`, `Asia`, `Australia`, `Korea`, `Brazil`), then the rest A–Z, then (checked) any region the release already has that isn't in the list (Manual review accepts any text). The list is served by B11 (`regions`). The regions value (prefill comparison and request) is the stored regions still checked, in their stored order, then newly checked ones in the list order above, so unchecking and rechecking a region doesn't reorder the group.
  - **Languages**: text input, comma-separated codes (`En,Fr,De`), prefilled from the stored list joined with `,`; saved as the trimmed, distinct (ordinal) list in the typed order, empty entries dropped (`En,,Fr ` → `["En","Fr"]`; empty input → `[]`).
  - **Revision**: text input (≤ 32 chars, e.g. `Rev 1`); empty = none.
  - **Disc**: number input 1–99; empty = not a disc. Shown only on `FileSets` (disc) systems, as Review allows disc numbers only there.
  - **Hack** and **Translated**: two `form-check form-switch` checkboxes.
  - **Version**: text input, shown only when Kind is `Update`; must match `ReleaseVersion.Valid()` (`1.0.1`); empty = none.
  - A preview line "New file name: `<name>`", computed in the browser by `editReleaseFileName` in `src/lib/releaseName.ts` (new), a port of B7 for the preview only (it skips the external logical-name budget and the ` (2)` clash suffix; the server's name wins and is shown in the success toast). It is not `reviewForm.ts`'s `manualFileStem`: that builds a stem from scratch, while B7 edits only the changed groups of the existing name. The line reads "File name unchanged" when B7 gives the current name.
  - **Submit** sends only the fields whose value differs from the prefill (B4 PATCH semantics); with none, Save closes the modal without a request.
  Buttons **Save** (primary) / **Cancel**. Field errors from a 400 show under each field (`invalid-feedback`); other errors in an `ErrorAlert` in the modal. Success: modal closes, toast "Release updated: <fileName>" (from the response), the game reloads; when the kind changed, the page switches to the tab the release now belongs to (`?tab=releases|updates|dlc`).
- **B4 API.** `PATCH /api/games/{id:guid}/roms/{romId:long}` (Admin), mapped in `LibraryEndpoints.cs` after `POST …/primary`; JSON body read as `JsonElement` and parsed by a new public static `ParseReleasePatch(JsonElement body)` → `(ReleaseEdit Patch, Dictionary<string, string[]> Errors)`, as `PATCH /api/games/{id:guid}` does with `ParsePatch` (a non-object body → 400 on `""` "A JSON object is required."; every property optional, an absent one is unchanged, `null` clears where allowed):
  `{ "kind": "release"|"update"|"dlc", "regions": string[], "languages": string[], "revision": string|null, "disc": int|null, "hack": bool, "translated": bool, "version": string|null }`.
  Validation runs only on the properties present (400 `ValidationFailed`, keyed by field; the checks that need the game (`disc` on a non-disc system, a region outside the list and the release's own) run in `EditReleaseAsync` and come back in the same 400 shape): `kind` one of the three; `regions` ≤ 10 distinct non-empty values (an empty list is allowed: no region, as Manual review), each in `NoIntroRegions.All` or already in the release's regions ("Must be known No-Intro regions."); `languages` ≤ 20 distinct values of 1–16 characters `[A-Za-z-]` ("Must be 1–16 letters or '-' each."); `revision` ≤ 32 chars after trimming, no `(`/`)` ("Must be at most 32 characters without parentheses."); `disc` 1–99 ("Must be 1–99.") and only on a `FileSets` system (else 400 `disc` "Disc numbers are for disc systems.", ReviewResolver's text); `version` matches `ReleaseVersion.Valid()` ("Must be like 1.0.1.") and only with kind `update` after applying the patch ("Only an update has a version."); an unknown property → 400 on that property ("Unknown field."). Update and DLC may be set on any system. Responses: 200 `{ "fileName": "<new name>" }`; 404 game or release; 409 `JobRunning`, `StorageMigrationPending` (`LegacyRefusal`), `TargetZipUnreadable`/`InfoJsonNewerSchema` (`OpenForEdit`), `SavesUnreadable` and `SavesIndexFull` (a rename that carries saves, B9); `IoError`, `VerifyFailed`, `DbWriteFailed` — every code mapped as `ToProblem` maps it today.
- **B5 Flags.** The stored flag list keeps its order: a flag whose field turned off is removed; one turned on is appended at the end (`Translated`, `Hack`, `Update`, `DLC`); a changed disc replaces the existing `Disc <n>` flag in place (case-insensitive match), a new one is appended at the end (as Review's builders put it last), a cleared one is removed. Kind `release` removes `Update` and `DLC`; `update` removes `DLC` and adds `Update`; `dlc` the reverse. Version is kept only for kind `update`; any other kind clears it.
- **B6 No-op.** A field equal to its stored value (lists compared in order, ordinal) is unchanged. When no field changes, nothing is written and the response is 200 with the current file name (no audit row).
- **B7 Name.** `ReleaseFileName.Edit(string fileName, ReleaseTags before, ReleaseTags after)` (new, `Core/Naming/ReleaseFileName.cs`, `ReleaseTags` (new) = regions, languages, revision, hack, translated, version) edits only the groups of the **changed** fields in the existing stem (`Path.GetFileNameWithoutExtension`); the extension is kept. For each changed field, its old group text is `(<regions joined ", ">)`, `(<languages joined ",">)`, `(<revision>)`, `(Hack)`, `(Translated)`, `[<version>]`:
  - old group found in the stem (ordinal, ignoring case, first match) → replaced by the new group, or removed together with one preceding space when the new value is empty/off;
  - not found and a new value set → the new group is inserted with a leading space before the first `[` group of the stem, or at its end when it has none (a new region group goes right after the base title instead: after the first `baseTitle.Length` characters when the stem starts with `baseTitle`, else at the B7 default position).
  Then `FileNameSanitizer.Sanitize`. Unchanged fields never touch the name, so Attach-style names (`<source stem> (Hack)`) and titledb names (`<name> [titleid][v0][1.0.1]`) keep their own text. Examples: `Tetris (World) (Rev 1).gb` + Hack → `Tetris (World) (Rev 1) (Hack).gb`; `Puzzle Land (Hack).gb` − Hack → `Puzzle Land.gb`; `Orbit [0100000000003800][v65536][1.0.1].nsp` version 1.0.1 → 1.0.2 → `Orbit [0100000000003800][v65536][1.0.2].nsp`; kind Update → Release on it removes `[1.0.1]`.
- **B8 Rename.** The release is renamed to the B7 name unless it equals the current name ignoring case:
  - **ROMs in the ZIP** (`EmbedRomsInZip`): the `roms/<old>` entry is written as `roms/<new>` (bytes copied, SHA-1 verified by the writer as for a move); a clash with another release's name gets the ` (2)` suffix through `FreeName(name, <the game's other releases' fileNames>)`, as a move does.
  - **External, not `FileSets`**: only the logical `fileName` changes, via `ExternalRomName.AllocateLogicalName` with the game's other releases' `FileName`s reserved (as `MoveReleaseExternalAsync` builds its `ExternalNameReservations`), so a clash gets the ` (2)` suffix; `externalFileName` and the file on disk are unchanged.
  - **`FileSets` systems** (disc systems): never renamed (play-disc B2 needs `fileName == externalFileName`, and cue sheets name their tracks); only the tags change. The modal hides the "New file name" preview and shows "Disc releases keep their file name; only the tags change." instead (`fileSets` comes from the game DTO, B11).
- **B9 What follows a rename.** The release's note (`notes/<old>.md` → `notes/<new>.md`, `CarryNote`) follows the new name. Saves are touched only when at least one save names the old file name (`GameSaves.Names`): then every save naming it gets the new `release` through `CarrySaves(zip, null, Renames((old, new)))`; when none does (or the game has no saves), the write carries no `SavesChange` and the writer copies `saves/` as it is (a version 1 index stays version 1). A game whose `saves.json` is unreadable refuses a rename with 409 `SavesUnreadable` before writing (it can't tell whether a save names the release); a tags-only edit (no rename) still works.
- **B10 Write.** `LibraryEditor.EditReleaseAsync` (new) follows `SetPrimaryReleaseAsync`: job lock (`JobRunning`), game and release by SHA-1 (`NotFound`), `LegacyRefusal`, `OpenForEdit`, one ZIP write from the ZIP's own info.json (`Metadata = Touched(current)`), roms re-ranked with `PrimaryRelease.Apply(roms, DatSourceOf(system), chosen)`, where `chosen` is `current.ChosenPrimarySha1` except that it becomes null when the edited release is that chosen one and its kind becomes `update` or `dlc` (an add-on is never kept as an Admin-chosen primary), then the DB mirror (`file_name`, `regions`, `region_key`, `languages`, `flags`, `revision`, `version`, `is_primary` follow the mirror as for every write). Audit: new `AuditActions.ReleaseEdited` (`"ReleaseEdited"`, in `All`; also added to the Activity report's `edits` list in `ReportEndpoints.cs`, with the other library edits), path = the ZIP, details `"<old fileName> → <new fileName>"` when renamed, else the old file name. Log `Release {FileName} of game {GameId} edited`.
- **B11 Data for the form.** `GET /api/games/{id:guid}` (`DetailAsync`) gains `fileSets: bool` on the game (from the system handler; `GameDetail.fileSets: boolean` in `types.ts`) and the new `GET /api/systems/regions` (any signed-in user, mapped next to `api.MapGet("/systems", …)`) returns `NoIntroRegions.All` in the B3 order as a string array. `RomDetail` in `types.ts` already carries `regions`, `languages`, `revision`, `version`, `flags`.

### Saves in per-user folders
- **B16 Layout.** `saves.json` version 2: each save's bytes are `saves/<owner>/<id><extension>`, `<owner>` = `uploadedBy` lowercased (invariant). Version 2 requires `uploadedBy` to pass `UsernamePolicy.Validate`; `saves/saves.json` stays the single index. Version 1 (today: `saves/<id><extension>`) is still read and copied unchanged by writes that don't touch saves.
- **B17 Model.** `GameSave` gains `[JsonIgnore] public bool Legacy { get; init; }`, set by `GameSaves.Parse` for every record of a version 1 index; `Entry` returns `saves/<id><ext>` when `Legacy`, else `saves/<owner>/<id><ext>`. `GameSaves.Records` (used by `LibraryZipWriter` on the index a write is about to store) leaves `Legacy` false: it only ever reads what `Serialize` wrote. `GameSaves.Version` becomes `CurrentVersion = 2`; `Parse` accepts 1 and 2 (any other: Unreadable "saves.json version N is not 1 or 2"); `Serialize` always writes version 2 and throws `ArgumentException` if any record is `Legacy`. Every existing caller of `Entry` (`IntegrityJob`, `LibraryZipWriter`, `SaveEndpoints` download, `LibraryEditor.Saves`, `GameSaves.Problem`) is then correct for both versions without change.
- **B18 Upgrade on save writes.** New `GameSaves.Upgrade(IReadOnlyList<GameSave> saves, Func<GameSave, Func<Stream>> openLegacy, Dictionary<string, Func<Stream>> added, HashSet<string> removed)` returns the records with `Legacy = false` and `uploadedBy` = `"admin"` (`AdminSeeder.AdminUsername`) when it was null or fails `UsernamePolicy.Validate`, else unchanged (`updatedBy` is left as it is). For each legacy record `r` becoming `n`: if `added` already holds `r.Entry` (the legacy name: a replaced file, or a record carried from another ZIP), that stream is moved to the key `n.Entry`; otherwise `added[n.Entry] = openLegacy(r)` (bytes from the ZIP that holds `r`); then `r.Entry` is added to `removed`. Records not in `saves` (a deleted save) are untouched, so their legacy entry stays in `removed` as today. Callers:
  - `WriteSavesAsync` (add, update, replace, delete): `openLegacy = s => () => zip.OpenEntry(s.Entry, s.SizeBytes)` on the game's ZIP, before `Serialize`.
  - `CarrySaves` (merge, last-release move, B9 rename): the target's own records are upgraded with the target ZIP as `openLegacy`, the carried source records with the source ZIP (their bytes are already in `added` under `carried.Entry`, so the re-key rule applies); for B9 (`target` null) the source ZIP for all.
  So every write that changes saves writes version 2.
- **B19 One-off migration.** New job `SaveFoldersJob` (`JobType.SaveFolders`, label "Moving saves to user folders", outcomes `Moved`, `Skipped`, `Error`), copying `ZipRepackJob`'s per-game loop and write (it already holds the job lock, so it never calls `LibraryEditor`): `LibraryTarget.OpenChecked` (failure → `Error` `ZipUnreadable`), `RomStorage.IsPending` → `Error` `StorageMigrationPending` (that game stays version 1, still readable; its next save write upgrades it), the free-space check (`InsufficientSpace`), `LibraryZipWriter.WriteCheckedAsync` with the game's info.json unchanged (no `Touched`) and the B18 `SavesChange`, `VerifyFailed`/`IoError`, then `mirror.ReplaceAsync`; one job item per game; cancel between games, over every game (`IGameRepository.ListAllAsync`, ordered by `ZipPath`; `GameSaves.Read` only reads the index, and `games.save_count` may be stale) — job total = all games: Absent or version 2 → `Skipped`; Unreadable → `Error` with the read problem (ZIP untouched); version 1 → rewritten with B18 (ownership: existing owners kept, null/invalid → `admin`) → `Moved`. Not cancellable mid-game. Audit: one `SaveUpdated` row per moved game with details "Moved saves to user folders". New `SaveFoldersStarter` (copy of `StorageMigrationStarter`) starts it once the app has started when the setting `saves.folders.migrated` (in `app_settings`) is not `"true"`, retrying every 5 minutes while the job lock is busy; the job sets the setting to `"true"` when it finishes without being cancelled (errors included: those ZIPs are already unreadable and need an Admin's hand, docs/zip-format.md). Registered in `AppHost` like `StorageMigrationStarter` (job `AddTransient<SaveFoldersJob>()`, started with `JobTrigger.Startup`; the audit actor is the job context's). A restore (`BackupService.RestoreAsync`) leaves the flag as the backup has it; a restored `false` reruns the job at the next start, which is harmless (version 2 games are skipped).
- **B20 Visibility unchanged.** Who sees and acts on a save (`SaveViewer`, User Management S1–S6), the per-release limit and every save route and response stay as they are; only entry names and the index version change.

### Battery saves in the player
- **B21 Upload.** The Saves tab upload form already accepts any file as **Battery** (B1 keeps `.sav`/`.srm` as the extension). Add the help text under the Kind radios: "Battery saves from other emulators (.sav, .srm) can be uploaded as Battery." (`form-text`).
- **B22 Auto-load.** When `EmulatorModal` opens without a `save` prop and `batteryExport` is true, it first calls `savesApi.list(gameId)` and picks the first (newest) save with `kind === 'battery'`, `releaseFileName === rom.fileName` (ignoring case) and `uploadedBy` equal to `auth.me.username` (ignoring case); the iframe is rendered only after that lookup (a `Loading` spinner in the frame box meanwhile) with that save as the play URL's `save`. A failed lookup plays without a save (no toast). An explicit `save` (Saves tab "Play with this save") wins. The library save always wins over the player's own in-browser copy (EmulatorJS keeps one per game): an in-browser save from a session whose modal never closed (tab closed) is overwritten without asking, unlike the Saves tab's confirmation "Loading this battery save replaces the in-browser save for this release." (user decision).
- **B23 Auto-store on close.** For a core with `batteryExport`, `EmulatorModal` passes a new `beforeclose` to `ConfirmModal` (Opera keeps `saveBeforeClose`): it asks the player for the battery save (`requestExport(target, 'battery', 5000)`: `requestExport` gains an optional `timeoutMs` (default the existing 30 s `exportTimeoutMs`), and a timeout now resolves the new reason `timeout`, whose `reasons` text for the manual buttons is the `error` text "Couldn't read the save from the emulator.") and, when `ok` and 1 byte–256 MiB, stores it: when the modal was opened with a battery `save` the user owns (B22 auto-load or the Saves tab), it replaces **that** save (`savesApi.replace`); otherwise as **Save battery to library** does (`saveToLibrary('battery')` logic: overwrite the user's newest battery save of the release, else add one named `Battery yyyy-MM-dd HH:mm`). An Admin playing another user's save (Saves tab) gets the latter rule, so it never overwrites someone else's save. Ownership of the played `save` (a `PlaySave` carries only `saveId`/`saveKind`) is checked at store time in the same `savesApi.list(gameId)` result: the record with that id whose `uploadedBy` equals `auth.me.username` (ignoring case); a missing record (deleted meanwhile) falls back to the newest-or-add rule. Success toast "Battery save stored in the library" and `onsaved?.()` (as `saveToLibrary`); `not-started`, `empty` (no save file: most games without battery RAM), `unsupported` and `timeout` (the player never answered within 5 s: not loaded yet or crashed) store nothing silently; any other failure (`busy`, `error`, an API error such as 409 `JobRunning`) shows a warning toast "Couldn't store the battery save" and the modal still closes. While it runs the modal stays open with the close button disabled (`ConfirmModal`'s existing `beforeclose` behaviour).
- **B24** No change detection: each close of a started game writes the save (one ZIP rewrite).

### Screenshot border
- **B25 Trim.** After a screenshot arrives (`screenshot()` in `EmulatorModal`), the PNG is decoded (`createImageBitmap`) onto a canvas and the new pure function `trimBounds(data: Uint8ClampedArray, width: number, height: number): { x, y, width, height }` in `src/lib/emulator.ts` finds the smallest rectangle outside which every row and column is "border": every pixel has `max(r, g, b) <= 16`. Rows are trimmed from the top and bottom, then columns from the left and right, of that rectangle only. An all-border image returns the full image. The trimmed image is re-encoded as PNG (`canvas.toBlob(…, 'image/png')`).
- **B26 Keep border.** When the trimmed rectangle differs from the full image, the preview shows a checkbox `id="screenshot-keep-border"` labelled "Keep border" (unchecked) above the Save/Discard buttons; checking it shows and saves the original PNG. When nothing was trimmed the checkbox isn't shown. **Save as Snap** uploads the shown image (same route and file name `screenshot.png`).
- **B27** A decode or encode failure keeps the original image without the checkbox (no toast).

## Risks
- **Downgrade drops save access:** an older app reads a version 2 `saves.json` as Unreadable (version check), copies `saves/` byte for byte and refuses save routes (`SavesUnreadable`); nothing is lost. Documented under Upgrades.
- **Migration I/O:** B19 rewrites every ZIP that has saves. For embedded systems that's the whole ZIP (ROMs included); free space is checked per game as `ZipRepackJob` does. It runs in the background after startup and holds the job lock, so library edits answer 409 `JobRunning` meanwhile.
- **Rename of a release referenced elsewhere:** bundle queues and collections reference games, not release names; downloads use rom ids. Saves and notes follow (B9). Integrity sees a consistent ZIP + DB after the mirror.
- **Auto-store on close** rewrites the game ZIP at each close (B24); on a large embedded ZIP (N64) that's a few seconds while the modal waits.
- **`viewport-fit=cover`** lets content reach under notches; only the footer (B28) and the sticky navbar are edge elements, and the navbar is not fixed to the top edge in standalone mode (sticky in page flow).

- **Auto-load overwrites the in-browser save** (B22, user decision): a session whose player wasn't closed (tab closed, navigation) never stored its battery save, and the next Play replaces that in-browser copy with the library one. Closing the player (B23) is what keeps progress.
- **`games.save_count`** is not trusted by the migration (B19 reads every game's index), so a stale count can't leave a ZIP on version 1.
