# External ROM storage and Nintendo Switch

## Summary
Disc-era and modern systems (Switch, GameCube, Wii, Xbox 360…) have multi-GB images that can't sensibly live inside a game's ZIP or be read into memory. Each system now declares whether its ROMs are **embedded** in the game ZIP (every existing system: yes) or stored **external**: next to the ZIP, named so they group with it, and pointed at from `info.json`. The ZIP keeps everything else (info.json, images, notes, ratings). Nintendo Switch (`switch`) is the first external system, identified by title ID through [blawar/titledb](https://github.com/blawar/titledb) because libretro has no Switch DAT or thumbnails.

## Out of scope
- GameCube, Wii, Xbox 360 and other large systems (later specs; this one builds what they need).
- Moving an existing system between embedded and external (the flag is fixed per system; no conversion tool).
- Building a ZIP with the ROMs on the fly for "Download ZIP" (decision: ZIP as stored + per-release downloads).
- Decrypting Switch content: no keys; XCI title IDs come only from the file name.
- titledb regions other than `US.en.json`; titledb descriptions (game `description` stays Admin-edited only).
- Nintendo Switch 2: its title IDs (`0400…`, 75 in `US.en.json` on 2026-11-10) are left out of the compact titledb file, so its dumps go to Review (T2, T4); a later spec can add it as its own system.
- Ingesting external-system ROMs from archives beyond today's archive limits (`ArchiveExtractor`: 100 non-directory entries and 256 MiB streamed from recognized ROM entries). Exceeding either limit rejects the archive as `ArchiveUnsafe`. A Switch file in an archive within those limits (e.g. a small DLC) is ingested from its extracted copy (I2, I5).

## Behaviour

### Storage flag
- **S1 Lookup.** `ISystemHandler` gains a required `bool EmbedRomsInZip { get; }` (no default implementation, so every handler states it). All 13 existing handlers return `true`; `switch` returns `false`. `GET /api/systems` adds `embedRoms` (bool) to each entry. `docs/adding-a-system.md` lists every system with its value. NSubstitute returns `false` for an unconfigured `bool`, so the concrete test handlers (`SystemHandlerDefaultsTests.Plain` and both `Headerless` test implementations) return `true`, and every test's `Substitute.For<ISystemHandler>()` (16 files under `tests/`, e.g. `InfoJsonTests`, `LibraryZipTests`, Data's `IntegrityJobTests` and `LibraryMirrorTests`) sets `EmbedRomsInZip.Returns(true)`; without it those handlers would silently become external. All handlers sharing a `Family` must agree on `EmbedRomsInZip`. `SystemRegistry` rejects a mixed family at construction with `InvalidOperationException` naming the family. Ingest and Review select their input mode before DAT or header matching can select another family member.
- **S2 Scope of the storage flag.** External ROM placement, verification, integrity and downloads apply only when `EmbedRomsInZip` is `false`. Embedded releases keep their current storage and downloads. Both storage modes receive schema v4, additive API fields and T8’s format-based image naming.

### External file naming and pointer
- **E1 Name.** An external ROM is the file `<ZipBase>.<rom fileName>` in the ZIP's own folder, where `<ZipBase>` is the ZIP name without `.zip`. Example: `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.zip` and `roms/switch/L/Legend of Zelda, The - Tears of the Kingdom.The Legend of Zelda - Tears of the Kingdom [0100F2C0115B6000][v0].nsp`. The shared `<ZipBase>.` prefix groups the files by name, except when E2 must shorten that prefix to fit.
- **E2 Length and clashes.** The final name, including any clash suffix, is at most 250 UTF-8 bytes (so `<final>.tmp` stays under ext4's 255-byte and NTFS's 255 UTF-16 code-unit component limits). When it's longer, the rom part's stem (before its extension) is cut from its end, at a char boundary (never splitting a surrogate pair), until it fits; the extension is kept. If the rom stem is cut to nothing and the name still doesn't fit (a long multi-byte `<ZipBase>`: `FileNameSanitizer.MaxLength` is 180 chars, up to 540 bytes), `<ZipBase>` is cut from its end the same way. Reserve both the final name and its staging name against files and directories, including destinations already allocated by this write for missing ROMs. For external games use the same UTF-8 component budget when allocating a ZIP name (at most 250 bytes including `.zip` and any clash suffix, before `.tmp`). Use one ZIP-name builder in ingest, title edit, move-to-new-game and the integrity location check. For an external game, title edit decides whether the ZIP path changes by comparing that builder's budgeted base for the old and new titles (case-insensitively, without clash suffix) instead of today's `Sanitize` comparison in `LibraryEditor.PatchAsync`, so a title change that only differs beyond the byte cut keeps the ZIP and its external files where they are (instead of renaming them to ` (2)`). A name is taken (case-insensitive) when a different file or folder already has it, or when a DB row lists it as the `external_file_name` of any game whose ZIP is in that folder, or when the opened destination ZIP already lists it (including a missing file belonging to another release of the same game) (so a game's missing file can't have its name reused by another game, which I6 self-repair would then overwrite; a dotted `<ZipBase>` such as `Mr. Driller` can produce the same name as another game's) → ` (2)`, ` (3)`… before the extension (candidate 1 has no suffix). Rebuild and truncate each candidate with its actual suffix reserved before checking occupancy. Allocate repair backups independently as siblings ending in `.repair.tmp`, fitting the complete name within 255 UTF-8 bytes even for an existing pointer of 255 UTF-8 bytes. Check these candidates against disk entries and other allocations. Implemented once in `Core/Storage/ExternalRomName.cs`. For integrity, accept either candidate 1 or a canonical ` (N)` suffix with N ≥ 2 (ASCII decimal, no leading zeros, within Int32). Compare the actual ZIP name with the whole candidate recomputed for that N, including any further shortening. Keep the existing bucket rule. For a newly allocated external ZIP path, also treat an equivalent full relative path in another game's DB row or another safe on-disk ZIP as occupied under the actual collation of `games.zip_path` (E4). Check before moving any sidecars. This can select a suffix even when neither physical path is an ordinal-ignore-case match.
- **E3 Pointer.** `info.json` **schema version 4**: each Rom gains `externalFileName` (string?, the file name only, resolved in the ZIP's folder). Validator (which now receives an id → `ISystemHandler` lookup instead of the bare id set, since it needs both `EmbedRomsInZip` and `RomExtensions`; `InfoJsonReader` builds it from `ISystemRegistry.All`): for a system with `EmbedRomsInZip = false` it is required; for an embedded system it must be null; when set it is a plain file name (no `/`, `\` or control character, no Windows-invalid characters `<>:"|?*` or DOS device basename: a new public `FileNameSanitizer.IsReservedDeviceName(string name)` tests the part before the first `.`, trimming trailing ASCII spaces, case-insensitively against today's private `Reserved` set plus `CONIN$`, `CONOUT$` and the Windows superscript variants `COM¹`–`COM³` and `LPT¹`–`LPT³`; `Sanitize` keeps its current set, so embedded naming output is unchanged; E2 allocation applies `IsReservedDeviceName` to external ZIP bases, sidecar names and `_removed` destinations and prefixes a match with `_`, as `Sanitize` does), and not `.` or `..`; unlike a rom `fileName`, `..` inside the name is allowed, because `<ZipBase>` is the sanitized title and may hold `...`, e.g. `Oh...Sir!!`), unique case-insensitively within the game, at most 255 UTF-8 bytes, and ends (case-insensitively) with one of the system's `RomExtensions` (so a hand-edited `info.json` can't point a download, move or delete at a ZIP, a `.tmp` or another non-ROM file). The v3→v4 upgrader adds `externalFileName: null`. Register it in `AppHost` alongside the existing v1→v2 and v2→v3 upgraders. Apps before this one treat a v4 file as `InfoJsonNewerSchema` (read-only, existing rule). `identification.method` gains the value `TitleDb` (T4) and image `source` gains `titledb` (T8). A stray `roms/<fileName>` entry for an external ROM is not a validator rule: the writer never writes one (W1) and integrity reports it as `EntryUnlisted` (G1). An external ROM's logical `fileName` also obeys the portable character and device-name checks and ends in a handler ROM extension. It still follows the existing logical-name rule forbidding `..` and fits the 255-Unicode-scalar `roms.file_name` column. The validator also rejects an external ROM whose recorded size exceeds its handler's `MaxRomSizeBytes`, even if the file is missing. A valid external ROM's recorded size still participates in G6 regardless of its current on-disk length. Its disk uses (E1, W5) are independently budgeted by E2. Use one external logical-name allocator in `ExternalRomName.cs` for automatic and Review naming, add-to-game, move and merge. Keep a valid unused logical name verbatim. When generating or adding a clash suffix, reserve the extension, device prefix if needed, and actual clash suffix within 255 Unicode scalars. Truncate only the stem at a scalar boundary and recheck the final name, including collisions after truncation, ordinal-ignore-case against the destination's current and newly allocated logical names. Reserve the generated T5 ID and version tags before truncating a titledb stem. Apply the separate E2 byte budget only to the physical names. Move and merge carry the note under the final logical name; embedded logical allocation keeps its current behavior. Null elements in `roms` or `images` produce `InfoJsonInvalid` in both storage modes. The v3 upgrader adds the field only to object elements of a `roms` array. Leave other shapes for typed deserialization and check for null elements before dereferencing objects in the validator.
- **E4 Database.** Migration `0018_external_roms.sql`: `ALTER TABLE roms ADD external_file_name VARCHAR(255) NULL`. `RomRow`, the mirror and `DbSync` carry it (`NULL` for every existing row; no backfill needed). `GET /api/games/{id}` release rows gain `externalFileName`. Add an `IGameRepository` batch lookup for ZIP-path equivalence under the configured `games.zip_path` column collation. Return groups of input paths and matching existing game IDs, with no .NET approximation of SQL equality. Include all observed ZIP paths and existing row paths in the external DB sync check. When distinct physical ZIPs compare equal in the database and any path belongs to an external system by folder, current metadata or existing row, skip the whole conflicting group as `ZipUnreadable`, preserve any existing mirror rows and let unrelated candidates sync. Keep each physical spelling in the details. When only one ZIP exists but a different mirrored game still owns an equivalent path whose presence cannot be ruled out, preserve that owner and skip the candidate. A safely confirmed absent old spelling keeps existing relocation/replacement behavior. Never let a path conflict reach `LibraryMirror.ApplyAsync`'s path-based delete. Use the same lookup for E2 allocation, including safe disk paths without mirror rows. On one connection, stage the input spellings with their ordinal IDs in a session-local temporary table using batches of at most 500. Group the entire staged set and join existing rows in SQL with the actual database column collation, then return the original spellings. The temporary table's input key is the ordinal ID so equivalent spellings survive staging. Drop it in cleanup. Run this comparison in sync only when at least one observed or mirrored ZIP is external. Preserve exact and ordinal-ignore-case path occupancy checks independently of SQL equivalence.

### Ingest of an external ROM
- **I1 Validation.** Extension and size checks as today (`MaxRomSizeBytes` is a `long`). In `IngestJob.ArchiveAsync`, check an external system’s archive container under the ingest root before calling `ArchiveExtractor.Extract`; an unsafe or inconclusive path or a container that vanished since the snapshot records one `Error IoError` item and does not call `FailFile` or `ApplyFate`. Check extracted entries under the job work root. For an external archive, any entry skipped as `TooRecent` keeps the archive in place, just as Review or Error does, even if other entries committed. For external archives, `ArchiveExtractor` rejects a recognized ROM entry whose normalized archive path exceeds 512 Unicode scalar values or whose basename exceeds 255 (`ArchiveUnsafe` for the container before processing any extracted entry), so the entry path and original file-name columns can store both values. For external entries write to `<entry index>/entry<lower-case ROM extension>` under the checked work directory, exclusively created, so a logical archive name is never used as a physical filename. Keep its original basename and normalized entry path for matching, display and audit. Record the checked archive container's file identity (device/inode on Linux or volume/file ID on Windows), length and mtime before extraction. If length or mtime differs from the ingest listing or the fresh mtime is under 10 s old, record Skipped TooRecent and keep the archive without extracting. Before deletion or any side-folder move, including the rejection and no-ROM branches, recheck the path and snapshot. If absent, unsafe, unreadable or final disposition fails, record an archive-level `Error IoError` item with no archive entry. A confirmed change to a safe container records `Skipped TooRecent`. Preserve the current container on a failed check and keep earlier entry outcomes. The extra item does not increment snapshot progress a second time. Emit a disposition audit only after the operation commits. For the external archive's logical path, perform the rooted-path and traversal checks on normalized separators, independent of platform (leading slash, drive prefix, NUL or any `..` component rejects the archive). Apply filesystem path checks only to the numbered physical extraction target. For external extraction, open the validated archive as a regular-file handle and confirm its identity, length and mtime against the fresh snapshot. Pass that open stream to the ZIP or 7z reader. After extraction and before processing any member or disposing of a rejected archive, recheck the handle metadata and the current path against the snapshot. A safe change yields one Skipped TooRecent item with no committed member releases. A vanished or unsafe path or an open failure yields one Error IoError item, preserves the source, and lets the job continue. Keep ArchiveCorrupt for parser failures after a successful open. Classify failures creating, opening, writing or closing the checked extraction output as `IoError`, not a corrupt input. Return one archive-level Error and preserve the container with no disposition or audit; for Review return `500 IoError` and keep Pending. Enforce streamed extraction limits as `ArchiveUnsafe` as before. External Review uses the same checked extraction and retains Pending, returning 500 IoError for a source-open failure or 500 VerifyFailed for changed bytes. Keep the final disposition recheck for changes while processing already extracted members. Before processing an external snapshot item, require the absolute original source path (the container for an archive) to fit the 1,024 Unicode-scalar source_path columns of job_items and ingest_review_items. If it exceeds that limit, leave it untouched and record one Error IoError item, with the record's source_path truncated at the limit, details stating the limit, and the full path in the log. Do this before extraction, hashing, Review queueing or side-folder disposition. Ingest job work cleanup is best effort, like Review work cleanup. If deleting an owned work directory fails, log it and keep the original job outcome or exception. Never traverse an unsafe replacement work directory during cleanup. An external archive with two recognized members whose normalized full entry paths are ordinally equal is `ArchiveUnsafe` before writing any extracted member. Review reopens by full path. Case-distinct paths and equal basenames in different directories remain distinct.
- **I2 Streaming hash.** The file is never read whole into memory: one streamed read computes CRC32, MD5 and SHA1 together (`NormalizeForHashing` is not called for external systems). `ReadHeader` receives the first `min(size, 1 MiB)` bytes. Cap the actual streamed bytes at `MaxRomSizeBytes`; if the source grows across the cap during hashing, apply the same `TooRecent` rule. Bypass the outer ingest-list age shortcut for external sources. For an external loose item take the fresh regular-file snapshot before size validation and hashing (file identity, length and last-write time). Use the fresh age and size for validation. If its length or mtime differs from the ingest listing, or its fresh mtime is under 10 s old, skip it as `TooRecent` before hashing. After hashing, compare its identity, length and mtime with the fresh snapshot. An archive entry uses the extracted size, skips loose age and mutation checks, and never compares its mtime with the archive's. Recheck the same loose-source snapshot immediately before staging, after target open and media. If identity, length or mtime changed at either check (still being copied in), the item is `Skipped` with reason `TooRecent` (file left in place, picked up by a later run; features.md broadens `TooRecent` to "modified < 10 s ago or changed while being hashed"). Cancellation keeps the documented item boundary: after starting an external loose item, pass `CancellationToken.None` to the entire pipeline and its current-item bookkeeping, including hash, lookups, media and Review updates. Check the job token before starting the next item. The archive already finishes with no cancellation between its entries; embedded loose files retain their current token behavior.
- **I3 Identification, dedupe, review, grouping** follow the existing steps 3–6 (SHA1 dedupe, review lifecycle, identification per the system's DAT source, grouping by system + base title). For an external libretro match, use the DAT ROM stem with the source extension lower-cased for both the stored release and the queued AmbiguousGroup ROM name. Parse the DAT stem for tags as today. For an external family, use only handlers accepting the source extension and actual streamed size for automatic identification and header-based assignment. Keep initial validation against the first extension match as today. If the header identifies an ineligible handler, queue a plausible unmatched input under the ingest-folder handler if eligible, else the first eligible family member. For an external Review DAT selection, reject a same-family handler that cannot store the original extension or verified size as `400 ValidationFailed` for `datSystem` before any write. The embedded family behavior is unchanged.
- **I4 Placement (move with rollback).** The move happens in `PackageAsync`, immediately before the ZIP write: after the target ZIP was opened (`TargetZipUnreadable` / `InfoJsonNewerSchema` leave the source untouched in ingest), the media fetch, and the entry-name clash rename. From the move on, the ZIP write, the mirror and `afterMirror` run with `CancellationToken.None`, so neither a job cancel nor a closed review request can strand the file; any exception from the ZIP write (not only `VerifyFailed`/`IoError`) rolls the move back before it is reported. If staging fails before source removal (`IOException`/`UnauthorizedAccessException`, e.g. disk full during a cross-volume copy), the item is `Error IoError`, the source stays where it was, and a partial `<final>.tmp` is deleted best-effort (else integrity reports it as `OrphanFile`). Use the shared W6 staged move. For a loose source that disappears before placement return `Error IoError`; for an unsafe or non-regular ingest source return `Error IoError` without opening or moving it. External Review resolution checks the loose path or the archive container with the G4 resolver before opening it or deciding the source is missing. Only a genuinely absent source follows `SourceMissing` cleanup. Apply the same distinction to `IngestJob`'s stale Pending cleanup: for external systems prune only a confirmed missing path. Keep and log unsafe paths and inconclusive IO or permission failures. Use the archive container path for archived rows. Add `SystemId` to `PendingReviewSource` and to its `IngestReviewRepository` projection so the cleanup selects the storage mode without guessing from the path. Embedded rows retain their current cleanup. An unsafe or non-regular source (including a directory or dangling link at the recorded path) returns `500 IoError` and keeps Pending. Apply the same external source check to Dismiss and to DeleteSourceAsync. For Delete, an unsafe or inconclusive path returns `500 DeleteFailed`, preserves the source and Pending rows and records no `ReviewDeleted` audit. Confirmed absence still clears all Pending rows for the source without an audit. The extracted entry is checked separately before hashing. If final promotion fails after source removal, roll back from the complete temp. If rollback fails, preserve that temp and return `Error IoError` with its path. Then the ZIP is written (its verify checks the external file, W1), the audit row recorded (right after the ZIP write, before the mirror: existing AU4 order), and the DB mirrored. If the ZIP write fails (`VerifyFailed`/`IoError`), a loose file is moved back to its original ingest path (a ` (2)` name if that path is taken) and the item is `Error` as today. For an archive member follow I5. If the DB mirror or `afterMirror` fails, the ZIP already names the file, so it stays in the library and the item is `DbWriteFailed`. The next ingest or integrity run repairs the mirror from the new or visibly changed ZIP (W1). Competing surviving ZIPs from an edit use W7. DB repair does not reconstruct a failed Review status update. A retry of an archived Review item follows T9; for a loose file, the next ingest removes the stale Pending row, or retry returns `409 SourceMissing` and removes it. Document that the release can already be in the library after this response. If the move back also fails, the item is `Error IoError` with details naming the actual surviving complete-copy path, which can be a temporary file in ingest. Integrity reports an unlisted surviving file only when it is under the library root. A crash during staging can leave `<final>.tmp`, which may be the only complete copy once the source is removed. Integrity reports it as `OrphanFile` (never deleted automatically; `CrashRecovery` deletes only `*.zip.tmp`). A crash after the rename and before the ZIP write leaves `<final>` unlisted, so integrity reports it as `OrphanFile`; for a loose source that file is the only copy (the Admin moves it back to `ingest/<system>/`). Automatic ingest preserves Pending rows on external-source `Error` outcomes, including the unexpected-exception fallback in `IngestJob.ProcessAsync`. Skip `CompleteSourceAsync` on these paths because its Error branch deletes Pending rows. Confirmed absence is handled by stale cleanup. Successful or terminal outcomes retain the existing completion behavior. For external Dismiss, Review Delete and Ingestion-page Delete, finish Pending bookkeeping with `CancellationToken.None` once the filesystem operation succeeds. External writes confirm that an opened target ZIP has the selected mirror row's game ID and system before any sidecar operation. Apply the check to ingest, Review, repair, edits and media retry, and to both source and destination in multi-game edits. A readable ZIP with the wrong identity returns `TargetZipUnreadable` with the source and ZIP unchanged. If verified loose bytes are fully restored under a different ingest name, update any Pending row matching the original loose path and SHA1 to the actual restored path. Do this under JobLock without the caller token, before releasing the item or request. Preserve OriginalFileName and the queued identification. Do not retarget on an incomplete restore or when the restored bytes failed the input check. On retarget DB failure return DbWriteFailed with both paths in the log and the original ZIP failure recorded as context. Leave both occupants untouched and document how to put the recovered copy back at its original path once that path is free. A later re-ingest of a successfully retargeted item matches the queued source instead of sending it to _duplicates.
- **I5 Source deletion.** There is no source left to delete after a successful move (`PackageAsync`'s final `File.Delete` is skipped for external ROMs); an archive entry's extracted copy (in `cache/work/<jobId>/`) is moved the same way. On ZIP-write rollback of an archive member, recheck the extraction-time container snapshot from I1 at the original path before discarding the moved copy. Do this in both ingest and Review, including archive-based self-repair. If the original container still matches, delete only the owned moved copy (W6). If the container is absent, changed, unsafe or unreadable, preserve the verified moved copy at its library path as an orphan. In self-repair that path is already listed by the original ZIP. First move the incoming copy to a new E2-allocated unlisted sibling with the same ROM extension using W6, then restore the owned repair backup to its original path if there is one. If moving the incoming copy to the orphan name fails, keep the verified incoming copy and the repair backup at their surviving paths and report both without overwriting either. Keep the original failure code, log the surviving path and include it in the ingest item details. Preserve any replacement container. Admin recovery moves the orphan back to the system's ingest folder when it is needed. Pass the snapshot from the extractor through the member context to the common rollback; never infer that the archive still holds those bytes from a successful extraction alone.
- **I6 Self-repair.** SHA1 dedupe stays global across systems. If the incoming and owning handlers use different storage modes, take the existing `Duplicate` path, even when the owner has an open self-repairable issue. Do not use raw external input to rebuild an embedded ROM or move an embedded source whose normalized bytes may differ from its on-disk bytes. A byte-identical external file whose external destination has an open `EntryMissing`, `EntrySizeMismatch` or `HashMismatch` issue is moved into place over `<externalFileName>` (same tmp + rename) and the ZIP rewritten (`Repaired`, existing rule D30). If the owned path already contains a file, first rename it to a reserved `.repair.tmp` sibling. Keep it until the ZIP commits. On placement or ZIP-write failure restore both the old library file and the incoming source; on ZIP commit delete the backup best-effort (any leftover is `OrphanFile`). Use the opened ZIP’s ROM with the same SHA1 as the repair target. If it is absent or its pointer differs from the mirrored one, return `Error TargetZipUnreadable` with stale mirror details and leave both files untouched; the next ingest or Integrity can reconcile the mirror. The open issues are looked up with entry name = the `externalFileName` (G1's key), not `roms/<fileName>`, and a `Duplicate`'s details read `same as <zip> › <externalFileName>`. Use a separate external lookup on `IIntegrityIssueRepository` that returns candidate open self-repairable issues with the stored path, pointer and GameId. Before repairing or resolving any issue, match both path and pointer ordinally ignoring case and require a matching GameId when present. The table's accent-insensitive collation may return a candidate for a different file. Keep the embedded query unchanged.
- **I7 Audit.** `Ingested` / `ZipRepaired` rows as today; details remain `release <fileName>` for normal ingest, `review resolve (<action>)` for Review, and null for `ZipRepaired`, as in AU4. Use the stored ROM name for normal ingest (an external ROM has no ZIP entry). The target path is the ZIP's. Today's `entries.Keys.First(k => k.StartsWith("roms/"))` would throw for an external ROM, so `PackageAsync` takes the release's `fileName` as a parameter instead.

### Library writes
- **W1 Writer.** `LibraryZipWriter` writes no `roms/` entry for a ROM with `externalFileName` and doesn't copy one; its verify checks, for each external file this write placed or renamed (ingest I4, self-repair I6, W2–W4; passed to the writer as `LibraryZipChanges.ExternalFiles`, a new optional last record parameter `IReadOnlyDictionary<string, ExternalFileSnapshot>? ExternalFiles = null` keyed by `externalFileName` ordinal-ignore-case, null = check none), that `<zip folder>/<externalFileName>` matches the W6 promotion snapshot and has length `metadata.sizeBytes` (no rehash; the bytes were hashed at ingest). Recheck each touched sidecar's snapshot just before every ZIP publication attempt, including retries. A missing or changed sidecar yields `VerifyFailed` and rolls back only copies still owned by the operation. External files the write didn't touch aren't checked, so metadata edits that leave the ZIP path unchanged, ratings, notes, adding another release and repairing another file still work. A write that renames a present wrong-length file fails verification and rolls back; integrity keeps reporting the bad file (G1). The writer has no system registry: it treats a game as external when its roms carry `externalFileName` (the validator makes that all-or-none per system), and a write as a rebuild at the current path when `existing` is not null and `Path.GetFullPath(existing.Path)` equals `Path.GetFullPath(target)` (ordinal-ignore-case); every other external write publishes a new path. For an external system open the ZIP temp with `FileMode.CreateNew`, and clean it up only if this write created it. An occupied temp yields `IoError` with the original ZIP and occupant intact. Publish a new external ZIP path with no overwrite, including a rename to a new ZIP path. Check the destination again for case-insensitive occupancy before publication and use the no-replace primitive for the final rename. Only a write rebuilding the ZIP at its current path uses replace. If another file takes the newly allocated path before publication, return `IoError` and undo placed ROMs. Notes for external ROMs are kept as today (`notes/<fileName>.md` inside the ZIP). No caller passes a `roms/<fileName>` new entry for an external ROM: ingest (`NewGameAsync`, `AddToGameAsync`), self-repair (`DuplicateOrRepairAsync`), move release and merge add one today, and the writer rejects a new entry `info.json` doesn't list with an `ArgumentException` that no caller catches. For an external same-path rebuild, make the staged ZIP's whole-second mtime strictly greater than the existing ZIP's before publication if their sizes are equal and the staged timestamp is not later. Set it to the existing whole-second mtime plus one second and re-stat the temp; if the filesystem cannot represent a later timestamp, fail with IoError before replacing the ZIP. This keeps app writes visible to DbSync after a mirror failure even when the compressed size is unchanged. For an external ZIP opened for writing, record its regular-file identity, length and mtime from the open handle. Immediately before each same-path replacement attempt, including every retry after a sharing failure, compare those facts with the current file at the checked path. If they differ or the path vanished or became unsafe, return IoError, leave the occupant alone and use the pre-commit rollback. The writer closes its own handle before replacement as today. For post-commit ZIP cleanup in W2–W5 and undo in W3, use the same snapshot check against the ZIP intended for deletion or replacement. Capture the staged ZIP snapshot before its final rename and return it to every checked write caller for mirror stamping and to W3 for undo, so undo never takes the identity of a new occupant from a fresh unverified lookup. For a checked write, build the mirror entry's size and whole-second mtime from the published ZIP snapshot. Do not take the stamp from a fresh FileInfo of the destination. Before mirroring, if the current path no longer matches the published snapshot, report DbWriteFailed and leave the committed filesystem state for reconciliation. If a published path has been replaced, skip old ZIP deletion in W2-W4, preserving the original recovery metadata. Recheck the target publication again immediately before old ZIP deletion. If it changed after the mirror check, keep the mirror result and log both paths for W7 recovery. Ordinary DB failures still use the cleanup order in W3 and W4. On an unsuccessful W4 result, expose whether the target publication was lost to ReportEndpoints via an init-only bool TargetPublicationLost on LibraryEditResult (default false). - **T4 Matching.** For a `TitleDb` system, step 4 takes the title id from the header field `titleId`, else from the first match of `\[(0100[0-9A-Fa-f]{12})\]` in the file name (upper-cased). A ticket's name carries the content's own id (the update or DLC id, not the base's; [blawar/nut’s PFS0 parser](https://github.com/blawar/nut/blob/master/Fs/Pfs0.py) and [ticket reader](https://github.com/blawar/nut/blob/master/Fs/Ticket.py)), which is what the kind rule below needs. A header id that isn't `0100…` (e.g. a Switch 2 `0400…` ticket) has no titledb entry (T2), so it goes to Review like a file-name id that doesn't match. The entry kind comes from the unsigned 64-bit hex ID: base = id with the low 13 bits cleared; `id == base` → base game, `id == base | 0x800` → update, otherwise apply the DLC and delta cases below. A base game matches when `ByTitleId(id)` exists. An update or DLC matches when `ByTitleId(base)` exists (the DLC's own entry, when present, gives its name). No title id, unsupported kind, or no required entry → Review `NoDatMatch` with file-name suggestions, subject to the existing `InvalidHeader` check for an unmatched non-plausible header. Skip the family’s usual fallback extension rename for external handlers so Review retains the original `.xci`, `.nsz` or `.xcz` extension. `identification` = method `TitleDb`, `datName` `titledb`, `datVersion` the manifest version, `datGameName` the base game's `GameName`. The kind rule matches titledb's data (every base id has its low 13 bits clear, every DLC id has bit 12 set and its base present) and nxdumptool's `title.h` (patch = application + 0x800, add-on content = (application & ~0xFFF) + 0x1000 + index); switchbrew doesn't state it. For an ordinary DLC use `base + 0x1001` through `base + 0x17D0`. For a data patch subtract `0x800`, verify the result is in that DLC range, and use the underlying DLC's titledb name when present while keeping the input ID in the file name. The maximum DLC index is 2000, so `01000000000117D0` patches to `0100000000011FD0`, within the same application bucket. An application delta is exactly `base + 0xC00`; flag and rank it as DLC, name it from the base with ` (DLC)` appended, and retain the delta ID in the filename. Other low-bit patterns go to `NoDatMatch`. See [nxdumptool title helpers](https://raw.githubusercontent.com/DarkMatterCore/nxdumptool/rewrite/include/core/title.h). Step 6 grouping uses the T5 base title (not `NoIntroName.Parse(GameName)`). An `AmbiguousGroup` review row of a `TitleDb` system stores, besides today's `datName`/`datVersion`/`datGameName`/`romName` (the T5 file name), the `titleId`; it also stores the computed base title, regions, languages, revision and flags in `DatIdentification`, serialized camelCase like today's fields as `titleId` (string), `baseTitle` (string), `regions` and `languages` (string arrays), `revision` (string or null) and `flags` (string array). Libretro rows keep only today's four fields; `types.ts` adds the six as optional properties of `datIdentification` (step 27). `Attach` (flag `None`) uses those queued values, ROM name and DAT version (method `TitleDb`), preserving the release identity across a DAT refresh. Use current metadata from the queued base ID when available, else `DatMetadata.Empty`.

The Insult Simulator` → `Oh…Sir! The Insult Simulator [<TitleId>][v0].nsp`; the game title keeps `...`), where `N` is the first case-sensitive `[v<ASCII digits>]` in the ingest file name parsed as UInt32 and formatted in invariant decimal without leading zeros; no match or overflow → `0`; an update with no entry uses the base name; a DLC with no entry of its own uses `<base name> (DLC)`. `revision` = `v<N>` when `N > 0`, else null. `flags` = `Update` or `DLC` for those kinds. `regions` = []; `languages` = the codes of the same titledb entry used for the release name, or the base entry when the name falls back to it. ## Risks
- **Partial moves.** A crash between file rename, ZIP write and DB commit can leave a file under the wrong name. Integrity reports missing pointers and unlisted files within the library. For an interrupted delete, also check `ingest/<system>/_removed/` for the moved file or its staging copy.
- **Long ingest items.** Hashing a 30 GB file takes minutes and holds the job lock; Cancel stops after the current item, as documented, so a cancel can wait for one long hash. A Switch file waiting in Review stays in `ingest/switch/` and, like every pending source (existing lifecycle), is hashed again by every Import all; Import selected (IN1) avoids that. Disk space: the move needs no extra space on the same disk, the file's size on another. Review resolution and edits run inside the HTTP request, so a cross-volume move or a long re-hash can outlast a proxy timeout: they run without the request's token (T9, W6) and deployment.md tells Admins to raise the proxy's read timeout.
- **titledb is a third-party JSON** (~90 MB): parsed with size caps, unknown fields ignored, URLs allowed only from one https host, image bytes still go through the existing caps and magic-byte checks.
- **Title-ID-only matching** can put a mislabelled file (wrong `[TitleId]` in its name) under the wrong game; the release keeps `originalFileName`, and move/delete fix it.
- **A 14th system breaks existing tests** (`DatsMissing`, counts, orders): fixed in the registration step.
