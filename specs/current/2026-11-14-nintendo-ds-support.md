# Nintendo DS support

## Summary

Admins can import Nintendo DS cartridge dumps into the library. The app stores each release inside its game's ZIP and offers browser play through the existing release player.

## Out of scope

- DSiWare support, DSi-mode execution, DS Download Play, multiplayer, and BIOS or firmware configuration. The DS unit code is informational for archival import. A DSi-enhanced cartridge may run in DS mode. Import eligibility does not establish that a cartridge can boot.
- Changes to the shared input archive limits, emulator version, or storage format. Writing ROM entries above 128 MiB with a faster Deflate level (Step 3) does not change the format.
- Touch-screen devices. Play accepts pointer (mouse) input as the stylus. Finger input on a touch device is not verified (see Open decisions and verification).

## Behaviour

- **B1. Import and storage.** Add `NintendoDsHandler` with `Id` `nds`, `DisplayName` `Nintendo DS`, `ShortName` `DS`, `Family` `nds`, `RomExtensions` `[".nds"]`, `MinRomSizeBytes` 512, `MaxRomSizeBytes` 536,870,912 (512 MiB, inclusive), `DatName` `Nintendo - Nintendo DS`, `EmbedRomsInZip` true, the default `DatSource` (Libretro), `DatFolder` (`no-intro`) and `MetadatKinds` (all four), `FileSets` false and the identity `NormalizeForHashing`. Accept case-insensitive `.nds` from `ingest/nds/`, loose or inside ZIP or 7z archives. The existing input archive caps still apply. They allow at most 100 non-directory entries, including skipped entries, and at most 256 MiB of combined extracted supported ROM bytes. Exceeding either cap fails the archive with `ArchiveUnsafe`. Supported dumps larger than 256 MiB must be imported loose. This includes the 30 entries of exactly 512 MiB in the 2026.10.07 DAT. Skip other archive member extensions. Reject unsupported loose extensions as `UnsupportedType`. Reject out-of-range loose sizes as `TooSmall` or `TooLarge`. Hash and store the original bytes in the game's ZIP, using the standard embedded release naming and `info.json` fields. Import and Review require Admin. Any signed-in user, with or without a role, can download the ROM through the standard attachment route. That route streams the ZIP entry as `application/octet-stream` with the stored file name. It ignores `Range` and sends the full entry with 200. Use the existing download errors and password-change gate.
- **B2. Identification.** Use libretro's No-Intro `Nintendo - Nintendo DS` DAT for SHA-1 identification. Use its `releaseyear`, `developer`, `publisher` and `genre` metadat for optional CRC32-based enrichment. Filter the DAT to `.nds` before indexing hashes, DAT search, suggestions and base titles. The DAT also lists `.bcn`, `.bin` and `.ids` entries. Keep the standard release naming, grouping and media lookup by DAT game name. Deduplicate by SHA-1 across the whole library before the header or DAT decision, as the existing global step 3 does (`IngestPipeline.IdentifyAsync`). On upgrade the app starts and creates the DS folders. **Admin → DATs → Refresh DATs** supplies the five required files. Until all five pass cache validation, every import request returns HTTP 409 `DatsMissing` without creating a job. This includes a selection that contains only other systems' files. An empty valid catalog is sufficient.
- **B3. Header and Review.** `ReadHeader` returns null for spans shorter than 0x160 bytes. Text fields keep bytes 0x20–0x7E and turn every other byte into `?`. `title` is the 12 bytes at 0x00 up to the first NUL, with trailing spaces trimmed and an empty result stored as null. `gameCode` is the 4 bytes at 0x0C and `makerCode` the 2 bytes at 0x10, kept whole with no trimming. `unitCode` (0x12) and `romVersion` (0x1E) are unsigned bytes. `headerChecksumValid` is the result of the CRC check below, following the GBA field name. Expose these six fields in the existing header view and classify the header as `nds`. The CRC is CRC-16 with initial value 0xFFFF and reflected polynomial 0xA001, over bytes 0x000–0x15D, compared with the little-endian value at 0x15E. On a mismatch, mark the header implausible, so an unmatched ROM is filed as `InvalidHeader`. A DAT hit remains authoritative. An unmatched ROM with a valid CRC enters Review, and its internal title can supply suggestions. Resolve it through the existing manual or DAT-selection workflow. That workflow reverifies the pending source hash before saving and leaves a changed source pending on verification failure.
- **B4. Browser play.** Expose `desmume` for eligible DS releases in the existing game detail Play dialog and library Quick Play. Use the existing embedded-release eligibility. Fetch the selected embedded ROM through its authenticated attachment route. Use the local non-threaded EmulatorJS 4.2.3 payloads and report pinned in [Pinned DeSmuME files](#pinned-desmume-files), never the CDN. Keep the generic `nds` control scheme and settings key, and pin the concrete core `desmume` before any saved `retroarch_core` is read. Hide the Core and Threads settings. Never select a `-thread` payload, even when `SharedArrayBuffer` exists and the saved settings enable threads. Never set `EJS_biosUrl` or external files for DeSmuME. The pinned core uses its built-in BIOS and firmware whenever the external files are absent, including when saved settings enable `desmume_use_external_bios` (see Decisions). Keep browser-local battery saves, per release file name, written at the existing 30-second interval. DeSmuME exposes no `RETRO_MEMORY_SAVE_RAM` (`retro_get_memory_data` in `libretro.cpp`). It writes its own `<release name without extension>.dsv` into the save directory, `/data/saves` (`PathInfo::LoadModulePath`, `BackupDevice` in `mc.cpp`), and keeps that file open. EmulatorJS mounts `/data/saves` as IDBFS with `autoPersist`, which the payload's glue persists only when a modified file is closed or the folder changes. EmulatorJS 4.2.3 never calls `FS.syncfs(false)`: the call in `GameManager.saveSaveFiles` is commented out. So Step 8 adds a guarded vendor edit: for `desmume`, `saveSaveFiles` also calls `this.FS.syncfs(false, …)`, and the 30-second interval then persists the open `.dsv`. EmulatorJS's save-file export and import buttons use RetroArch's SRAM path (`save_file_path`), which DeSmuME never writes, so they are hidden for DS (see Decisions). Set these defaults through `EJS_defaultOptions`, alongside the existing `save-save-interval`:
  - `desmume_screens_layout: 'top/bottom'`, so both screens show with the lower screen below. This is also the core's default and is set to be explicit.
  - `desmume_pointer_mouse: 'enabled'` and `desmume_pointer_type: 'touch'`, so a pointer press acts as a stylus press at that position on the lower screen. The core's default type is `mouse`.
  - `lockMouse: 'disabled'`. The payload's `core.json` has `options.supportsMouse: true`, which EmulatorJS copies into `enableMouseLock` when the core loads. That turns on pointer lock when the canvas is clicked. `setupSettingsMenu` applies `EJS_defaultOptions` after the core loads, so this default wins unless the viewer saved another value.

  Saved per-game settings override these defaults, as for every core. On a viewer's first launch of a release, no settings key exists yet. The runtime then applies these defaults through the settings menu after the core starts, not through the boot-time core options file. The pointer options are read on every option update, so they take effect on that first launch. Step 11 tests both the first launch and a launch with saved settings. The DS core streams the ROM from EmulatorJS's in-memory file unless a viewer enables `desmume_load_to_memory`, which defaults to `disabled`. The browser size gate measures the default.

  See Verification gates for large-ROM playback and distribution.

## Risks

- **Server memory.** Embedded import and Review hold one full ROM in memory, up to 512 MiB, while hashing and writing the ZIP. Today both paths copy it again, and Review also grows a `MemoryStream`. Deleting a release also buffers the whole entry before writing the `_removed/` copy (`LibraryEditor.CopyToRemoved`). Steps 1 and 2 leave one ROM-size array for import and Review, and none for deletion. Downloads, moves, merges, ZIP rewrites and integrity hashing already stream. Step 7 measures and documents peak memory.
- **ZIP rewrite time and disk.** Every library ZIP write re-deflates every entry with `CompressionLevel.Optimal` and then re-reads each ROM to check its SHA-1 (`LibraryZipWriter.WriteTmpAsync`, `CopyEntryAsync`, `VerifyAsync`). This happens for new releases and for note, image, metadata, move and delete edits. A DS game with several 512 MiB releases therefore re-deflates gigabytes for a one-line note, and the job lock stays held throughout. Step 3 writes ROM entries above 128 MiB at `Fastest` to cut the CPU time (see Decisions). It still inflates, deflates and re-hashes every entry. The temporary ZIP is written beside the original, so a write needs free disk space at least equal to the new ZIP. A delete also needs space for the `_removed/` copy. Step 7 measures time, memory and disk.
- **Browser memory.** The player buffers the response as a `Blob`. EmulatorJS then reads it into an `ArrayBuffer` and copies it into the emulator file system. The browser size gate measures this separately.
- **Distribution.** The payloads carry no licence text, so the app must ship the notices itself. The source revisions are verified above. The remaining gate is the notice set (see Verification gates).

## Decisions

- 2026-11-14 Embedded storage → keep the DS ROM bytes inside each game's ZIP (user).
- 2026-11-14 DS input → accept `.nds` only, with the existing shared input archive limits and loose import through 512 MiB. The 2026.10.07 DAT has 7,554 ROM entries: 7,471 `.nds` from 128 KiB to 512 MiB, 30 of them exactly 512 MiB, plus 55 `.bcn`, 23 `.bin` and 5 `.ids` (code and No-Intro DAT).
- 2026-11-14 Embedded read memory → reuse the original byte array when importing or resolving unchanged large dumps and verify both entry points (reviewer).
- 2026-11-14 Release deletion memory → stream `LibraryEditor.CopyToRemoved`, which today buffers the entry twice. This applies the embedded read memory decision to the one remaining whole-ROM buffer that a 512 MiB release reaches (reviewer, code).
- 2026-11-14 Browser engine → pin DeSmuME from EmulatorJS 4.2.3 and keep the generic DS controls. Use only the packaged non-threaded assets.
- 2026-11-14 BIOS and firmware → no app override. In DeSmuME `c6317a4`, `desmume_use_external_bios` is read only at first boot. When it is enabled, `PrepareBiosARM7`/`PrepareBiosARM9` mark a BIOS as loaded only after reading the file, and fall back to HLE otherwise. External firmware loads only when both BIOS files loaded (`NDSSystem.cpp`). The player never supplies those files, so a stale enabled setting still boots on the built-in BIOS and firmware. E2E seeds that setting before its second launch to prove it (upstream source, reviewer).
- 2026-11-14 Pointer defaults → `desmume_pointer_type` defaults to `mouse` (a relative cursor) in `libretro_core_options.h`, so set `touch` for absolute stylus positions. It is read on every option update, so the runtime default applies. Disable `lockMouse`, which the payload `core.json`'s `options.supportsMouse: true` otherwise enables (upstream source, pinned runtime).
- 2026-11-14 Header fields → add `headerChecksumValid`, following GBA, so a DAT-matched release with a bad CRC shows why (reviewer).
- 2026-11-14 Upgrade → retain the existing global DAT preflight and require all five DS catalog files. Keep Basic and Full ROM counts unchanged.
- 2026-11-14 Browser size → measure the supported Chromium baseline. If reliable 512 MiB playback fails, enforce the largest validated size for Play and retain the 512 MiB import and download limit (user).
- 2026-11-14 Distribution → hold browser play until both package variants are tied to exact corresponding source and redistribution notices (user). The revisions are now verified from the binaries and public repositories ([Pinned DeSmuME files](#pinned-desmume-files)). Only the notice set remains (reviewer).
- 2026-11-14 Runnable fixture → add an original homebrew DS cartridge, built with a pinned devkitPro image and committed with its source and library notices. E2E checks guest output on both screens, stylus input and save persistence. This differs from earlier browser-play specs, which checked only launch routing and assets. It is the only automated proof that the core runs, and the browser size gate needs a cartridge that boots (user).
- 2026-11-14 E2E input → assert stylus input with a pointer (mouse) click, which `desmume_pointer_type: 'touch'` maps to an absolute press. Finger input on a touch device is not tested (reviewer).
- 2026-11-14 Deletion copy failures → errors reading the ZIP entry, including an `IOException` that escapes today, are `VerifyFailed`. Destination errors are `IoError`. Both delete the partial `_removed/` file. A cleanly read entry with a different SHA-1 is still copied with a warning, as today (third review, code).
- 2026-11-14 Changed source during the bounded read → ingest returns `Error` `IoError` and leaves the file in place. Review returns `VerifyFailed` and keeps the item `Pending` (third review, code).
- 2026-11-14 Registration → register DS after Saturn, so it is last in registry order. The menu, README and `/api/systems` order by display name, so DS appears between Nintendo 64 and Nintendo Entertainment System (third review, code).
- 2026-11-14 Large-ROM measurement inputs → the seed CLI gains `--nds-generate` and `--nds-dat`. The Step 7 run uses them in the E2E compose stack. Step 10's E2E staging reuses `--nds-dat` instead of a separate mode. Step 7 also measures elapsed time, disk headroom and a note edit on a game with a 512 MiB release (third review).
- 2026-11-14 ZIP rewrite cost → every library ZIP write re-deflates every entry, so edits to a game with 512 MiB releases are slow and hold the job lock. `LibraryZipWriter` writes ROM entries larger than 128 MiB (`LibraryZipWriter.FastCompressionAboveBytes`) with `CompressionLevel.Fastest`. Everything else keeps `Optimal`. Every existing embedded system's maximum is at most 64 MiB plus 528 header bytes (NES), so only DS entries change. Entries stay Deflate, and existing ZIPs stay readable. A large entry is re-written at `Fastest` on the next write of its ZIP. Verification still re-reads every ROM. The other options considered were accepting the cost (recommended by the reviewer) and storing DS entries uncompressed (user).
- 2026-11-14 E2E pixel checks → sample a quarter point of each screen inside the located guest frame, not the centre. EmulatorJS letterboxes the frame. The core can draw a white cursor around the touch point, although in `touch` mode a press does not refresh it (fifth review). The fixture's colours are named once and kept clear of black and white (third review, upstream source).
- 2026-11-14 E2E launch order → the first launch runs with no saved settings and proves the stylus defaults. The second launch runs with stale saved settings (`melonds`, threads, external BIOS) and proves the core pin, the thread guard, the BIOS fallback and save persistence. EmulatorJS 4.2.3 writes the boot-time core options file only when a settings key exists, so a seeded first launch would never exercise a fresh viewer's runtime default path (fourth review, pinned runtime).
- 2026-11-14 System colour → DS gets its own badge colour token like every shipped system, and keeps the controller icon fallback (fourth review, code convention).
- 2026-11-14 DS battery saves → add a guarded `GameManager.saveSaveFiles` edit that calls `FS.syncfs(false)` for `desmume` only, so the existing 30-second interval persists DeSmuME's open `.dsv`. Hide EmulatorJS's save-file export and import buttons for DS, because they read and write RetroArch's SRAM path, which DeSmuME never uses. Without the edit, IDBFS `autoPersist` would persist the file only when it closes, and closing the dialog would lose the save. The other options were verifying first and editing only on failure, and documenting DS saves as unverified (user, fifth review, upstream source and payload glue).
- 2026-11-14 Step size → split the original Step 1 (bounded reads, the streamed deletion copy and ZIP compression) into Steps 1–3. Each is an independent commit with its own tests, within the spec skill's ~300-line step size. The later steps are renumbered 4–11 (fifth review, `.claude/skills/spec/SKILL.md`).
- 2026-11-14 E2E job lock → the DS E2E test waits for `GET /api/jobs/current` to return 204 before and after its import. The preceding test's restore leaves an import job running, and a second start returns 409 `JobRunning` (fifth review, code).
