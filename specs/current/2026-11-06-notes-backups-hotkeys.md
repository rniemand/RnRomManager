# Release notes, DB backups and hotkeys

## Summary
Five changes in one branch: the Game page shows each release's original ingest file name and lets any signed-in user keep a Markdown note per release (stored in the game's ZIP under `notes/`); the app backs up its database daily to `Paths:Backups`, keeping the last N, with an Admin page to configure it and a startup restore (`Backup:RestoreFrom`); users can view and rebind global hotkeys from a navbar (?) button, with four new navigation hotkeys; the navbar becomes sticky.

## Out of scope
- No change to how `originalFileName` is recorded: it already exists on every ROM in `info.json` (required since schema v1, set by ingestion and review resolution from the ingest name and kept through moves and merges), in `roms.original_file_name` and in `GET /api/games/{id}`. Existing ZIPs already have it, so no backfill.
- No `info.json` schema change: notes are found by entry name, not listed in `info.json`.
- Notes are not searchable, not audited, not in the DB, and not shown in the library list.
- Backups cover the database only, not the library ZIPs, ingest or cache. No backup download/upload in the UI, no off-site copy, no restore from the UI.
- No hotkeys beyond the five listed actions; no per-page hotkeys.

## Behaviour

### Original file name
- **B1** On the Game page Releases tab, a release whose `originalFileName` differs from `fileName` (ordinal) shows a second line under the file name: `small text-body-secondary text-truncate` "Original: <originalFileName>", with the full name as `title`. Equal names show nothing extra.

### Release notes
- **B2** A release's note is the ZIP entry `notes/<rom fileName>.md` (e.g. `notes/Tetris (World) (Rev 1).gb.md`): UTF-8 without BOM, at most 64 KiB (65,536 bytes), Markdown. A release has a note iff that entry exists (ordinal name match, like every ZIP entry lookup).
- **B3** `GET /api/games/{id}` adds `hasNote: bool` to each release, read from the ZIP's entry names (one ZIP open per request). A ZIP that can't be opened reports `hasNote: false` for every release (logged at Warning) and the endpoint still returns 200.
- **B4** `GET /api/games/{id}/roms/{romId}/note` → `200 text/markdown; charset=utf-8` with the note; `404 NotFound` when the game, the release or the note doesn't exist. Read through `LimitStream` (64 KiB cap; over it → `409 NoteTooLarge`, added to `LibraryEndpoints.ToProblem`'s 409 list). An unreadable ZIP → the existing `TargetZipUnreadable` mapping; a newer-schema ZIP is still readable (GET only reads the entry).
- **B5** `PUT /api/games/{id}/roms/{romId}/note` body `{ "text": string }` → `204`. `text` is normalised to `\n` line endings first; empty or whitespace-only → the note is deleted (same as B6; `204` even when there was none). More than 65,536 UTF-8 bytes **after normalisation** → `400` with field error `text`. Missing/non-string `text` → `400` field error `text`.
- **B6** `DELETE /api/games/{id}/roms/{romId}/note` → `204`, or `404 NotFound` when there's no note.
- **B7** B4–B6 are open to **any signed-in user** (like ratings), not audited (logged at Info with user id, game id and entry name). PUT/DELETE take the job lock and rewrite the ZIP through `LibraryZipWriter` like every edit: `409 JobRunning` when busy, `409 InfoJsonNewerSchema` for a newer-schema ZIP, `404 NotFound` for an unknown game/release, the existing `VerifyFailed`/`IoError` mappings otherwise. The write goes through `LibraryEditor`'s normal write + mirror path, so `games.zip_size_bytes` / `zip_mtime_utc` (and `info_schema_version` for an older ZIP, which is rewritten in the current schema as on any write) are updated and the next DbSync/quick check doesn't see a changed ZIP. The game's fields, including `metadata.updatedAt`, are left as they were: a note is not a game edit.
- **B8** Every ZIP write keeps notes: for each ROM listed in the **new** `info.json`, `notes/<fileName>.md` is copied from the existing ZIP when present, unless the write replaces or removes it. A note whose ROM is no longer listed is dropped (so deleting a release, or the whole game, deletes its notes). A copied note over 64 KiB fails the write as `VerifyFailed` naming the entry.
- **B9** Moving a release to another or a new game carries its note: the note is written into the target under the release's final file name (after a ` (2)` clash rename) and dropped from the source. Merging a game carries every source release's note the same way. A release that arrives in a ZIP (move, merge, ingest, review resolution) **without** a note never adopts an orphan `notes/<its name>.md` already in that ZIP: the writer's caller puts that entry in `RemovedEntries`.
- **B10** Integrity's `EntryUnlisted` check ignores `notes/<f>.md` for every `f` listed in `roms`; any other `notes/` entry (an orphan) is still reported as `EntryUnlisted` (Warn), and left alone.
- **B11** On the Releases tab each row gets a note icon button (`btn-sm`, `aria-label` "Note for <fileName>" / "Add note for <fileName>"): a filled note icon when `hasNote`, an outline one otherwise. It opens one `ConfirmModal` (`size="lg"`) titled "Note — <fileName>". Layout (no second modal is ever opened):
  - A `btn-group` at the top of the body: **View** / **Edit** / **Preview** (radio-style buttons). View is the default when a note exists (fetched with B4); Edit when there's none (View is then disabled).
  - **View** and **Preview** render the Markdown with `marked`, sanitised with `DOMPurify` before `{@html}`; links get `target="_blank" rel="noopener noreferrer"`. Preview renders the textarea's current text.
  - **Edit**: a `textarea` (monospace, 12 rows) with a live byte counter "n / 65,536 bytes" (UTF-8, after `\r\n`→`\n`), red and Save disabled over the cap.
  - The modal's confirm button is **Save** (`onconfirm`, sends B5), enabled only when the text changed. A **Delete note** `btn-outline-danger` sits at the bottom left of the body when a note exists; clicking it swaps it for an inline "Delete this note? **Yes** / **No**", and Yes sends B6.
  - Save and Delete refresh the release's `hasNote`, show a success toast and close the modal. `409 JobRunning` → `toasts.jobRunning`; other errors show `ErrorAlert` inside the modal and keep the text.
  - Closing the modal (Cancel, ×, Escape) discards unsaved edits without a prompt, like every other edit modal.
  - Save's enabled state uses a new `ConfirmModal` prop `confirmDisabled?: boolean` (default `false`; the button is disabled when `busy || confirmDisabled`), also used by B25.
- **B12** Deleting a release in the Game admin modal says "…and its note" in the confirmation when that release `hasNote`; deleting the game says "…and its notes" when any release `hasNote`.

### Database backups
- **B13** A backup is a ZIP `rnrommanager-<yyyyMMdd-HHmmss>.zip` (UTC time of the start) in `Paths:Backups` (new, default `/app/backups`, validated and created like the other paths). Written to `<name>.tmp` and moved into place only when complete. Contents:
  - `manifest.json`: `{ formatVersion: 1, backupId: GUID, createdAt (ISO UTC), appVersion, database, migrations: [script names from schema_versions, in order], tables: [{ name, rows }] }`.
  - `schema.sql`: `SHOW CREATE TABLE` for every base table of the configured database, in name order, each followed by `;`.
  - `data/<table>.jsonl`: one JSON object per row, column name → value: `null`; numbers; `true`/`false` for `TINYINT(1)`/`BOOL` (MySqlConnector reads them as `bool`); strings, including `CHAR(36)` GUIDs (read as `Guid`, written as lowercase `D` format); `DATETIME`/`TIMESTAMP` as ISO-8601 UTC strings; any binary/blob column as `{ "$b64": "…" }` (no current table has one; kept so a future column can't break backups). Restore converts each value back by the target column's type.
  All tables are read inside one `START TRANSACTION WITH CONSISTENT SNAPSHOT` (REPEATABLE READ), so the backup is consistent without taking the job lock; jobs and edits keep running.
  If the name is already taken (two runs in the same second), ` (2)`, ` (3)`… is added before `.zip`. The temp file is `<name>.zip.tmp`.
- **B14** After a successful backup, the oldest `rnrommanager-*.zip` files beyond the retention count are deleted (with any `<name>.restored` marker, B19). Only files matching the backup name pattern are touched. Retention never deletes a backup that has a `.restored` marker or is named by `Backup:RestoreFrom`, and those don't count toward N. A failed backup deletes its `.tmp` and deletes nothing else. Stale `rnrommanager-*.zip.tmp` files (from a crash) are deleted before each run.
- **B15** Backup settings are stored in a new `app_settings` table (migration 0015, `name VARCHAR(64)` PK, `value VARCHAR(255)`): `backup.enabled` (default `true`), `backup.time` (`HH:mm`, container local time from `TZ`, default `03:30`), `backup.retention` (1–365, default `30`). Missing rows mean the defaults. Validation errors (`400`, field errors `time` / `retention`): time not `HH:mm` 00:00–23:59; retention not an integer 1–365.
- **B16** A `BackupScheduler` hosted service runs the daily backup at `backup.time` using `ScheduleCalculator.NextDaily` (same DST rules as the quick check). Saving settings reschedules immediately (no restart). Disabled → no scheduled runs. Missed runs aren't caught up. One backup runs at a time (its own lock, not the job lock): a scheduled run that finds a manual one running is skipped (Info). Failures are logged at Error. `BackupService` keeps the "last result" in memory (lost on restart), updated by every run, scheduled or manual.
- **B17** Admin-only endpoints (`AuthSetup.AdminOnly`):
  - `GET /api/admin/backups` → `{ enabled, time, retention, timeZone (container TZ id), nextRunAt (ISO UTC | null), running: bool, lastResult: { at, ok, fileName?, error? } | null, backups: [{ fileName, sizeBytes, createdAt }] }`, backups newest first.
  - `PUT /api/admin/backups/settings` body `{ enabled, time, retention }` (all required) → `200` with the GET body.
  - `POST /api/admin/backups` → runs a backup now and waits for it: `201` with `{ fileName, sizeBytes, createdAt }`; `409 BackupRunning` when one is running; `500 BackupFailed` (ProblemDetails, message logged) when it fails. Counts toward retention.
- **B18** New Admin tab **Backups** (`/admin/backups`): a settings card (Enabled switch, time `<input type="time">` labelled "Daily at (server time, <TZ id>)" using a `timeZone` field added to the GET body, retention number input, Save), next run shown in the browser's local time, next run and last result, a "Back up now" button (spinner while running, success/error toast), and the backups table (file name, created (local time), size via `FileSize`), with `EmptyState` when none. A short note says where the files are and links to the restore docs.
- **B19** **Restore on startup**: when `Backup:RestoreFrom` (`Backup__RestoreFrom`) is set, startup (after the DB is reachable, before migrations) restores that backup:
  1. The value must be a bare file name (no `/`, `\`, `..`) of an existing file in `Paths:Backups`; otherwise startup fails (Fatal, exit 1) naming the problem.
  2. If `<file>.restored` exists next to it, the restore is skipped with a Warning ("already restored on <time>; remove Backup__RestoreFrom") and startup continues normally.
  3. The manifest must be `formatVersion` 1 and every migration it lists must be known to the app; otherwise startup fails (`backup is from a newer app version`).
  4. Every base table in the configured database is dropped (`FOREIGN_KEY_CHECKS=0`), `schema.sql` is run, and every `data/*.jsonl` is inserted with parameterised multi-row inserts (batches of 500) per table; row counts are checked against the manifest. Any error fails startup (Fatal); the restore is safe to retry because it starts by dropping everything.
  5. `<file>.restored` is written (ISO UTC time), a Warning logs the backup id, time and row counts, and startup continues: migrations apply anything newer than the backup.
  6. A Warning reminds the operator to run **Integrity → Run quick** so the DB matches the library ZIPs, which may be newer than the backup.
  The configured database must already exist (possibly empty): `WaitUntilAvailableAsync` fails on an unknown database before the restore runs, so the runbook says to create it first (e.g. via the MariaDB container's `MARIADB_DATABASE`).
  `Backup:RestoreFrom` is added to `EffectiveSettings` (a `Backup` section), so it shows in the startup "Effective config" log and on Admin → Settings.
- **B20** `Paths:Backups` is a new `VOLUME` in the image, a new volume line in the documented compose file, and `.dev/backups` in `setup-dev.ps1`. The e2e stack relies on the image's anonymous `VOLUME` (no compose mount, so `test-e2e.ps1` needs no new variable).

### Global hotkeys
- **B21** Actions and default bindings (canonical form `Ctrl+Alt+Shift+Meta+<Key>`, modifiers in that order; `<Key>` is `A`–`Z`, `0`–`9` or `F1`–`F12`, matched on `KeyboardEvent.code` so Alt/Option doesn't change the letter):

  | Id | Action | Default | Editable | Role |
  |---|---|---|---|---|
  | `search` | Open global search | `Ctrl+K`, `Ctrl+Space`, `Meta+K` | no | any |
  | `nav.library` | Go to Library | `Alt+Shift+L` | yes | any |
  | `nav.ingestion` | Go to Ingestion | `Alt+Shift+I` | yes | Admin |
  | `nav.review` | Go to Review | `Alt+Shift+F` | yes | Admin |
  | `review.next` | Open the first review item (Review page when the queue is empty) | `Alt+Shift+G` | yes | Admin |

  The requested `Ctrl+I/F/G/L` clash with browser shortcuts (italic/page info, find, find next, address bar), so the defaults keep the letters with `Alt+Shift`.
- **B22** A binding must include `Ctrl`, `Alt` or `Meta`; must not be `Ctrl+Alt+<Key>` without `Shift` or `Meta` (that is AltGr on Windows and types `@`, `€`… on many layouts); must not equal a reserved combination (`Ctrl+K`, `Ctrl+Space`, `Meta+K`) or the binding of another action **the user's role allows** (bindings of actions the role can't use are ignored for conflicts and kept unchanged); an editable action may be unassigned (`null`). The same rules live in `Core/Users/Hotkeys.cs` and `src/lib/hotkeys.ts`.
- **B23** Bindings are saved per user: migration 0016 adds `users.hotkeys TEXT NULL` (JSON object of overrides, action id → combination or `null`; `NULL` column = all defaults). `GET /api/auth/me/hotkeys` → `{ bindings: { <id>: string | null } }` with defaults merged in for every editable action (any role). `PUT /api/auth/me/hotkeys` body `{ bindings: { <id>: string | null } }` → `200` with the merged result; unknown ids, a bad format or B22 violations → `400` with field errors keyed `bindings.<id>`. Overrides equal to the default aren't stored. An Admin's bindings for Admin actions are kept if their role is later removed; they just don't fire. If two role-allowed actions end up sharing a binding (e.g. the Admin role is given back), only the first in B21 table order fires, GET returns both as stored, and the hotkeys modal shows the inline conflict error on the later row and blocks Save until it's rebound or unassigned.
- **B24** The root layout loads the bindings once the user is signed in and `mustChangePassword` is false (the endpoint is blocked until then), including right after a password change, and listens on `keydown` at `window`: it ignores repeats, events with `getModifierState('AltGraph')`, events while any Bootstrap modal is shown (`.modal.show`), and everything while `mustChangePassword`; on a match for an action the user's role allows, it calls `preventDefault()` and runs it. Hotkeys fire even when focus is in a text field (they always carry a modifier). `review.next` calls `GET /api/review?status=Pending&page=1&pageSize=1` (the queue's default, unfiltered `created_at, id` order) and goes to `/review/<id>`, or `/review` when empty or on error. Global search keeps its own handler; `search` is listed for display only.
- **B25** A (?) button in the navbar (`aria-label` "Keyboard shortcuts", `Icon name="help"`, before the theme toggle, hidden while `mustChangePassword`) opens a `ConfirmModal` (`size="lg"`) "Keyboard shortcuts" listing the actions the user's role allows: action, binding rendered as `<kbd>` keys (or "Not assigned"), and an Edit button for editable ones. Edit puts the row into capture mode ("Press keys…", `aria-live="polite"`): the next keydown with a non-modifier key becomes the binding; `Backspace`/`Delete` alone unassigns; `Escape` cancels capture (and only capture: the capture handler calls `stopPropagation()` + `preventDefault()` so Bootstrap's `keyboard: true` Escape doesn't close the modal; Escape outside capture closes it as usual). Invalid or conflicting captures show an inline error and aren't applied. Edits are pending until saved: the modal's confirm button is **Save** (`PUT`, enabled when something changed); a **Reset to defaults** `btn-outline-secondary` at the bottom left of the body sets every editable row back to its default as pending edits (Save then sends them; nothing is sent by Reset itself). Saving updates the live bindings at once and closes the modal; errors show `ErrorAlert` and keep the edits.

### Sticky navbar
- **B26** The navbar has Bootstrap's `sticky-top`, so it stays at the top while the page scrolls. Its user dropdown and mobile collapse menu still open, and modals and the global search (z-index 1055) render above it (sticky-top is 1020).

## Risks
- **Downgrade drops notes:** an older app version's writer copies only listed entries, so its next write of a ZIP silently drops `notes/`. Documented in `zip-format.md`; no schema bump because notes don't touch `info.json` (a bump would make older apps read-only on every ZIP, which is worse).
- **Backups contain secrets:** password hashes and data-protection keys. Docs say to keep `Paths:Backups` private; backup files are never served over HTTP.
- **Restore is destructive and not transactional** (MariaDB DDL auto-commits). Mitigated by: explicit file name in `Paths:Backups` only, the `.restored` marker against repeated restores, refusal of newer-schema backups, and retry-safe ordering (drop everything first). The runbook says to stop the app and take a fresh backup first if the DB is still readable.
- **Restored DB vs newer ZIPs:** the ZIPs stay the source of truth; the runbook and a startup Warning direct the operator to run a quick integrity check.
- **Markdown XSS:** notes are user content rendered as HTML; always through `DOMPurify`, covered by a vitest case with `<script>`/`onerror` payloads.
- **Hotkey clashes on some layouts/OSes:** `Alt+Shift` switches input language on some Windows setups; users can rebind.
- **Backup size/time:** tables are streamed row by row; the largest (`audit_events`, 30-day retention) stays moderate. The consistent snapshot holds an MVCC view, not locks.
