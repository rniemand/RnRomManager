# MS-DOS support

## Summary
Adds an MS-DOS system (`dos`) for Admins who keep DOS games as one ZIP per game (eXoDOS / Total DOS Collection style). There is no SHA1 DAT for DOS, so a new `DatSource.None` sends every DOS file to Review, where the Manual tab starts with a title taken from the file name. Releases are stored next to the game ZIP as `.dosz`, and play in the browser with the EmulatorJS `dosbox_pure` core. That core requires threads (`requiresThreads` in the vendored `emulator.js` lists `ppsspp` and `dosbox_pure`), so it plays only on a cross-origin isolated tab, like PSP. In-game saves stay in the browser.

## Out of scope
- Loose `.exe`/`.com`/`.bat` files, game folders, and loose CD images (`.iso`, `.cue`/`.bin`, `.img`, `.chd`, `.m3u`). A CD game goes inside its ZIP; DOSBox Pure mounts images it finds there.
- Any DAT or hash matching, including libretro's `dat/DOS.dat` (its CRCs are of the inner `.EXE`, not the archive) and libretro-thumbnails box art. Box art comes from IGDB image suggestions or uploads; the placeholder is stored until then.
- Copying DOS saves to or from the library Saves tab from the player (the isolated tab has no modal, as for PSP).
- A play size cap beyond the browser's memory.
- Touch-only devices: DOS games need a keyboard; a touch-first device gets EmulatorJS's virtual gamepad as every core does (`play.js` E1), and nothing more.
- The SPA's ingestion-page `isArchive` regex (`lib/ingestDelete.ts`): Shift+click on a DOS `.zip` row still asks for confirmation, which is harmless.

## Behaviour

### System (S)
- **S1** Handler `DosHandler` (new) in project `RnRomManager.Systems.Dos` (new): `Id` `dos`, `DisplayName` `MS-DOS`, `ShortName` `DOS`, `Family` `dos`, `RomExtensions` `[".dosz", ".zip"]`, `MinRomSizeBytes` 64, `MaxRomSizeBytes` 4 GiB (`4L * 1024 * 1024 * 1024`), `DatName` `DOS`, `DatSource` `DatSource.None`, `MetadatKinds` `[]`, `EmbedRomsInZip` false, `FileSets` false, `BrowserCore` `dosbox_pure`, `ReadHeader` always null, its own 512×512 placeholder box art (`Resources/boxart/dos.svg`, `dos.png` and a `README.md` saying it was drawn for this project, as `RnRomManager.Systems.Sony/Resources/boxart/` has). The project follows `RnRomManager.Systems.ThreeDo`, the closest single-handler project: one handler plus an `EmbeddedResources` loader.
- **S2** `SourceExtension` returns `.dosz` for `.zip` and `.dosz` (any case) and null otherwise. A DOS release is therefore always stored as `<ZipBase>.<stem>.dosz`, never `.zip`. This is required, not cosmetic: `IntegrityJob` (around line 236) and `DbSync.ScanZips` treat every `.zip` under `roms/<id>/` as a library ZIP. `.dosz` is a ZIP that DOSBox Pure mounts the same way. `InfoJsonValidator` also refuses an `externalFileName` ending `.zip` (any case) on any system, with `rom '<fileName>' externalFileName must not end with .zip`, so an imported, restored or hand-edited `info.json` can't point a release at a file Integrity and DbSync would read as a game ZIP.
- **S3** `IgdbPlatforms.ById["dos"] = 13` (IGDB's DOS platform), so the IGDB lookup and image suggestions work for DOS games.
- **S4** Systems tab: `systemEmulators.json` gets `"dos"` with DOSBox Pure (`https://github.com/schellingb/dosbox-pure`, windows, macos, linux) and DOSBox Staging (`https://www.dosbox-staging.org/`, windows, macos, linux). `icons.ts` maps `'system-dos': 'bi bi-terminal'` (asserted in `lib/stores/stores.svelte.test.ts` beside `system-tgcd`). `lib/systemColours.ts` adds `'dos'` to its id union and `dos: { name: 'dos', foreground: '#fff' }`, and `app.css` adds `--bs-dos: #3f4a56;` and `.text-bg-dos` beside the `tgcd` ones.

### No-DAT source (N)
- **N1** `DatSource.None = 2` (new): the system has no DAT files. Refresh DATs downloads nothing for it, and the Admin → DATs page shows no row for it (it already lists manifest entries only).
- **N2** `DatCache` (its `Prepare`/`Load` loop over `systems.All`) skips a `None` handler: `For("dos")` stays null and neither a strict refresh nor startup logs or throws for it. Without this, `DatCache.Read` throws for `dos` and every Refresh DATs fails with "DATs for dos can't be used: …".
- **N3** `IngestJob.Preflight` requires loaded DATs only for handlers whose `DatSource` isn't `None`. The `DatsMissing` code and message are unchanged.
- **N4** With no store, the existing code already does the rest: no match, so every DOS file goes to Review as `NoDatMatch` with no suggestions (`SuggestionEngine.Find(null)` returns `[]`), and a DAT pick is refused by `ReviewResolver`'s existing "Choose a game in the loaded DAT." check.
- **N5** `GET /api/review/{id}` adds `hasDat: boolean`, false when the item's system has `DatSource.None` (next to `addOns`). `ReviewDetail` in `types.ts` gets the field (required); the `noMatch` fixture in `routes/review/review-page.test.ts` gets `hasDat: true`.
- **N6** Review item page: when `hasDat` is false, the tabs are `['attach', 'manual']` (no Suggestions tab, so no "Search the … DAT" box) and Manual is the default tab.
- **N7** Manual tab prefill: when `hasDat` is false, the Manual form starts with `title` = `titleFromFileName(originalFileName)` (new, `lib/reviewForm.ts`); every other field stays empty. The function drops the extension, cuts at the first ` (` or ` [`, turns `_` into spaces, collapses whitespace and trims; an empty result gives `''`. Examples: `Doom (1993)(id Software).zip` → `Doom`; `Secret of Monkey Island, The (1990)(Lucasfilm)[!].zip` → `Secret of Monkey Island, The`; `Commander_Keen_4.zip` → `Commander Keen 4`. The title is filled once per item id: a page-local `let prefilledFor: number | null = null` (new, not reactive state); in the load effect's success callback, after `item = i`, when `i.hasDat === false && prefilledFor !== i.id`, set `manual.title = titleFromFileName(i.originalFileName)` and `prefilledFor = i.id`. The B21 reset effect is unchanged (it empties the form on an id change, before the item arrives). A later reload of the same id (`reload`) doesn't touch the form, so an Admin's edits survive; moving to another id (Add and Next, the Review next shortcut, a link) prefills from the new item's name. Systems with a DAT keep the empty form.
- **N9** Add and Next: when `hasDat` is false, the Manual form shows a second button, `Add and Next` (`btn btn-outline-primary ms-1`, `type="button"`), right after `Add manually`. It validates and resolves exactly as `submitManual` does, through `resolveWith(toManualRequest(manual), `Added as <title>.`, true)`, so the page then opens the next Pending item as Use and Next does (or the game when none is left). It's disabled under the same rule as Use and Next (`disabled || typeof next !== 'number'`), with the tooltip `No more items in the review queue.` when `next === 'none'`. Systems with a DAT don't show it.
- **N8** README supported-systems table: the DAT column says `None` for a `None` system (`SupportedSystemsTableTests.Row`).

### Ingest (I)
- **I1** A `.zip` or `.7z` is an archive container only when its ingest folder's handler doesn't list that extension in `RomExtensions`. New `ArchiveExtractor.IsArchiveFor(ISystemHandler? handler, string fileName)` returns `IsArchive(fileName) && !(handler?.RomExtensions contains the extension, ignoring case)`. `IngestJob` (the `FileSets`, external and embedded archive branches, lines ~143–156) and `IngestFileDeleter` (line ~146) use it in place of `IsArchive`. The deleter change is a fix, not a rename: with `IsArchive`, deleting a pending DOS `.zip` from the Ingestion page passes the path as `archivePath`, and `DeletePendingBySourceAsync` then deletes only rows with that `archive_path`, so the DOS row (whose `archive_path` is null) would be left behind. Nothing changes for any other system, since none lists `.zip` or `.7z`.
- **I2** So a `.zip` or `.dosz` in `ingest/dos/` is one ROM file: validated by size (S1), hashed as a stream, and queued for Review with the file left in place. A `.7z` in `ingest/dos/` is still unpacked; its `.dosz` entries are ingested, and `.zip` entries are skipped as nested archives (the extractor's existing rule).
- **I3** Resolving a DOS item (Manual or Attach) moves the file next to the game ZIP under the existing external naming, with the `.dosz` extension from S2 (`ReviewResolver`'s `originalExtension` already calls `SourceExtension`). Download serves that `.dosz` file as is.

### Browser play (P)
- **P1** Vendoring: `package.json` adds `"@emulatorjs/core-dosbox_pure": "4.2.3"`. `scripts/vendor-emulatorjs.mjs` copies `dosbox_pure-thread-wasm.data`, `dosbox_pure-thread-legacy-wasm.data` and `reports/dosbox_pure.json` (the package ships threaded payloads only), next to the PPSSPP block. `licenses.json` gets an entry for the package: `GPL-2.0` (the payload's `license.txt`), url `https://github.com/EmulatorJS/dosbox-pure`. `emulator-licenses/` gets `dosbox_pure-LICENSE.txt` (the payload's GPL-2.0 `license.txt`) and `dosbox_pure-NOTICE.txt` (laid out like `puae-NOTICE.txt`: the files it covers, `npm @emulatorjs/core-dosbox_pure 4.2.3`, and the corresponding source as `https://github.com/EmulatorJS/dosbox-pure/tree/<commit>`, the commit taken from the version string in the `.wasm` as PUAE's was, and the bundled libraries the implementer finds in that repository, each with its own `dosbox_pure-<lib>-LICENSE.txt` as `puae-libchdr-LICENSE.txt` does). The vendor script copies them, `coreLicenses` in `vendorEmulatorjs.test.ts` lists them, and the `licenses.json` string names every licence they hold (as the `puae` and `desmume` entries do). The README attribution gets a DOSBox Pure line after the Beetle PCE one, in the same form: the name and short commit linked to `https://github.com/EmulatorJS/dosbox-pure/tree/<commit>`, `(MS-DOS)`, and its licences.
- **P2** Vendor patches (guarded edits in `vendor-emulatorjs.mjs`):
  - the threads edit sets `threads = true` for `dosbox_pure` as it does for `ppsspp` (when `SharedArrayBuffer` exists);
  - the `arrayBuffer()` read-error edit includes `dosbox_pure`;
  - (new edit, after `const altName = this.getBaseFileName(true);` in `emulator.js`'s `gotGameData`) for `dosbox_pure` only: write the downloaded bytes to `altName` unchanged, set `this.fileName = altName` and resolve, skipping `checkCompression`. Without it EmulatorJS unpacks the ZIP and boots its first supported file (often `INSTALL.BAT` or `SETUP.EXE`); with it DOSBox Pure mounts the whole ZIP and shows its own start menu.
  - `dosbox_pure` is not added to the `getCore()` guard or `params.js`'s `hidesCoreChooser`: it's the only core in EmulatorJS's `dos` group, so no other core can be chosen.
- **P3** Play is offered for external DOS releases: `LibraryEndpoints.ExternalBrowserCores` and `externalBrowserCores` in `emulator.ts` add `dosbox_pure`; `PlayDiscCores`/`playDiscCores` don't, so `play.js` fetches the file from `/download` (as for `desmume`).
- **P4** Isolated page `static/emulator/play-dos.html` (new), a copy of `play-psp.html` with `<title>DOS · RnRomManager</title>` and `<body data-player="dos">`. `SecurityHeaders` replaces `PspDocumentPath` with `IsolatedDocumentPaths` (`/emulator/play-psp.html`, `/emulator/play-dos.html`; case-insensitive) and sends `PspEmulatorPolicy` and COOP/COEP on both.
- **P5** Page routing: `params.js` replaces `pspCore` with `isolatedPlayers = { ppsspp: 'psp', dosbox_pure: 'dos' }`; `parsePlayParams(search, player)` takes the page's `data-player` as `player?: string` (`'psp'`, `'dos'` or `undefined` for `play.html`; JSDoc `@param {string} [player]`) and returns null unless `isolatedPlayers[core] === player` (undefined for every modal core). `play.js` passes `document.body.dataset.player` and runs `listenForMessages` only when it is undefined. Existing calls in `emulatorParams.test.ts` change with it: every `parsePlayParams(…, true)` becomes `parsePlayParams(…, 'psp')` and `parsePlayParams(…, false)` drops the argument (about 12 calls, including the `play-psp.html accepts only ppsspp, and play.html rejects it` test). `cores` adds `dosbox_pure`. `discError` keeps its PSP (UMD) wording by testing `core === 'ppsspp'` directly. `emulator.ts` replaces `isolatedBrowserCore` with `isolatedPages = { ppsspp: 'play-psp.html', dosbox_pure: 'play-dos.html' }`; `opensInNewTab(core)` is true for both and `playUrl` uses the core's page. Every existing PSP caller (Play buttons, Global Search, game results, the `GamePlayed` audit on link click) follows `opensInNewTab`, so DOS gets the new-tab link behaviour with no further change.
- **P6** Browser checks: `pspBrowserError(browser)` becomes `isolatedBrowserError(browser, core)`. PSP keeps its three messages word for word. DOS checks secure context and isolation only (the legacy payload needs no WebGL 2):
  - `DOS games need a secure page: open RnRomManager over HTTPS or on localhost. A plain-HTTP network address can't run them.`
  - `This page isn't cross-origin isolated, so DOS games can't use threads. Ask an Admin to check that the proxy keeps the Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers.`
- **P7** `play.js` on `play-dos.html`: runs the P6 check before any request, then shows `Downloading ROM…` and loads `/api/games/{game}/roms/{rom}/download` as for `desmume`; no BIOS; no `listenForMessages` (no modal, as for PSP). `EJS_Buttons` hides `saveSavFiles` and `loadSavFiles` for `dosbox_pure`, as it does for `desmume`: they export and import RetroArch's SRAM file, which DOSBox Pure never writes (its saves are the `.pure.zip`, P8), so they would offer an empty export. It sets `EJS_threads = true` for `dosbox_pure` as it does for PSP (today `if (isPsp) ejs.EJS_threads = true;`): EmulatorJS's `downloadGameCore` refuses a `requiresThreads` core without it ("Error for site owner"), before the P2 payload choice runs.
- **P8** Saves: DOSBox Pure writes drive changes to `/data/saves/<name>.pure.zip`, which EmulatorJS 4.2.3 persists in IndexedDB (`GameManager.js` mounts `/data/saves` as IDBFS with `autoPersist`). They stay in that browser, keyed by the content name. Since two DOS games may share a title (and so a release file name), `contentFileName` in `params.js` returns `<gameId>-<name>` (with `#` still replaced by `_`) for `dosbox_pure`. EmulatorJS 4.2.3 replaces `gameUrl` with the `File`'s name before `gotGameData`, so `getBaseFileName(true)`, and with it the P2 no-extract edit's `altName` and DOSBox Pure's `<content>.pure.zip`, come from that name; each game's save is its own. `EJS_gameName` stays `params.name`. The Saves tab can still upload and download files for DOS releases, but not play them, the same as PSP. Docs say: "DOS saves stay in this browser. The Saves tab can store files, but can't load them into the player." Persistence across tab closes is a step 5b manual check. On `beforeunload` EmulatorJS calls its `exit` event, which runs `saveSaveFiles()`, `restart()` and `saveSaveFiles()` again and then unmounts `/data/saves`; IDBFS (`autoPersist`) writes a file to IndexedDB when it is closed. Whether DOSBox Pure has closed its `.pure.zip` and IndexedDB has committed before the tab is gone is what the check finds out. If it fails, step 5b adds a guarded sync edit for `dosbox_pure` next to the `desmume` one in `saveSaveFiles()` (the 30-second interval then persists it) and checks again. If it still fails, stop and ask the user (Implement step 4) before documenting anything.

## Risks
- **A `.zip` stored under `roms/dos/`** would be read as a broken game ZIP by Integrity and DB auto-repair. S2 makes that impossible for files this app writes; a `.zip` an operator copies there by hand is reported as it would be for any system.
- **Memory:** the whole release is held in the tab while it loads (several copies briefly). Large CD-based ZIPs can fail to start on low-memory devices; EmulatorJS shows its own error. No cap is added (Out of scope).
- **One review per game:** with no DAT, a large collection means many Manual resolutions. The prefill (N7) and Add and Next (N9) keep each one short.
- **Unrelated systems:** I1 changes behaviour only for a handler that lists an archive extension; today none does. N2/N3 change nothing for `Libretro`/`TitleDb` handlers.
- **Licence:** DOSBox Pure is GPL-2.0, which the image already ships for other vendored cores (PUAE).
