# WonderSwan and WonderSwan Color

## Summary
Two new systems, WonderSwan (`ws`, mono) and WonderSwan Color (`wsc`), in a new `RnRomManager.Systems.WonderSwan` project, for the Admin who ingests ROMs and everyone who browses and plays the library. They split like Game Boy / Game Boy Color and Neo Geo Pocket / Color: one family, a shared base class and footer reader, the cartridge footer's colour byte decides colour vs mono for unmatched files, and each has its own libretro No-Intro DAT. Both play in the browser with EmulatorJS's `mednafen_wswan` core (Beetle WonderSwan), which isn't vendored yet: this spec vendors `@emulatorjs/core-mednafen_wswan` `4.2.3` the way Beetle NeoPop was (`2026-11-24-neo-geo-pocket.md`). No BIOS (the core boots the cartridge directly).

## Out of scope
- Pocket Challenge V2 (`.pc2`, libretro DAT `Benesse - Pocket Challenge V2`: 75 entries, no metadat, no thumbnails). It would be a third system of its own family (no footer byte tells it from a WonderSwan cart); left for a later spec. `BrowserCoreExtensionsTests` lists `.pc2` as `NewSystem`.
- A system icon (`icons.ts`): like `ngp`/`ngpc`, both use the controller fallback.
- Vertical (portrait) games: the footer's `vertical` flag is stored and shown, but the player isn't rotated; EmulatorJS's own `ws` controls and the core's options are used as they are.
- A `getCore()` pin, a core-chooser hide or a control scheme: EmulatorJS 4.2.3's `ws` group holds only `mednafen_wswan` (`"ws": ["mednafen_wswan"]` in `emulator.js`), as `ngp` holds only `mednafen_ngp`.
- An automatic DAT refresh after upgrading (documented manual step).

  Facts (libretro-database `master`, `metadat/no-intro`, DAT version `2026.11.14`, checked 2026-11-25): both systems have all five files (`no-intro`, `releaseyear`, `developer`, `publisher`, `genre`) and a `libretro-thumbnails` repository (`Bandai_-_WonderSwan`, `Bandai_-_WonderSwan_Color`). The mono DAT lists 219 `.ws` entries (512 KiB–16 MiB); the colour DAT 229 `.wsc` entries (128 KiB–8 MiB). Neither lists another extension.
- **W2 Footer.** `WonderSwanFooterReader` (new, static class) with `public const int FooterSize = 16;` and `Read(ReadOnlySpan<byte> rom)` (never throws). Returns null when `rom.Length < FooterSize`. Otherwise, with `f = rom[^16..]` (the cartridge footer at the top of the ROM; layout as in Beetle WonderSwan's `libretro.c`, which reads `f[6..16]` as its 10-byte `header`), a header:
  - `IsPlausible`: `f[0x0]` is `0xEA` (the reset vector's `JMP FAR`, which every cart needs to boot).
  - `ClassifiedSystemId`: `wsc` when `f[0x7]` is exactly `0x01`, else `ws` (`0x00` and any other value), whether plausible or not.
  - `Title`: null (the footer has no title; Review suggests from the file name).
  - `Fields`, in this order: `publisherId` (`"0x"` + two upper-case hex digits of `f[0x6]`, e.g. `"0x01"`), `colour` (bool, `f[0x7] == 0x01`), `gameId` (int, `f[0x8]`), `version` (int, `f[0x9]`), `romSize` (`"0x"` + two upper-case hex digits of `f[0xA]`), `saveType` (`"0x"` + two upper-case hex digits of `f[0xB]`), `vertical` (bool, bit 0 of `f[0xC]`), `mapper` (`"0x"` + two upper-case hex digits of `f[0xD]`), `checksum` (`"0x"` + four upper-case hex digits of the little-endian uint16 at `f[0xE]`), `checksumValid` (bool: the sum of every ROM byte except the last two, modulo 65,536, equals `checksum`).
- **W3 Ingestion.** The existing family pipeline, as for NGP/NGPC:
  - A `.ws` or `.wsc` file in `ingest/ws/` or `ingest/wsc/` is checked against both DATs; a DAT hit decides the system (a colour-flagged ROM listed in the mono DAT is stored as `ws`).
  - Unmatched: an implausible footer → `InvalidHeader`; a plausible one → Review (`NoDatMatch`) under the classified system, renamed first when its extension isn't the classified system's (`RenameToClassifiedExtension`): a colour `.ws` becomes `.wsc`, a mono `.wsc` becomes `.ws`.
  - Under 16 bytes → `TooSmall`; over 16 MiB → `TooLarge`. Another family's file (e.g. `.gb`) in `ingest/ws/` → `UnsupportedType`; a `.ws` in `ingest/gb/` → `UnsupportedType`; a `.pc2` in `ingest/ws/` → `UnsupportedType`.
  - Releases have the Header button; `info.json` `header` holds W2's fields.

## Risks
- **Two new systems break every full-registry DAT manifest** (`DatsMissing`) and the count/order assertions: all fixed in step 2's single commit.
- **Licence notice accuracy.** W8's facts were read from the payload and the source at `fbc945d`. Step 4 re-checks the pinned hashes and the `license.txt` = `COPYING` equality; if either differs, W7/W8 no longer apply: stop and ask.
- **V30MZ's non-SPDX licence.** It only asks for credit, which the NOTICE and README give; expressed as `LicenseRef-V30MZ`. `LicenseInfoTests` doesn't validate SPDX ids (checked), so the string passes as is.
- **Footer check misfires.** A ROM whose last 16 bytes don't start with `0xEA` fails `InvalidHeader` when unmatched (such a cart wouldn't boot). Checksum mismatches (common in hacks and some dumps) never fail; they only show `checksumValid` false.
- **Checksum cost.** `checksumValid` sums the whole ROM (≤ 16 MiB) once per ingest, in memory already read for an embedded system: negligible.
- **Image size.** About 1.75 MB more vendored output.
