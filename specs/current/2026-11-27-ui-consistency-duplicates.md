# UI consistency, hash search and duplicate cleanup

## Summary
Makes the Game page, Integrity and Admin tables feel consistent: action buttons become small link-style icon buttons (the style of the Game Metadata table's quick-edit pencil), images and saves get clearer layouts with drag-and-drop uploads, and sizes use the size badge. Adds SHA1/MD5 search, a **Duplicate SHAs** report, a ROM Tools **Duplicates** tab to reclaim the space `ingest/<system>/_duplicates/` uses, orphan-file deletion and game links on Integrity, and backup downloads. For Admins (most actions) and every signed-in user (search, report, layouts).

## Out of scope
- Restyling buttons on pages this spec doesn't name (Library, Collections, Review, Ingestion, other reports, other Admin tabs).
- Moving, renaming or ingesting files from `_duplicates/` (delete only), and listing `_duplicates/` on Ingestion.
- CRC32 search; hash search in the Collections list (`/api/collections`) or in report search boxes.
- Restyling `IngestFileTable` (shared with Ingestion and Deleted ROMs).
- Deleting Integrity files other than `OrphanFile`.
- Any change to how ingest decides a file is a duplicate.

## Behaviour

### Icon buttons (I)
- **I1** A new `IconButton` component (`lib/components/forms/IconButton.svelte`, (new)) is the house icon-only action: it renders `Button` with `variant="link" size="sm"`, class `p-0`, an `icon`, an `aria-label` (prop `label`, required) and a tooltip (prop `tooltip`, default = `label`) through `fromAction(tooltip, …)`, exactly like the quick-edit pencil in `GameHeader.svelte` (`class="text-body-secondary p-0 … quick-edit"`). Props: `icon`, `label`, `tooltip?`, `tone?: 'default' | 'danger' | 'success' | 'primary' | 'warning'` (default `default`), `href?`, `download?`, `target?`, `rel?`, `disabled?`, `onclick?`, `class?`, plus `...rest` passed to `Button` (for `aria-expanded`, `data-*`). Tone → class: `default` `text-body-secondary`, `danger` `text-danger-emphasis`, `success` `text-success-emphasis`, `primary` `text-primary-emphasis`, `warning` `text-warning-emphasis`. `disabled` only affects the `<button>` form (an `href` link can't be disabled; callers hide it instead). The quick-edit pencil itself switches to `IconButton` (same look; its `ms-auto quick-edit` classes stay).
- **I2** Groups of icon buttons sit in a `d-flex align-items-center gap-2` wrapper (the gap keeps targets apart for WCAG 2.2 target spacing). Every converted button keeps its current `aria-label` text exactly, so screen-reader names and e2e locators don't change, unless a rule here names a new one.
- **I3** Size badge: a file size shown in a list uses `<span class="badge text-bg-light border"><FileSize bytes={…} /></span>`, as `ZipBrowser` (Z2) and `GameImages` already do.

### Drop zones (Z)
- **Z1** A new `DropZone` component (`lib/components/common/DropZone.svelte`, (new)) wraps a region (`children` snippet). Props: `disabled?`, `accept?: (file: File) => boolean`, `ondrop: (files: File[]) => void`, `hint: string`, `class?`. While files are dragged over it (`dragenter`/`dragover` with `dataTransfer.types` including `Files`, the `hasFiles` check `UploadImageModal` uses) it shows a `border border-2 border-primary border-dashed rounded` outline and a `bg-primary-subtle` tint; it calls `preventDefault` on `dragover`/`drop` so the browser doesn't open the file. The highlight clears on `drop` and on a `dragleave` whose `relatedTarget` is outside the region (`UploadImageModal`'s `onDragLeave` check). On drop it passes the accepted files (all files when no `accept`) to `ondrop` (only when at least one is accepted) and the rejected ones to an optional `onreject?: (files: File[]) => void` (only when at least one is rejected); a mixed drop calls both. `disabled` ignores drags. Below the region it shows `hint` as `small text-body-secondary` (with `Icon name="upload"`). Drop zones are a mouse convenience; every one has a keyboard/button path (the section's Upload or Add button).

A `JobRunning` failure stops the remaining uploads (they'd all fail). Rejected (non-image) files, from `onreject`, toast once `Only image files can be uploaded; skipped {n} file(s).` (warning, `n` via `formatCount`); the images in a mixed drop still upload. The zone is disabled while `busy` (uploads set `busy`).

### Global search (GS)
- **GS1** When the whole trimmed query is 40 hex characters (SHA1) or 32 hex characters (MD5), case-insensitive, `GET /api/games?q=` also matches games owning a release (`roms`) or set file (`rom_files`) with that hash, OR-ed with the existing word match. It applies everywhere `GameRepository`'s filter runs with `q` (Global Search, the Library and Collection detail search boxes, `GameTypeahead`, `GameAdminModal`, `SystemGames`).
- **GS2** A hash-matched game whose title doesn't contain the query returns `matchedOn = { field: 'sha1' | 'md5', value: <matched file name> }`. The list query adds a column `HashMatchFileName` (new; `NULL` without a hash query): the matching release's `file_name`, else the matching set file's `file_name` (release first, then smallest name). `SearchMatch.Find` gains a last, optional parameter `(string Field, string FileName)? hashMatch = null` (so `SearchMatchTests`' existing calls compile unchanged) used after the title check and before developers (a hash query never matches metadata words in practice). `lib/types/GameListItem.ts`'s `matchedOn.field` union gains `'sha1' | 'md5'`; `matchLabels` in `GlobalSearch.svelte` gains `sha1: 'SHA1'`, `md5: 'MD5'`. Opening a hash match opens the game page (no tab).
- **GS3** shortcut: `md5` has no index on `roms`/`rom_files`, so an MD5 query scans both tables; acceptable as it only runs for an exact 32-hex query. A comment in `GameRepository` says so.

### Duplicate SHAs report (D)
- **D1** New report tab **Duplicate SHAs** at `/reports/duplicate-shas`, after **Duplicates** in `reportTabs` (icon `report-duplicate-shas` (new, `bi bi-fingerprint`)), for every signed-in user like Duplicates; merge and dismiss stay Admin-only.
- **D2** A group is 2+ games of one system that share a file hash across their releases (`roms.sha1`/`md5`) and set files (`rom_files.sha1`/`md5`): one group per `(system, sha1)`, plus one per `(system, md5)` only when the matching files don't all share one SHA1 (so an identical file isn't listed twice). Groups sort by system, then the smallest matching file name, then hash. Group title = the smallest matching file name, with a `badge text-bg-light border font-monospace` `SHA1 <first 12 hex>…` / `MD5 <first 12 hex>…` (full hash in its `title` attribute and a `CopyButton` with `label="SHA1"` / `label="MD5"`).
- **D3** API: `GET /api/reports/duplicates?match=hash` (new value; error text becomes `Must be title, igdb or hash.`). Each group adds `hashKind` (`sha1` | `md5` | null) and `hash` (lower-case hex | null); `baseTitle` is the smallest matching file name. Games, suggested target order, paging and system filter are as for the other matches.
- **D4** Dismiss: `POST /api/reports/duplicates/dismiss` accepts `{ system, gamesKey, hash: "sha1:<40 hex>" | "md5:<32 hex>" }` (`DismissDuplicateRequest` gains `string? Hash`). Validation order: when `hash` is given (non-null), `baseTitle` or `igdbId` also given → 400 `errors.hash` `Give hash alone, without baseTitle or igdbId.`; a value not matching `^(sha1:[0-9a-f]{40}|md5:[0-9a-f]{32})$` → 400 `errors.hash` `Must be sha1:<40 hex> or md5:<32 hex>.`; otherwise the baseTitle/igdbId check is skipped. When `hash` is absent the existing baseTitle/igdbId rules and messages run unchanged, except that the "neither given" case's message becomes `Give baseTitle, igdbId or hash.` (key `igdbId`; "both given" keeps `Give baseTitle or igdbId, not both.`). Stored as `match_kind = 'hash'`, `base_title = <hash value as sent>` (fits `VARCHAR(8)`/`VARCHAR(255)`; no migration); 204 as today. `HashGroups` drops a group with a dismissal row `('hash', system, '<kind>:<hash>', gamesKey)`, as `TitleGroups`/`IgdbGroups` do.
- **D5** Merge is the existing `POST /api/reports/duplicates/merge`. The page reuses the Duplicates page: its body moves into `lib/components/reports/DuplicateGroupsReport.svelte` (new folder `reports`, added to the style guide's `components/<folder>` list) with prop `mode: 'games' | 'hash'`; `/reports/duplicates` renders `mode="games"` (Match by filter as today), `/reports/duplicate-shas` renders `mode="hash"` (no Match by filter). Empty: `No games share a file hash.` State (system, page) is component state, as Duplicates. In hash mode the `{#each}` key and the group heading id include the hash (`group-{gamesKey}-{hash}`), since two hash groups can share games, system and smallest file name (e.g. `Track 02.bin` on two discs). Global Search lists the new tab with the other reports (it reads `reportTabs`).

### Integrity (IN)
- **IN1** `DuplicateGameId` issues get `gameId` = the duplicated game id; `DuplicateSha1` issues get `gameId` = the game in the library that owns the clashing SHA1 (`clash.Owner.Id`; the skipped ZIP isn't mirrored). `DbSyncSkipItem` gains `Guid? GameId = null`, set by `DbSync` for these two reasons, and `IntegrityJob` passes it into `IntegrityFinding`. Open issues pick it up on the next run through `TouchAsync` (it already updates `game_id`). For these two types, when the issue has a `gameId`, the Path cell shows the path as plain text followed by a link `Open game` (`ms-2`) to `/games/{gameId}` (the path names the skipped ZIP, not the linked game's); other types keep today's linked path. The details text stays plain. A game that isn't in the database (possible for `DuplicateGameId`) opens the game page's existing "This game doesn't exist any more." state.
- **IN2** `OrphanFile` rows with status `Open` get a delete `IconButton` (tone `danger`, aria-label `Delete {zipPath}`, tooltip `Delete file`) in a new last column (header visually hidden `Actions`), shown only while no job runs. It opens `ConfirmModal` titled `Delete orphan file`, message `Delete {zipPath} from the library folder? This can't be undone.`, confirm `Delete` (`confirmClass="btn-danger"`, `busy` while the call runs). On success: toast `Deleted {zipPath}.`, the issue list reloads. On failure the modal closes, `toasts.jobRunning(e)` handles `JobRunning`, any other problem toasts its title (danger), and the list reloads.
- **IN3** API: `POST /api/integrity/issues/{id:long}/delete-file` (Admin). 404 (`Problems.NotFound`) when the issue doesn't exist (new `IIntegrityIssueRepository.GetAsync(long id, CancellationToken)` returning `IntegrityIssue?`). 409 `NotOpenOrphan` "Only an open orphan file can be deleted" unless type `OrphanFile` and status `Open`. Under `JobLock.TryAcquire("Deleting orphan file")`, else 409 `JobRunning` (`JobStart.Running`). Under the lock it re-checks the path isn't now part of the library — no `games.zip_path` equal to it (new `IGameRepository.ZipPathExistsAsync(string zipPath, CancellationToken)`, compared under the column's collation) and no external file (`IRomRepository.ListExternalAsync` + `ExternalIntegrityCheck.FileKey`, as `IntegrityJob` does) — else 409 `NoLongerOrphan` "The file is now part of the library; run a check". The file is resolved with `SafePath.Resolve(Paths:Roms, zipPath)` and classified with `ExternalRomPath.ClassifyFile` (as `IngestFileDeleter` does): `Found` (a regular file reached without links) is deleted; `Missing` counts as already deleted (resolved and `204`, but not audited: as in `IngestFileDeleter`, only a file that existed gets an audit row); any other status (a link, a special file, a directory, a linked folder on the way), or an `UnsafePathException` from `SafePath.Resolve`, → 409 `NotDeletable` "The path isn't a plain file; remove it by hand", issue left Open, nothing audited. An `IOException`/`UnauthorizedAccessException` on delete → 409 `DeleteFailed` "The file couldn't be deleted", issue left Open, nothing audited (logged as a warning). On success the issue is marked `Resolved` at once (`ResolveAsync([id], now)`), audited as new `OrphanFileDeleted` (in `AuditActions.All`, path `roms/<zipPath>` via `AuditPaths`), and the response is `204`. The work lives in a new Core class `OrphanFileDeleter` (`Core/Integrity/OrphanFileDeleter.cs`), registered in `AppHost`, copying `IngestFileDeleter`'s lock/audit pattern.
- **IN4** Issues table is compact: `DataTable` gets `class="mb-2 small"` and cells use `py-1`; the Type column is `badge text-bg-light border` with the type name; the Status column is a badge — `Open` `text-bg-warning`, `AutoRepaired` `text-bg-info`, `Resolved` `text-bg-success` (new `issueStatusClass` in `lib/jobs.ts`).
- **IN5** Paging uses the house `Pagination` with its page-size selector (10/20/50/100), default **10**, remembered per browser under `rnrm.pageSize.integrity-issues`. `readPageSize(table, fallback = defaultPageSize)` (new optional `fallback` parameter) lets the page default to 10; changing size or filters goes back to page 1. The hard-coded `pageSize = 50` and the hand-made Previous/Next nav go.

## Risks
- **False hash groups:** generic set files (e.g. a silent audio track) can be byte-identical across unrelated games, so D2 may group games that aren't duplicates. Mitigated by showing the matching file name and hash, and by Dismiss; merging stays a confirmed Admin action.
- **Deleting the wrong file:** orphan delete re-checks the library under the job lock (IN3) and uses `SafePath`; `_duplicates` deletes go through the existing validated `IngestFileDeleter`. Both are permanent and confirmed.
- **Backup downloads** carry password hashes and keys: Admin-only, audited (A3).
- **MD5 search** scans `roms`/`rom_files` (GS3); only for exact 32-hex queries.
- **Accessible names** must not change (I2), or e2e and screen-reader users break; the few new names are listed in IM4 and R1.
- **Small targets:** link-style icons are ~20px; I2's `gap-2` spacing meets WCAG 2.2 target-size spacing.
