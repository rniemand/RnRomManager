# Arcade (MAME 2003-Plus)

## Summary
Adds an arcade system, `mame2003`, for Admins who keep MAME 0.78 / MAME 2003-Plus romsets (one `.zip` per set). Ingest identifies a set ZIP by its file name (the set name) plus the CRC32s of the files inside it, against the MAME 2003-Plus XML DAT, and stores the ZIP next to the game ZIP byte for byte (never repacked). Clones are releases of their parent's game, and every matched release records its set name and parent/BIOS links. Releases play in the browser with the EmulatorJS `mame2003_plus` core, operator-supplied because the MAME licence forbids commercial use; the play page loads a clone's parent set and a BIOS set (e.g. `neogeo`) from the library next to the game.

## Out of scope
- An FBNeo system or a shared "Arcade" library view. A future FBNeo system is a separate system with its own id, DAT and romsets; nothing here prepares a shared view (decision 2026-11-24).
- Sets that need a CHD (the DAT's 80 games with `<disk>`), and samples (`sampleof`): ingest ignores both, and those games may play without sound effects or not at all.
- Merged-set awareness: a merged parent ZIP that also holds its clones' ROMs is matched as the parent only; its clones aren't created from it.
- Renaming or rebuilding sets (no fix-up of wrong entry names, no split/merge conversion).
- Matching a ZIP whose name isn't a set name by its CRCs alone.
- `.7z` sets: a `.7z` in `ingest/mame2003/` is unpacked as for every system, and its `.zip` entries are skipped as nested archives (the extractor's existing rule).
- MAME NVRAM, high scores and EmulatorJS save states in the library Saves tab.
- Box art from the 2003-Plus thumbnail repos (`libretro-thumbnails/mame2003-plus-thumbnail-sources`): only the libretro `MAME` thumbnail folder is used (G6).
- Hiding Play for BIOS sets: a BIOS set's game keeps its Play button, and the core reports that it can't run it (decision 2026-11-24).

### DAT source (D)
- **D1** `DatSource.Mame = 3` (new): the system's DAT is one MAME `-listxml` file downloaded from `Sources:MameDatUrl` (new option in `SourcesOptions`, default `https://raw.githubusercontent.com/libretro/mame2003-plus-libretro/master/metadata/mame2003-plus.xml`; `SourcesOptionsValidator` requires an absolute http(s) URL with the message `Sources:MameDatUrl must be an absolute http(s) URL (got '<value>').`, as for `TitleDbUrl`). `EffectiveSettings` lists it next to `TitleDbUrl`. One URL serves every `Mame` handler, so `DatRefreshJob.CheckPlan` refuses two, after the DatName check: `Systems 'a' and 'b' both use Sources:MameDatUrl; nothing was refreshed.`
- **D2** Parsing, `MameDat.Parse(Stream)` (new, `src/RnRomManager.Core/Dats/MameDat.cs`): an `XmlReader` with `DtdProcessing.Ignore` and `XmlResolver = null` (the file starts with an inline DTD; it's never processed, so no entity expansion or external fetch). It reads `<game>` (and `<machine>`, the newer element name, the same way) elements: `name`, `cloneof`, `romof`, `runnable` (`no` → `IsBios`), `isbios` (`yes` → `IsBios`), `<description>`, `<year>`, `<manufacturer>`, and each `<rom>`: `name`, `size`, `crc` (lower-cased), `merge`, `bios`, `status` (`nodump` → `NoDump`). Every other child element is skipped. A game with no `name` or no `description`, a ROM without `crc` that isn't `nodump`, or a duplicate game name (ignoring case) fails the parse with `DatParseException` naming the game. A file with no games fails with `No <game> elements found.` The real file passes these rules: on 2026-11-24 it had 6,078 games (23 `runnable="no"`), 94,393 ROMs, no duplicate names, no game without a description and no crc-less ROM outside `nodump`. Model (new, same file): `MameDat(IReadOnlyList<MameSet> Sets)`, `MameSet(string Name, string Description, string? Year, string? Manufacturer, string? CloneOf, string? RomOf, bool IsBios, IReadOnlyList<MameRom> Roms)`, `MameRom(string Name, long Size, string? Crc32, string? Merge, string? Bios, bool NoDump)`.
- **D3** Store: `DatStore` gets a constructor `DatStore(MameDat dat, string version)` (new). It sets `DatName` = `DatStore.MameName` (new const, `"MAME"`), `Version` = `version`, and `Roms` = one `DatRom` per set, in file order: `GameName` = description, `RomName` = `<set name>.mamez`, `SizeBytes` = the sum of its ROM sizes, `Crc32`/`Md5`/`Sha1` = `""`. So the Review DAT search (`GET /api/dat/search`), `SuggestionEngine` and `BaseTitles` work on descriptions; `BySha1` never matches a MAME entry (a lookup is always 40 hex chars). New members: `MameSet? BySetName(string name)` (ignoring case) and `DatMetadata MetadataForSet(string name)`: `ReleaseYear` from `<year>` when it is 4 digits (`19??` and `198?` give none), `Developers` and `Publishers` both `[manufacturer]` when present, `Genres` `[]`; `DatMetadata.Empty` for an unknown name.
- **D4** Refresh: `DatRefreshJob` downloads `Sources:MameDatUrl` once when a `Mame` handler is registered (one progress item, current item `mame/MAME.xml`), capped at `MaxFileBytes` (64 MiB; the file was 25,333,189 bytes on 2026-11-24), parses it with `MameDat.Parse` (a parse failure fails the refresh and keeps the old set, as a libretro parse failure does), and stages it as `mame/<DatName>.xml` (`MameDat.RelativePath(datName)`, new; folder const `MameDat.Folder = "mame"`). Its manifest entry has `DatName` `MAME`, `Version` = the download time as `yyyy-MM-dd'T'HH:mm:ss'Z'` (UTC; the DAT has no version), and the SHA1 of the bytes. The result's `versions` and Admin → DATs (`DatEndpoints.ListedDats`) list entries under `mame/` as they list `titledb/` ones, so the row shows `MAME`, its version and its download link.
- **D5** `DatCache.LoadSystem` loads a `Mame` handler as `LoadTitleDb` does its file, with the same manifest-row checks (exactly one row for `mame/<DatName>.xml`, its `DatName` equal to the handler's, a non-null version; not the titledb date-format rule), reading through `DatManifest.ReadCheckedBytes` with `DatRefreshJob.MaxFileBytes` as the cap, then the same SHA1 check against the manifest row, then `new DatStore(MameDat.Parse(stream), entry.Version!)`. A missing or mismatched file fails as a missing libretro file does (strict: the refresh fails; startup: logged, no store, so ingest refuses with `DatsMissing`).

### Ingest (I)
- **I1** A `.zip` in `ingest/mame2003/` is one ROM file (MS-DOS I1's `ArchiveExtractor.IsArchiveFor`, unchanged), so it goes through the external path: size check (S1), one streamed hash, then I2.
- **I2** Entry list: for a handler with `DatSource.Mame`, `ProcessExternalAsync` reads the set ZIP's central directory after hashing, through `MameZip.ReadEntries(Stream)` (new, `src/RnRomManager.Core/Ingest/MameZip.cs`) on a second checked open of the same file (`ExternalRomPath.OpenRead` with the snapshot, as `HashCheckedAsync` opens it), and passes the entries to `IdentifyAsync` (a new optional parameter `IReadOnlyList<MameEntry>? mameEntries`, null for every other system). It returns each non-directory entry's file name (the part after the last `/`) and `ZipArchiveEntry.Crc32` as 8 lower-case hex digits; no entry is decompressed. A file `ZipArchive` can't open (`InvalidDataException`) fails as `InvalidHeader` with details `not a readable ZIP: <message>`; more than 4,096 entries fails as `InvalidHeader` with `more than 4096 files in the set ZIP`. A snapshot change between the hash and this read is `Skipped` `TooRecent`, as for the hash.
- **I3** Match, `MameMatcher.Match(MameSet set, IReadOnlyCollection<MameEntry> entries)` (new, `src/RnRomManager.Core/Ingest/MameMatcher.cs`; `MameEntry(string Name, string Crc32)` in the same file): the **required** ROMs are the set's ROMs that are not `NoDump` and have no `Merge` and no `Bios` attribute. The result is `Complete` when every required ROM's CRC is among the entries' CRCs (entry names are ignored, so renamed files still match; extra entries are allowed), else `Incomplete` with the missing required ROMs' names in DAT order. A set with no required ROMs is `Complete` when at least one of its non-`NoDump` ROMs' CRCs is present, else `Incomplete` listing them all. `SelfContained` (bool) is also returned: true when the entries also hold every non-`NoDump` ROM that has a `Merge` and no `Bios` attribute and, when the set has ROMs with a `Bios` attribute, at least one of them.
- **I4** In `IdentifyAsync`, a `Mame` candidate matches when `store.BySetName(<file stem>)` finds a set and `MameMatcher.Match` is `Complete`. The file stem is the source name without its last extension (`sf2.zip` → `sf2`, `SF2.ZIP` → `SF2`, matched to `sf2`). Dedupe (step 3) is by the ZIP's SHA1 as for every file. A `Mame` candidate never takes the SHA1/TitleDb path.
- **I5** No set of that name → Review `NoDatMatch` with no suggestions and no header. A set of that name but `Incomplete` → Review `NoDatMatch` with no suggestions and the review item's header `{ "setName": "<DAT set name>", "description": "<description>", "missingRoms": "<names joined with ', '>" }`, the list cut after 20 names with `, … and <n> more`. The Review page shows it in its existing header table.

### Identity and grouping (G)
- **G1** A matched set's release: logical `FileName` `<DAT set name>.mamez` (through `ExternalRomName.AllocateLogicalName`, as every external release), stored next to the game ZIP as `<ZipBase>.<set name>.mamez` (the existing E1 naming), its bytes the source file's. `OriginalFileName` is the source name. `Regions`, `Languages` `[]`, `Revision` null, `Flags` `[]` (a BIOS set: `["BIOS"]`). `Identification` = `Dat`, `DatName` `MAME`, `DatVersion` the store's version, `DatGameName` the set's description (the thumbnail key, G6). `IdentificationMethod.Dat`'s doc comment adds: "or, for a `DatSource.Mame` system, a romset whose every required ROM CRC is in its ZIP (Arcade I3)".
- **G2** `Header` (info.json `header`, and so `roms.header`) of a matched release: `{ "setName": "<DAT set name>", "cloneOf": "<parent>" | null, "romOf": "<romof>" | null, "isBios": <bool>, "selfContained": <bool> }` (I3), all JSON primitives. This is where parent/clone and BIOS links are kept; the game page's **Header details** button (in the release card's body) shows them.
- **G3** Base title: `NoIntroName.Parse(<description>).BaseTitle` of the **parent** set when `cloneof` names a set the DAT has, else of the set itself. So `sf2ua` (`Street Fighter II - The World Warrior (US 910206)`, clone of `sf2`) groups with `sf2` under `Street Fighter II - The World Warrior`, whether the parent is in the library or not. Step 6 (group by system + base title) is unchanged, so unrelated parent sets with the same base title share a game, as same-titled No-Intro games do: on 2026-11-24, 43 base titles had more than one parent set (`commsega` and `commando` are both `Commando`; five `Trivial Pursuit` sets). An Admin splits one out with Move release; later releases of that title then go to Review as `AmbiguousGroup` (G5).
- **G4** Metadata: `store.MetadataForSet(<set name>)` (D3) at ingest. `LibraryEditor.MetadataFor` gets a `DatSource.Mame` branch placed after its existing `DatGameName`/store guard (so a release without `DatGameName`, i.e. Manual, gets `DatMetadata.Empty`): `store.MetadataForSet(<header setName>)`, or `DatMetadata.Empty` when the header has no `setName`. `ReviewResolver`'s AmbiguousGroup branch uses `store.MetadataForSet(<header setName>)` for a `Mame` item.
- **G5** AmbiguousGroup: a `Mame` release is queued with G2's object as the review item's header (a `RomHeader` whose `Fields` are G2's, passed to `QueueReviewAsync`), and with the queued identification `{ datName, datVersion, datGameName, romName, baseTitle }`, `baseTitle` being G3's. `ReviewResolver`'s AmbiguousGroup branch, for a `DatSource.Mame` system, takes `title` from `baseTitle` and flags `["BIOS"]` when the header's `isBios` is true, else `[]` (no regions, languages or revision), instead of `NoIntroName.Parse`; the header is carried by the existing `item.Header` path.
- **G6** Box art and snaps come from the existing libretro-thumbnails lookup with `DatName` `MAME` and `DatGameName` the description (`libretro-thumbnails/MAME` is keyed by MAME description, e.g. `Street Fighter II - The World Warrior (World 910522).png`). Where the current MAME description differs from the 0.78 one, no image is found and the placeholder is stored, as for any miss; IGDB suggestions (S3) fill the gap.
- **G7** Primary release: `PrimaryRelease.Order`, for `DatSource.Mame`, ranks releases whose header `cloneOf` is null (parents, and releases without a header) ahead of clones, then by `PrimaryReleaseRanker` as today. In 0.78 `pacman` is a clone of `puckman`, so `puckman.mamez` is primary over `pacman.mamez`. An Admin's chosen primary (`ChosenPrimarySha1`) still wins.

### Review (R)
- **R1** `GET /api/review/{id}`'s `hasDat` is false for `DatSource.Mame` as well as `None`, so a MAME item gets the Attach and Manual tabs only (MS-DOS N6), Manual prefilled from the file name (N7) and Add and Next (N9). `ReviewEndpoints`' comment says why: an arcade set is identified only by its name and CRCs, and a DAT pick would name the release after a set it doesn't hold.
- **R2** `ReviewResolver` refuses `Action` `Dat` for a `DatSource.Mame` item, before any other check of that action: `ReviewResolutionResult.Invalid("action", "Arcade sets can't be resolved from a DAT pick; use Manual or Attach.")`.
- **R3** Manual and Attach (`NoDatMatch` items) resolve as for any external system (MS-DOS): the file keeps its bytes and gets the `.mamez` extension (`SourceExtension`), named by `ReviewResolver`'s existing rules: Attach as Release `<stem> (Unverified).mamez`, Attach with another flag `<stem> (<flag>).mamez`, Manual `<title>` plus any regions, revision and flags in parentheses, then `.mamez`. For a `DatSource.Mame` system the release's header is null, not `item.Header`: I5's `missingRoms` header describes the review, not the release, and a header with `setName` would make G4 and P2 treat an unverified file as the DAT set. The header is kept only when the resolution goes through `ReviewResolver`'s AmbiguousGroup branch (the queued DAT identity, G5); every other resolution of a `Mame` item, including Manual of an AmbiguousGroup item, stores a null header. The rule is keyed on that branch, not on the item's reason or the action alone.

The `-thread-` payloads are not used (`requiresThreads` doesn't list the core).
  - `params.js`: `cores` adds `mame2003_plus`; `operatorCores.mame2003_plus = { system: 'Arcade (MAME 2003-Plus) games', display: 'MAME 2003-Plus', short: 'MAME', option: 'Emulator:Mame2003PlusCorePath' }`; `hidesCoreChooser` lists it (EmulatorJS's `mame` group also has `mame2003`); `controlSchemeFor` needs no entry (the core's first group is `mame`).
  - `src/RnRomManager.Web/scripts/vendor-emulatorjs.mjs`: `mame2003_plus` joins the three lists that hold `mupen64plus_next` (the explicit-core pin in `getCore()`, the `threads = false` guard and the no-CDN guard), and the comment above `edits` says why (EmulatorJS's `mame` group also holds `mame2003`, which isn't delivered). No new vendor edit.
  - `BrowserCoreExtensionsTests`: `CoreExtensions["mame2003_plus"] = "zip|"` (the NUL-terminated `valid_extensions` string in `mame2003_plus_libretro.wasm`, read on 2026-11-24; the package's `core.json` says `["zip"]`), `["mame2003_plus"] = "cb6d9c80a88b65d1579d16d02128a678f8d1cd3f51de1479e647cea27b13247b"` in the payload SHA-256 table, and `.mamez` for `mame2003` in `Exceptions` with the reason `"stored as .mamez and handed to the core as <set>.zip by play.js"`.
- **P2** `GET /api/games/{id:guid}/roms/{romId:long}/romset` (new, `LibraryEndpoints`, any signed-in user and `.WithMetadata(MaintenanceExempt.Instance)`, as `/download`): for a `mame2003` release, `200 { "setName": string, "deps": [{ "setName": string, "gameId": guid, "romId": long }], "missing": [string] }`:
  - `setName`: `RomRow.Header`'s `setName` (the DAT's spelling, so `SF2.ZIP` plays as `sf2`), else the `OriginalFileName` stem (a Manual/Attach release, R3).
  - Dependencies: the `romOf` chain from the loaded DAT, starting at `setName`'s set (`BySetName`): its `romOf`, then that set's `romOf`, stopping at null, an unknown set, a repeat or after 2 steps. Each is looked up with `Task<IReadOnlyList<RomRow>> IRomRepository.ListBySetNamesAsync(string systemId, IReadOnlyCollection<string> setNames, CancellationToken)` (new; `roms` rows of that `system_id` whose `JSON_UNQUOTE(JSON_EXTRACT(header, '$.setName'))` is one of the names, compared lower-cased, as `LibraryRepositories` already queries `JSON_EXTRACT(r.header, …)`), so only DAT-matched releases count; the primary release first, then the lowest rom id. Found ones go to `deps` in chain order, the others to `missing`.
  - When the release's header has `selfContained` true, `missing` is `[]` (a non-merged set plays without them; found deps are still listed and loaded).
  - With no loaded DAT, `deps` and `missing` are `[]`. A release of another system, or a missing game or rom, is `404` (`Problems.NotFound`, as `/download`).
- **P3** `play.js` for `mame2003_plus`, after `checkOperatorCore`:
  - It fetches `/api/games/{game}/roms/{rom}/romset` (`credentials: 'same-origin'`). On 401 it shows `sessionExpired`; on another failed status `Couldn't load the romset list (HTTP <status>).`; on a network error `Couldn't load the romset list.`
  - When `missing` isn't empty it stops with, for one name, `This game needs the <name> romset. Import it into Arcade (MAME 2003-Plus), then play again.`, and for several, `This game needs the <names> romsets. Import them into Arcade (MAME 2003-Plus), then play again.` (`<names>` joined with `, `, in `missing` order).
  - Otherwise it shows `Downloading ROM…` and loads the release from `/download` (`LibraryEndpoints.ExternalBrowserCores` and `externalBrowserCores` in `emulator.ts` add `mame2003_plus`; `PlayDiscCores` doesn't), then each dep from its own `/download` with `Downloading <setName>…`. A failed dep download stops with `Couldn't load the <setName> romset (HTTP <status>).`, `sessionExpired` on 401, or `Couldn't load the <setName> romset.` on a network error.
  - The game is handed to EmulatorJS as `new File([content], '<setName>.zip')` (not `contentFileName`); `EJS_gameName` stays `params.name`. EmulatorJS writes a `mame`-group game as is (`gotGameData`'s arcade branch). The deps go in `ejs.EJS_externalFiles = { '/<dep setName>.zip': <bytes>, … }`, which `GameManager.loadExternalFiles` writes as is (a key not ending in `/` isn't unpacked) before the game loads, as play.js already does for Sega CD, 3DO and TurboGrafx-CD firmware. MAME then finds `<parent>.zip` and `<bios>.zip` beside the game. No vendor edit.
- **P4** `EJS_Buttons` hides `saveSavFiles` and `loadSavFiles` for `mame2003_plus`, as for `desmume` and `dosbox_pure`: MAME 2003-Plus keeps NVRAM and high scores in its own files, not RetroArch's SRAM file. Docs say: "Arcade NVRAM and high scores aren't kept in the library. The Saves tab can store files, but can't load them into the player." Whether they survive closing the tab is a step 9 manual check, recorded in `docs/features.md` as found.
- **P5** Play is offered for external `mame2003` releases through `ExternalBrowserCores` (P3) in the modal (`play.html`), since the core needs no threads.

## Risks
- **Ingest refuses until the MAME DAT is fetched** (`DatsMissing`), as for every new libretro system; the README upgrade note says so.
- **Upstream DAT drift:** D2 fails the whole file on one bad row. The file passes today (D2); a later upstream mistake makes Refresh DATs fail and keeps the previous DAT, which the Admin sees on the Jobs page.
- **DAT size:** 25 MB of XML is parsed at startup and on every refresh (streaming `XmlReader`) and held as ~6,000 sets and ~94,000 ROM rows in memory.
- **XML safety:** the DTD is ignored and no resolver is set (D2), so the inline DTD can't expand entities or fetch anything.
- **DAT newer than the core:** the DAT is fetched from `master`, the pinned core was built on 2025-06-14 (its `reports/mame2003_plus.json`). A set added or changed upstream since then is matched but may not run; the step 9 checks use long-standing sets.
- **Same-titled parents merge** (G3): about 1.4% of parent sets share a base title with an unrelated one and land in its game until an Admin moves them out.
- **Wrong-version sets** (from newer MAME) mostly go to Review; Manual/Attach keeps them, but they may not run on the 0.78 core.
- **Play memory:** the game plus up to two dependency ZIPs are held in the tab; large sets can fail on low-memory devices (EmulatorJS shows its own error).
- **Unverified upstream behaviour:** that MAME 2003-Plus finds a parent and a BIOS ZIP written beside the game (P3) is a step 9 manual check with a real split clone and a Neo Geo game. If it fails, stop and ask the user (Implement step 4) before documenting anything.
- **Licence:** the core is not shipped (MAME non-commercial licence); the operator supplies it, checked against pinned hashes.
