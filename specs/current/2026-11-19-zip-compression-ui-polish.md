# ZIP Compression, Missing Metadata Report and UI Polish

## Summary
Admins can set a per-system **ZIP compression** level (Store / Med / High) on the ROM Zip Config tab. Changing it starts a background job that repacks every game ZIP of that system. This is meant for systems like Nintendo DS, where the ZIP only bundles files, so ROM access stays fast. A new Admin-only **Missing Metadata** report lists games with no year, developer or publisher. It has a "next" shortcut. The emulator gets on-screen touch controls and a screenshot-to-Snap button. The SPA gets mobile and polish fixes: the navbar closes after navigation, tab lists scroll, the library shows 3 cards per row on phones, shortcuts get Run buttons, the delete modal body scrolls, the Review page gets a remaining-items counter, and smaller fixes.

## Out of scope
- Compression for systems whose ROMs are stored beside the ZIP (Switch, 3DS, disc systems, DS while beside ZIP): not editable (Z5).
- Per-game tracking of compression levels: a cancelled or failed repack leaves a mix of levels (all readable), resumed by **Repack again** (Z9), which rewrites every game again.
- Auto-resuming a repack after a restart.
- Recompressing ZIPs of other kinds (backups, log archives, play-disc ZIPs).
- Touch controls for an emulator that isn't EmulatorJS (E1).
- Screenshots for non-Admins (the image upload is Admin only).
- A game-page **Next** button for Missing Images (only Missing Metadata gets one, M7).
- A Screenshot button for PSP: its player (`play-psp.html`) opens in a new tab, not in `EmulatorModal`, so it has no toolbar. PSP still gets the touch controls (E1), since that page loads the same `play.js`.
- A README supported-systems table change: compression doesn't change a system's "ROMs stored", formats, DAT or browser play.

## Behaviour

### ZIP compression
- **Z1** New `enum ZipCompression { Med = 0, Store = 1, High = 2 }` in `Core/Library`. `Med` is `0` so `default(ZipCompression)` is today's behaviour: an NSubstitute `IRomStorageSettings` (used by many existing tests) returns the default value from `Compression(...)`, which would otherwise be `Store`. API strings are the enum names. The SPA shows "Store", "Medium" and "High".
- **Z2** `LibraryZipWriter.CompressionFor(entryName, sizeBytes, fastAbove, compression)` picks the level for every entry, including `info.json`, notes, images and saves:
  - `Store` → `CompressionLevel.NoCompression` for every entry.
  - `Med` → exactly today's rule: `Fastest` for a `roms/` or `saves/` entry larger than `fastAbove`, else `Optimal`.
  - `High` → `CompressionLevel.SmallestSize` for every entry.
  - The writer gets the level through its constructor: `LibraryZipWriter(InfoJsonReader reader, ZipCompression compression = ZipCompression.Med)`. `fastAbove` stays the existing `FastCompressionAboveBytes` init property. The existing 3-argument `CompressionFor` is replaced (its callers in `WriteTmpAsync` and `LibraryZipCompressionTests` move to the 4-argument form); the static `WriteTmpAsync` gets the level as a new parameter next to `fastAbove`, from both `WriteAsync` and `WriteCheckedAsync`. The `info.json` entry (today hard-coded `Optimal` in `WriteTmpAsync`) follows the rule too. Copied entries are re-deflated (`CopyEntryAsync`), so they take the new level. ZIPs are read the same whatever their level, so nothing on the read side changes.
- **Z3** The setting is stored in `app_settings` as `storage.zipCompression.<systemId>` = `Store`/`Med`/`High`. No migration. The key is at most 40 characters and fits `VARCHAR(64)`. No key = `Med`, today's behaviour, so nothing changes until an Admin acts. A value is read as an exact, case-sensitive match of one of the three names (not `Enum.TryParse`, which would also accept `med` or `2`); any other value is ignored with a warning, as `LoadAsync` does for a bad `storage.embedRoms` value, and `Med` is used. The existing `RomStorageSettings` / `IRomStorageSettings` (already loaded at startup and after a backup restore, and reloaded by `ApiFactory.ResetAsync`) grows two members:
  - `ZipCompression Compression(string systemId)`
  - `Task SetCompressionAsync(string systemId, ZipCompression level, CancellationToken)`, which writes the DB first, then memory.
  - `LoadAsync` also loads the compression key of **every** registered handler, by name.
  A value restored from a backup that differs from the ZIPs on disk is harmless: the levels just differ until the next write or repack.
- **Z4** Every `new LibraryZipWriter(` site passes `settings.Compression(<game system id>)`: `IngestPipeline`, `GameMediaRetry`, `LibraryEditor` (+ `.External`), `StorageMigrationJob` (+ `.Embed`) and the new repack job. Implement greps `new LibraryZipWriter(` so no site is missed. Each class takes `IRomStorageSettings` as an optional constructor dependency; null (tests) means `Med`. `IngestPipeline`, `GameMediaRetry` and `LibraryEditor` (primary constructors) get it as a new last parameter `IRomStorageSettings? zipSettings = null`, so existing test constructions still compile; `StorageMigrationJob` already has `romStorage`. The system id is the system of the game whose ZIP is written (for a move or merge across systems, each ZIP uses its own game's system). So any edit, save, image upload or storage move of a game rewrites its ZIP at the system's current level. A beside-ZIP system's writes use its stored level too. That only touches `info.json`, images and notes, and is harmless.
- **Z5** A system is **compression-configurable** when its effective `EmbedRomsInZip` is true. If DS is moved beside its ZIP, its stored level is kept, but it can't be edited until DS is moved back into the ZIP.
- **Z6** `GET /api/admin/rom-storage` (B12 of the ROM Zip Storage spec) adds two fields per system: `zipCompression` (`Store`/`Med`/`High`) and `compressionConfigurable` (bool, Z5). The SPA's `RomStorageRow` (`lib/api/types.ts`) gains `zipCompression: 'Store' | 'Med' | 'High'` and `compressionConfigurable: boolean`.
- **Z7** `PUT /api/admin/zip-compression/{systemId}` (Admin only), body `{ "level": "Store" | "Med" | "High" }`. The body is read as `JsonElement`, as in `PUT /api/admin/rom-storage/{systemId}`. Checks run in this order:
  - unknown system → `404` (`Problems.NotFound`);
  - missing or malformed body, or `level` not a string equal (case-sensitive) to one of the three names → `400` `Problems.Validation` keyed `level`, message "Must be Store, Med or High.";
  - system not compression-configurable → `400` `Problems.Create(ctx, 400, "NotConfigurable", "This system's ZIP compression can't be changed.")`.
  
  Then (the job, the stored key and every later check use the registry's `handler.Id`, not the route's casing, as `PUT /api/admin/rom-storage/{systemId}` does):
  - `level` equal to the current value (`settings.Compression(handler.Id)`) → `204`, nothing saved, no job;
  - otherwise the repack job starts with that change through `runner.StartAsync(createJob(handler.Id, level), JobTrigger.Manual, DatEndpoints.UserId(ctx.User), ct)` → `202 { jobId }`. If the lock is busy (null) → `DatEndpoints.JobRunning(ctx)` (`409 JobRunning`) and **nothing is saved**.
- **Z8** `POST /api/admin/zip-compression/{systemId}/repack` (Admin only) uses the same `404` / `NotConfigurable` checks. It starts the repack job with no change → `202 { jobId }`, or `409 JobRunning`. A system with no games still gets a job, which ends with 0 items.
- **Z9** **Repack job** `ZipRepackJob` (`JobType.ZipRepack`; the name fits `jobs.type VARCHAR(16)`; cancellable). It carries `(systemId, ZipCompression? level)` through `public delegate IJob ZipRepackJobFactory(string systemId, ZipCompression? level)`, declared in `Api/ZipRepackJobFactory.cs` (new) and registered in `AppHost` as `StorageMigrationJobFactory` is (transient job resolved from DI, then its `SystemId` and `Level` properties set). Constructor dependencies: `IGameRepository`, `ILibraryMirror`, `InfoJsonReader`, `ISystemRegistry`, `IJobItemRepository`, `IOptions<PathsOptions>`, `IAuditLog`, `IFreeSpace`, `TimeProvider`, `IRomStorageSettings`, `ILogger<ZipRepackJob>`.
  0. Under the lock it re-checks Z5 (a storage move may have finished between the endpoint's check and the job's start). Not configurable any more → nothing is saved or audited, no game is repacked, the job succeeds with summary `{ repacked: 0, error: 0 }` and logs a warning (as `StorageMigrationJob` skips a change that no longer applies).
  1. Its first action, under the lock: if `level` is given and differs from the current value → `SetCompressionAsync`, then audit `ZipCompressionChanged` (new; joins `AuditActions.All`) with the system id, Details `<old> → <new>` in the API names (for example `Med → Store`), and the requesting Admin (`context.Actor`, as `RomStorageChanged`). If `level` equals the current value (a race), nothing is saved or audited, and the job still repacks every game, like Repack again. If the save fails, the job fails before any repack and the setting is unchanged.
  2. It lists the system's games with the existing `IGameRepository.ListAllAsync`, filtered to `SystemId` equal to the job's system (ignoring case) and ordered by `ZipPath` (ordinal). No new query. `context.Progress.SetTotal(count)`, `SetCurrentItem(zipPath)` and `ItemDone()` per game. One job item per game: `JobItem { JobId, FileId = GameId = game id, SystemId, SourcePath = AuditPaths.Library(zipPath), Outcome = "Repacked" | "Error", Reason = code (null on success), Details, CreatedAt }`, as `StorageMigrationJob` writes them.
  3. Per game (once started, a game is not cancellable, as in `StorageMigrationJob`):
     - Re-open the ZIP with `LibraryTarget.OpenChecked(library, row.ZipPath, reader, row.Id, row.SystemId)` (as `StorageMigrationJob.MigrateAsync` does); below, `existing` is `target.Zip!` (disposed with `using`) and `game` is `target.Game!` (the `InfoJsonGame` from the ZIP, not the `GameRow`). Any failure (missing, unreadable, `info.json` unreadable or newer schema) → `Error` `ZipUnreadable` with the target's details, nothing written. A game that's pending a storage move (`RomStorage.IsPending(handler, game)`, `handler` being the job's system from `ISystemRegistry.ById(systemId)`, the same one step 0 re-checks) → `Error` `StorageMigrationPending`.
     - Free space: `freeSpace.AvailableBytes(existing.Path)` must be at least the sum of the ZIP's uncompressed entry lengths (`existing.EntryNames.Sum(n => existing.EntryLength(n) ?? 0)`) + the current ZIP size + `StorageMigrationJob.SpaceMarginBytes` (64 MiB) (a Store repack can approach the uncompressed size), else `Error` `InsufficientSpace` with details `<needed> bytes needed at <path>, <free> free`. A null result (free space can't be read, e.g. a network share) skips the check, as `StorageMigrationJob.EmbedAsync` does.
     - Rewrite the ZIP in place through `new LibraryZipWriter(reader, settings.Compression(systemId)).WriteCheckedAsync(library, existing.Path, existing, new LibraryZipChanges(game, new Dictionary<string, Func<Stream>>()))` (`library` = `paths.Value.Roms`) (same `info.json`; every entry `info.json` lists, every note and every save carried, as for any edit: an entry `info.json` doesn't list is dropped, exactly as today's writes do). A leftover `<zip>.tmp` makes `WriteCheckedAsync` fail with `IoError` for that game; `CrashRecovery` deletes `*.zip.tmp` at the next start, so Repack again then succeeds. The writer's existing verification (SHA-1 and size of every `roms/` entry) runs before publish. `LibraryZipVerifyException` → `Error` `VerifyFailed`; `IOException` / `UnauthorizedAccessException` → `Error` `IoError`; ZIP untouched either way.
     - After publish, `mirror.ReplaceAsync(new MirrorEntry(game, row.ZipPath, published.Length, published.LastWriteTimeUtc), CancellationToken.None)`, so `zip_size_bytes` / `zip_mtime_utc` match. A `DbException` or `InvalidOperationException` → `Error` `DbWriteFailed`. The ZIP is valid, and a repack-again fixes the row.
     - Any other exception → `Error` `Unexpected` with the message, logged at Error (as `StorageMigrationJob`); the job goes on with the next game.
     - Success → item `Repacked`.
  4. Summary `new { repacked, error }` (as `StorageMigrationJob` returns `{ migrated, error }`). Cancel and shutdown stop between games. A game is never half-written (atomic tmp + move). No per-game audit; the job items are the record.
- **Z10** `'ZipRepack'` joins the job `type` union in `lib/api/types.ts` (inline on `CurrentJob.type`; `jobLabels` is a `Record` over `CurrentJob['type']`, so it won't type-check otherwise). `jobLabel('ZipRepack')` = "Repacking ZIPs". The footer indicator and the Jobs page pick it up. The item outcome `Repacked` joins `outcomes` and `outcomeClasses` in `lib/jobs.ts`, with class `text-bg-success` (as `Ingested` and `Repaired`).

### Missing Metadata report
- **M1** A game is **missing metadata** when `release_year IS NULL`, or `JSON_LENGTH(developers) = 0`, or `JSON_LENGTH(publishers) = 0`. `developers` and `publishers` are `JSON NOT NULL` (`0002_games.sql`, no default) and unknown is written as `[]` (`JsonStringListHandler` in `LibraryRepositories.cs` serializes `value ?? []`), so no NULL check is needed. The report covers every `games` row, as Missing Images does (it has no hidden, deleted or update filter).
- **M2** `GET /api/reports/missing-metadata` (**Admin only**) takes:
  - `system` (validated like Missing Images);
  - `missing` = `any` (default) | `year` | `developer` | `publisher`;
  - `q` (trimmed; blank = no filter; over 100 chars → "Must be at most 100 characters.", as the Review list; matched as `g.display_title LIKE @q` with `SqlLike.Contains(q)`, as `IngestReviewRepository` does, so `%` and `_` are literal; display title only, not `title`);

  - `page`, `pageSize` (through `Paging.Validate`, as Multiple Releases: page ≥ 1, pageSize 1–200, default 50).

(the shared `Validate`), `missing` "Must be any, year, developer or publisher.", `sort` "Must be name, system or year.", `dir` "Must be asc or desc.". ### Emulator
- **E1** **Touch controls.** EmulatorJS 4.2.3 (vendored) ships a virtual gamepad. At start it's shown only if `this.touch` is set, which a `touchstart` on its Start button sets (`vendor/data/src/emulator.js` ~459 and ~1036), and its setting defaults to enabled only when the user agent looks mobile (`isMobile`, ~5045). In `static/emulator/play.js`, when the device's primary pointer is touch (`matchMedia('(pointer: coarse)').matches` only; a touchscreen laptop with a mouse or trackpad doesn't count):
  - set `EJS_defaultOptions['virtual-gamepad'] = 'enabled'`;
  - inside the existing `EJS_onGameStart` handler (which already chains an earlier handler), right after `gameStarted = true` and before its early `return` for games with no save to apply, call `EJS_emulator.toggleVirtualGamepad?.(true)` (in 4.2.3 it's an arrow property assigned while EmulatorJS builds its UI, ~3456, not a class method, hence the optional call), unless `EJS_emulator.getSettingValue?.('virtual-gamepad') === 'disabled'`: a user who turned the gamepad off in EmulatorJS's own settings menu (~5042, saved per browser) keeps it off.
  
  `EJS_defaultOptions` is already set for every system (`save-save-interval`, plus the DS keys); the new key is added to that object, not a second assignment. Implement first reproduces the missing gamepad with Chrome mobile emulation (touch on) and confirms why it's hidden. ## Risks
- **Data loss during repack:** each ZIP is written to a tmp file, verified (SHA-1 and size of every ROM entry) and atomically moved, as for every library write. A failure leaves the original untouched (Z9).
- **Time and disk:** a repack rewrites every ZIP of a system and holds the job lock for its whole run (no ingest or edits; Site users' save uploads, replacements and deletes go through `LibraryEditor`'s job lock too, so they get `409 JobRunning` until it ends; the features.md repack text says so). The modal warns about this, there's a per-game free-space check, and cancel plus Repack again are available.
- **High on large ROMs:** `SmallestSize` on 512 MiB DS ROMs is slow on every later write (saves, image uploads). The legend recommends High only for small ROMs. It isn't blocked.
- **Store makes ZIPs larger:** the library grows by roughly the compression savings. The free-space check is per game, not for the whole run. The modal says so.
- **Touch controls:** the root cause is unconfirmed (E1). Implement verifies with mobile emulation; the user confirms on a real phone in Finish.
- **Bootstrap `.nav-tabs` change is global:** every tab list scrolls instead of wrapping. The e2e and docs screenshots may shift.
