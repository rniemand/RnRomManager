# UI polish and Activity report

## Summary
A batch of UI fixes across Library, Game detail, Collections, Reports, ROM Tools, About, footer, Global Search and Admin, plus a new Admin-only **Activity** report (recent added ROMs, sign-ins, browser plays, saves, edits, deletions, jobs, last backup). Browser plays become a new `GamePlayed` audit event so they can be reported. For every signed-in user; Activity and Admin pages for Admins only.

## Out of scope
- New storage for plays beyond the audit log (no migration; plays, saves, edits, deletions and sign-ins in Activity cover the 30-day audit retention only).
- Auditing release-note edits or ratings.
- Redesigning pages beyond the listed items; no new dependencies (Bootstrap 5.3 + Bootstrap Icons only).

### Browser plays
- **B22** `POST /api/games/{id}/roms/{romId}/played` (any signed-in user, antiforgery as all POSTs) records `GamePlayed` (system, game, actor, `path` = `AuditPaths.Library(<game ZIP path>)` like the other game events, so B21's file-name fallback works, `details` = release name, i.e. the ROM's `fileName` as the card's heading shows it) and returns `204`; unknown game or a release not in it → `404` (`Problems.NotFound`, code `NotFound`, via the existing `roms.GetAsync(id, romId)` + game lookup pattern). No job lock; not `MaintenanceExempt` (a short request, so a starting restore waits for it like other API calls; during a restore `MaintenanceGate` answers it `503` like every `/api` call, and the client ignores that). The SPA calls it fire-and-forget (errors ignored, with `{ noRedirect: true }` so an expired session's `401` doesn't navigate to `/login` mid-play) from one place for the modal: `EmulatorModal` once per opening: on each false→true change of `open` (mounting with `open` already true counts as an opening) while the same guard as its player holds (`open && rom && core`, and a non-empty `gameId`); a prop changing while open (e.g. `GameResults`' fresh `rom` literal, a refetch after save) records nothing more; so every modal play counts once (game page, Library and collection quick play, Global Search, play-with-save from `GameSaves`). Every PSP `target="_blank"` play link (game page release card and `GameResults`' `playAction`) records on `click` and middle-button `auxclick` through the same helper in `lib/emulator.ts`, and so does Global Search's PSP path (B27); "Open in new tab" from the context menu fires no event and isn't counted.

## Risks
- **Audit volume:** one `GamePlayed` row per play start; negligible next to ingest rows, purged at 30 days. The route has no rate limit, so a signed-in user scripting it could fill the 10,000-event audit queue (`AuditLog`, which drops events when full) and bury the plays list; accepted, since users are trusted site members (Decisions).
- **e2e selectors** break for B2, B3, B5, B9, B23, B26 and B30 (Changes); each is updated in the step that changes it.
- **Missing-core e2e checks** (`mvp.spec.ts` 32X ~:1392 and SNES ~:1435) fail on any `/roms/` request after the core `HEAD` answers. B22's POST is sent when the modal opens, but `openGame` reloads the page (`page.goto`), so the first POST waits for the antiforgery `GET` and can land after the `HEAD`; step 12a makes both trackers skip URLs ending in `/played`.
- **DAT download path safety:** the name is only a lookup key into the checked manifest; no client path reaches the file system.
- **Discovery search vs "app never normalizes names":** `q` is a display filter on labels only; grouping and keys are untouched (Decisions).
- **Hidden Activity tab:** the route itself is guarded by `AdminOnly` (and the layout shows only `NotAllowed` there) and the API by `AuthSetup.AdminOnly`, so a Site user typing the URL sees "Not allowed".
