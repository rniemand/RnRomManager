# 3DO support

## Summary
Adds the 3DO (`3do`) as a disc system. Its bin/cue sets and standalone `.iso` images are imported against the Redump DAT and stored next to the game's ZIP, as Sega CD, Saturn and PlayStation discs are. Releases play in the browser on EmulatorJS's Opera core through the existing play-disc endpoint. Opera's licence forbids commercial use, so, like Genesis Plus GX and Snes9x, the operator supplies its files (`Emulator:OperaCorePath`), and a 3DO BIOS from the BIOS folder.

## Out of scope
- Bundling Opera or any 3DO BIOS or Kanji font ROM.
- A header reader: `ReadHeader` returns null (no Header button; unmatched files go to Review, never `InvalidHeader`).
- `.chd`, `.ccd`, `.mds`, `.gdi` (Redump hashes the raw tracks, so a CHD would never match).
- Multi-disc swapping in one session (one disc per launch), choosing a BIOS per game, the 3DO arcade BIOS and Kanji ROMs, and NVRAM export beyond EmulatorJS's own save handling.
- Seeded 3DO games in the Basic/Full test sets and an e2e play case (vitest covers the player, as for Sega CD).
- Real-game boot checks before the PR: the maintainer does them after merge, as for the previous browser-play specs.

## Behaviour
- **B1 Handler.** `ThreeDoHandler` in a new project `RnRomManager.Systems.ThreeDo` (namespace `RnRomManager.Systems.ThreeDo`; a C# identifier can't start with a digit):

  | Member | Value |
  |---|---|
  | `Id` / `Family` | `3do` / `3do` |
  | `DisplayName` / `ShortName` | `3DO` / `3DO` |
  | `RomExtensions` | `.bin`, `.cue`, `.iso` (`[0]` = `.bin`) |
  | `MinRomSizeBytes` / `MaxRomSizeBytes` | 16 / 1 GiB (per file, as Sega CD) |
  | `DatName` | `The 3DO Company - 3DO` (libretro `metadat/redump/`, and the thumbnails folder) |
  | `DatFolder` / `MetadatKinds` | `DatKind.Redump` / `[]` |
  | `EmbedRomsInZip` / `FileSets` | false / true |
  | `BrowserCore` | null until Step 8, then `opera` |
  | `ReadHeader` | null always |
  | `DefaultBoxArtPng` | a new 512×512 3DO placeholder drawn for this project (no logo or trade dress), with its SVG source in `Resources/boxart/` |

  `3do` is its own family, so a `.bin` in another system's ingest folder is never tried against the 3DO DAT and vice versa.
- **B2 Registration.** `AddSystemHandler<ThreeDoHandler>()` goes after `SegaCdHandler` in `AppHost.AddSystemHandlers`, so `3do` is last in registry order. The project is added to `RnRomManager.slnx`, the Api `.csproj` references and the Dockerfile restore layer (as `NintendoDs` was), with a test project `RnRomManager.Systems.ThreeDo.Tests`. Startup creates `roms/3do/` and `ingest/3do/` with their standard subfolders. `/api/systems` lists it (sorted by `DisplayName`: after 32X, before Atari 2600). The README row sits between 32X and Atari 2600. It gets its own badge colour (`--bs-3do`, a hex used by no other token, ≥ 4.5:1 with its foreground; any object key `'3do'` is quoted in TS) and the `bi bi-disc` icon. After upgrading, an Admin runs **Refresh DATs** once (one Redump file, no metadat); until then ingestion returns `DatsMissing`.
- **B3 Ingest.** Nothing new in Core: the `FileSets` rules apply as for Sega CD. A `.cue` with its `.bin` tracks is one release; files keep their exact names next to the ZIP; a taken name is `NameTaken`; a DAT hit on the data track names the game; an unmatched `.bin`/`.iso` goes to Review as `NoDatMatch`. `.cue`/`.bin` Review items follow the existing `ReviewResolver` set rules.
- **B4 play-disc.** `PlayDisc.MaxBytesBySystem` gains `3do` → 1 GiB (inclusive; above it 409 `PlayDiscTooLarge`). 3DO takes Sega CD's shapes unchanged: a single `.bin` or `.iso` streamed as-is, or exactly one `.cue` with up to 99 bins returned as a stored ZIP with the cue rewritten. Anything else is 409 `InvalidPlayDisc`.
- **B5 Opera core files.** `EmulatorOptions.OperaCorePath` (`Emulator:OperaCorePath`, env `Emulator__OperaCorePath`), default empty (3DO play off). Validated like `Snes9xCorePath`: empty or fully qualified; a missing absolute directory passes startup; whitespace fails. Shown on **Admin → Settings** as `emulator.operaCorePath`. It may share a folder with the other operator cores. `OperatorCoreManifest` gains `Opera = "opera"`, display name `Opera`, mismatch code `EmulatorEndpoints.OperaCoreMismatch` (`"OperaCoreMismatch"`), and the three files of `@emulatorjs/core-opera@4.2.3`: `opera-wasm.data`, `opera-legacy-wasm.data` (package root) and `opera.json` (from `reports/`), each pinned by exact length and SHA-256 measured in Step 5. `HEAD`/`GET /api/emulator/cores/opera[/<file>]` then behave exactly as for Snes9x (204/200, 401, 403, 404, 409 `OperaCoreMismatch`, 500 `IoError`, `Cache-Control: no-store`, no Range).
- **B6 Player wiring.** `opera` joins:
  - `params.js`: the `cores` allowlist, `hidesCoreChooser`, and `operatorCores` with `{ system: '3DO games', display: 'Opera', short: 'Opera', option: 'Emulator:OperaCorePath' }`. So a missing core reads "3DO games need the Opera core files: ask an Admin to set them up (Emulator:OperaCorePath)." and a mismatch "The Opera core files don't match EmulatorJS 4.2.3: ask an Admin to replace them (Emulator:OperaCorePath).";
  - `vendor-emulatorjs.mjs`: the explicit `getCore()` pin, the forced single-threaded payload, and the local payload error instead of the CDN retry (the same three edits as `snes9x`). Opera is **not** added to the vendored `cores` list: no Opera file is copied into `static/emulator/vendor` or the image;
  - `controlSchemeFor` returns null for `opera` (EmulatorJS's `3do` group default).
- **B7 Play eligibility.** `opera` joins `LibraryEndpoints.ExternalBrowserCores` and `externalBrowserCores` in `emulator.ts` (Step 8). Every 3DO release is external, so its play URL always carries `&disc=1` (the existing `playDisc` / `rom.externalFileName !== null` logic). `play.js` treats `opera` as always-disc, like `yabause`: it loads from play-disc whether or not `disc` is present (Step 7), so an `opera` URL without `disc=1` never calls `/download`.
- **B8 3DO launch.** For `opera`, the player, in order:
  1. runs the operator-core HEAD check for `opera` (B6 messages);
  2. fetches the BIOS files from `/api/emulator/bios/<name>` **one after another, in the order `panafz10.bin`, `panafz1.bin`, `panafz1j.bin`, `goldstar.bin`, `sanyotry.bin`** (`threeDoBios`), each with `loadOptionalBios(name, 1048576, threeDoBiosSizeError(name))`:
     - a 404 skips that file;
     - a file that isn't exactly 1 MiB stops the launch with `threeDoBiosSizeError(name)`: "The 3DO BIOS <name> in the BIOS folder (Paths:Bios) must be 1 MiB: ask an Admin to replace it.";
     - any other failure stops the launch with `optionalBiosError`'s message.

     The first error stops the launch even if an earlier file loaded, and the later files aren't requested;
  3. if none was found, stops with `threeDoBiosMissing`: "3DO games need a BIOS: ask an Admin to put panafz10.bin, panafz1.bin, panafz1j.bin, goldstar.bin or sanyotry.bin in the BIOS folder (Paths:Bios)." No disc, loader or core file is requested;
  4. loads the disc from play-disc (`discError` unchanged);
  5. sets `EJS_externalFiles` with every found BIOS at `/<name>`, `EJS_paths` from `operatorCorePaths('opera')`, and `EJS_disableCue = false` only if Step 6's check (B10) shows Opera 4.2.3 needs it to read a cue. If B10 shows Opera doesn't pick the BIOS by itself, its BIOS option is set to the **first found** file in the order above, merged into the existing `EJS_defaultOptions` object (keeping `'save-save-interval': '30'`); no Opera key is set otherwise. The chooser stays hidden.

  A disc that needs a specific console's BIOS may fail inside the core; the app doesn't read the disc.

  `contentFileName(core, game, name)` keeps its signature. For `opera`, a content file named after any of the five BIOS names (any case) becomes `<game id>-<name>`, so a disc never overwrites firmware. All five names pass `IsBiosName`.
- **B9 README.** The supported-systems table gains `| 3DO | `3do` | Next to ZIP | `.bin`, `.cue`, `.iso` | Redump | — |` in Step 2, whose Play cell becomes `` `opera` `` in Step 8.
- **B10 Assumptions verified in Steps 5 and 6.** Outside the repo (`npm pack @emulatorjs/core-opera@4.2.3` in a scratch folder; and the Opera libretro source at the commit its build names, else `master`):
  - (Step 5) the package holds `opera-wasm.data`, `opera-legacy-wasm.data` and `reports/opera.json`; measure their lengths and SHA-256 for B5, and record the payloads' `license.txt` terms;
  - (Step 6) `core.json` extensions include `cue` and `iso`; whether EmulatorJS 4.2.3 disables cue generation for `opera` (then set `EJS_disableCue = false`);
  - (Step 6) with no `system_directory` set by EmulatorJS 4.2.3, Opera looks for its BIOS in the content root `/`, where `EJS_externalFiles` writes them; how it chooses among several (its BIOS core option and default); and that all five files are 1 MiB;
  - (Step 6) Opera's NVRAM storage default (per game or shared) and whether its saves go through `RETRO_MEMORY_SAVE_RAM`, which EmulatorJS 4.2.3 persists. If it writes its own file under the save directory instead, that file is never synced (the `desmume` trap).

  Record each in § Decisions. If the package is missing a file, the BIOS can't be found at `/`, a BIOS size differs, or Opera writes its own save file, stop and ask the user.

## Risks
- **Licence.** Opera is "LGPL/Non-commercial" (libretro core info), so nothing is bundled: no `package.json`, lockfile, `licenses.json` or `emulator-licenses/` change. A test asserts the vendored output holds no Opera file. The docs link Opera's licence and state that no 3DO BIOS is included.
- **Core assumptions.** Cue handling, BIOS location and BIOS choice are inferred; Steps 5–6 check them first (B10).
- **BIOS mismatch.** Accepting any of five BIOS files means a game that needs a particular console's BIOS may not boot. Documented in `docs/features.md`, not solved.
- **Green commits.** `SupportedSystemsTableTests` compares README rows with handlers, so Step 2 adds the row with `—` and Step 8 sets `opera`. Every full-registry DAT manifest in the API integration tests must list `IngestSeeder.ThreeDoDat` once the handler is registered, or ingestion fails `DatsMissing`; Step 2 updates them all in one commit.
- **Id starting with a digit.** `3do` is used as a folder, URL segment, CSS custom-property suffix and object key. Step 2's tests cover the badge, the icon, `/api/systems` and (`SystemStartupTests`) the `roms/3do/` and `ingest/3do/` folders; Step 3 covers ingest from `ingest/3do/`.
