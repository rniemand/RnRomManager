# SNES and Atari browser play

## Summary

Let signed-in library users play Super Nintendo cartridge releases through the existing browser player. Keep the existing Atari Jaguar, Lynx and 7800 launch paths covered and list all four cores in the README.

## Out of scope

- EmulatorJS upgrades, extra console peripherals, specialty SNES firmware, and ROM format or storage changes.

## Behaviour

- **B1.** Game list and detail responses advertise `snes9x` for `snes`. The library card Play action targets the primary release when eligible, using `playRomId` and `playRomFileName`. If the primary release is ineligible, the card offers no Play action. The game detail Play action targets the selected eligible release. Use the existing embedded-release eligibility rules and leave Play visible when operator files are unavailable. Both actions open the same-origin cartridge modal and use `GET /api/games/{id}/roms/{romId}/download`. Play uses the bytes and name already stored in the game's ZIP. This covers normalized `.sfc` entries from `.smc` imports and existing embedded entries named `.smc`. The player supplies the release name as `EJS_gameName` and uses the existing cartridge file naming and save behavior. Standard cartridges need no BIOS request. Keep the existing battery-save defaults and leave the cue override unset. Both pinned Snes9x payloads list `.sfc` and `.smc` in `core.json`.
- **B2.** Operators supply the EmulatorJS 4.2.3 Snes9x files through `Emulator:Snes9xCorePath` (environment variable `Emulator__Snes9xCorePath`). The default is empty. Accept empty or fully qualified paths at startup, including a directory that does not yet exist, and show the effective setting as `emulator.snes9xCorePath`. The directory may be shared with the other operator cores. A signed-in user who has completed any required password change can use the existing `HEAD /api/emulator/cores/snes9x` and `GET /api/emulator/cores/snes9x/{name}` routes. Return bodyless 204 from HEAD when all three files verify and 200 from GET with the requested verified bytes. Preserve the verifier's outcomes: 401 without a valid session, 403 while a password change is required, 404 for an unavailable file or path (including an unset or missing directory, zero-byte file, unsafe path, or unlisted GET name), 409 for a nonempty length or hash mismatch, and 500 for unreadable files. HEAD uses precedence 500, then 409, then 404 when multiple files fail. GET returns `Snes9xCoreMismatch` for 409 or `IoError` for 500. Use the exact ordinal core ID and file basenames, serve the verified in-memory bytes, ignore Range, and keep `Cache-Control: no-store` on responses handled by the endpoints.
- **B3.** The cartridge modal accepts `snes9x` and sends a same-origin authenticated HEAD before requesting the ROM or loader. Reuse `operatorCoreError` with the system label `SNES games`, display and short labels `Snes9x` and the option `Emulator:Snes9xCorePath`. A 404 shows setup instructions, 409 asks for the matching 4.2.3 files, 401 shows session expiry, and other statuses or network errors use the existing operator-core error pattern. A failed check stops launch. After preflight, keep the cartridge ROM error handling, including session expiry on 401, the HTTP status for other unsuccessful responses, and the generic ROM error on a failed request or body read.
  - On success, use `operatorCorePaths` to map the two payload basenames and `snes9x.json` to their corresponding same-origin API GETs. Apply the existing explicit core pin and hide only `retroarch_core`. Leave `EJS_controlScheme` unset so EmulatorJS uses its singleton `snes` group. Keep `EJS_disableDatabases = true`, which disables EmulatorJS's core cache as well as the ROM cache.
  - After **Start Game**, the 4.2.3 player requests the report and then one payload. A saved enabled WebGL 2 setting selects `snes9x-wasm.data` if WebGL 2 is supported. Otherwise it uses `snes9x-legacy-wasm.data`, including on fresh settings because the pinned report has no `defaultWebGL2`. Force a single-threaded payload regardless of any saved thread setting. A failed report GET, including 401, uses the upstream nonfatal fallback and still attempts the payload. A failed payload GET, including 401 after preflight, shows `Error downloading core (<filename>)` with no CDN payload retry. Follow the existing loader-script error handling.
- **B4.** Existing Atari mappings stay available for their supported cartridge releases: `jaguar → virtualjaguar`, `lynx → handy`, and `a7800 → prosystem`. Keep the current bundled assets and cartridge launch paths. The handlers accept Jaguar `.j64`, `.jag`, `.rom`, `.abs`, `.cof`; Lynx `.lnx`, `.lyx`; and 7800 `.a78`, `.bin`. In 4.2.3 each core is the only member of its control group (`jaguar`, `lynx`, `atari7800`), and its report and selected payload load from the bundled same-origin assets. Exercise one existing synthetic seed per system with an empty BIOS directory.
- **B5.** The README's supported systems table matches the handlers for all four consoles, with `snes9x` in the SNES row in the same commit as the handler change. The README feature overview and external-core attribution identify Snes9x as operator-supplied, following PicoDrive. Document the setup and failure messages in the feature and configuration docs. Operator documentation gives exact pins and a read-only Docker mount example for a directory outside app- or user-writable areas and readable by app UID 1654. Show obtaining the exact archive directly with `npm pack @emulatorjs/core-snes9x@4.2.3` in a scratch directory, without installing it as an app dependency. Copy the two payloads from `package/` and the report from `package/reports/` into the root of the mounted directory. Show how to check the three SHA-256 values before setting the path.

Use these three files from the published [`@emulatorjs/core-snes9x@4.2.3` npm archive](https://registry.npmjs.org/@emulatorjs/core-snes9x/-/core-snes9x-4.2.3.tgz). The manifest and setup instructions use the installed basenames.

## Risks

- Both pinned payloads contain the Snes9x noncommercial licence in `license.txt`. Use the existing operator-supplied core flow and link the licence from the setup documentation. [Snes9x licence](https://github.com/snes9xgit/snes9x/blob/master/LICENSE)
- The modern and legacy payloads must match the pinned loader. Take all three files from the npm archive pinned above and verify both payload-selection paths.

## Decisions

- 2026-11-14 The three Atari cores are already registered, bundled and listed in the README. Retain their implementations and verify their launch behavior (code).
- 2026-11-14 Use the pinned EmulatorJS Snes9x build and the existing operator-supplied core flow, as used for PicoDrive and Genesis Plus GX (code and upstream license).
- 2026-11-14 Use the npm archive as the byte source for all three production pins. Preserve the pinned loader's nonfatal report fallback and use the existing local-only failure path for WASM payloads (published archive and pinned loader source). [EmulatorJS 4.2.3 loader source](https://github.com/EmulatorJS/EmulatorJS/blob/v4.2.3/data/src/emulator.js#L563).
- 2026-11-14 Keep the stock-image Playwright tests reproducible with the existing synthetic seeds. Check the real SNES setup error separately from the success routing path, which controls only the HEAD response. The Atari cases also fetch the bundled player assets. Gameplay and input smoke checks depend on authorized playable ROMs (Basic seeds and stock e2e stack).
- 2026-11-14 Keep the existing embedded-release eligibility rules and stored bytes, including legacy entries named `.smc`. The handler accepts both extensions, and both payloads list them in `core.json` (SNES handler, library routes and published archive).
- 2026-11-14 Use the existing signed-in API authorization and operator-core error policy. A 401 before loading the player gets the session-expiry message. After **Start Game**, the pinned player treats HTTP failures as download failures, so a report failure is nonfatal and a payload failure shows the local core error (shared verifier, operator-core tests and pinned player).
- 2026-11-14 Use the upstream SNES controls and WebGL 2 preference. The published report has no WebGL 2 default, so fresh settings use the legacy build. Single-threaded selection is enforced in the app as for the other operator cores (published report and pinned player).
